1. 结论

  • 两个作业 + 性能验收可以一起用，全程没有人工干预。提交按 pair=on 拆成主作业和草稿作业，检查和性能测量都在计算节点上跑；没有暂停、没有失败的会话，调度器上的申请没有人动过。
  • 性能验收抓到了行为测试抓不到的两处变慢，并且修好了。第一版 76 条行为检查全过，但命令行启动打印帮助慢了 47.5%、Telegram 重复写同一段文字慢了 38.9%。一次 4.2 分钟、$2.06 的性能修复之后，215 条标准全部通过。
  • 代价主要在冻结阶段。每个选中的叶子都要一个设计者会话（28 个同时跑），评审的文件从 50 个变成 107 个，再加上在节点上测量性能文件。到封存为止花了 $128.75，上次是 $98.55；整次 $132.36 对 $105.16（+26%）。
  • 这次排队不再是问题。9 个节点申请各等 15–105 秒，合计 9.7 分钟；上次有一个申请等了 42 分钟。差别在申请现在写明 32 GB 内存（上次不写，分区给 4 个核的申请配了 184 GB）。
  • 交付的代码和原版的重复明显变高，需要你看一眼。重复度 68%（上次 36%），36 个函数有 60% 以上和原版相同（上次 0 个），逐行相同 57.1%（上次 41.7%）。作者第一次调用只用了 32.9 分钟、59 轮（上次 50.7 分钟、87 轮）：它不再自己重写来降低重复度。体积没有因此变小，反而大了约 2 个百分点。详见第 7 节。
  • 体积目标仍然没达到（57.96% 对 50%），作业也仍然没有为此做任何事（没有优化轮）。这和上两次一样。

5. 性能验收

性能契约是怎么来的

  • 冻结阶段，28 个选中的叶子各有一个设计者会话，除了补行为测试，还写性能文件：计时文件（跑一段工作量、量时间）和计数文件（数某种操作的次数，例如写了几次输出）。
  • 这些文件先在原版上测量，再把对应的叶子人为放慢，看测不测得出来；测不出来的不算标准。然后交给评审。
  • 封存时的性能契约：48 个文件（27 个计时、21 个计数），220 个基准，其中 215 条是验收标准（91 条计时、124 条计数）；5 条计时项因为“放慢了也测不出来”不算标准，照常测量、不参与判定。
  • 25 个叶子有标准；3 个叶子的设计者说明了不适合写性能测试（deprecated-aliases、examples、version）。
  • 评审否决了 12 个性能文件：4 个是因为工作量不是使用者会跑的规模（只是为了让差别显出来），其余 8 个理由各不相同（例如计数文件没有量到实际的工作，或界限定得不对）；另有 1 个没有可用的标准。通过的 48 个。
  • 在计算节点上测量。封存前的测量和验证合计 26.4 分钟（契约记录的 validation_seconds）。

12. 口径和没有做的事

  • 时间取自作业自己的事件和操作记录；花费和 token 取自各次调用的记录（Claude Code 报的美元数），缓存读取单列。
  • 等节点的时间取自调度器的记账（只读查询），是各申请从提交到开始的秒数之和。
  • 只跑了一次。和上次的差别里混着三样东西：性能验收、PR #40 对作者行为的影响、排队情况不同。分不开的地方正文里都按“这次对上次”写，没有归到某一个原因上。
  • 交付的代码没有另外做人工检查或第三方对拍；“行为保持”指 76 条冻结的检查和 215 条性能标准，加上回放的原测试。
  • 性能是在一台计算节点上、同一批次里对比的相对值，不是对某个硬件的绝对承诺。
  • 没有改 nanolize 的代码，没有动调度器上的任何申请，交付的分支没有推送。
  • 这一页公开了：六个 nanolize 提交号、一个分支名和两个 PR 号、tqdm 的提交号、实验的时间和花费、调度器上各个申请的时间和大小、性能文件里两个基准的说明。没有写账户名、分区和队列的名字、机器名和文件路径。
