结论

  1. 新格式清单成为默认流程。改技能文档和 README 里的步骤顺序，把转换报告的处理规则写进技能文档；plan 和 review 遇到旧格式清单时给一句提示。不做自动转换，因为转换之后有一步必须由人或 agent 看报告补内容。
  2. 转换时默认把纯数据文件带过去。字面数据占 90% 以上的文件自动带；50% 到 90% 之间的只列在报告里；--no-carry 关掉；报告写明带了什么、占多少。
  3. 无人值守成为默认。owner_attends 的默认值改成 false。已经保存的作业行为不变。
  4. nanolize 自带三个 Claude 适配器。作者、控制器、写事实和补测试各一个，文件名和文档都标明只用于 Claude Code。原脚本里写死的模型、目录、提示词前缀、依赖环境，全部改成从一个设置文件读，这个文件由启动作业的 agent 写。
  5. 漏配置时提交即拒绝。新格式清单下，作者不是 codex 又没给写事实和补测试的运行器，或者没有可用的单文件测试命令，提交时直接报错并写明要给什么，不再悄悄跳过。
  6. 试调运行器，不通就自己修好接着跑。对每个不是内置 codex 命令的运行器做一次很小的真实调用，提交前一次，作业启动时再一次。不通时由启动作业的 agent 自己修好再继续，不停下来等人。
  7. $nanolize <目录> 支持 Claude。现有的一行入口只会用 codex。改完后它可以由 Claude Code 来启动，作业里的作者、控制器、写事实和补测试也可以用 Claude；不写明时，作业用的 agent 和启动它的 agent 是同一种。
  8. 无人值守选项。入口加 unattended=on。带上它，agent 按给定的范围自己提交，出错时按技能文档里的规则自己处理，全程不等人。“不要停下来等我”和“遇到错误自己绕过并记录、不靠放宽验收来绕”这两段话都不用再写进 prompt。

不改的只有一条：范围的默认值仍是 core。改完后要在 prompt 里写的只有：项目、范围、用什么模型、要不要无人值守，以及汇报要求。

和第一版相比：新增第 6、7、8 三处；原来待确认的五项都已按建议定下，见已定的取舍。

这一页的内容来自读 main 的代码和这次实验的记录。没有改代码，也没有跑测试；文中标了“实现时确认”的地方是还没有核实的。

改动 1　新格式清单成为默认流程

改文档里的步骤顺序，加一句提示，不做自动转换

现状

技能文档和 README 的默认步骤是：写功能图和检查，再建一份登记原版每个文件、类、函数的详细知识库。转换成新格式是可选步骤，文档里的说法是“想让重写能改变原版结构时再用”。plan 和 review 对两种清单都照常接收，不作任何提示。

改成
  • 技能文档、README 和流程文档里的默认步骤改为：写功能图和检查 → contract-propose → 看转换报告 → plan / review。建详细知识库的做法挪到后面，写成“要保留原版结构时的另一种做法”。
  • 转换报告的处理规则写进技能文档（见下表），以后不用在 prompt 里重复。
  • plan 和 review 拿到没有声明对外约定的清单时，在输出里加一句提示：默认流程是先转换，要保留原版结构可以忽略。只提示，不拒绝。
  • 给 MCP 加一个转换工具。现在转换只有命令行入口，走 MCP 的 agent 做不了这一步。
原因

不在 plan 里自动转换，有两个原因。一是转换只读 Python 源码，配置项、注册名、文件格式这类用户依赖的东西读不出来，转换后必须有人看报告把它们补进 interface，自动转换会把这一步跳过去。二是转换要写一个新文件，输出文件已存在时会拒绝，塞进 plan 里不好处理。

兼容

旧格式清单和已经保存的计划照原样读取，行为不变。非 Python 项目走默认流程时转换会得到什么，要在实现时确认；确认之前文档里写明这类项目仍用原来的做法。

写进技能文档的转换报告处理规则

报告里的项目默认处理
checks_left_out、checks_not_inspected照常继续，把数量记进汇报
external_capabilities_without_check照常继续。这些节点在作业冻结时由测试设计者补测试
internal_capabilities_not_reached、unresolved_exports只记录
carried（新增）已经自动带过去，把文件数和占比记进汇报
carry_candidates数据占比 50% 到 90% 的文件。数据是用户依赖的表（类别表、映射表）就带，否则不带
配置项及默认值、注册名、文件格式、固定提示文字仓库里有而且用户依赖的，用一句话写进对应节点的 interface

改动 2　转换时默认把纯数据文件带过去

90% 以上是数据的文件自动带，其余只列出来

现状

转换报告只列出候选文件（carry_candidates），门槛是文件里一半以上是字面数据。带不带、带哪些，要在启动作业时用 --carry 逐个写明。文档原话是“不点名就不带”。

改成
  • 转换时，字面数据占 90% 以上的 Python 文件直接写进新清单的 carry 列表，和清单里原有的合并。
  • 50% 到 90% 之间的文件继续只列在 carry_candidates 里，并附上各自的数据占比。
  • 加一个开关 contract-propose --no-carry，关掉自动带。
  • 报告新增 carried：每个被带的文件、它的 token 数和数据占比，以及合计占原版多少。
  • 评审页面和公开页面的数据里加一行：带了几个文件、多少 token 不计入体积。
原因

作者看不到原版，纯数据文件它只能凭记忆默写：写错了检查失败，写对了又是逐字重复原版。门槛比“列为候选”高，是因为带过去的文件整个不重写，而且体积比较时两边都不算它；一半是代码的文件自动带过去，等于那一半代码原样照搬。

兼容

只影响新做的转换。清单里已经写了 carry 的照原样保留。被带的文件仍然要过原有的校验：不能是测试文件，必须是普通文件，总数不超过 2000 个。

改动 3　无人值守成为默认

owner_attends 的默认值从 true 改成 false

现状

默认有人值守。控制器遇到说不清的语义，或者想追加检查时，可以带“等待”提问，作业随即暂停，直到有人回答并恢复；暂停期间作业的期限照常流逝。没人盯的作业可能一直停到超时。

改成
  • 默认值改成 false：提问只记录在案，作业按已有证据继续。
  • 想让作业停下来等人回答的，在 controller_policy 里显式写 owner_attends: true。
  • 相关文字跟着改：命令行和 MCP 的帮助、作业为等人而暂停时的提示、控制器提示词里讲这个设置的那一句、文档。
  • 每一轮给控制器的上下文里，始终写出这个字段，不再只在无人值守时才写。
兼容

新作业会把 false 明确存进自己的设置。改动之前建的作业，存的是 true 或者没有这个字段，恢复运行时仍按有人值守处理，这条判断规则不动。

影响

在评审页面上点提交的人，如果希望作业遇到问题时停下来等自己，以后要显式设一次。控制器提出的追加检查之类的修改请求，没人批准就不会生效，跑完后值得看一下它问过什么。

改动 4　nanolize 自带三个 Claude 适配器

实验里作者、控制器、写事实和补测试用的是三个放在运行目录里的脚本，一共 460 行。把它们收进 nanolize，以后用 Claude 跑不用每次重写。

放在哪里、怎么标明是给 Claude 用的

改成
  • 新目录 src/nanolize/runners/，三个模块：claude_author.py（作者）、claude_controller.py（控制器）、claude_role.py（写事实、审事实、设计测试、审测试）。
  • 三者共用的部分放进 _claude_session.py：拼命令、沙箱、超时、读事件流、保存记录。
  • 标明 Claude 专用的三处：文件名带 claude_ 前缀；每个模块开头第一句写明“只用于 Claude Code”；文档里单独一节，标题写明适用范围。找不到 claude 命令时直接报错。
用法

仍然是显式配置，三处各指向一个模块，都读同一份设置文件：

作者            python -m nanolize.runners.claude_author     --settings 设置文件
控制器          python -m nanolize.runners.claude_controller --settings 设置文件 {result_path} {schema_path}
写事实和补测试  python -m nanolize.runners.claude_role       --settings 设置文件 {result_path} {schema_path}

三种会话默认都在沙箱里运行：只有自己的工作区可写，设置里列出的目录不可见。实验里写事实和补测试的会话没有进沙箱，“不改现有文件、不联网”只靠提示词约束；现在改成默认进。跑测试的解释器在工作区之外，通过 expose 只读挂进来。要关掉沙箱，必须在设置里显式写 "sandbox": "none"，这一点会记进每次调用的记录。机器上没有沙箱程序又没有显式关掉时，适配器拒绝启动并说明原因。

nanolize 的代码认不出一个自写的作者脚本背后是不是 Claude，所以这一层不做“自动选用”。自动选用放在入口那一层做，见改动 7。

脚本里写死的内容，改成从设置文件读

原来写死的内容出现在改成
模型名三个脚本设置里的 model。不给时用 Claude 命令行自己的默认模型，实际用的模型记进调用记录
要对会话隐藏的目录：使用者的存储目录，以及主目录下存放以前的运行、缓存、其他会话记录的几个子目录三个脚本设置里的 hide 列表。nanolize 不内置任何路径
沙箱里要保留可读的目录（例如装着测试依赖的环境）作者脚本设置里的 expose 列表，只读挂载
调用记录写到脚本旁边的目录三个脚本设置里的 record_dir；不给时，写事实和补测试的记录放进 nanolize 为这次调用建的目录
运行目录里的设置文件（时限、依赖目录、解释器路径）作者、控制器并入同一份设置文件
加在提示词前面的三段文字（这次实验的背景和约束）作者、控制器设置里的 prompt_prefix，列出文件。nanolize 不自带任何前缀
目标项目的包名（用来确认依赖环境里没有混进目标代码）作者脚本设置里的 forbidden_in_dependencies
给作者建虚拟环境时写死的 Python 版本目录作者脚本按 base_python 的实际版本算出来
重试次数和间隔、可用工具各脚本设置里可改，默认值沿用实验里的

写事实和补测试的时限不用配，nanolize 每次调用都会把时限写在给适配器的请求里，脚本本来就是从那里读的。

设置文件的样子

{
  "model": "<模型名>",
  "sandbox": "bwrap",
  "hide": ["/path/to/earlier-runs", "~/.cache/pip"],
  "expose": ["/path/to/test-environment"],
  "record_dir": "/path/to/run/model-calls",
  "author": {
    "timeout": 14400, "attempts": 3, "retry_pause": 180,
    "tools": "Bash,Read,Edit,Write",
    "prompt_prefix": ["/path/to/run/prompt-common.txt", "/path/to/run/prompt-author.txt"],
    "base_python": "/path/to/python",
    "dependencies": "/path/to/dependency-links",
    "forbidden_in_dependencies": ["<目标项目的包名>"]
  },
  "controller": {
    "timeout": 900, "tools": "Bash,Read",
    "prompt_prefix": ["/path/to/run/prompt-common.txt", "/path/to/run/prompt-controller.txt"]
  },
  "role": { "tools": "Bash,Read,Write" }
}

为什么用设置文件，而不是把目录写在命令行参数里

原因

nanolize 会检查作者的启动命令：命令里出现原版目录、作业状态目录，或者它们的上级目录，提交就被拒绝，目的是防止作者够到原版。要隐藏的目录恰恰就是这些，写在命令行参数里过不了这道检查。实验里的脚本把路径写在脚本内部，所以没碰到。放进设置文件，命令里只出现设置文件自己的路径，检查不用改。

不变

适配器自己固定的部分保留在代码里：无界面运行、不保存对话、只读项目级设置、不加载外部连接器、不允许调用子代理，以及告诉模型“答案写成一个 JSON”的那段话。这些是适配器成立的前提，不是某次运行的设置。

测试

项目的测试不调真实的 Claude。新增的测试用一个假的 claude 程序，输出事先录好的事件流，检查用量汇总、命令记录、超时收尾、答案提取、设置文件校验和沙箱命令的拼法。打包检查里加一条，确认安装后的包里有这三个模块。

改动 5　漏配置时提交即拒绝

写事实和补测试的运行器

现状

作者不是 codex、又没给这个运行器时，分两种情况。有节点完全没有检查：提交被拒绝，报错清楚。每个节点都至少有一个检查：作业照常启动，冻结时“写事实”和“补测试”整步跳过，只留一条事件；作者拿不到测试事实，现有检查无效的节点也没人补测试。

改成

新格式清单下，只要“写事实”或“补测试”开着、作者不是 codex、又没给运行器，提交时就拒绝。报错里写明要设哪一项，并提到自带的 Claude 适配器。

跑单个测试文件的命令（test_template）

现状

清单里一个 pytest 检查都没保留、策略里又没给这条命令时，分两种情况。有节点完全没有检查：提交已经会被拒绝。每个节点都至少有一个检查：作业照常启动；冻结时如果发现某些检查无效，这些节点没法补测试，只留一条事件，最后记为未验证。

改成

新格式清单下，只要“补测试”开着、又推不出这条命令，提交时就拒绝，报错里给出写法。确实不需要补测试的，在策略里关掉 design。

兼容

两条都只对新格式清单生效。旧格式清单保持现在的行为（跳过并留事件），不影响已有的用法。

改动 6　试调运行器，不通就自己修好接着跑

试调两次，哪一次不通都不停下来等人

现状

nanolize 不会事先检查运行器能不能用，坏了要到第一次真正调用时才暴露。作者的运行器要等冻结全部做完才第一次被调用：这次 detectron2 实验启动七个多小时后，作者还一次都没被调用过。现有的诊断工具只看依赖和程序在不在，不发起真实调用。

改成

  • 每次对作者、控制器、写事实和补测试各做一次很小的真实调用，检查三件事：会话能启动；答案按要求的格式回来；用量被报告。
  • 提交前不通：agent 看适配器的报错，自己修（设置文件、环境或适配器本身），重新试，直到通过再提交。
  • 作业启动时不通：作业不算失败，停在这一步等恢复，报错写进事件。agent 修好之后恢复作业，作业重新试调，通过后接着往下跑。这是作业的第一步，之前没有任何工作会丢。

原因

修了就能接着跑，是因为适配器每次调用都重新读设置文件。改设置文件不用动作业已经定下来的启动命令，也不用重新建作业。

适用
