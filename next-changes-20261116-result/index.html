一、结论

现在 main 里有什么

  • 27 个问题的修复。每个问题至少一个提交，带一个修复前会失败的测试和一个独立的复现脚本。其中 7 个在评审后换了做法或撤回了一部分（M9、M15、M18、M19、M23、M24、M1）。
  • 性能验收（默认关）：用户开关、设计者写的计时文件和计数文件、同机三分支的测量内核、证据工具、最多 2 次性能修复、回退、带缺口交付、进度页和报告页、文档和三个技能。
  • graphify 准备工具：把固定版本 0.9.111 装进 nanolize 自己的缓存目录；技能在没装时调用它。
  • 体积优化默认上限 3 → 2，任务成本评估的轮数跟随作业的上限。
  • “有 Slurm 就用”按方案没有改默认行为；修了检查执行器的两个缺陷（都是真实运行找出来的），技能里加了一句“先等队列”。
  • 方案之外修掉的 10 个 main 上原有的缺陷，例如：设计测试的试运行按“所有能力都选中”来计划；原版回放在计算节点上什么都没测；新版 Python 写出的源码老解释器读不了；冻结阶段的作业在节点用不了时只能失败。

怎么验证的

  • 测试：Python 测试函数 +485，16 个新测试模块，前端测试 +22。
  • CI，7 次运行：最终提交在 Python 3.11、3.13 和打包检查上全部通过（3,626 个测试）。前 4 次各有失败项，原因都是测试自身的问题（钉死了一个会变的数、靠旧默认值），都在下一次推送前修掉；第 5 次（117 个提交）一次全绿。第 6 次和第 7 次（最终提交）的第一次尝试在 3.11 上各有一个不同的原有测试出错，都是测试自己的竞争条件，分支没有改过它们；第 7 次失败的那个作业在同一个提交上重跑后通过。
  • 两轮独立评审：第一轮 86 条（6 条严重的全部修掉）。第二轮只审第一轮之后的修复，49 条。没有第三轮。
  • Codex 会话独立验证，三遍：35 项里 32 项在各自最后被看过的代码上通过。前两遍一共找出 7 个要修的情形（其中 2 个是修复带来的退步），都已修，另指出 1 个文档里写明的限制；第三遍又构造出 2 个情形，留作已知限制。
  • 测量内核在真实项目上调参：tqdm，登录节点和计算节点各一遍，不调模型。
  • 真实运行，三次都已完成：tomli（Codex）：原报告里它的 6 个问题，4 个确认修好（M1、M2、M9 的第一种情形、M19），1 个只做到“不再交白卷”（M12），1 个没有机会验证（M18）。tqdm（Claude Code，开性能验收）：56 / 56 项检查，体积 42.1%；收集脚本判定 16 项已修、1 项要人看（看过是干净的）、13 项没有机会；性能验收的经过见第二段。packaging（Codex）：398 个待改写的测试全部发出、339 个迁移成功（原来 39 个），51,511 个用例有了逐用例证据，夹具报错带上了类型和阶段并让一次修复把通过的检查从 7 项变成 92 项；交付的候选 100 / 100，体积 28.8%；收集脚本判定 19 项已修、2 项要人看、8 项没有机会。

还开着什么

  • packaging 的状态是“带失败交付”，尽管 100 项检查全部通过。原因是安装检查：宿主 agent 把安装命令写成了 pip install .，而安装命令在检出目录之外运行，要用 {repo} 指代候选，所以每个候选都以同样的方式失败。交付的树是能安装的（用改对的命令手工核对过）。nanolize 没有拦住它，见下一条的 (5) 和 (6)。
  • packaging 回放离开验收的原版测试：193 个测试函数在原版上通过、在交付的代码上不通过（保留的 402 / 488，耦合的 278 / 385）。这只是报告，不改变状态；这些测试不在验收范围里，但“检查全部通过”不等于“和原版行为完全一样”。
  • 性能验收的真实运行没有展示的，因为没有发生：带缺口 performance_not_preserved 交付；回退一次优化；超时或无结论的标准；在计算节点上的测量——这次所有标准都是在登录节点上定的、也是在那里判的。这些只有测试。
  • 三次真实运行找出、还没处理的六个需要改 nanolize 的问题：(1) 要求“自动”的检查执行器只给队列两分钟，之后把整个作业的检查永久移到本机；(2) 评审服务在慢机器上启动超时，留下一个废弃的评审；(3) 一个叶子节点的性能文件被拒之后，如果它另有一个被接受的，就不会再被问；(4) controller 给作者的修复说明超过长度上限 131 个字符，整个回答被拒，更正一轮后通过；(5) 运行技能的第 02 阶段没有说安装命令在检出目录之外运行、必须用 {repo}；(6) 冻结之前没有任何一步在原版上试一下安装检查，所以一个 7 小时 40 分的作业要到第一个候选才知道命令是错的，而冻结后的命令改不了。前四个来自 tqdm 的运行，后两个来自 packaging。
  • 三个已知限制，按决定保留：(1) 由处理器时间决定的性能基准，抓不到“只是等得更久”的候选；(2) M14：指向“运行目录名加点和后缀”的同级目录的 file: 网址，在百分号编码写法下被多拒绝；(3) M19：文件名本身带方括号的依赖清单读不对。后两个是 Codex 验证者构造出来的情形，真实运行里没见过。
  • 第二轮评审里 5 条低级别的问题没有处理，也没有记录原因；逐条列在验证一节。
  • 固定流程的基准记录没有重录，必须在它的录制环境里重录。这个测试在这台机器和 CI 上是跳过的。
  • 两次 Codex 运行里没解释清楚的一点：多数角色的每个会话用掉的 token 是原来那次运行的几倍（tomli 3 到 5 倍，packaging 2 到 4 倍；packaging 整个作业 1.26 亿个 token、7 小时 40 分，原来是 4,560 万、4 小时 18 分）。有一条事实不支持“原因在 nanolize”：同样带着这些改动的 tqdm 运行，事实阶段比它的参考运行更便宜。详见验证一节。
  • CI 里两个原有测试的竞争条件没有修，在 main 上还会偶尔让 3.11 的运行出错一次。
  • 没有验证的：M15 和 M16（三次运行里都没有机会）；graphify 在 Codex 沙箱里实跑；M18 对真正的 Atheris；回放和执行器的两个修复在真实调度器上；见最后一节。

设计测试的试运行按“所有能力都选中”来计划。一个被选中的叶子节点如果在完整的图里是父节点（它的子节点都被排除了，用 core 范围时很常见），它在试运行的敲除矩阵里没有对应项，于是为它设计的每个测试都被拒绝，它最后是未验证。做 M12 的子代理用一个探针脚本在 main 和分支上都跑出来。已修：554536b。试运行改用作业自己的选择。有修复前会失败的测试和独立的复现脚本；Codex 会话验证通过。
一次设计里两个检查可能同名。后一轮的检查名字可能和前一轮重复，重复时整个设计中止。做 M6 的协作会话在自己复查时发现。已修：20708fd。名字改用只增不减的计数器。Codex 会话验证通过（旧代码名字是 3、2、3，新代码是 3、4、5）。
交付后的原版测试回放，在计算节点上什么都没测。回放把两棵树复制到作业进程的临时目录，再把任务发给节点；节点看不到那个目录，两边都是“执行失败”，记录却写着“已完成”。方案里把它列为“可能已经存在、没有验证”的问题；负责测量内核的协作会话验证后确认属实。已修：6efb8c4（副本改放在作业目录下）、7569c34（评审后：被中断的回放留下的东西，下一次回放前清掉）。新增 5 个测试；Codex 会话验证通过。没有在真实的调度器和共享存储上验证过。
回放的副本里留着 Git 链接。作业的工作树是链接出来的工作树时，副本保留了指回原仓库的 .git 文件。同一个协作会话在修上一条时发现。已修：28a07b3。Codex 会话验证通过。

设计者写什么

  • 两种文件，和行为测试分开放，不合并：计时文件 bench_<名字>.py，里面是普通函数 bench_<名字>()，每个只通过公开接口跑一段工作量，不做断言；可以配一个 setup_<名字>()，在计时之外准备数据。计数文件 count_<名字>.py，是普通的 pytest 文件，断言的是“做了多少工作”（某个函数被调了几次、次数怎么随输入增长），不是返回值。
  • 每个函数是一个基准，编号 perf-N，带一句话的文档字符串说明它量的是什么工作。这句话是之后唯一会给作者看的关于基准的内容。
  • 给哪些节点写：每个被选中的叶子节点，除了被豁免的、内部的、没有独占 Python 源码的。设计者可以回答“这个节点没有值得量的东西”。一个节点一轮最多 3 个性能文件，一个计时文件最多 8 个函数，一次调用应在 0.001 到 5 秒之间。
  • 性能文件不是清单里的检查，不是行为验收标准，也不写事实；它们列在作业目录的 performance-contract.json 里，和契约一起封存。
  • 只有被要求写性能文件的会话才拿到性能相关的提示词和回答格式；同一个作业里别的会话拿到的和关着时一样。
  • 测试、场景文件和计数文件不能从同一个节点的计时文件里导入东西，这样的文件在运行之前就被拒绝。这样一个被拒的计时文件不会连累已经通过的测试（第二轮评审后改成这样）。

一个基准怎么成为验收标准

  • 冻结阶段，每个计时文件要过一次试运行：拿原版和“把这个节点变慢了的原版”比。变慢的方式是：节点独占的 Python 文件里，每个普通函数保留函数体，再把它用掉的处理器时间多花一遍（靠干活，不靠睡眠），也就是“至少慢一倍”。
  • 只有在节点变慢时确实跟着变慢、而且超过允许差距的基准，才算验收标准。没跟着变慢的（slowdown_not_detected）说明它的时间花在别处：它留在文件里，每个候选都会量、会报告，但永远不决定任何事。
  • 其他不算标准的原因：在原版上就失败、一次调用太慢、噪声太大、节点变慢后它报错、节点没有可以变慢的函数体。
  • 计数文件按设计测试的方式验证：在原版上通过、重复运行稳定、节点被敲除后因行为而失败。只有在原版上确实运行并通过的测试才算标准。

怎么测量

  • 从不拿存下来的时间和后来的时间比。每次测量是同一台机器上的一个批次，三条分支：原版、原版再来一次、被评判的那个（候选；冻结时是变慢的原版）。每条分支都是一份全新的导出，轮流跑，每轮换一个先跑，同一时刻只有一个进程。
  • 三条分支里的性能文件都用原版的那一份，所以候选的树里这些路径上放了什么都不影响。
  • 一个函数一轮的时间是它若干次调用的中位数。调用次数在冻结时定下来（取三次调用里最短的一次来算：总共约 0.2 秒，最少 5 次、最多 1000 次；单次超过半秒的最少 3 次），写进契约，之后每一边都重复同样多次。
  • 默认 5 轮；如果前 3 轮里文件的每个函数都比允许差距的一半还小，3 轮就结束。
  • 噪声取两者中较大的：同一轮里原版和原版自己的差距，或者同一条分支在两轮之间的最大变化。允许差距就是用户的容差（默认 20%）；噪声比它大时放宽到噪声的 1.25 倍并在记录里写明；要放宽到 100% 以上时，这个基准这次“无结论”，既不算通过也不算失败。
  • 比允许的慢的基准，在同一个批次里单独再量一次，两次都说慢才算慢。候选的一次运行最多给原版的三倍时间再加 10 秒。停在某个函数里的运行会先整份重量一次；再次停在这个函数里，它才记为 timed_out，文件去掉它继续量。这样一个卡死的函数不会连累后面的，一次偶然被机器按住的运行也不会让相同的代码失败。
  • 量不出来的从不算失败：时间用完、分支导不出来、运行改动了别的运行要读的文件、运行时审计没通过、原版自己在这一批里失败，都是“无结论”。
  • 计数文件在同一批里原版跑一次、候选跑一次：原版通过而候选失败的测试记为慢（bound_exceeded）。用户的容差对计数不适用，上界是设计者写在测试里的。

两个时钟，以及为什么

  • 每次调用同时记两个时间：经过的秒数（用户实际等的时间）和进程用掉的处理器时间。
  • 方案里只有第一个。在真实的 tqdm 上一试就不行：这台登录节点给整个账号 4 个核、按 100 毫秒的周期限流，十多个 agent 共用。一个进程用完配额就被按住到下一个周期，于是相同的代码、每次调用 15 到 100 毫秒的工作量，两次运行的秒数能差 70% 到 590%，而处理器时间稳定在 3% 以内。
  • 规则：秒数稳定的地方由秒数决定。秒数的噪声超过了用户的容差、而处理器时间的噪声更小时，由处理器时间决定，记录里写明是哪个时钟（clock），两个时钟各自的结果都留着（clocks）。
  • 代价（写进了文档和报告页）：由处理器时间决定的基准，候选如果只是“等得更久”（睡眠、锁、网络、子进程），不会被追究。这样的比较照样记为通过，不产生缺口；结果里有一个计数（by_processor_time），进度页和报告页会写明有几个基准是按处理器时间判的，用户私有的记录里两个时钟的比值和噪声都在。这不只发生在被限流的机器上：只要原版自己的秒数波动超过容差（比如工作量本身等待的时间不稳定），就由处理器时间决定。Codex 验证者用探针演示过：原版每个进程随机等 0、6 或 12 毫秒，候选每次调用多等 30 毫秒，秒数是原版的 4.83 倍，比较结果是通过（秒数噪声 156%，处理器时间比值 0.998）；同一个探针里相同的代码通过，候选自己放在基准路径上的文件被换回了冻结的那一份。统筹会话决定不改这条规则：现在改，有让相同的代码在限流机器上失败的风险，而调参显示那是更糟的错误。建议是在安静的计算节点上测量。在 tqdm 的调参里，计算节点上的基准都是由秒数决定的，那里的噪声只有百分之一二。

在作业里的位置：工具、修复、回退、缺口

  • 每个候选的验证顺序：行为检查 → 行为比对 → 安装检查 → 性能比较 → 任务成本评估。
  • 新工具 compare_performance 只量行为已经被接受的候选；之前调用只会记下“行为验收未完成”，什么都不跑。一次有结论的比较对这个候选一直有效，再调用不会重量（否则可以一直量到某次落进容差）。之后又观察到什么都不影响它（比如又做了一次只比一个检查的筛查）。但恢复出来的候选是新候选，会重新测量：同样的代码因此可能得到第二个读数，读数通过的话，恢复出来的那一份就不带缺口交付（评审的 L2 和第二轮的 F8，记录在案没改）。体积没量出来的候选，记录里写的是 size_not_measured。
  • 行为通过、但有标准没过的候选，进入性能修复（最多 max_repairs 次，单独计数），排在任何优化之前。作者读到的是每个没过的基准的编号、所属能力、设计者的那句话、慢了多少和允许多少；可以按“失败后可参考源码”的规则读这些能力的原版文件。作者还读到是哪个时钟决定的、不是用时的失败是什么（超出上界、报错的类型、超时）、还剩几次修复。绝不给文件路径、函数名、工作量的代码或原版的用时。写出来的东西照常过防默写那一关，只有一个例外：用户允许的最后一次性能修复，草稿不会因为重复原版被退回，因为重写只能是再一次性能修复，而已经没有了（controller 作业里之后还可能有别的调用从这些草稿接着写）。
  • 两种回退：一次优化如果让某个基准比“记住的候选”（它之前的那个候选）更差，就恢复到那个候选：原来没失败的基准现在失败了；或者原来就慢的基准又慢了，超出了这个基准自己的允许差距；或者原来只是慢，现在跑不了。记住的候选当初没有读数的基准（计数、报错、无结论）不参与这个比较，所以真把这种基准弄慢的优化不会因此回退。性能修复把行为弄坏了，同样恢复到记住的候选，这次修复仍然计数；上一次被接受的修复就是记住的候选，即使它修好一个基准的同时让另一个变差了。
  • 修复次数用完仍然慢：这既不是停止也不是失败。任务成本评估开着、并且它要求优化时，作业继续做用户允许的优化（最多 --max-optimization-attempts 次；让基准比之前更差的优化按上面的规则回退）；评估关着或者没有要求优化时，直接带缺口交付（统筹会话的决定，提交 44c6989）。
  • 缺口 performance_not_preserved 永远不标为失败。它有四种情况：没保持（量到了变慢）、无结论、没有标准、没测量。配置了发布远端的作业（固定作业和 controller 作业都是），只要交付带着这个缺口（四种情况都算）并且没有别的失败，就不推送（blocked_performance）。
  • 公开的结果、进度页和报告页只显示数字和枚举值（状态、容差、轮数、基准数、通过/变慢/无结论各多少、最多慢了多少、修复用了几次、回退了几次、有几个基准由处理器时间决定）。基准对应的文件、函数、那句话和全部样本只在用户私有的记录里。
  • 性能不进可移植验证包：在别的机器上重放用时没有意义。

和方案不同的地方，以及原因

不同的地方原因
加了处理器时钟方案只用经过的秒数。在共享、限流的机器上相同的代码秒数能差几倍（见上）。不加的话，在这种机器上要么什么都判不了，要么把相同的代码判为变慢。
生成器也被变慢方案把“只有生成器的节点”列为覆盖不到。tqdm 的迭代入口 __iter__ 就是生成器，不变慢的话“迭代一个包着的可迭代对象”这个最核心的工作量成不了标准。现在量的是从进入或恢复到下一次 yield 的时间，在 yield 之前补上。
变慢按处理器时间算，而且不累计第一版按经过的秒数算、并把短调用多付的开销记账带到后面的调用。前者让被按住的调用之后干更久，变慢的那条分支自己轮与轮之间差 80% 以上；后者让先跑的 5 万次 update() 留下几秒的账，两个本该是标准的基准被判成“没察觉变慢”。代价：只是在等待的函数不会被变慢，只等待的工作量成不了标准。
容差 50% 以上时，按容差的两倍变慢方案里变慢的倍数是常数。但容差允许设到 500%：容差一旦接近 100%，“慢一倍”就不再超过允许差距，什么都成不了标准。现在保证一个标准总能察觉“用户允许值的两倍”的变慢（评审 M2）。
单独的 _ 不算私有名字设计文件的检查原来拒绝任何下划线开头的名字，包括循环里最常见的 for _ in range(n)。在 tqdm 上演练设计路径时发现；main 上对所有设计文件都这样。
提交时多了三条拒绝方案只有“没有运行单个测试文件的命令”一条。另外加了：没有任何测试模板、命令不启动 Python 解释器、清单没有知识库。都是“开了也做不了”的情况，早点说比冻结到一半失败好。
修复用完之后继续做优化方案写的是“性能不达标期间不会选体积优化”。评审指出这样一来，修复用完后用户允许的优化永远不会被尝试，任务成本退步时固定作业还会以失败结束，和“分开计数”“永远不因性能而失败”矛盾。统筹会话决定：继续做评估要求的优化，让基准比之前的候选更差的优化回退（不只是“原来通过、现在失败”），交付时写明缺口。
多了一个模块方案是两个新模块。实际是三个：测量内核 performance.py、计时程序 benchmark_runner.py，以及“作业拿一份测量记录做什么”的 performance_evidence.py。这样三个会话可以并行写，接口先写成一份说明。

已知的限制

  • 非常短的调用。给一次调用做标记要约 2 微秒。比这还短的调用被放慢的远不止一倍，所以“大量极短调用加大量别的工作”的工作量会比“慢一倍”这个说法更容易成为标准。评审者量到过：节点只占 12% 时间的工作量慢了 4.6 倍。没有已知的修法，文档里给出了数字。
  • 不会被变慢的：异步函数、模块顶层、类体、lambda，以及只是在等待的函数。只有这些的节点没有验收标准，契约里会写明原因。
  • GPU 工作量第一版不计时（已定）。提示词没有禁止设计者写 GPU 工作量。
  • 处理器时钟决定时不追究等待。见上面“两个时钟”一节：这样的比较记为通过、不产生缺口，结果里只有一个计数；Codex 验证者的探针里，秒数是原版 4.83 倍的候选通过了。按决定保留。
  • 固定作业里，等待之后没有评估。条件：任务成本评估开着；第一个候选变慢，它的评估在等性能修复（记为 performance_acceptance_pending，不跑任务代理）；之后没有一次性能修复留下候选（每次的输出都被拒，或者一次被拒之后没有时间、token 或次数再来一次）。固定作业这时交付第一个候选，带 task_effort_not_passed，结果里写明原因 performance_acceptance_pending（报告页有对应的一句话）。因为没有评估，这个作业也不会去做用户允许的优化。controller 作业会在交付前补上评估。没有修的原因：最终拒绝之后，被交付的那次尝试的证据已经封存，补评估需要第二次决定，不是这一轮的小改动。
  • 评审留下的两条低级别问题：被变慢的函数多一个局部变量；一个标准可能在一个时钟上被接纳、在另一个时钟上被评判。
  • controller 作业里的优先级是建议，不是硬性拦截（已定）。

没有验证的

  • tqdm 以外的项目；带原生扩展的项目。
  • 作业自己的 compare_performance 在计算节点上跑（调参时是直接调用内核；真实运行是在登录节点上量的）。
  • 带缺口交付、回退一次优化、超时或无结论的标准：在真实运行里都没有发生，只有测试。真实的设计者只在一个项目（tqdm）上写过基准。
  • 在新步骤处停止并恢复一个真实的工作进程。任务成本评估的“等待性能结论”有了测试（一个真正评估任务的 controller 作业，任务代理是离线替身）和评审者的整作业探针（固定作业，评估是合成的）；用真实的任务代理没有验证过。
  • 进度页演示页面里没有开着开关的录像。页面和报告站点在 tqdm 那次交付上实际显示的内容，结果文件里没有记录。

graphify 准备工具

新工具 prepare_graphify（命令行 nanolize graphify-prepare）已经进了 main：把固定版本 0.9.111 的 graphify 装进 nanolize 自己的缓存目录，返回可执行文件路径。技能从“没装就跳过”改成“没装就调用它”。在这台机器上真实安装过一次，用返回的可执行文件跑通了图谱提取。没有在 Codex 会话的沙箱里实跑过。

  • 装在哪：~/.cache/nanolize/tools/graphify-<版本>/（遵循 XDG_CACHE_HOME），每个版本一个独立环境，所有运行共用。30 天没用过、带 nanolize 回执的旧版本目录会被顺带清掉。
  • 怎么装：建一个 venv，然后 pip install --only-binary :all: --no-cache-dir --retries 2 --timeout 15 graphifyy==0.9.111。只装现成的安装包，pip 不执行任何构建脚本；离线时几秒内失败。
  • 绝不做的事：不启动 graphify 的任何命令（连 --version 都不跑）。安装的那次调用在 pip 之后不启动任何东西，版本和包清单从 pip 的元数据文件里读。复用已有的安装时，会启动一次这个环境自己的解释器来问版本（第二轮评审后改回这样，见下）。不写仓库、不写用户的 PATH 目录、不写任何 agent 的目录。
  • 失败时：返回 unavailable 加原因和日志路径，不抛异常，不会让运行停下。只有两种情况抛异常：没给 allow_execution=True，或参数格式不对。
  • 实测（这台机器，一次真实安装）：56 秒装好（venv 18 秒、pip 36 秒），33 个包，247 MB、6,184 个文件；第二次调用 0.24 秒直接复用。网络盘上的文件锁能用。用返回的可执行文件在 nanolize 自己的仓库（392 个文件）上提取图谱，2 分 10 秒，11,546 个节点；产物能被 import_understanding 读入。
  • 技能：PATH 上有 graphify 就用它（不管版本，技能要求报告实际用的版本）；没有就调用工具。只有工具返回 unavailable 或用户写了 graphify=off 时才跳过，原因写进阶段小结。宿主放弃了第一次调用时，技能让它再调一次（服务端会把安装做完）。tqdm 的真实运行（Claude Code）里正是这样走的：PATH 上没有 graphify，nanolize 装了固定版本并建出了图谱（1,185 个节点、2,056 条边）。

和方案不同的地方

  • pip 加了 --no-cache-dir：否则它会写用户的 pip 缓存，违反“不写自己目录之外的地方”。
  • 缓存目录落在 Git 仓库里时返回 unavailable 而不是抛异常：安装失败不该让运行停下。判断“在仓库里”要求 .git 目录里有 HEAD，因为一个空的 .git 目录曾让所有临时目录都被拒。
  • 所有版本共用一把锁（方案是每个版本一把），这样清理旧版本和使用它们不会撞上。
  • 评审后：版本和包清单改从元数据文件读（评审 L-11 指出“不运行已安装包的任何代码”原来靠的选项并不跳过 .pth 文件）。
  • 评审后：一次调用给自己的日志文件加锁，下一次调用会等它；安装程序超过时限仍在跑时返回新原因 installation_in_progress。这解决了“服务端在 pip 中途被杀”的情况，没有采用评审给的两种修法。

  • 常量在 repair_policy.py，命令行、MCP 工具、评审服务和控制器都用它。进度页在记录里没有上限时不再显示“/3”，只显示“已用 N 轮”。
  • 文字里写着“默认 3”的地方（命令行帮助、MCP 工具说明、给宿主 agent 的说明、技能、两份 README、两份文档）都改了；生成的提示词文档和演示页面重新生成。
  • 新增 tests/test_optimization_default.py（3 个）：命令行、MCP、评审服务和控制器的默认值都等于这个常量。原来没有任何测试断言这个默认值。
  • 已有的评审和作业保持 3；只有新启动的评审用 2。

评审发现了什么

  • H-1：一个原有测试（tests/test_execution_control.py 里关于“尝试次数上限”的测试）靠的是默认 3，默认改成 2 后失败。负责的子代理没有跑这个模块，是第三次 CI 运行和评审同时指出的。已修（f93c650）：这个测试显式写 3。
  • M-1：用户显式给 max_optimization_attempts=3 时，只能做两次优化：任务成本评估自己的轮数默认值也变成了 2，先到的是它。已修（872b7e5）：作业里，评估的轮数上限等于作业的上限，除非用户自己写了。由此带来的变化：上限设成 0 或 1 时，评估的轮数也是 0 或 1（原来是 2，main 上是 3）。

有 Slurm 就用

“有 Slurm 就用”按方案不需要改代码：检查的执行位置默认就是自动判断。但在这台集群上实际去用的时候发现，默认的自动判断在这里会悄悄退回登录节点，要让检查真的上计算节点还需要五样东西；另外查出并修掉了执行器的一个缺陷。

  • 站点配置文件。在这个登录容器里，调度器的提交命令按默认安装直接失败（它的站点过滤脚本找不到一个配置文件）。作业的环境里要有指向站点共享配置的环境变量。
  • 账号。不指明账号的提交被拒绝。
  • 分区。只跑 CPU 的检查要指明 CPU 分区。
  • QOS。默认的 QOS 下，一个申请可能排几个小时（调参时有一次预计八小时后才开始）；要指明短任务的 QOS。
  • 更长的排队等待。执行器默认只等 120 秒；这里的队列经常更久（调参时等过约 35 分钟）。真实运行里把等待上限设成了 1,800 秒。
  • 这五样都是通过作业的环境和 check_executor 的现有设置给的，nanolize 没有为此改代码。不给的话，作业退回登录节点，并在 check-executor.json 和一条事件里说明原因——不会报错，所以不注意就看不到。
  • 执行器的两个缺陷（已修，都是真实运行发现的）：调度器报告批次结束后，执行器只花 10 秒读节点写回的结果，在网络文件系统上会把成功的批次读成“节点没写结果”（75e4a32）；冻结阶段的作业在节点用不了时既不能移回本机也不能暂停，只能失败（6dfe76c：要求“自动”的作业现在会把检查移回本机并重做被打断的采集）。见“新发现的问题”。
  • 仍然没改的：探测之后的批次，要在队列里等满“排队上限的十倍”才算节点用不了。排队上限设成 1,800 秒时就是五小时。想快一点，可以把排队上限设小、给批次一个更短的申请时长让调度器早点排上，或者用调度器自己的命令取消正在排队的批次（作业会在 75 秒后把它当成节点不可用）。文档里现在写了这三种办法。
  • 这台集群的两个限制（只读查询得到的）：短任务队列每个用户同时只能有四个已提交的任务；一个申请超过约半小时的批次，在分区忙的时候可能排几个小时。
  • 技能里加的一句话（已定事项第 15 条，提交 3afae57）：无人值守时，作业因计算节点不可用而暂停，先按原样恢复、等队列；连续三次这样暂停之后才改成本机继续，并记进 issues.md。
  • 这次验证用的真实运行，统筹会话另定了一条只对它们生效的规则：一个批次排了 20 分钟、预计还要 30 分钟以上才开始时，让宿主 agent 把检查移回登录节点。这和上面那句“先等队列”不同，只是为了让验证运行在当天跑完。

四、决定和偏离

项目所有者的要求是：自己决定、不要来问，但要留记录。下面是这些记录的整理，按类别分组，每条一两句话。原先列出的 22 条待定事项已全部按建议执行，不在这里重复；这里只列方案和那 22 条没有定下来的事，以及做的和方案不一样的地方。完整的记录在工作目录里，每个包一份。

工作怎么组织

决定原因
一个统筹会话、三个协作会话、八个子代理（七个各做一组修改，一个准备真实运行；评审者另算），各自在自己的工作树和分支上提交，统筹会话逐个挑进集成分支。各项改动碰的文件重叠很多（尤其是测试设计那个文件），按“谁改同一批函数”来分工，冲突由写代码的一方自己解决。
每个问题除了测试之外，另留一个独立的复现脚本：在 main 上打印 BUG，在分支上打印 FIXED。让 Codex 会话能不依赖随修复一起写的测试来独立验证。
整套测试不在这台机器上跑，交给 PR 的 CI。草稿 PR 在第一批修复集成后就开了。这台登录节点给所有会话一共 4 个核，同时有十多个 agent 在工作；本机只跑改动涉及的测试模块，再加一个“按 CI 的单进程顺序”的探针。
评审从一开始就定为两轮，由没写过这些代码的子代理做；第二轮只审第一轮之后的修复。没有第三轮。经验是“修复的修复”最容易出问题，所以第二轮的修复必须比它修的东西更小、更保守，拿不准就把改动收回去。替代第三轮来核对这些最后的修复的是：每个修复自己的“修复前会失败”的测试、CI、Codex 会话在最终提交上重跑复现脚本，以及在真实项目的清单上做修复前后的转换对比。
第二轮的每一条严重和中等问题，都连同评审者给的“最小修法”送回原来的负责方。规则是：采用评审者的最小修法，除非能证明它是错的；低级别的只修一两行就能确定的，其余记录在案。
评审意见送回原来写代码的那一方，并带一条规则：main 原来做对的事必须仍然做对；新的读法没把握时，宁可保持 main 的行为。好几个第一版为了修报告里的情形，改变了 main 上原本正确的结果（见下一组）。
真实运行不用这台机器上已装的插件，而是每个提交单独构建一份运行时，在新开的会话里跑。已装的插件要继续给机器上别的会话用，保持在 main。
真实运行开在“包含第一轮全部修复”的提交上，不是最终提交。运行要几个小时，第二轮评审在它之后。之后的改动较小，由测试、CI 和 Codex 会话在最终提交上的复验覆盖；本页写明两个提交。
真实运行里，一个批次排队 20 分钟、预计还要 30 分钟以上才开始时，让宿主 agent 把检查移回登录节点。只对这几次验证运行生效，为了当天跑完。它和技能里新加的“先等队列”不同。实际执行时发现冻结阶段的作业移不了（E-2），两次 Codex 运行都是取消后重开。
真实运行的检查执行器设置里加了 1,800 秒的排队上限。分区很忙；默认的 120 秒下，要求“自动”的作业会把全部检查退回登录节点。这是机器配置，不是 nanolize 的改动。

评审之后撤回、或改回 main 行为的

决定原因
M18：方案的第二点（重入保护）撤回。它让排在审计后面的查找器能把允许范围之外的文件加载进来，而 main 会把这种情况判为违规。报告里的实际情形（钩子排在前面）不受影响。

M24：读代码跟不上的测试（启动程序、星号导入等）保持找回，沿用原检查的能力。第一版把确实在驱动项目的测试也送去改写，理由还是错的。这等于对这一类测试保留了 main 的兜底规则，和已定事项第 7 条的字面不完全一致。
M9：通过子类访问的私有属性，只在源码里看得到项目的类定义了它时才报告。第一版会写出项目根本没有定义的名字。代价见 M9 的卡片：第二轮评审发现收窄后它在 bidict 上读不出来，为此又补了一个修复（959f5fb）。
M15：放弃“把没跑的检查的旧失败数补进来”，停滞规则保持 main 的算法，只多一个判断。补进来的数在 controller 作业里两种情况下是错的，会让 main 能继续的作业被判为停滞。
M19：去掉“名字像依赖清单就保留”这一支，只保留确实交给安装器的清单。否则任何命令 -c、-r 后面的文件都会被原版覆盖。
M1：离开验收的检查的环境变量只记“已省略”，不记摘要。这些检查不会被运行，摘要没有任何东西会去核对，却把值的指纹带进了包。
第二轮，M13：第一轮加的“一批检查最多 12 MiB 用例状态”收回，换成“main 读得了的报告永远保留用例”。12 MiB 的上限让一些在 main 上能保留全部用例的作业丢了证据。
第二轮，graphify：第一轮“复用时也只读元数据、不启动解释器”的一半收回。否则解释器已经换了版本或跑不起来的安装会一直被回答“可用”。评审者给的另一种修法会留下“坏的安装被说成可用”的状态，所以没有采用。
第二轮，性能设计：第一轮“被拒的计时文件触发其余文件重跑”的两行收回，换成“从计时文件导入东西的文件直接拒绝”。那次重跑正是已经接受的行为测试会丢掉的地方。
第二轮，性能验收：“做得更差的候选不取代记住的候选”只对任务优化成立，不再对性能修复成立。没有任何东西会因为一次性能修复“换掉了某个基准”而回退它，所以它必须是记住的候选；否则之后的回退会退过头。

M20：保留的选项要么带着它的值一起留，要么都不留；读到 -- 为止。Codex 会话发现第一版读过了 --；顺着查出带错值会让命令被 pytest 拒绝。

M22：differs 只对输出类检查比较标准输出和标准错误。否则稳定的检查会因为 pytest 打印的用时而显示“不同”。

M27：没有任何会话报花费时，合计是空值而不是 0。0 会被读成“免费”。
M7：没有暂停请求的作业不加 hold 键；事件里加一句“冻结期间取消的作业不能恢复”。保持旧记录逐字节不变；否则“要立刻停请取消”这句建议会掩盖取消的代价。

M16：报告文件最多 64 KiB，不跟随链接；被拒的评审调用仍然带回它的报告。那次调用已经付过费了。

性能验收里方案没定的细节

决定原因
一次有结论的比较对这个候选一直有效。否则慢 25% 的候选可以被一直重量，直到某次落进容差。
被接受的性能修复成为“记住的候选”，即使它更大、而且仍然慢。优先级是性能先于体积。
一个节点一次回答最多 3 个性能文件，由代码截断，不由回答格式拒绝。格式里限成 3 的话，多交一个文件会让整份回答（连同行为测试）作废。
计时文件被整份退回、而下一轮什么都没交时，把它当备用文件收回来。方案漏了这种情况，节点会白白没有性能文件。
性能契约只要设计步骤跑过就会写，哪怕一个文件都没接受。这样“没有标准”和“没设计”在记录里分得开。
计数文件按两份用例报告（原版一份、候选一份）来判断，不走行为比对的函数。性能测试不是行为验收标准，不该被行为比对的规则读到。
报告页的性能段落只有英文；进度页中英文都有。报告页本来就没有中文词典。
没通过的性能比较在所有页面上都是“缺口”，从不显示为“失败”；进度页第 06 阶段因此显示“有缺口”。和“永远不因性能而失败”一致。
记住的候选上“无结论”的基准不参与“优化有没有把它弄得更差”的比较。第二轮的 F2。代价是明说的：一次优化如果真的弄慢了这样一个基准，不会因此被回退。另一种做法代价更大：这种基准第一次有结论的读数会回退一次根本没碰它的优化。
其余和方案不同的地方（两个时钟、生成器、变慢的定义、_、修复用完后继续优化等）见“修改的内容和方式”里性能验收一节的“和方案不同的地方”。

真实运行、Codex 验证和 CI 期间的决定

决定原因
E-2 的修法：要求“自动”的作业，冻结阶段把检查移回本机并重做被打断的采集；明确要求“必须用调度器”的作业保持失败，只把报错说清楚。要求必须用调度器的用户不该被悄悄换地方。约定是：做不到又小又安全，就只写成已知限制；最后做成了一个提交。排队等待的十倍规则没有动，那是另一条规则，留给项目所有者决定。
E-3 的修法：收窄写事实一方的规则，而不是放宽评审一方。已定事项第 8 条的本意是产品的数据和配置文件（cactus 的情形：作者必须提供的文件），不是测试目录下的夹具文件，作者根本看不到它们。先提出的相反做法（让评审者放行夹具）没有采用。
正在跑的三次运行不为 E-3 重开。它让事实变少、事实阶段变贵，但不影响这几次运行要验证的任何一项；本页写明它对运行的影响。
E-4（Codex 自己的沙箱偶尔启动不了命令）只记录，不改。“所有命令都没启动的会话算失败并重跑”是一条对每个角色都生效的新规则，在最后一轮评审之后不再加新规则。留给项目所有者。

留下的三个已知限制

  • 性能验收：由处理器时间决定的基准，抓不到只是“等得更久”的候选。验证者的探针：原版每个进程随机等 0、6 或 12 毫秒，于是原版自己的秒数就不稳；候选每次调用多等 30 毫秒、计算量不变。候选的秒数是原版的 4.83 倍，比较结果是“通过”：秒数的噪声是 156%，所以由处理器时间决定（比值 0.998）。同一个探针里，相同的代码通过（处理器时间比值 1.0055，噪声 2.7%），候选自己放在基准路径上的文件被换回冻结的那一份，放宽到 100% 以上的算无结论。验证者的结论是“文档写明的限制，不是文档和实现不一致”。统筹会话决定不改：现在改规则，有让相同的代码在限流机器上失败的风险，调参显示那是更糟的错误；记录、结果和两个页面都写明有几个基准是按处理器时间判的；建议在安静的计算节点上测量。
  • M14：一个被多拒绝的网址。运行目录叫“某目录”时，指向同级的“某目录.后缀”目录的 file: 网址，在百分号编码写法下被当成指向运行目录而拒绝（指向“某目录-后缀”的不会）。不带编码的同样写法在 main 上本来就被拒绝，所以这次修复只是让两种写法一致。它错在安全的一侧：产品的一个网址被多拒绝，没有放行任何东西。

六、修改后的情况

使用 nanolize 的人会注意到什么

新的选项和工具

  • performance=on|off（技能）、--performance on|off|JSON（命令行）和 MCP 工具的 performance 参数。默认关；关着时什么都不变。
  • MCP 工具 prepare_graphify 和命令 nanolize graphify-prepare。MCP 工具从 47 个变成 48 个。第一次调用会在缓存目录里装约 250 MB，这台机器上用了约一分钟。
  • 开了性能验收的作业，controller 多一个作业工具 compare_performance（作业工具从 40 个变成 41 个）；没开的作业看不到它。
  • audit_check_scope 多一个参数 check=名字，用来取单个检查的明细。

变了的默认值和上限

  • 体积优化次数的默认上限：3 → 2。任务成本评估的优化轮数默认跟随作业的上限。
  • 用例报告的读取上限：2 万个用例 → 10 万个；标识总量 2 MiB → 8 MiB；报告 8 MiB → 32 MiB。超出原上限的大报告，在比对记录可能读不回时会放弃逐用例证据并写明原因；原上限以内的报告永远保留。
  • .ai .eps .psd .bmp .tif .tiff .icns .otf .avif .heic 归为二进制资源，不再让体积计量“不完整”。
  • 每个节点待改写的原版测试不再截到 40 个：超过 40 个的节点会多出设计会话，每个有整项排除的节点多一次评审。提交前的估算会显示多出来的会话数。

变了的回答、事件和文字

  • audit_check_scope 和带输出文件的 plan_capabilities 的回答变短：给汇总和要处理的列表，明细要另取或读计划文件。命令行的 scope-audit 仍是完整输出。
  • 计划阶段多一条提示：点名那些只用一句话描述接口、又没有检查覆盖的对外节点。
  • 暂停的回执多一个字段，说明它是在当前步骤之后生效，还是要等契约封存。
  • 迁移的汇总事件换了句式（一个分母）。测试设计之后多三条事件：重新采集基线之前、之后，以及契约封存时（带验证包的状态）。配置引用了候选里没有的文件时多一条事件。
  • 技能和文档里的默认时限改成按项目大小分四档的说法；graphify 一步从“没装就跳过”改成“没装就调用工具”；无人值守时计算节点不可用要先等队列。
  • 进度页：记录里没有优化上限时显示“已用 N 轮”，不再显示“/3”。
  • 要求“自动”选择执行位置的作业：调度器报告批次结束后，最多等 75 秒读节点的结果（原来 10 秒）；冻结阶段节点用不了时，把检查移回本机并发一条事件，而不是失败。

变了的记录（私有记录多了键，原有的键都保留）

  • 基线：每一轮重复运行的记录（stability.repeats）；用例证据不可用时的原因（case_evidence_reason）。
  • 修复反馈和错误记录：setup/teardown 的阶段（phase）；缺失的数据文件名（missing_file）；配置引用的缺失路径。
  • 进度记录：每个检查最近一次观察到的失败数（check_failures）。设计记录：迁移的各个计数、没被采纳的排除及原因。
  • 调用记录：三个 Claude 适配器顶层都有 cost_usd、cost_complete、turns；controller 的调用记录里模型、推理强度和沙箱模式有值；评审者调用的结果里有 review。
  • 验证包：有“离开验收的检查”的作业现在能导出验证包了（原来是不可用）。

转换结果会和以前不同

  • 用字符串拼私有模块名再导入的测试、只读工作流或 LICENSE 这类文件的测试，现在归为“待改写”而不是“找回”。在 tqdm 上，和 main 相比唯一改变去向的测试是 test_auto。
  • 找回的检查可能比以前多声明能力（它的文件离不开的那些）。去掉其中某个能力的选择，会让这个检查一并退役，而不是留下一个候选无法收集的检查。在 tqdm 上是两个 contrib 检查多了 contrib-builtins。

合并之后现在要做的事

  • 工具契约的摘要变了。原因：新增工具、几个工具的说明或参数变了（暂停、审计、计划、启动评审、体积优化默认值、性能参数）。这些改动已经在 main 里：把安装更新到现在的 main 之前启动、还没提交的评审要重新启动；更新之前创建的作业不能在新代码下恢复。更新安装之前，先让在跑的作业跑完。
  • 已装的插件要重装。插件版本号没有变（0.8.0），已装的插件会继续用旧的技能文本：新的服务端配旧技能时，没装 graphify 仍然会跳过那一步。要重装运行时并刷新插件；Codex 一侧同样要刷新并重启会话。
  • 已有的评审和作业保持 3 次优化，只有新启动的评审用 2。
  • 想让检查上计算节点的站点，先看“有 Slurm 就用”一节：有些集群需要在作业的环境和 check_executor 设置里补上站点配置、账号、分区、QOS 和更长的排队等待，否则自动判断会不声不响地退回本机（原因写在 check-executor.json 和一条事件里）。
  • 新版本做的体积计量拿到旧版本上校验可能被拒（如果它排除了新归为二进制资源的文件）。
  • 固定流程的基准记录要在它的录制环境里重录，见下。合并之后 main 上没有任何自动检查在比对它，所以这件事现在就该做。
  • 自己写安装检查命令时，用 {repo} 指代候选的副本，不要写 .。安装命令在检出目录之外运行；写错的命令现在不会在冻结前被发现，冻结之后也改不了。在 nanolize 补上这两处之前，这要靠使用的人自己注意。
  • “检查全部通过”不等于“和原版行为完全一样”。交付之后看一眼“回放离开验收的原版测试”那一项：packaging 的运行里，100 项检查全部通过的候选，在这些测试上有 193 个测试函数退步。

已知的限制和没关上的事项

问题修复里已知的限制

  • M9、M23、M24 的共同前提：对测试文件的读取是静态的，只跟随文档列出的那些写法；没列出的写法是已知限制。M9 仍然读不出的：getattr(obj, 变量)、辅助函数拼出的名字、子类覆盖私有钩子、只在函数里导入的基类、只通过动态方式绑定的属性、赋值不止一次或在条件里赋值的别名。
  • M14：指向“运行目录名加一个点和后缀”的同级目录的 file: 网址，在百分号编码写法下被当成指向运行目录而拒绝（Codex 第三遍构造的情形；不带编码的写法在 main 上本来就这样）。指向这次运行没用到的本机目录的 file: 网址会被保留（方案里写明的残余风险）。
  • M24：读代码跟不上的测试（启动程序、星号导入、没人定义的夹具等）仍然被找回并沿用原检查的能力。只断言 autouse 夹具副作用的测试会被读成“什么都没体现”而进待改写（评审者读出来的，没有探针，没有改）。事实规则的修复（E-3）没有用真实的写事实和评审事实的会话验证过。
  • M23：一个文件只要导入了某个能力，它的测试就随这个能力一起离开（留下并写进了文档）。测试只在运行时才需要的东西看不到。
  • M15：通过诊断契约缩小范围、或定向范围里有检查没能运行时，停滞计数仍可能被清零（main 上也一样）。
  • M18：排在审计后面、把所有别的查找器问一遍的查找器仍然会递归（main 上也一样）；另一个 main 上原有的口子没有动。
  • M19：只认 tox 的 deps 和运行 pip 的命令；环境变量形式的约束文件、uv 和 pip-compile 一类命令引用的文件只报告、不保留。项目自己的 requirements.txt 被 tox 引用时，候选里是原版的。文件名本身带方括号的依赖清单读不对：被点名的不保留，旁边同名不带方括号的文件反而被保留（Codex 第三遍构造的情形）。
  • M13：超过上限时的压缩证据没有做。超出原上限（2 万个用例）的大报告，在比对记录可能超过 32 MiB 时放弃逐用例证据：比如一个 9.2 万个用例的测试集。
  • M6：评审仍然整份文件地接受或否决。
  • M16：不带围栏的代码不拒绝；超过 30 条的发现只在记录里。
  • M11：评审页面上不显示那条提示；评审开始后才加选的节点不会被点名。

性能验收已知的限制

  • 极短调用（约 2 微秒以下）在“变慢”时被放慢的远不止一倍，这类工作量比“慢一倍”的说法更容易成为标准。
  • 异步函数、模块顶层代码、只是在等待的函数不会被变慢；只有这些的节点没有标准。GPU 工作量不计时。
  • 由处理器时间决定的基准，抓不到只是“等得更久”的候选：这样的比较记为通过、不产生缺口，结果里只有一个计数。Codex 验证者的探针里，秒数是原版 4.83 倍的候选通过了。按决定保留；建议在安静的计算节点上测量。
  • 固定作业里，任务成本评估开着、第一个候选变慢、之后没有一次性能修复留下候选时：交付的候选没有任务成本评估（task_effort_not_passed，原因 performance_acceptance_pending），也因此不会去做用户允许的优化。controller 作业会在交付前补上评估。
  • 恢复出来的候选是新候选，会重新测量，同样的代码可能因此得到第二个读数。性能缺口本身不让作业失败，但开了开关的作业仍然会因为别的原因失败。
  • controller 作业里“性能先于体积”是建议，不是硬性拦截。

真实运行里找出、还没处理的（需要改 nanolize）

  • 要求“自动”的检查执行器只给队列 120 秒；探测批次没开始，就把整个作业的检查永久移到登录节点，只在一个记录文件和一条事件里说明。在忙的集群上这是常态。
  • 启动评审服务的等待时间是写死的：在很忙的机器上第一次调用超时，留下一个状态停在“启动中”的废弃评审目录；宿主重试后成功。预热过的 MCP 服务端回答工具列表也用了 27.1 秒，离客户端的 30 秒上限很近。
  • 一个叶子节点的性能文件被拒之后，如果它另有一个被接受的性能文件，就不会再被问；给它的反馈没有会话读到。
  • controller 给作者的修复说明上限是 4,000 个字符；超出时整个回答在执行前被拒，这一轮只允许更正一次。
  • 运行技能的第 02 阶段没有说安装命令在检出目录之外运行、必须用 {repo} 指代候选；冻结之前也没有任何一步在原版上试一下安装检查。写错的安装命令要到第一个候选才暴露，冻结之后改不了，作业只能以“带失败交付”结束（packaging 的运行正是这样）。

运行环境

  • 冻结阶段节点用不了时的自动移回本机，只对要求“自动”的作业生效，而且探测之后的批次要在队列里等满排队上限的十倍才算用不了。正在运行的作业不能用“恢复并改成本机”来移。设计步骤在提交设计文件之前遇到节点不可用时，设计以“没有测试”结束。
