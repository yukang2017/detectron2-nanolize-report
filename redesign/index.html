nanolize 改动方案

对 main 分支要做的三项改动、各自的意义和依据 · 2026-11-12 · 基准:main 862a02ec5

现在的 main 分支能让重写后的代码通过全部检查,但压缩不了:上一次对 detectron2 的完整运行,交付结果是原版体积的 98.4%。原因有三个:作者模型凭记忆把原项目默写了出来;原版的注释几乎原样保留;给作者的材料和检查都把内部结构钉死了,只能在函数内部做文章。下面三项改动分别针对这三个原因。

改动一

给作者的材料改粗

不再给逐个登记声明的 knowledge,改给用户筛选后的功能图,加每个节点的对外约定。

改动二

检查由测试 agent 编写

不再直接用原仓库的全部测试。由独立的 agent 按功能图写行为测试,只从对外约定进去。

改动三

注释规则和防默写

注释默认不写。和原版逐函数比较,整体 40%、单个函数 60%,一开始告知,最多重写一次。

一览:main 现在怎么做,改成什么

方面main 现在改成意义
给作者的材料细的 knowledge:每个文件的声明清单、每个签名、内部函数都登记功能图加对外约定;内部实现不登记作者可以改结构,不再只能压缩函数体
节点的接口所有登记的接口都要保留每个节点标明"对外"或"内部";内部节点只保行为底层模块之间的接口也能重新设计
检查的来源owner 提供的检查,主要是原仓库的单元测试和按功能写的探针独立的测试 agent 按功能图编写;能直接用的原测试沿用检查不再依赖内部的文件名和函数名
作者的自检逐个比对公开名字和参数只比对对外约定里的名字合并、继承、改名不再被报为差异
注释规则要求"只留读者需要的",实际几乎原样保留默认不写,只在读者必须猜的地方加一行体积的主要下降来源
默写没有规则,也不告诉作者;只在交付后给 owner 一个数字规则加度量:一开始告知,超线点名重写一次知名项目上不再交付一份默写稿
"保留功能"的含义原仓库的检查全部通过所选节点的对外行为保持不变换来结构上的自由;代价见下文

改动一:给作者的材料改粗

从"逐个登记的 knowledge"改成"功能图加对外约定"

main 现在

冻结阶段,工具把 knowledge 包放进作者的工作区,作者按它实现每一项功能。对 detectron2,这份 knowledge 有 9,177 条记录、7.7 MB,是原版源码(3.3 MB)的 2.3 倍。其中给 280 个文件各有一份声明清单,共登记 2,152 个函数签名,包含 411 个下划线开头的内部函数。

与之配套的还有三处:规则要求保留"所有已登记接口"的类型标注;每次调用的任务说明是"为这些 knowledge 记录里的声明写文件";自检脚本逐个比对公开名字和参数。

改成
  • 给作者的是用户在页面上筛选之后的功能图,也就是用户自己看到并确认过的那份。
  • 每个节点附一份对外约定:外部可见的名字和签名、配置项、命令行参数、注册的组件名、文件格式、固定的报错文字。只列外部能看到的,不列内部实现和文件布局。
  • 每个节点标明"对外"或"内部"。对外的节点接口固定;内部的节点只保行为,接口由先写的作者决定,后写的作者读已有的草稿。
  • 纯数据的文件(类别表、默认配置值等)原样带入候选,不让作者重写。
  • 不再把细的 knowledge 交给作者。
意义
  • 放开结构。现在作者能自由发挥的只有函数体和私有辅助函数,改动后可以合并类、调整模块划分、删掉不对外的中间层。
  • 减少触发默写的线索。精确的文件路径加精确的签名,足以让模型认出是哪个项目的哪个文件,然后把函数体背出来。
  • 作者要读的材料少得多。
依据

试跑里,原版第 1 组的 142 个函数和方法,在每一份草稿里都是 142 个全在,类和继承关系一个没变,新增的只有 10 到 18 个私有辅助函数。在这种约束下,无论怎么施压,代码量都停在原版的 80% 以上(见"试验数据")。

作者做结构性合并时,和登记清单直接冲突:它把 RotatedBoxes 的三个方法改成从 Boxes 继承之后,自检脚本报"缺少名字"。

改动二:检查由独立的测试 agent 编写

从"原仓库的测试"改成"按功能图写的行为测试"

main 现在

检查由 owner 提供并冻结。对 detectron2 是 160 项:71 项是原仓库自带的测试文件,89 项是按功能写的探针。原仓库的单元测试直接导入内部模块和函数,所以即使 knowledge 写粗了,文件布局和内部函数名仍然动不了。

工具里已经有测试设计和测试评审两个角色,但只用于"现有检查没覆盖到的节点"。

改成
  • 由一个独立的测试 agent 编写检查。它依据用户筛选后的功能图,可以参考原代码和原测试。
  • 原测试能直接用的就沿用。判定标准:只调用对外约定里的名字。导入了内部函数或依赖内部布局的,由测试 agent 参考它改写。
  • 写的是行为测试,从节点的对外接口进去,比较输入和输出,不按内部函数逐个测。
  • 不管是沿用的还是新写的,都要先在原版代码上跑通且结果稳定,才能作为检查。
  • 测试 agent 和写代码的作者不是同一个,用互相独立的会话;测试对作者不可见,作者只得到"哪项没过"的反馈。
  • 作者的自检脚本只比对对外约定里的名字,不再比对内部名字。
  • 不测量新测试在原版代码上的覆盖率。工具已有的"故意改坏代码,看测试能否发现"的有效性校验保留。
意义
  • 和改动一配套。只改粗 knowledge 而继续用内部单元测试,结构还是被钉住;两边一起放开才有用。
  • 检查对着用户选中的功能。用户在功能图上删掉的节点,不会再有针对它的检查。
  • 隔离不变。读过源码的 agent 只写测试,写代码的 agent 仍然先不看源码。
依据

160 项检查完整跑一遍约 18 分钟(探针 6.5 分钟,原仓库测试 11 分钟)。检查的数量取决于功能图分了多少个节点(106 个)和原仓库有多少测试文件,不取决于签名登记得多细。

改动三:注释规则和防默写

注释:默认不写

main 现在

规则是"为下一个 agent 写,只留读者需要的",并有一句"不要为了体积目标删掉该留的"。上一次完整运行里,Python 的注释和文档字符串保留了原版的 99.3%。

改成

默认不写注释和文档字符串;只在读者光看代码必须猜的地方加一行;拿不准就不写;不带入原项目的注释。属于行为的文字(报错、帮助信息、格式字符串)和法律要求的声明保留。

意义

这是体积下降的主要来源。试跑里第 1 组的注释降到原版的约 20%,总体积因此到了原版的 60% 到 64%。

防默写:度量、告知、最多重写一次

main 现在

提示词只禁止"读原仓库"和"复制别的实现",没有提凭记忆复现。工具在交付后会算一个"与原版逐行相同的比例",但只给 owner 看,明确规定不发给作者。体积目标只是参考,不达标照常交付。

改成
  • 规则。新增一条:可以认出这是哪个项目,但它公开的源码不是交付物,不得凭记忆写出它的文件、函数体、注释;按给定的材料用最少的代码和结构自己设计。
  • 度量。把作者写的每个函数体和原版比较:忽略空白和注释,不计签名、装饰器、import;少于 8 个字符的行不计。结构放开之后,比较不再依赖"同一路径、同名函数",改成和原版全部代码比。
  • 两条线。按文件夹(一组功能)整体不超过 40%;单个函数不超过 60%,只判不少于 8 行的函数。
  • 一开始告知。从作业的第一次作者调用起,就告诉作者会比较以及这两条线。
  • 最多重写一次。超线时点名具体的函数,让作者只重写这些;整体超线时把相同行最多的函数也列出来。重写一次后不管结果如何都继续,并把数字报告给 owner。
  • 是否启用由实测决定。度量本身很便宜(整个 detectron2 约 5 秒)。每个作业都量,第一组的比例高才启用告知和重写;模型没背过的项目比例自然低,规则不会触发。不靠"项目是否知名"来判断。
  • 只给数字。发给作者和 controller 的只有百分比、数量和作者自己的文件路径与函数名,不含原版的任何一行。
意义
  • 知名项目上不再交付默写稿。这是模型自身的记忆造成的,不是运行中泄露了源码(见"默写的来源")。
  • 成本可控。每组最多多一次调用,不会反复被拒卡住。
  • 对没背过的项目没有影响。
依据

见下面的试验数据。只改提示词拦不住默写;一开始告知能压掉约 20 个百分点;点名到函数再重写一轮,又压掉 25 到 30 个百分点,并且比整组重写快。

试验数据

都是对 detectron2 做的。完整运行用的是已并入 main 的那版代码;小试验在分支 claude/independent-rewrite 上,只跑第 1 组(数据结构和运行时工具,原版约 2.9 万 token)。每次都把写出的文件替换进原版,跑相关的原仓库测试,结果全部和原版一致(78 通过、12 跳过)。

  • 告诉作者的具体数字影响不大:说 25% 和说 40%,首稿只差 5 个百分点。作者写的时候看不到自己的读数,它在调用结束时写道"我没法度量那个比例"。
  • 函数级点名比文件级有效:文件级反馈下作者把整组 25 个文件全部重写;函数级反馈下只改被点名的函数,10 到 14 分钟完成。
  • 不管用哪种做法,代码量都停在原版的 81% 到 88%。相同的行少了一半,代码并没有因此明显变短。这是改动一和改动二要解决的问题。

为什么 40% 和 60%

相同行的来源(第 1 组)占全部行
材料明确规定的内容(固定的报错文字等)约 5%
不到 5 行的小函数(通常只有一种自然的写法)约 12%
其余,可以重写的部分重写一轮后约 37%

约 17% 的相同是避免不了的,所以整体 25% 太严:试过一次,一轮重写后是 33%,仍有 9 个小函数超线。按 40% 和 60%(不少于 8 行)试的那次,被点名的 23 个函数一轮全部改到线下,整体 46%。

已接受的取舍

  • "保留全部功能"的含义变了。从"原仓库的检查全部通过"变成"功能图上所选节点的对外行为保持不变"。依赖内部函数的调用方不再保证兼容。
  • 检查的保证变弱。agent 写的测试覆盖不如原仓库多年积累的测试,行为偏差漏掉的风险更大。不为此测量覆盖率。
  • 这是一次大改,涉及材料的生成、检查的来源和验收的含义三块。不先做小规模验证,直接改工具。

不变的部分

  • 作者写第一稿时不看源码;某项功能的检查失败后,修复时可以参考那项功能的原文件。
  • controller 决定步骤、按组分批写、候选保存和验收的流程。
  • 原生代码来源检查、全新环境安装检查这类交付检查。
