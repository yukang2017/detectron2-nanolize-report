结论

  • 交付了，但带缺口。 候选代码在两次全量对比里 46 组检查全部通过，全新环境里的 3 项安装检查也通过。作业仍然不声明“行为完整保留”，原因是两件事：一个原版测试在冻结基线时在原版代码上失败；两个能力（auto 和 contrib-concurrent）没有任何检查。
  • 体积达到目标。 总 token 降到原版的 41.65%。降幅主要来自文档字符串、注释和非 Python 文件；Python 代码本身保留了 72%。
  • 防默写检查起了作用。 作者的初稿有 61% 的行与公开的原版相同，保存被拒绝，34 个文件各被退回重写一次。重写后是 36%，低于 40% 的上限。
  • xhigh 让冻结阶段又贵又慢，并直接造成了一个缺口。 冻结阶段（写事实、补测试、录基线）用了 77 分钟，其中写事实和补测试的会话花了 102.79 美元。一个测试审阅会话撞上 855 秒的时限，它负责的 8 个测试文件全部作废，其中 7 个属于后来没有检查的那两个能力。
  • 问题清单共 11 条：4 条需要改 nanolize，7 条是遇到的现象。见“问题清单”一节。

三个缺口

  • 缺口一：一个原版测试在冻结基线时失败。 tests/tests_pandas.py 里的 test_pandas_leave 在原版代码上失败（期望 100/100，得到 99/99）。这个检查因此不算验收标准，整次行为对比停在“未验证”。候选在这个检查上 8 个用例全部通过。启动对话在没有改动的原版上重跑了 78 次，全部通过，没能复现；这个测试用的是没有设种子的随机数，按它的写法大约每 230 次会失败一次。失败的原因没有查明。

没有验证的

  • 花费 167.26 美元不含启动对话本身（它调用了 48 次 nanolize 工具），也不含超时的那次测试审阅（没有记到金额），所以实际总额略高。
  • tests-pandas 在原版上失败的原因没有查明。
  • 没有做同一项目在默认 effort 下的对照运行，所以 xhigh 多花了多少时间和钱没有数据。
  • 任务成本评估没有开启。
  • 这次运行只跑了一遍。
  • 通过检查不等于行为等价：检查只覆盖它们执行到的情况。
