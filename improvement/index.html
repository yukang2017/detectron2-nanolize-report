nanolize 流程修改建议

结论

先做六件事。它们都不改变“作者不看源码”这个定位，前三件改动小、证据最硬：

  1. 把失败细节交给作者，但不给自由文本。三次运行的 502 次失败观测，输出里全都有可以自动提取的错误信息，作者一条也没收到；两个 Codex 运行为此空等 owner 各六七个小时。其中近三分之二是“缺模块、缺名字”，在集成时就能静态发现，不用跑任何检查。（T1，已有原型）
  2. 停止奖励删文档，先只改那一句话。策略要求删、度量奖励删、内核还优先保留删得最狠的候选，这三处在当前分支上都没变。按只计代码的口径重算，本次运行的 23.1% 减量只剩 10.5%。（T2，度量已有原型）
  3. 把已经算出来的信号用起来，堵住白跑。验证时已经算了公开签名的差异却没人看；guide 让收尾多跑一轮全量；收尾预留的时间不够时会撞上硬时限，什么都不交付。（T7）
  4. 并行执行检查，隔离，并且只认通过。实测 8 个并发共用一棵树，160 个检查里 100 个失败；各用一份副本则与串行结果一致。没通过的要回原树单独重跑，否则偶发失败会成为清不掉的验收缺口。（T3）
  5. 用短会话。本次运行每个作者会话的上下文涨到 55 万到 81 万 tokens。在同一个工作区里按范围依次跑短会话，缓存读取量能降到约四分之一，不需要合并。（T4）
  6. 让作者在会话里自检，先做不跑测试的那一种。编译、import 公开模块、比对公开接口，不增加任何泄露面。（T5）

一个要你们拍板的方向。这几次实验里质量最好的结果来自“看源码、原地改写”，它也让并行和会话内自测变得容易。但它改变产品定位，而且有一个实在的风险：目标会变成“删掉检查没覆盖到的东西”。建议先做它的一小步：让 harness 原样拷贝 owner 标记的文件（原生内核、数据表）。这不需要新模式，就能省掉约三分之一交付体积的重打和其中的出错风险。完整的模式和需要的护栏见 T6。

换到当前分支之后变了什么。它在 main 之上的 5 个提交都是平台和健壮性修复，33 条建议的状态一条都没有变，原型挪过来没有冲突。新出现的两件事都在“放行超过 2 MiB 的文件”的下游：内容不是文本、后缀又不在名单里的文件，会让作业跑完全程后必然失败（H9）；大的文本数据文件会整份计入体积基线，主导体积目标（H10）。两件都用最小仓库跑作业实测过，解法是同一个：一份由 owner 确认的“原样携带”清单，也就是 T6 的第一步。详见对照当前分支。

按本次流程运行的时间线估算，验证提速加并行作者可以把 11.5 小时压到 5.5 到 7 小时；文档策略的修改不增加成本。这些是估算，没有实测，拆解见落地顺序。

需要先拍板的五件事

这五件事已经有了决定。据此整理的改动清单见修改清单；下面保留的是当时的问题。

  1. 错误的类型和候选自己的位置，能不能给作者？缺失的模块名呢？代码里明确写着失败细节“never an author”，这是有意的决定。T1 给的是封闭词表，不带任何消息；模块名是否算可以透露的接口要你们定。
  2. 要不要改策略那句话？它属于冻结契约，改动要升契约版本、重录固定策略的对照基准。
  3. “不看源码”是不是硬性要求？如果不是，原地改写值得做一次对照实验；如果是，至少可以让 harness 原样拷贝标记的文件。在当前分支上，这份携带清单还要用来处理无法度量的文件和大的数据文件，并且要在体积口径里加一个免计类别。
  4. 检查在哪里跑？这几次运行的 CPU 检查都跑在只有 4 核配额的登录容器里，并行最多快两倍多。要真正提速得把检查派到计算节点上。
  5. 大仓库的默认预算给多少？默认的作业时限是 2 小时，detectron2 上光是 main 新增的冻结步骤就可能用掉大半；收尾预留的时间也是按小仓库的量级算的。

七个重点改动的具体做法

下面七项是对着代码逐个推敲过的（推敲和评审时用的是 main，涉及的位置在当前分支上没有变化）：先确认现状，再用已有运行的数据量化，能做原型的做了原型，最后请一个独立的评审专门挑错。评审推翻或收紧了其中不少做法，下面写的是修改后的版本，改了什么见评审之后改了什么。前两项的原型在当前分支之上的一个本地分支里，没有推送。

T1把失败细节交给作者，但不给自由文本（对应 A1）

已做原型有实测数据评审后改过
现状
当前代码已经从检查输出里提取失败的测试和每个测试的第一条错误，还会识别“测试里的 import 失败”，但这些只写给 owner；作者只拿到检查编号、退出码和指向测试事实的 knowledge_ids。
数据
三次运行里共有 502 次失败的检查观测，502 次的私有输出里都有可以自动提取的细节。共 363 个错误，其中 233 个是 import 类（201 个“找不到模块”，32 个“找不到名字”），其余是运行时异常。本次运行第一次全量对比的 7 个失败里，5 个就是缺模块。这些信息作者一条也没收到，两个 Codex 运行为此向 owner 提了 11 次诊断请求。
为什么不能直接把消息给作者
候选的代码就运行在检查进程里。如果异常消息原样回到作者手里，候选可以把测试文件的内容塞进异常，现在“每个检查一个退出码”的窄通道就变成了能回读验证方文件的宽通道。所以默认不给任何自由文本。
改法，分两层
  1. 静态的一层，集成时做，不运行任何检查。harness 已经有每个检查的静态 import 证据（check_scope.py）。把“检查从项目里 import 的模块和名字”与“候选实际提供的”比对，缺的作为一类候选缺陷报告，走现有 import_shadowing 那条通道。它能覆盖上面 363 个错误里的 233 个，而且在跑任何检查之前就能发现，省掉一轮全量对比。
  2. 运行时的一层，用封闭词表。对“原版通过、现在不通过”的用例，只报告三样：异常类型（只取内置异常名，其余一律记为 Exception）；是谁抛的（候选、候选调用的库、验证方）；候选自己文件里最内层的那一帧。文件必须真实存在于候选树里，路径和函数名限长。每个检查最多 5 条，其余只计数。
  3. 可选项：owner 信任作者的 runner 时，可以打开“候选自己抛出的异常的消息”，限长一行，并经过知识包那个文本过滤器。
原型
第二层已经做了：failure_digest.py，接进了 JUnit 解析、失败分类和作者反馈，13 个新测试通过。只对 controller 作业生效，固定策略的反馈字节不变。同样的条目会进入 controller 的问题记忆，这是有意的：它只包含类型和候选自己的位置。
挪到当前分支时补了一处。这个分支开始支持 macOS，那里的临时目录在系统别名路径下（/var 实际是 /private/var），异常栈里的路径和工作树的路径可能一个带别名一个不带。原来按路径前缀判断“这一帧是不是候选自己的文件”，遇到这种情况会全部判成“其他”，摘要就空了。现在工作树路径的两种写法都认，有测试。
需要你们定的
静态那一层要不要给出缺失模块的名字。测试事实规则不允许写带点的模块路径；如果坚持，可以只说“某个功能缺 N 个被检查 import 的模块”。
没做完的
私有的检查结果里多了一个 case_errors 字段。固定策略的对照基准在别的环境里会跳过，这里没法验证，合并前要在录制环境里重录，或者给这个字段也加开关。非 JUnit 的检查目前拿不到候选树的位置，只能报告类型。

已做原型有实测数据评审后改过
现状
三处在同一个方向上用力：策略要求“激进删除文档和注释”；体积按整个文件文本计数；内核在已验收的候选里保留 tokens 最少的那个，停下来时恢复它。
数据
用新的度量重算本次运行：按现在的口径体积减了 23.1%；去掉注释、文档字符串和大型字面量数据表之后，代码只减了 10.5%，其中 Python 逻辑代码减了 5.6%。公开定义的文档覆盖率，按代码里自己对“公开”的定义算，从 58.7% 掉到 15.1%（前文的 55.6% 和 13.5% 把嵌套函数也算了进去）。
改法
  1. 只改策略那一句（policy.json 的 minimal_explanation，以及 runner.md 里的“Keep documentation minimal”）。这是成本最低、效果最直接的一步，建议稿见文末。
  2. 质量数字只做 owner 一侧的报告：写进测量记录、交付报告和运行页面，不发给不看源码的 agent。尤其是“与原版相同行的比例”，它是在拿候选去比原版，放进 controller 能看到的结果里就成了探测原版的通道，而且会鼓励为了显得不同而改写。
  3. 不把代码 tokens 设成目标，也不设文档覆盖率下限。前者会重新打开已经堵上的口子（把逻辑挪进字符串或数据表来“减代码”）；后者会招来凑数的文档字符串。
  4. “保留 tokens 最少的已验收候选”在内核里（rewrite_stages.py:123-138）。可以改成比较时不计注释和文档字符串，或者保留最近一个已验收的候选。这一条影响固定策略，要和对照基准一起改。
原型
code_quality.py：对计入体积的文件给出代码、注释、文档字符串、数据表四类 tokens，公开定义的文档覆盖率（沿用代码里自己对“公开”的定义），以及与原版同名文件相同内容的比例。结果只进测量记录，controller 看到的摘要没有变。7 个新测试通过。
注意
策略文本是实时加载进反馈的，而 contract.json 是冻结的：改了文本，续跑的旧作业会同时看到两个版本，所以要一并升契约版本。同一段策略文本每个会话会出现在 6 个地方，改的时候要一起改。

T3并行执行检查：隔离，并且只认通过（对应 B1、B5）

有实测数据设计稿评审后改过
现状
当前代码仍然逐个串行执行检查。只有叶子敲除用了线程池，而且是在各自的导出副本里跑。
实测
在交付的代码树上重跑了 160 个检查。串行记录是 16.4 分钟。8 个并发共用一棵树时，160 个里有 100 个失败，而它们单独跑都是通过的。8 个并发、每个并发一份私有副本时，159 个的退出码和输出哈希与串行记录完全相同，1 个撞上 300 秒超时；墙钟 7.3 分钟，只快了 2.2 倍。只快这么多是因为这台登录容器的 CPU 配额只有 4 核（系统报 64 核），并发的检查在互相节流。按记录的单项耗时做理想排程，8 个并发应该在 2.1 分钟跑完；要在核数足够的机器上才达得到。
三条约束
  • 不能共用一棵树：这些检查运行时会在工作树里放临时数据。
  • 代码把证据定义为“在封存的工作树上观测到的”，而且同一份代码一次通过一次失败会成为清不掉的验收缺口。所以并行引入的任何偶发失败都不能被记成失败。
  • 副本隔离不了可编辑安装和树内的环境：这类仓库里 import 仍然会落到真实的工作树上。
改法，沿用敲除的做法
  1. 采集基线时，给每个检查多做一次“在导出副本里的对照运行”。结果与原树上一致的检查才标为可并行，这个标记进基线记录。
  2. 取证时，可并行的检查在各自的私有副本里并发跑；通过的直接记为通过。
  3. 任何没通过的，都回到封存的工作树上单独重跑一次，以这次串行的结果为准。这样并行只会加快“确认通过”，不会制造新的失败记录。
  4. 线程数由 owner 写在检查声明的环境变量里。它已经在每个检查的环境指纹里，不需要新机制，也不能逐次调用临时改。
  5. 超时规则不动：会超时的检查最终都会被串行重跑。
预期
在只有 4 核配额的登录容器上，上限就是实测的两倍多。要更多，得把检查派到计算节点上，这和 B5 的常驻执行器是一件事。main 新增的重复基线和敲除也会直接受益。
当前分支上要多注意三点
  • 副本可能很大。单文件 2 MiB 的上限取消了，工作树里可以有很大的资源文件，每个并发一份副本的成本随之变大。建副本时用写时复制的克隆（APFS、btrfs、XFS 支持），不支持的文件系统上退回普通拷贝；不要用硬链接，检查改写文件时会改到封存的工作树。先量一次建副本的耗时，再定并发数。
  • 清理不能指望子进程收养。这个分支在 macOS 上运行时没有子进程收养，脱离的孙进程可能活过一次运行。并行副本要按会话或进程组结束进程，然后再删副本。
  • 路径检查沿用新加的那个函数。副本如果放在系统临时目录下，“路径上不能有符号链接”的检查要用这个分支新加的 records.redirected，不要再写一份，否则在 macOS 上会被 /var 这个系统别名挡住。

T4短会话优先，并行其次（对应 C1、C3、D1）

有实测数据设计稿评审后改过
现状
每个作者会话都拿到完整的契约和完整的知识包，会话里什么都做。并行工作区和按文件合并已经实现，但 guide 把它们描述成“独立的备选方案”。
数据
  • 本次运行里每个作者会话的上下文从约 1.2 万一路涨到 55 万到 81 万 tokens。把每个会话按范围拆成 4 个，缓存读取量降到现在的 26%，省下 $38 里的 $28。
  • 用现有计划里的数据就能自动划分：按 4.5 万 tokens 封顶，detectron2 的 106 个功能分成 23 个范围，中位数 3.2 万 tokens；452 个文件里只有 8 个被多个功能共有。
  • 一个范围的作者需要读的知识中位数是 2.4 万 tokens，而不是面对 235 万的整包；全部功能的索引只要两三千 tokens，现在的 index.json 是 10 万。按这个办法实际生成了一份样例。
第一步：同一个工作区里按范围跑短会话
在一个工作区里依次调用作者，每次只负责一个范围（run_agent 已经能传功能列表），提示词只指向这个范围的知识。不需要拆工作区，也不需要合并，就能拿到上下文变短的全部收益。只省 tokens，不省墙钟。
第二步：并行，要先解决文件归属
不看源码时，文件布局是作者自己定的，两个范围完全可能写到同一个路径，合并会被拒绝。所以并行之前要给每个范围指定它可以写的模块路径（来自接口契约）。原地改写模式下文件本来就在，天然不相交。
现有的限制
一批最多 20 个请求、8 个并发，作者调用数设上限时最多 20：23 个范围要么调上限，要么把范围并到 20 个以内。一批是一个操作，所以只能整批合并，除非改操作协议；每次合并都是一个需要完整证据的新候选。每个作者各写一份报告映射，而流程只读作业自己那份。任务书是新的“从源码到作者”的文本，要过知识包的文本过滤器，并作为冻结输入封存。

T5让作者在会话里自检：先做不跑测试的那一种（对应 A2）

设计稿评审后改过
现状
作者写完整个会话才由 controller 取证，一轮约 50 分钟。goal 模式的子代理每改一个文件就跑一次定向测试。
先做的版本
harness 提供一个作者可以调用的命令，对当前草稿做三件事：编译全部文件；逐个 import 契约里的公开模块；把草稿的公开接口和接口契约比对。它不运行任何测试，返回的全是作者本来就有的信息，却能在会话内抓到占失败大头的 import 和接口错误。
跑检查的版本为什么要慎重
它是一个可以反复提问的通过/失败探测器：作者可以对着它二分出期望值，或者针对测试写特例。如果再配上错误消息，就成了会话内的回读通道。所以只建议在原地改写模式下，或者 owner 明确允许时开启；每个会话限次数，只返回通过/失败和 T1 的封闭词表；结果不是证据，不参与验收。
通道
不能用工作区里的文件：作者会话期间 .nanolize-rewrite 下的任何改动都会被判为篡改，其他位置的文件又会被当成草稿。要用 harness 一侧的命令行或 MCP 工具，并且在独立的副本里做，不碰候选的工作树。

T6“看源码、原地改写”：先做小的替代，模式本身要你们定（对应 F1、E4、E7）

设计稿有实测数据评审后改过
为什么值得考虑
这几次实验里质量最好的结果来自这种做法。不看源码时，Fable 作者写出 66 万 tokens 的代码，其中 83% 的行是凭记忆默写的上游：初次实现的三次会话花了 $115，按相同行的比例估算约有一半花在重打上。Codex 作者确实在重写，但到检查全过用了 15 到 19 小时。
小的替代，不需要新模式
让 harness 原样拷贝 owner 标记的文件，比如原生内核和数据表，作者不写也看不到。本次运行里 LVIS 类别表（16.4 万 tokens）和原生内核（5.1 万）合起来占交付体积的三分之一，全是作者重打的，旋转 IoU 的那个内存安全问题也出在这里。这一步不动“不看源码”的定位，就能省掉这部分的输出和风险。
在当前分支上，这一步从“省钱”变成了“必需”。单文件上限取消之后，几 MB 的数据文件可以进入范围，而不看源码的作者没有办法把它默写出来，见 H10。
携带清单具体怎么做
  1. 计划里加一个字段。owner 在评审页面确认的一组路径，随计划冻结；controller 和作者都不能改。
  2. 页面自动给出候选。无法度量的文件（H9）、单个文件占体积基线超过一定比例的数据文件（H10）、原生源码。owner 逐个选“携带”“交给作者重写”或“排除”。
  3. 集成时按验证方拥有的文件处理。和冻结的测试、检查输入走同一条路，逐字节保留；作者生成了同名文件就拒绝并反馈。
  4. 度量里加一个免计类别。携带且未改动的文件，分子分母都不计。这是口径变更，要升口径版本、重录固定策略的对照基准。
  5. 知识包只给接口。携带的模块给名字和签名，数据文件给路径和格式，不给内容。
完整的模式
作者在原版生产代码的副本上按行为冻结规则改写，测试仍然归验证方。起点是一个通过全部检查的候选，之后每一步都是一次保持行为的简化，通过就留下，不通过就退回，于是任何时刻都有可以交付的结果。试验过一次：用现有的集成步骤，把 detectron2 原版的 739 个非测试文件原样当作草稿集成回去，得到的代码树与原版逐字节相同，只有 4 个符号链接形式的文档被拒绝。
评审指出的问题
  • 它动的是产品定位。guide 第一句和工作区记录都写着作者不看源码。
  • 不只是在 modes.py 里加一个值：模式在执行、页面和独立修复几处都被断言，以前的 prune 模式是特意移除的。“验收之后保持全绿继续缩小”的阶段现在其实已经有了。
  • 第 0 个候选不保证全绿：基线不可用或检查不稳定时不成立；owner 的交付检查从没在原版上跑过。
  • 最大的风险：目标会变成“删掉检查没覆盖到的东西”，覆盖缺口变成悄悄的删除。
需要的护栏
  1. 复用已有的原地修改守卫：公开契约变化和保留的源码缺失，在代码里已经是会判为不安全的问题码。
  2. 覆盖围栏：采基线时收集行覆盖，没有被任何检查执行到的代码默认只能原样保留，要改必须在报告里逐条说明理由。
  3. 开始前先在原版上跑一遍 owner 的交付检查，确认起点真的全绿。
  4. 叶子测试和敲除（已有）保证每个功能至少有一个会因它失败的测试。

T7把已经算出来却没人用的东西用起来（对应 E2、A3、H3、H5）

设计稿评审后改过
静态签名差异
验证时已经在算公开签名的静态差异，但既不算问题也不反馈。三次运行里它分别记下了 35、95、88 处变化，其中就有盲评评审指出的 nms_rotated 去掉装饰器那一处。它按原版文件名和精确的 AST（含装饰器）比较，而“必须保留原版路径布局”这个开关现在是关的，所以它是被有意降级的：原样反馈会透露原版路径，当作门槛又会强迫保留原布局。改法：按功能汇总（哪个功能有几个公开名字的签名变了或不见了）反馈给作者，并写进交付报告，作为待确认项。
评审角色
reviewer 的输出只进日志，controller 读不到，却照样扣一次作者调用。改法：让评审把结论写进一个有固定格式的产物，controller 能读到；或者在修好之前从 guide 里去掉这个角色。
多跑的一轮全量
guide 要求收尾时跑“a full run_checks”，它会把全部保留检查再跑一遍，而验收只读其中 owner 的交付检查。建议步骤其实已经只点名交付检查，所以只需要改 guide 的措辞。
收尾预留的时间
作者时间用完时，流程已经会恢复最好的候选并交付。问题在预留的时间：它按“300 秒加两倍的原版检查耗时”算，在 detectron2 上约 38 分钟，而本次运行里一次完整的取证加交付用了约 45 分钟。预留不够就会撞上硬时限，那时作业直接失败、不可恢复、什么都不交付。改法：预留时间按本作业实测的“全量对比加安装加交付”耗时来算；预算耗尽后允许 owner 追加预算并续跑。
