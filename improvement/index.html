nanolize 流程修改建议

依据 detectron2 上的五次实验，并对照最新的 main 分支逐条核对代码，给出 41 条修改建议：33 条来自实验，8 条是读 main 时新发现的。其中七项重点改动写出了具体做法，前两项已经做出原型并通过了现有测试。目标是三件事：生成的代码质量更高，压缩过程更省时间，更省 tokens。

结论

先说判断。如果目标是“结果质量高、少浪费 tokens 和时间”，而不是“必须不看源码独立实现”，最该做的是给流程加一个“看源码、原地改写”的模式（T6）。作者从一个所有检查都通过的起点出发，一步步把代码变小，任何时刻手里都有可以交付的结果。按范围并行、会话内自测、接口保持一致，这些在不看源码时很难做到的事，在这个模式下是现成的。这几次实验里质量最好的结果就是这样做出来的。

不管走哪条路线，下面六件事都值得先做。前三件改动小、证据最硬：

  1. 把失败细节交给作者。三次运行的 502 次失败观测，输出里全都有可以自动提取的错误信息，作者一条也没收到；两个 Codex 运行为此空等 owner 各六七个小时。main 上零件都在，只差放行。原型已通过现有测试。（T1）
  2. 停止奖励删文档。策略要求删、度量奖励删、兜底选择还优先交付删得最狠的候选，这三处在 main 上都没变。按只计代码的口径重算，本次运行的 23.1% 减量只剩 10.5%。（T2）
  3. 把已经算出来的信号用起来，堵住白跑。验证时已经算了公开签名的差异却没人看；收尾多跑一轮全量；撞上总时限什么都不交付。（T7）
  4. 并行执行检查，但必须隔离。实测 8 个并发共用一棵树，160 个检查里 100 个失败；各用一份副本则与串行结果一致。（T3）
  5. 按范围拆分，用短会话。现有计划里的数据就能把 detectron2 自动分成 23 个文件不相交的范围；每个范围的作者只需读约 2.4 万 tokens 的知识，而不是面对 235 万的整包。（T4）
  6. 让作者在会话里自己验证。这是流程和 goal 模式差距最大的地方。（T5）

按本次流程运行的时间线估算，验证提速加并行作者可以把 11.5 小时压到 5.5 到 7 小时；文档策略的修改不增加成本。这些是估算，没有实测，拆解见落地顺序。

需要先拍板的五件事

  1. “不看源码”是硬性要求，还是可以加一个原地改写的模式？这决定了后面一半建议的优先级：知识包的重构、接口清单、数据资源只为不看源码服务。
  2. 能不能把候选自己产生的错误信息给作者？main 的代码明确写着这些细节“never an author”，这是有意的决定。T1 给出了一条更细的边界：候选写的可以给，测试写的不给。
  3. 要不要改策略那句话和体积口径？它们属于冻结契约，改动要升契约版本、重录对照基准，规划页面上的数字也会跟着变。
  4. 检查在哪里跑？这几次运行的 CPU 检查都跑在只有 4 核配额的登录容器里，并行最多快两倍多。要真正提速得把检查派到计算节点上。
  5. 大仓库的默认预算给多少？默认的作业时限是 2 小时，detectron2 上光是 main 新增的冻结步骤就可能用掉大半。

T1把失败细节交给作者（对应 A1）

已做原型并通过现有测试有实测数据
现状
main 已经从检查输出里提取失败的测试和每个测试的第一条错误，但只写给 owner；作者只拿到检查编号、退出码和指向测试事实的 knowledge_ids。
数据
三次运行里共有 502 次失败的检查观测，502 次的私有输出里都有可以自动提取的细节：259 次有异常行，243 次有逐用例的结构化报告（点名了 822 个失败用例）。异常类型里 ModuleNotFoundError 192 次、FileNotFoundError 44 次、ImportError 18 次。例如本次运行第一次全量对比的 7 个失败里，5 个是“No module named detectron2.export.api”这一类。这些信息作者一条也没收到，两个 Codex 运行为此向 owner 提了 11 次诊断请求。
边界怎么划
不按“是否来自验证方”划，而按“这段文字是谁写的”划。候选自己的代码抛出的异常、它的消息、它自己文件里的调用栈，都是候选产生的，不含原版源码，可以给作者。测试写的东西不给：断言的文本、期望值、测试自己的代码行和名字。缺失的公开名字（import、属性、调用签名）是契约本来就要求的接口，也可以给。这里有一处要你们定：缺失的名字往往带着模块路径，而 main 的测试事实规则不允许写带点的模块路径。如果坚持这一条，摘要可以只说“缺少一个模块或名字”并指出它属于哪个功能，由作者去查该功能的接口契约。
改法
  1. 新模块 failure_digest.py：从 JUnit 用例的失败文本或普通 traceback 里取出 {type, origin, where, message}，origin 按调用栈里有没有候选文件判定；消息去掉绝对路径和控制字符，限长 300 字符；每个检查最多 5 条不同的错误，其余只计数。
  2. leaf_test_validity.parse_junit(path, root)：有 root 时多返回 case_errors，每个未通过的用例一条，最多 100 个用例。
  3. verification._run_check：把运行所在的树传给解析器。
  4. repair_policy.classify_verification_failures：失败的义务多带一个 errors 字段，只包含“原版通过、现在不通过”的用例的错误。
  5. rewrite.safe_feedback：更新那句“只提供诊断状态”的说明。
原型结果
本地分支上共改 6 个文件、270 行（含 9 个新测试）。断言失败只报告类型，不带文本；期望值不会出现在输出里（有测试断言这一点）。把原型放到这三次运行的真实输出上重放：旧格式的报告没有调用栈，只能按最保守的规则处理，即便如此，363 个错误里也有 243 个带着明确的消息（201 个“No module named …”、32 个 ImportError、9 个 AttributeError、1 个签名不符），其余 120 个给出了异常类型。
还要做的
把同样的摘要按别名汇总给 controller（各类错误的数量即可）；测试文件的判定现在用的是通用规则，应改成计划里的受保护文件清单；文档里“never an author”的表述要同步改。

T2停止奖励删文档：策略、度量、兜底选择一起改（对应 E1、E6、H2）

已做原型并通过现有测试有实测数据
现状
三处在同一个方向上用力：策略要求“激进删除文档和注释”；体积按整个文件文本计数；兜底策略把“tokens 最少的已验收候选”当作最佳候选恢复。
数据
用新的度量重算本次运行：按现在的口径体积减了 23.1%；去掉注释、文档字符串和大型字面量数据表之后，代码只减了 10.5%，其中 Python 逻辑代码减了 5.6%。公开定义的文档覆盖率从 55.5% 掉到 13.6%，83.1% 的行与原版同名文件里的行相同。
改法
  1. 策略文本（policy.json 的 minimal_explanation）换成：公开的类和函数保留一条简短文档字符串；保留解释“为什么”的注释；删掉复述代码的注释和重复签名的样板；不得为了体积目标删文档，目标只计代码。runner.md 里“Keep documentation minimal”一并改掉。
  2. 新模块 code_quality.py：对计入体积的文件给出代码、注释、文档字符串、数据表四类 tokens，公开定义的文档覆盖率，以及与原版同名文件相同行的比例。只出数字，不出名字。
  3. measure_code 的结果里带上这三组数字，controller 和运行页面都能看到。
  4. 体积目标改按代码 tokens 计（冻结时对原版算一次作为基准）；总 tokens 继续报告但不作目标。
  5. strategies/advice.py 里“已验收候选中取 tokens 最少的”改成按代码 tokens 比较，文档覆盖率不得低于原版的某个比例。
原型结果
code_quality.py 和 measure_code 的接线已完成，5 个新测试通过；在原版和本次交付物上跑出的数字就是上面“数据”一栏。策略文本没有改：它是冻结契约的一部分，改它要同时升契约版本并重录对照基准，这一步留给你们决定。
注意
策略文本每个会话会出现在 6 个地方（提示词、契约、overview、index、feedback、每次查询结果），改的时候要一起改；也建议顺手只保留一处。

T3并行执行检查：必须隔离，并且要管线程数（对应 B1、B5）

有实测数据设计稿
现状
main 仍然逐个串行执行检查。只有叶子敲除用了线程池，而且是在各自的纯净导出里跑。
实测
在交付的代码树上重跑了 160 个检查。串行记录是 16.4 分钟。8 个并发共用一棵树时，160 个里有 100 个失败，而它们单独跑都是通过的。8 个并发、每个并发一份私有副本时，159 个的退出码和输出哈希与串行记录完全相同，1 个撞上 300 秒超时；墙钟 7.3 分钟，只快了 2.2 倍。只快这么多是因为这台登录容器的 CPU 配额只有 4 核（系统报 64 核），并发的检查在互相节流。按记录的单项耗时做理想排程，8 个并发应该在 2.1 分钟跑完；实测达不到，原因是检查本身是多线程的，并发时互相抢 CPU。
结论
三条设计约束都是实测出来的：不能共用一棵树，这些检查运行时会在工作树里放临时数据；要给每个检查固定线程预算，否则并发越多单项越慢；超时不能按墙钟写死，并发时有一个本来 100 秒左右的检查撞上了 300 秒上限。
改法
  1. 检查策略里增加 parallel: {workers, threads_per_check, isolation}，默认 1 个并发，行为与现在完全相同。
  2. isolation: "copy" 时，为每个并发准备一份候选树的私有副本（含编译产物），检查在自己的副本里跑；副本在一次调用内复用。每份副本跑完后核对有没有被改动，沿用现在“检查不得改变候选”的规则。
  3. threads_per_check 通过环境变量给到每个检查；基线和候选必须用同一个值采集，把它纳入基线指纹。
  4. 超时改成“原版串行耗时的倍数加固定余量”，并去掉 300 秒的硬上限；或者并发时把超时乘以并发带来的减速系数。
  5. 结果仍按声明顺序记录，产物格式不变，所以上层的比较、台账和验收都不用动。
预期
在 64 核的机器上，8 个并发配合线程预算，全量对比有望从 16 到 20 分钟降到 3 到 5 分钟。更大的并发要看内存和磁盘。main 新增的重复基线和敲除也会直接受益。

T4按范围拆分、短会话、每个范围一份任务书（对应 C1、C3、D1）

有实测数据设计稿
现状
并行工作区和按文件合并都已实现，但 guide 把它们描述成“独立的备选方案”；每个作者会话都拿到完整的契约和完整的知识包；建议步骤从不产生并行作者的动作。
数据
  • 用现有计划里的数据（功能图、每个功能的文件和源码 tokens）就能自动划分：按 4.5 万 tokens 封顶，detectron2 的 106 个功能分成 23 个范围，中位数 3.2 万 tokens。452 个文件里只有 8 个被多个功能共同拥有，其中 4 个会跨范围。goal 模式人工切的是 22 个。
  • 一个范围的作者需要读的知识（去掉标识符的接口和行为契约）中位数是 2.4 万 tokens，而不是面对 235 万的整包。全部功能的索引只要 5 千 tokens，现在的 index.json 是 10 万。
  • 本次运行里每个作者会话的上下文从约 1.2 万一路涨到 55 万到 81 万 tokens。如果把每个会话按范围拆成 4 个，缓存读取量降到现在的 26%，省下 $38 里的 $28。
改法
  1. 冻结时由 harness 算出划分并写进计划：按功能树自底向上合并兄弟节点，直到接近上限；被多个功能共有的文件归给依赖最少的一方，其余方只读。
  2. make_workspace 额外生成作者视图：INDEX.md（每个功能一行）和每个范围一个目录，里面是任务书、本范围功能的契约（不带标识符）、它所依赖功能的接口摘要。规范包保持原样，只是不再要求作者先读。
  3. 任务书由读原版的那一步产出，与测试事实同一批：归属文件、相关检查的别名、本模块特有的不变量。上限 1 千 tokens。
  4. run_workspace_agents 的每个请求带上范围 ID；提示词只指向本范围的目录。
  5. controller 的 guide 增加一段默认流程：先按划分并行实现，每完成一个范围就合并并跑该范围的定向对比，全部合并后再跑全量；建议步骤在首轮实现时给出并行作者的动作。并行数默认值按范围数和机器核数给。
风险
跨范围的依赖有 166 条。每个范围需要其他范围的接口才能自检，所以接口清单（D3）要先于代码存在；合并后的集成检查（C2）是兜底。

T5让作者在会话里自己验证（对应 A2）

设计稿
现状
作者写完整个会话才由 controller 取证，一轮约 50 分钟。goal 模式的子代理每改一个文件就跑一次定向测试。
改法
  1. 工作区里放一个小客户端：python .nanolize-rewrite/check.py [检查别名…]。它只做一件事：往请求目录写一个文件，然后等结果文件出现。
  2. 作者会话期间，worker 里起一个服务线程监听请求目录。收到请求后：把当前草稿快照到一份私有副本，按保存候选的规则做集成（保护文件、遮蔽检查），需要时构建，然后只跑本范围已授权的检查，把 T1 的摘要写回。
  3. 这些结果不是证据：不进台账的证据类，不参与验收，只写一条普通日志。验收仍然只认保存候选之后的正式观测。
  4. 加预算：每个会话最多 N 次、每次最多跑 M 个检查、总时长上限，用完后客户端直接返回“预算已用完”。
为什么不破坏隔离
作者得到的仍然只有 T1 允许的内容；检查程序、测试文件和期望值都不进工作区。唯一的新能力是“早一点知道”。
依赖
需要 T1（否则返回的只是退出码）和 T3 的隔离副本机制（否则会和正在进行的操作抢同一棵树）。

T6增加“看源码、原地改写”的模式（对应 F1）

设计稿有实测数据
为什么
这几次实验里质量最好的结果来自这种做法。不看源码时，Fable 作者写出 66 万 tokens 的代码，其中 83% 的行是凭记忆默写的上游，每一行都按输出 token 付了费：初次实现的三次会话花了 $115，按相同行的比例估算约有一半花在重打上。Codex 作者确实在重写，但到检查全过用了 15 到 19 小时。本次运行拿到第一个全绿的候选是在第 9.9 小时。
关键性质
原地改写把流程从“从零写到全绿”变成“保持全绿，逐步变小”。第 0 个候选就是原版，所有检查天然通过；之后每一步都是一次保持行为的简化，通过就留下，不通过就退回。于是任何时刻手里都有一个可以交付的候选，预算用完也不会空手。
改法
  1. modes.py 增加 refine。make_workspace 在这个模式下用原版的生产代码初始化作者仓库（测试和受保护文件仍然不拷）；现有的“用某个已保存候选的文件初始化工作区”的代码路径可以直接复用。
  2. 策略里的 source_separation 在这个模式下换成一组行为冻结规则（E5）：名字、导入位置、参数、异常类型和消息、日志文本、注册名、配置键都不许变；无法证明不影响行为就不改，记入“可做未做”。
  3. 首个候选直接保存原样的树并取证，作为绿色起点；之后的作者调用用 optimize 角色，按范围进行。
  4. 知识包仍然生成，但只在检查失败时用来查“期望什么”，不再要求先读。
  5. 交付报告里注明模式，并给出 T2 的相同行比例，说明改写深度。
可行性检查
用 main 现有的集成步骤做了一次试验：把 detectron2 原版的 739 个非测试文件原样当作作者的草稿集成回去（83 个测试文件不给作者）。集成成功，得到的代码树与原版逐字节相同；唯一的差别是 4 个符号链接形式的文档被当作“生成的链接”拒绝，需要按受保护的原版文件处理。也就是说，“第 0 个候选就是原版”在现有代码上基本是通的。
代价
不再是独立实现；改得深时评审读出的行为差异更多（goal 模式 17 处，流程 5 处），所以要有 E2 的探针和 T1 的反馈作护栏。对需要净室实现的仓库保留现在的模式。

T7把已经算出来却没人用的东西用起来（对应 E2、A3、H3、H5）

设计稿
静态签名差异
验证时已经在算公开签名的静态差异，但既不算问题也不反馈。三次运行里它分别记下了 35、95、88 处变化，其中就有盲评评审指出的 nms_rotated 去掉装饰器那一处。改法：按功能汇总后反馈给作者，说明哪个功能有几个公开名字的签名变了或不见了；名字本身只在它所在的文件也存在于候选里时才给，因为 main 的反馈规则是不透露原版的文件位置。同时写进交付报告。它是静态比较，会有误报，所以先作为待确认项，不直接当验收门槛。
评审角色
reviewer 的输出只进日志，controller 读不到，却照样扣一次作者调用。改法：让评审把结论写进一个有固定格式的文件，成为一类产物，controller 能按别名读到；或者在修好之前从 guide 里去掉这个角色。
多跑的一轮全量
guide 要求最后跑“完整的 run_checks”，它会把全部保留检查再跑一遍，而验收只读其中 owner 的交付检查。改法：guide 和建议步骤都只点名交付检查。
撞上总时限
现在作业直接失败、不可恢复、什么都不交付。改法：到时限时走和“修复停滞”相同的路径，恢复最好的已验收候选并交付。
