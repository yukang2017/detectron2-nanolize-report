二、新流程

什么时候用两个作业

  • 选中部分不少于 20,000 个原版 token：两个作业。记录里 python-dotenv 是 1.1 万，tqdm 是 6.4 万，detectron2 是 86 万。理由：第一版要写十分钟以上，并行才有意义；python-dotenv 上配对只省 1 分钟。
  • 负责人可以强制开或关。
  • 一个作业时顺序是：建工作区 → 录基线 → 设计测试 → 再录基线 → 封存 → 第一版 → 保存、对比、安装检查 → 修复 → 交付。下面主作业和草稿作业的每条规则对它同样适用，只是没有导入这一步。

2 录基线敲除只做声明的那几对
3 设计测试所有目标一次设计完；不带事实

5 封存从这里起测试不再变

4 保存，报“草稿完成”不对比、不修复、不交付

主作业：每一步的规则

步骤规则

草稿作业：每一步的规则

步骤规则
1建工作区用程序在提交时建的第二个仓库副本。和主作业同一个提交、清单、选择。对你来说仍然是指向一个文件夹
2录基线、封存基线不带敲除，在登录机上跑，不产生任何证据。封存得到作者的工作区：契约、行为描述和接口条目、自检
3第一版固定流程驱动，没有 controller。按计划的 scope 一层一层写：一层只有一个 scope 就是一次调用；有几个就同时写，最多 4 个
4保存，报“草稿完成”不对比、不修复、不交付。导入之后这个作业结束

作者拿到什么，被告知什么

  • 从空工作区开始，按功能图和契约自己设计模块和函数，用最少的代码实现选中的功能。
  • 每次调用都能读源码，实现和修复一样：这次调用负责的功能、这些功能声明依赖的功能、以及它们的上级功能，对应的原版源码文件放在工作区里一个只读目录下，调用结束后收回。
  • 借出的只有体积清单里的源码和配置，没有测试、文档和启动脚本。另外排除两样：被某个检查按名字运行的测试模块；封存清单保护的路径。
  • 不许把文件、函数体、注释、docstring 抄过来；不许 import 或运行借来的文件；不必照搬原版的文件布局和辅助函数。
  • 从第一次调用起被告知：每个文件都会和原版逐行比较，超过限制的会被打回重写。这句话原样保留；实际上保存不会因此被拒。
  • 每次调用记下：借了哪些文件、因为上限截掉了哪些、会话实际打开了几个、重合度是多少。
  • 知识包里只剩行为描述和接口条目。结构和接口从功能图来；行为的细节从源码来。

合流点的规则

  1. 导入只发生在主作业封存之后。封存之后不再设计测试，草稿作业的任何东西都进不了测试。
  2. 导入是一个会等的操作。它等草稿作业报“草稿完成”，有时限，可以暂停和取消。只有草稿作业失败、被暂停或超时，主作业才自己写第一版。
  3. 导入前核对。两个作业的提交、清单、选择三个摘要一致；每个文件的摘要和草稿作业检查点里封存的一致；路径都在树内，没有链接。落在主作业受保护路径上的文件在结果里点名。
  4. 导入记成一次“第一版实现”。集成如果拒绝了导入的文件，后面接的是一次被告知“这些路径归校验方”的实现调用。
  5. 导入之后一切照旧。主作业自己量重合度、保存、集成、对比。草稿作业的任何检查结果都不算证据。
  6. 台账。导入留一条记录：草稿作业的编号、候选的编号、文件摘要、它的借阅记录、它的作者用量。用量记进主作业的 token 账；借阅记录写进主作业的报告。
  7. 导入是带请求号的一次性操作。恢复运行时不会再导入一次。
  8. 取消和暂停互相传递。取消主作业就取消草稿作业；暂停默认两个一起停；主作业封存失败或被取消时草稿作业停下，它的候选留着。

第一次完整对比之前，由规则决定的事

这些地方今天是停下来等 controller 拿主意的。新流程里 controller 不在，所以写成规则：

  • 基线不能用：重录一次；还不能用，暂停，等负责人。
  • 基线过期：重录。
  • 设计测试：所有目标一次做完；做不出有效测试的节点，带着缺口封存。
  • 导入的文件被集成拒绝：接一次实现调用。
  • 计算节点不可用（冻结里、试跑里）：等。不结束作业，不带着缺口封存，不挪回登录机。
  • 两个作业时，主作业封存之前，拒绝手动调用它的设计类工具。发起运行的那个对话看得见草稿的结果，这条规则保证它没法据此影响测试。

检查在哪里跑

  • 两个作业时，主作业：只在计算节点上跑，不用“自动”。CPU 数按敲除的并发数申请；节点空闲多久释放，设到能盖住整个冻结（这个选项最长一小时）；申请的时长按实测。
  • 草稿作业自己的那次基线：登录机。tqdm 上 2.7 分钟；detectron2 上是 36 分钟的检查，会占着登录机的核。
  • 一个作业时：按现在的规则。
  • 排队堵住时，校验链等着，草稿照常写。并行的收益变小，正确性不受影响。

报告里写什么

  • 作者查阅过原版：每次调用借了多少文件、打开了多少。不再出现“没看过源码”的说法。
  • 重合度：整体的百分比，超过阈值的函数。原来的两个限制（整体 40%，8 行以上的函数 60%）变成标记用的阈值。
  • 体积，和以前一样。
  • “这个检查验证了什么”：以前用事实里的句子，现在用测试函数的名字和场景用例的名字。这些只给负责人看，不给作者。

三、删掉什么

因为旧模式不留，这些是删除，不是加一个开关。

删掉的具体是什么
写事实这一步这一步本身和它在冻结顺序里的位置；撰写者、评审者两个角色和它们的提示词；补写的第二遍；提交前估算里事实的那部分；进度页上的这一步；“不写事实”的开关
设计测试里的事实测试必须附带的事实；事实和测试的绑定；只查这些文字的几道门槛；评审里“事实有没有覆盖断言”的部分；场景说明的评审和长度上限（只留一个不评审的名字）
作者知识包里的事实原版测试的事实、设计出的测试的事实、场景的事实三种记录；失败反馈里指向事实的编号；“事实缺口”和“没有事实的测试”两种记录
“作者看不到源码”这种模式借源码的两种旧方式（检查失败后才借；从不借）和它们的限额（每次最多加 5 个功能，每个作业 15 个）；controller 给修复多借几个功能的参数；docstring 示例的例外和它的上限；功能图文字里对“像实现的文字”的筛查；提示词、报告、记录、文档、skill 和工具说明里所有“没看过源码”的说法
防默写的拒绝（默认）默认不再拒绝保存，也就没有随后的重写和那一轮 controller。拒绝的机制留在代码里，默认关着：验证时如果重合度太高，改一个设置就能打开
第一次完整对比之前的 controller这之前的回合；设计调用里由 controller 选节点；冻结预留；guide 里讲冻结、第一版实现和重写的部分
第一档里没有对象的三项C2 整条（写事实的三处改进）；C1 的三处（场景按函数给结论、说明的长度、点了测试名字的事实）；D1 的第 3 部分（给探针写事实）

不动的：敲除和试跑的门槛；测试只能从对外契约的名字进入；迁移用了私有名字的原版测试；检查只按编号告诉作者；作者的自检；封存；集成时把受保护的文件放回去； 行为对比和安装检查；交付前对正是那份代码的完整对比；交付后的原版测试回放；提交之前的整个阶段（功能图、行为描述、接口条目照旧）。
