几个词

冻结、封存
写代码之前的准备阶段叫冻结，最后一步叫封存。封存之后“什么算对”就定下来了。
基线、敲除
基线是每个检查在原版上的结果。敲除是把一个功能节点从原版里拿掉再跑检查；会因此失败的检查才算这个节点的有效测试。
事实
把测试钉住的行为用文字写出来给作者用。这一版里没有了。
固定流程、controller、guide
固定流程是代码里算出来的“下一步做什么”。controller 是每一轮可以改写这个决定的模型会话；guide 是给它的说明书。这里说的固定流程不是 fixed 策略，后者是一种完全不用 controller 的作业。
scope、层
scope 是交给一个作者会话写的一组功能。互不依赖的 scope 在同一层，可以同时写。
主作业、草稿作业
主作业做校验方的事和合流之后的一切；草稿作业只写第一版代码。
演练
用假的模型把整条流程跑通，不花钱。验收里用它。
运行代号
A、B、D：三次 tqdm。E、F：detectron2。G：python-dotenv。

二、新流程

什么时候用两个作业

三个条件都满足才配对：

  • 选中部分的体积不少于 20,000 个原版 token。这是计划里现成的那个数（源码加配置）。记录里 python-dotenv 是 10,684，tqdm 是 63,962，detectron2（E）是 862,266。 理由：第一版要写十分钟以上，并行才有意义；python-dotenv 上配对只省 1 分钟。
  • 提交时探测到可用的计算节点。没有调度器、或者探测不到节点的机器上不配对。
  • 不是 fixed 策略的作业。它不用实现工作区，导入对它没有意义。

负责人可以强制开或关；强制开而没有节点时，提交被拒绝并说明原因。一个作业时顺序是：建工作区 → 录基线 → 设计测试 → 再录基线 → 封存 → 第一版 → 保存、对比、安装检查 → 修复 → 交付。 下面主作业和草稿作业的规则对它同样适用，只是没有导入这一步，检查在哪跑按现在的规则。

主作业 校验方，检查在计算节点上跑

1 建工作区
2 录基线敲除只做声明的那几对
3 设计测试所有目标一次设计完；不带事实
4 再录基线单独一步
5 封存从这里起测试不再变

草稿作业 只写第一版，没有 controller

1 建工作区程序自己建的第二个仓库副本
2 录基线、封存不带敲除；不设计测试
3 第一版从空工作区写；可以读源码；按层写
4 保存，报“草稿完成”不对比、不修复、不交付
↓ 合流：主作业封存之后，等草稿完成，导入 ↓

主作业，合流之后

6 导入核对、记账
7 保存、集成、行为对比、安装检查重合度由主作业再量一次
8 修复或优化对比有了结果，controller 才出场
9 选定、交付报告写明查阅过原版

主作业：每一步的规则

步骤规则
1建工作区不变
2录基线敲除只做检查声明的那几对。不再等写事实。两个作业时在计算节点上跑
3设计测试固定流程一次覆盖所有目标：缺有效测试的节点，加上有原版测试要迁移的节点。设计者同时开工的数量等于目标数。测试和场景不带事实；场景用例的名字就是场景函数的名字，不评审。评审只看实质：测试是不是恒真、是不是钉住了实现细节或计时、节点行为错了它还会不会过、迁移的测试是不是和原来一样强。这一步到提交测试为止
4再录基线单独一步，在提交了测试的树上录。可以等待、可以重做、报告进度
5封存不变。开了任务评估时，任务基准在封存之后、导入之前准备好
6导入见下面“合流点的规则”
7保存、集成、行为对比、安装检查重合度在保存时由主作业自己量，只量不拒
8修复或优化第一次完整对比有了结果，controller 才出场，之后和今天一样：没过，由它决定修什么；过了，由它决定要不要优化体积、什么时候交付。修复调用同样可以读源码。失败的断言比较的两个值、输出第一处不同的那一行，每次修复都给
9选定、交付不变。报告的内容见本节最后

草稿作业：每一步的规则

步骤规则
1建工作区用程序在提交时建的第二个仓库副本。和主作业同一个提交、清单、选择，同一份查重设置。对你来说仍然是指向一个文件夹
2录基线、封存基线不带敲除，在登录机上跑，不产生任何证据。封存得到作者的工作区：契约、行为描述和接口条目、自检
3第一版固定流程驱动，没有 controller。按计划的 scope 一层一层写：一层只有一个 scope 就是一次调用；有几个就同时写，最多 4 个，写完合并
4保存，报“草稿完成”所有 scope 都写完并保存，才算草稿完成。有一个 scope 的调用失败，草稿作业就算失败，主作业自己写。不对比、不修复、不交付。导入之后这个作业结束

作者拿到什么，被告知什么

  • 从空工作区开始，按功能图和契约自己设计模块和函数，用最少的代码实现选中的功能。
  • 每次调用都能读源码，实现和修复一样：这次调用负责的功能、这些功能声明依赖的功能、以及它们的上级功能，对应的原版源码文件放在工作区里一个只读目录下，调用结束后收回。
  • 借出的只有体积清单里的源码和配置，没有测试、文档和启动脚本。另外排除两样：被某个检查按名字运行的测试模块；封存清单保护的路径。
  • 不许把文件、函数体、注释、docstring 抄过来；不许 import 或运行借来的文件；不必照搬原版的文件布局和辅助函数。 只有一样要照抄：被某个检查当作测试来运行的 docstring 示例。今天这是个例外，新流程里它是常态。
  • 不许读工作区以外的东西。这句和今天一样。
  • 从第一次调用起被告知：每个文件都会和原版逐行比较，超过限制的会被打回重写。这部分文字原样保留；实际上保存不会因此被拒。
  • 每次调用记下：借了哪些文件、因为上限截掉了哪些、重合度是多少。会话实际打开了几个文件，由内置的两个适配器从自己的事件流里数；负责人自带的 runner 没有这个数，报告里写“不可得”。
  • 知识包里只剩行为描述和接口条目（清单里有搬运文件时还有它们的记录）。结构和接口从功能图来；行为的细节从源码来。
  • 检查没过时，作者得到：检查的编号、功能名、错误类型、出错位置、对比的值；失败的是场景用例时，还有那个用例的名字。测试函数的名字永远不给作者。

合流点的规则

  1. 导入只发生在主作业封存之后；开了任务评估时，还要在任务基准准备好之后。封存之后不再设计测试，草稿作业的任何东西都进不了测试。
  2. 导入是一个会等的操作。它等草稿作业报“草稿完成”，有时限，可以暂停和取消。只有草稿作业失败、被暂停或超时，主作业才自己写第一版。
  3. 导入前核对。两个作业的提交、清单、选择三个摘要一致；每个文件的摘要和草稿作业检查点里封存的一致；路径都在树内，没有链接。落在主作业受保护路径上的文件在结果里点名。
  4. 导入记成一次“第一版实现”。集成如果拒绝了导入的文件，后面接的是一次被告知“这些路径归校验方”的实现调用。
  5. 导入之后一切照旧。主作业自己量重合度、保存、集成、对比。草稿作业的任何检查结果都不算证据。
  6. 台账。导入留一条记录：草稿作业的编号、候选的编号、它包含哪些 scope、文件摘要、它的借阅记录。借阅记录写进主作业的报告。草稿作业的作者用量不管有没有导入都记进主作业的 token 账。
  7. 导入是带请求号的一次性操作。恢复运行时不会再导入一次。
  8. 取消和暂停互相传递。取消主作业就取消草稿作业；暂停默认两个一起停；主作业封存失败或被取消时草稿作业停下，它的候选留着。

第一次完整对比有结果之前，由规则决定的事

这段时间没有 controller。下面这些，今天有的是 controller 定的，有的是直接让作业结束的，新流程里都写成规则。

  • 第一版怎么写：按计划的 scope 一层一层写，不管是一个作业、草稿作业，还是主作业自己补写。今天只有 controller 会按 scope 写，固定流程自己是一次调用写完全部； 它按层写只在负责人打开并行模式时才有，而那个开关同时会把别的并发数调大、让修复也分组。新流程里“按层写第一版”单独成为固定流程的行为，不带出那些别的效果。
  • 基线不能用：重录一次；还不能用，暂停，等负责人。
  • 基线过期：重录。
  • 设计测试：所有目标一次做完；做不出有效测试的节点，带着缺口封存。

只在两个作业时才有的：

  • 导入的文件被集成拒绝：接一次实现调用。
  • 计算节点中途不可用（冻结里、试跑里）：等，等到负责人设的排队时限；过了就暂停等负责人，已经做完的步骤留着。不结束作业，不带着缺口封存，不挪回登录机。
  • 主作业封存之前，拒绝对它手动做三件事：指定节点的设计调用、给检查打标记、修订契约。发起运行的那个对话看得见草稿的结果，这条规则保证它没法据此影响测试。

检查在哪里跑

  • 两个作业时，主作业：只在计算节点上跑，不用“自动”。CPU 数按敲除的并发数申请。申请的时长按实测。节点空闲 15 分钟才释放，这样相邻的几批共用一个分配，而每次申请仍然在半小时以内。
  • 草稿作业自己的那次基线：登录机。tqdm 上按 2.7 分钟估；detectron2 上是 36 分钟的检查，会占着登录机的核。
  • 一个作业时：按现在的规则。
  • 排队堵住时，校验链等着，草稿照常写。并行的收益变小，正确性不受影响。
  • 已有的运行，检查全部是在登录机上跑的。所以第六节里没有一个数字是在节点上量到的。

和其他功能的关系

  • 任务评估。任务基准今天在封存之后、任何作者调用之前准备。两个作业时，草稿作业的作者更早开工，但它在另一个作业里，碰不到任务基准；主作业的导入排在任务基准准备好之后。时间线里要加上这一步。
  • 性能验收。草稿作业的作者收到和今天一样的“代码会被计时”的提示。性能修复仍然由 controller 决定，它在第一次完整对比有结果之后就在场。
  • fixed 策略。不配对。其余改动（不写事实、可以读源码、查重不拒）同样适用。
  • 旧版本留下的作业。不能用新版本恢复，这和今天一样：作业只能由启动它的那个版本恢复。用新版本给旧作业重新出报告、或校验旧的校验包时，新版本认出旧格式，说明要用旧版本，不去兼容。

报告和进度页写什么

  • 报告：作者查阅过原版，每次调用借了多少文件、打开了多少。不再出现“没看过源码”的说法。
  • 报告：今天给“作者拿到过事实的检查”打的那个标记（意思是这种检查通过不算独立的证据）去掉，换成对整份交付的一句话：作者能读到所有被检查功能的源码。
  • 报告：重合度的整体百分比和超过阈值的函数。原来的两个限制（整体 40%，8 行以上的函数 60%）变成标记用的阈值。体积和以前一样。
  • 进度页：“这个检查验证了什么”今天用事实里的句子，新流程里用测试函数的名字和场景用例的名字，从测试文件和用例报告里读，不新增模型输出。这些名字不进作者的工作区，也不进给作者的反馈。 交付的报告本来就不显示这些句子，也不显示用例的名字，这一点不变。

三、删掉什么

因为旧模式不留，这些是删除，不是加一个开关。最右一栏是它归哪个工作包。

删掉的具体是什么包
写事实这一步这一步本身和它在冻结顺序里的位置；撰写者、评审者两个角色和它们的提示词；补写的第二遍；提交前估算里事实的那部分；进度页上的这一步；“不写事实”的开关2
设计测试里的事实测试必须附带的事实；事实和测试的绑定；只查这些文字的几道门槛；评审里“事实有没有覆盖断言”的部分；场景说明的评审和长度上限（场景函数的名字留作用例名）2
作者知识包里的事实原版测试的事实、设计出的测试的事实、场景的事实三种记录；失败反馈里指向事实的编号；“事实缺口”和“没有事实的测试”两种记录2
其他用到事实的地方负责人授权修订契约之后的重新冻结里“先补写事实”那一环；任务评估里“之后又写了事实，任务基准作废”那条规则；计划和导出里按事实做的判断；runner 试调和隔离条件里对事实开关的引用；controller 的工作区里的事实，以及 guide 里“修复前先读知识记录”那句；报告里“作者拿到过事实的检查”那个标记2、3
“作者看不到源码”这种模式借源码的两种旧方式（检查失败后才借；从不借）和它们的限额（每次最多加 5 个功能，每个作业 15 个）；controller 给修复多借几个功能的参数；docstring 示例“不借就不要求”的那条分支和它的上限（照抄示例成为常态）；功能图文字里对“像实现的文字”的筛查；提示词、报告、记录、文档、skill 和工具说明里所有“没看过源码”的说法1
防默写的拒绝（默认）默认不再拒绝保存，也就没有随后的重写和那一轮 controller。拒绝的机制留在代码里，默认关着：验证时如果重合度太高，改一个设置就能打开1
第一次完整对比有结果之前的 controller这之前的回合；设计调用里由 controller 选节点；冻结预留；guide 里讲冻结、第一版实现和重写的部分3
第一档里没有对象的四项C2 整条（写事实的三处改进）；C1 的三处（场景按函数给结论、说明的长度、点了测试名字的事实）；D1 的第 3 部分（给探针类的检查写事实）；E1 里“保存因防默写被拒时，委托可以接着做那次重写”不做

不动的：敲除和试跑的门槛；测试只能从对外契约的名字进入；迁移用了私有名字的原版测试；检查只按编号告诉作者；作者的自检；封存；集成时把受保护的文件放回去； 行为对比和安装检查；交付前对正是那份代码的完整对比；交付后的原版测试回放；提交之前的整个阶段（功能图、行为描述、接口条目照旧）。

每个包有自己的单元测试，并且要过仓库的全部检查。验收一栏写的是在此之外、用演练来确认的事。

五、顺序

  • 包 0 → 包 1 → 包 2 → 包 3 → 包 4，依次做。
  • 包 0 在前，是因为它改的设计测试那一步，包 2 要在上面接着改；它的 D1 是包 2 拿走事实之后，修复时仅剩的指路信息。包 0 里的 A1 和 A2 和谁都不相干。
  • 包 2 依赖包 1：先让作者能读源码，才能拿走事实。
  • 包 3 依赖包 1：没有拒绝和重写之后，对比之前才没有需要 controller 的事。
  • 包 4 依赖包 1、2、3：草稿作业开工不需要冻结的产物，是因为不再有事实；它没有 controller，靠的是包 3。包 4 里“节点不可用时等待并重做”还要用到包 0 的 A4。检查执行器的另外两件事（按实测时长申请、并发数跟着分配走）不依赖别的，可以提前。
  • 包 3 做完时，一个作业的新流程已经完整，python-dotenv 这样的小项目用的就是它。
  • 一个分支，从 main 的 71d386d 开出来。删掉写事实这一步之后，固定流程的对拍记录要重录。验证跑的是这个分支；你看过结果再决定合并。
  • 开始实现、推送、开 PR，都等你发话。

八、仍然没量过的

  1. 没有一次运行是在新流程下跑的，而且这次是先实现、后验证。体积、重合度、第一稿没过的检查数、第一版的时长，都要到第七节才知道。退路是不合并分支；重合度有一个现成的开关。
  2. 检查成了防“删行为”的唯一防线。以前没有测试覆盖的行为作者根本不知道；现在作者看得见，在体积目标下可以决定不要它，而且不会有任何检查失败。
  3. 换个写法的抄写能通过一切。重合度比的是每个函数去掉空白后的行，改变量名就能绕开。报告里的重合度和体积是仅有的两个信号。
  4. 检查通过的含义变了。作者能读到被检查功能的源码，一个通过的检查说明的是“行为保住了”，不再是“没看过答案也做对了”。报告里会写这句话。
  5. 修复少了指路的东西。没过的检查不再指向事实，只有功能名、错误类型、位置和对比的值，场景用例多一个名字。B 那次没有事实的那个检查，修复用了 10.8 分钟，靠试。包 0 里的 D1 是补这个的，够不够要看验证。 controller 也看不到事实了，而它仍然读不到源码，所以它对一个没过的检查知道得比作者少；guide 让它只指明是哪个检查、哪个功能，诊断交给作者。
  6. 借源码的范围是作者和原版测试之间唯一的过滤。它有自己的测试（包 1 的验收）。“作者可以读原版”不能变成“作者可以读仓库目录”。
