A　给作者的事实被误拦或误删

作业冻结时把测试钉住的行为写成文字事实交给作者。这一组的问题都让本该到作者手里的事实丢了。

A1用弯引号引用的 Windows 字符串被当成本机路径 报告列为缺陷

python-dotenv（008） · src/nanolize/knowledge.py

现象

一条事实用弯引号引用了测试里的字面值 “C:\Users\”，被判为“含有绝对位置”而拒绝。同一句话换成直引号就能通过。

原因

位置过滤器把右弯引号当成路径的一部分，于是把裸的 C:\Users\ 读成了某个用户目录下的路径。

修改
  • 各种弯引号、角引号、直角引号和全角引号（共 18 种）现在和直引号一样对待：路径到引号为止。裸的 C:\Users\ 仍是普通取值，“C:\Users\alice” 仍被拒绝。
  • 评审时发现同一个缺口的另一半：这些引号后面紧跟的本机路径以前认不出来（直引号里的会被拒，弯引号里的不会）。这次一并补上，公开页面的脱敏和验证包的扫描也用同一条规则。

A2提到被带文件名字的程序输出事实被删掉 报告列为缺陷

tomli（I12） · src/nanolize/knowledge.py

现象

一条冻结的事实规定了基准程序输出的标题和分隔线的精确排版，却没有到作者手里。作者两个候选都卡在这项检查上，靠读原版才修好。

原因

被原样带过去的文件，知识里关于它内容的记录会被裁掉。裁剪规则按文件名匹配，输出标题里的 “Parsing data.toml 1 times:” 恰好含有被带文件的名字，这条行为事实就被当成文件内容记录删了。

修改
  • 被检查钉住的记录不再因为提到被带文件的名字而裁掉。测试事实（按它的形状认：有对应的测试、编号以 fact. 开头、类型是行为）和检查点名的记录原样保留。
  • 知识库里描述被带文件自身内容的记录，照旧裁剪。

A3事实里出现 test 这个词，就被当成泄露了测试名 报告列为缺陷

click（FACT-01 至 10） · src/nanolize/leaf_test_design.py

现象

10 条事实提议被拒，理由都是“事实点了测试的名字”。实际内容是子命令名 test、帮助输出 “Usage: foo test [OPTIONS]”、普通字符串值 test、被测类型名 TestType。两个测试最终没有任何事实。

原因

收集“测试标识”时遍历了整个语法树：测试函数内部定义的、名字以 test 开头的命令回调，以及名字以 Test 开头的被测辅助类，都被算了进去。

修改
  • 函数内部定义的东西不再算测试标识：测试函数里定义的、名字叫 test 的命令回调，现在只是一个普通的词。
  • 模块级和类级的规则和以前完全一样：名字以 test 开头的函数、名字以 Test 开头或继承自测试基类的类，都仍然算。
注意

第一版改得更宽（没有测试方法的类也不算），评审指出这会让“测试方法来自别处基类”的真实测试类的名字流到作者手里，所以收回到只放开函数内部这一种。报告里的 TestType 是在测试函数里定义的，仍然放行。

A4事实评审漏判一条，整份文件的事实全部作废 报告列为观察

more-itertools（Q02） · src/nanolize/leaf_test_design.py

现象

评审者收到 40 条事实，两轮都只返回 39 条判决。两轮各有 37 条被认可，但因为“评审不完整”，80 条全部丢弃。这个测试文件的 617 个测试没有任何事实到作者手里，作业修了 11 个候选才通过。

原因

规则要求每条事实恰好有一条判决，缺一条就整轮作废。

修改
  • 没有判决的那条事实单独丢弃，其余判决照常生效。没有判决的超过五分之一、并且不止一条时，仍算评审不完整。
  • 评审者拿到的每条事实都带编号，判决按编号对应，不用自己数位置。这是评审查出来的：原来“一条不能少”的规则同时也是唯一能发现“评审者数错位置”的检查，去掉它之后要另外防。
  • 被丢事实对应的测试进入第二轮重写；重写不出来就如实记为没有事实覆盖。

A5事实被压到长度上限，句子写到一半就断了 报告列为观察

more-itertools（Q02） · src/nanolize/prompts/prompts.json

现象

多条事实长度在 1,496 到 1,500 字符之间，结尾是半句话，或者用一个占位符代替没写完的数值列表，随后被评审否决。

原因

每个文件最多 40 条、每条最多 1,500 字符，撰写者把尽可能多的内容塞进一条里。提示词没有说写不下时该怎么办。

修改
  • 撰写者的提示词加一段：一条事实自成完整的话；写不下的放进另一条或不写，不能截断；长的数值列表要么写全，要么写出生成规则。
  • 评审者的提示词加一句：以半句话结尾、或用占位符代替数值的事实不算准确。条数和长度的上限没有变。

B　清单转换和来源审计读测试文件

转换和冻结审计都要读测试文件，判断它用了哪些名字。

B1命令点名的测试文件，因为也在源码清单里而没被读 报告列为缺陷

bidict（N06） · src/nanolize/graph_contract.py、src/nanolize/leaf_assignment.py

现象

基准检查的命令和输入都点名了 microbenchmarks.py，转换却把这项检查列为“没读到内容”，冻结审计给出的来源是“未知”。文件里对私有名 BidictBase._write 的依赖既没有被剔除，也没有被写明。

原因

挑选一项检查的测试文件时，先把生产源码清单里的文件排除掉，然后才识别命令里明确给出的文件。

修改
  • 检查的 pytest 命令自己点名的测试模块，即使文件名看起来像生产源码，也作为这项检查的测试文件来读。转换和冻结审计用同一个判断。
  • 它只对点名它的那项检查算测试文件，对其他检查仍然是项目的模块。这一条是评审后加的：否则别的检查用到它的私有名字时会看不出来。
注意

bidict 那项基准检查确实用了私有名，所以现在会在转换时被剔除（加 --keep-checks 可以保留）。

B2实例字段追踪把不同测试函数里的同名局部变量混在一起 报告列为缺陷

more-itertools（N02） · src/nanolize/graph_contract.py

现象

转换漏掉了保留检查需要的三个实例字段（callback_iter._executor、serialize._iterator、serialize._lock）。作者不知道要保留这些字段，相关失败修了好几轮，最后靠负责人补充说明才解决。

原因

追踪“哪个变量是哪个类的实例”时，按变量名在整个文件范围内登记。两个测试函数各自用局部变量 it 构造了不同的类，这个名字就被判为不确定，后面对它的私有字段访问都认不出来。

修改
  • 实例变量按作用域追踪：每个函数和方法的局部变量各归各的，模块级的名字照旧共享。改一个函数里的局部变量名，不再影响另一个函数里找到什么。
  • 只作为参数出现的名字沿用原来的全文件规则，这样 pytest fixture 的常见写法不会漏。global 和 nonlocal 按 Python 自己的规则处理。
  • 在 more-itertools 真实的测试文件上核对：原来只找到 1 个字段，现在找到报告里漏掉的 3 个，另外多找到 1 个，没有丢失。

C　节点测试的有效性与测试设计

一个测试要在原版通过、可重复、并且把对应节点剔除后失败，才算这个节点的有效测试。

C1测试里用 runpy 运行命令行程序，剔除后的失败被判成“破坏了导入” 报告列为缺陷

bidict（N09） · src/nanolize/leaf_test_validity.py

现象

给比较工具设计的测试在原版上 14 个用例通过。剔除节点后测试正常失败，却被判为“剔除破坏导入、无法评估”，提案被拒，这个节点也不再有第二轮，最终没有有效测试。

原因

判断失败类型时，把堆栈里所有“模块顶层”的帧都当成导入。runpy 运行脚本的入口也是这样一帧，于是在读用例的失败结果之前就判成了导入失败。

修改
  • 按顺序读 pytest 的堆栈：紧接在 runpy 执行入口下面的那个“模块顶层”帧是被运行程序的入口，不是导入，这种失败算行为失败。
  • 测试里的惰性导入、被运行的程序自己导入的坏模块，仍然判为导入失败。用真实的 pytest 在各种堆栈样式下核对过。

C2行为是导入期数据或重导出的节点补不上测试，测试带的事实也丢了 报告列为缺陷

requests（6） · src/nanolize/leaf_test_validity.py、src/nanolize/leaf_test_design.py、src/nanolize/execution.py

现象

状态码表和兼容层两个节点，两轮共 4 份测试提案都因“剔除后没有失败”被拒。被拒的测试里有历史别名（early-hints=102 等）的事实，没有进入作者的知识；首个候选果然漏掉了 6 个别名。

原因

剔除只替换函数体。数据表在导入时建好，兼容层的函数来自别的节点的重导出，剔除本节点的函数改变不了被测的值。计划里只收被接受的测试和它们的事实。

修改
  • 一个节点到最后没有有效测试时，它最后一轮里“在原版通过、可重复、只用对外约定、但剔除后没有失败”的提案不再直接丢掉，而是交给评审。评审接受的，作为“钉住但没有剔除证据”的检查保留下来，它们的事实也一起交给作者。
  • 这个节点仍然记为未验证，原因单列为“有钉住的测试但没有剔除证据”，和“完全没有测试”区分开。钉住的检查不让任何节点算作已验证，包括依赖它的内部节点（评审查出第一版在这里会多算一个已验证）。
  • 候选必须通过钉住的检查，和其他检查一样。
注意

报告提的另外两个方向没有做。“把两种剔除方式的结果合并得宽松些”会让任何测试都能算这类节点的有效测试，评审也同意现在的读法是保守的。“对公开数据做受控变异”是一个新功能，这次没有加。

C3评审否决的理由不会回到设计者，节点因此失去全部测试 报告列为缺陷

tqdm（第二份报告，bug 2） · src/nanolize/leaf_test_design.py

现象

monitor 节点唯一的测试通过了自动校验，评审者因为其中一个断言在正确代码上约有 3% 的概率失败而否决了整个文件，并写明了改法。之后没有再设计，节点没有任何测试；而这个节点恰好有真实的行为差异（解释器退出时会挂住）。

原因

评审排在所有设计轮次之后，只做一次。它否决的文件直接丢弃，理由不交给设计者，也不再开一轮。

修改

原因

D　任务成本评估

作业在重写前后各请独立的模型做同一个修改任务，比较花费。

D1任务套件缺少任务需要的输入文件，仍然被接受并封存 报告列为缺陷

python-dotenv（010） · src/nanolize/effort_schema.py、src/nanolize/effort.py

现象

任务和隐藏验收都需要一个输入文件，设计者最终交上来的套件里却只有一个占位文件。套件通过了校验并被封存，第一次独立验收就因为缺文件而中断，任务成本比较没法做。

原因

套件校验只检查文件条目的字段和路径是否合法，不检查任务用到的输入文件是否都给了。

修改
  • 设计出的套件在绑定之前多一项检查：任务文字、评分标准或检查脚本里写明要用的输入文件，必须在该变体提供的文件里；缺了就作为“任务设计无效”退回。
  • 只对新设计的套件生效。已经冻结的套件和负责人自己给的套件不重新判，所以恢复旧作业不受影响。
  • 评审后减少了误判：只是判断存在与否的路径、拼出来的前缀、写明“不存在”的文件，不再被当成缺失。

D2结尾带斜杠的目录链接被拒，任务评估整项不可用 报告列为缺陷

现象

  • 其他拒绝都保留：目标在仓库外、中间有空段、绝对路径等。

D3设计者没有被告知“两份任务的提示文字必须不同” 报告列为缺陷

bidict（N12） · src/nanolize/effort_schema.py、src/nanolize/prompts/prompts.json

现象

原因

修改
  • 留出任务算不算“不同”，按求解者真正拿到的东西判断：提示文字和输入文件都与开发任务相同才拒绝。
  • 这条规则写进了设计者的提示词和输出格式的说明。

D4任务要求的输出字段，求解者的固定格式不允许 报告列为缺陷

tqdm（第一份报告，B1） · src/nanolize/effort_schema.py、src/nanolize/prompts/prompts.json

现象

原因

修改
  • 设计者、求解者、评分者三方的提示词都写明求解者最终回答有哪些固定字段；任务另外需要的内容，放进任务指定的文件或已有字段里。
  • 设计出的任务如果明确要求“最终回答”带别的字段，绑定之前拒绝。
  • 评审后收紧了识别范围：只认写明“最终回答”的说法；任务说的是交付文件里的字段时不拒绝。

D5比较两次试验时，读的是评分之前的记录 报告列为观察

bidict（N20） · src/nanolize/job_tools/

现象

修改

E　controller 的回答被执行端拒绝

E1回答格式允许的 request_id，执行端必然拒绝 报告列为缺陷

tomli（I13） · src/nanolize/strategies/controller.py

现象

controller 给出的 request_id 里有空格，执行端拒绝了这个调用，同一批后面的两个调用也被跳过，这一轮白费。

原因

回答格式只要求它是不超过 100 个字符的字符串；执行端要求只含字母、数字、连字符和下划线，且不以 op- 开头。两处的规则不一致。

修改
  • 回答格式里的 request_id 用上和执行端同一条规则，两处共用一个定义。执行端的检查保留。
  • 用一次真实的 Codex 调用确认了它的结构化输出接受这条正则约束。

E2给作者的指令超过长度上限，整轮作废 报告列为缺陷

tqdm（第二份报告，bug 1） · src/nanolize/strategies/controller.py

现象

controller 写的修复指令有 4,527 个字符，上限是 4,000。调用被判无效，同一批后面的保存、比较、安装检查都被跳过，这一轮白花了约 2 分钟和 31 万 token，之后只能跑一次不带针对性指令的修复。

原因

上限是有意设的，说明里也写了。问题在于超限的代价是丢掉整轮，controller 没有机会改短重发。

修改
  • 回答在任何调用执行之前就被拒绝时，同一轮里再问一次：把哪里错了（哪个调用、哪个参数、实际长度和上限）告诉 controller，让它重答。第二次还被拒，才算无效轮。
  • 每轮只纠正一次，token 记两次之和。已经有调用执行过的回答不重问。长度上限本身没有变。
注意

参数的长度上限写不进回答格式，因为调用的参数是作为一段 JSON 文本传的。所以用“纠正一次”来兜住。

取舍记录

修改时遇到需要取舍的地方，按对整个项目的判断处理，逐条记在这里。

作业启动时的试调，在哪里默认开

程序接口默认关，review 命令和 MCP 工具默认开。全部默认开会让每个用自定义运行器的已有测试和调用方多出一次调用，固定流程的对照记录也会变。

节点补不上测试时，保留什么

  • 报告给了两个方向：对公开数据做受控变异，或者把经评审成立的测试和事实保留下来、同时标明没有剔除证据。选了后者，因为它不改变“什么算有效测试”，只是不再把已经验证过的东西丢掉。
  • “放宽两种剔除方式的合并规则”没有做。那样一来，对这类节点随便写一个测试都算有效。

“事实里不能出现测试名”放开到哪一步

第一版放开得更多，评审指出会漏掉“测试方法来自别处基类”的测试类。最后只放开“函数内部定义的名字”，模块级和类级的判断和以前一字不差。

事实评审漏判时，多少算“评审过了”

漏的不超过五分之一就算，只漏一条时总是算。40 条漏 1 条可以，漏 9 条不行。同时给每条事实编号，防止评审者数错位置。

任务评估的新检查，对哪些套件生效

只对新设计的套件生效。已经冻结的套件每次恢复都会重新校验，如果用新规则判它们，升级之后恢复旧作业会失败。

带摘要编号的验证包，要不要换版本号

要。不换的话，旧版本的 nanolize 会接受这种包，然后把正确的候选报成回归。

controller 的参数上限，放进回答格式还是事后纠正

request_id 的规则能写进格式，写了。参数长度写不进去（参数是以一段 JSON 文本传的），所以改成“被拒后同一轮里纠正一次”。

适配器的会话能不能直接写作业的记录目录

不能。会话如果能写那个目录，就能伪造“某条命令执行过”的证据和用量。适配器另建一个只放答案的目录，会话结束后由适配器把答案拷过去。

不报告用量的运行器，试调算不算通过

不算。方案里写的三项检查包括用量。代价是这类运行器的作业会在第一步暂停，所以暂停提示里写明了怎样关掉试调。

评审做几轮

开工前定的规矩是每个工作包一轮独立评审，评审后的修复不再送审。只对沙箱适配器破了例：第一轮查出两处高危，修复引入了新的机制，所以对修复又审了一轮。

沙箱要不要断网

  • 不断。会话本身要联网访问模型，沙箱没法只给它留这一条路。真实运行里验证过：沙箱内可以从公开的包仓库下载到目标项目。这一点如实写进了文档，挡住它的是给作者的指示和重复度比较。
  • 第二次真实运行里作者联网装了一个计数工具。处理办法有两个：告诉作者不要联网，或者给作者一个自带的计数工具。选了前者，因为它只是一句话，而且和 Codex 默认沙箱下的情况一致（那里作者本来就连不上网）。后者是新功能，没有做。
