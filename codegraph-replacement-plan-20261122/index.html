用 codegraph 替换 Graphify：修改方案

已经定了：以后用 codegraph 代替 Graphify 来给仓库建结构图。这一页是替换的完整方案：依据是什么，钉哪个版本、怎么装怎么跑，Graphify 的代码、安装和说明怎么去掉，新的数据怎么接进功能清单和页面，分几期做，有什么收益和风险，以及还要你定的事。它取代此前那版以 Graphify 为基础的方案；那一版里和工具无关的部分（提交前把关、范围基线）保留了下来。

1. 先说结论

  • 替换是整件的，不留两套，而且只能是一个合并请求。第一期做完之后，main 上没有 Graphify 的安装、运行、文档和技能说明，入口只走 codegraph（留下的只有三样：三处“跳过名单”里它的输出目录名、识别旧记录时给提示用的文字、清理旧安装的规则）。不能拆成“先接上、再删掉”两步：测试把技能说明、工具清单和图信息的格式都钉在一种工具上，中间状态过不了自动测试。
  • 替换的同时把“图没有被用上”一起解决。现在 Claude Code 主持的一行入口运行里，图生成并导入之后就被搁在一边。新的做法是：主持会话照旧写功能清单，转换并提交之后，用一步“绑定”把清单落到索引上，页面上的关系图随之出现，每个功能列出它的文件，功能之间的关系带着类型和处数。
  • codegraph 给的是结构，不是功能。它没有任何功能划分。什么算一个功能、哪些是核心，仍然由主持会话和你定；这一点和换不换工具无关。
  • 全方案一条规则：事实边和提示边。codegraph 标为“按导入解析”的边算事实（抽查 60 条跨文件调用全对）；其余的（按限定名、按名字匹配、按对象类型推断）只算提示，不进清单，不拿来拦截，也不拿来推依赖。实测里读到的连错的边都在提示这一类里；事实边里的导入、引用、继承这几种没有抽查过。
  • nanolize 自己的导入表继续做主。“文件之间有没有依赖”用导入表加事实边：在 detectron2 上得到 541 对功能依赖，Graphify 是 544 对，覆盖了其中 538 对（没覆盖的 6 对里有 2 对在 Graphify 那边本来就是连错的）。索引补上的是导入表没有的东西：谁在第几行调用了谁、import 时执行了什么、C++ 的引用。
  • 安装比现在更保守，运行由 nanolize 自己做。钉 1.6.4 和四个平台包的校验值，下载一个文件、核对、解压，不运行安装程序。建索引不再交给主持会话照文档敲命令，而是 nanolize 的一个工具在本地盘的副本上做完，固定关掉遥测，永远不调用它那条会改 agent 配置的安装命令。
  • 换工具本身不会让以前失败的运行变成功。detectron2 那次三类失败里，可视化那条两个工具都看得到，配置文件那条都看不到；真正起作用的是第二期（提交前把关）和第三期（范围基线），它们在这份方案里保留并按新工具改写。
  • 它有明确看不到的东西（3.6 节）：经项目自己的导入钩子导入的代码、一半的函数内导入、配置文件、注册表里按名字取东西、Python 和 C++ 之间的关系。Graphify 靠按名字推断多连上了几对真的依赖，换了之后这几对要靠导入表和实跑来兜。
  • 分五期。第一期是替换本身，是最大的一期。第二、三期针对 detectron2 那次两回取消的原因。还要你定的事有 16 件（第 10 节），每件我都给了建议。

  • “对”里面有 37 条是靠继承成立的。其中 6 条连到的是基类里的定义、运行时可能被子类的覆盖版本接走，7 条只在某一种具体的子类组合下成立；判断时按“对”算了。把这 13 条也算成错，连错的估计值是约 2.5%。
  • tqdm：同样的算法得到 27%。原因是一件事：跨文件按名字匹配的 147 条边里有 128 条是测试里对同一个 pytest 夹具的调用，被连到了那个夹具函数上（实际被调用的是夹具返回的函数）。按导入解析的 22 条全对；按限定名解析的 5 条也对（都靠继承）；方法调用 18 条里 1 条错。

那 5 处里有一处是星号导入、一处是 C++ 的头文件引用：在 codegraph 的边上，星号导入和整体导入长得一样，要看它记下的那条导入语句的原文才分得开。codegraph 比 Graphify 多报的 2 对里，一对是按名字连错的（把握 0.4，按 3.3 节的规则属于提示边），另一对是两个原样带过去的 C++ 文件之间的引用，无害。

如实说一点。“整体导入”这件事，nanolize 自己的导入表对 Python 也分得出来。“import 时执行了什么”它现在没有：静态证据里那 77 条注册记录只记名叫 register 的那类调用，不分是不是在模块顶层，上面那 6 次注册不在其中；要自己做得新写一段收集模块顶层调用的代码。符号的起止行号，nanolize 的静态证据里 Python 的也已经有了（detectron2 是 2,764 个，和 codegraph 的数一样）。codegraph 真正独有的是：谁在哪个文件第几行调用了谁（到符号一级，并且顺着转出的名字找到真正定义它的文件），以及 C++ 等其他语言。

3.6 换了之后仍然看不到的

  • 功能划分。它没有任何分组，只有目录。什么算一个功能、哪些是核心，仍然由主持会话和你定。
  • 经项目自己的导入钩子导入的代码（detectron2 的 detectron2.projects.*）：查过的 14 对里，两个文件之间没有任何边。Graphify 靠按名字推断连上了其中一部分。
  • 函数内部的导入：只有约一半有迹可循（tqdm 是 5 对里 1 对）。这件事继续靠 nanolize 自己的导入表。
  • 配置文件：代码到 YAML 的引用、YAML 之间的继承，都没有。
  • 注册表：谁登记进了哪个注册表，要从“解析不出的引用”里按名字去找；按字符串名字从注册表里取东西，哪个工具都看不到。
  • Python 和 C++ 扩展之间的关系。
  • super() 调用和模块级对象上的方法调用（detectron2 里 99 对）：没有解析，但留着记录，两个文件之间另有导入或继承的边。

这些正是第三期“范围基线”（在只留下保留部分的原版上实跑一遍）要兜住的。

3.7 另一个看过的选项：Understand-Anything

读了它的代码，没有运行。它的图主要由模型按提示词写出来（估计一次要 45–50 个 agent 会话），按它的设计每次的结果不会相同，中途要等人确认；它确定性的那一层只读模块顶层的导入，比 nanolize 自己的导入表还弱；它的分组是建筑层和业务流程，不是可以勾选的功能树。所以不采用。它有几个做法值得借，都不需要用它这个工具：确定性的事实由脚本重新算、不采信模型写的；“每个文件恰好属于一个分组”做成硬性检查。

4.2 怎么装

现在的 Graphify换成 codegraph 之后
装在哪里nanolize 自己的工具目录（在用户的缓存目录下），每个版本一个 Python 虚拟环境同一个工具目录下，按版本和平台各一个子目录（两种机器共用一个主目录时不用来回重装）。不放进任何仓库，不放进任何 agent 的配置目录，不加到 PATH
怎么取让 pip 安装钉住版本的 Graphify 包；它的一串依赖由 pip 当场解析和安装从包登记处下载一个平台包的压缩包，先核对 sha512，对上了才解开。不运行任何安装程序：没有 pip，没有 npm，不执行包里的任何脚本。解包时只接受普通文件和目录，带链接或越出目录的条目一律拒绝（Linux arm64 的包里全是普通文件；两个 macOS 的包没有打开看过，如果里面有链接，这条规则会让它们装不上，到时再定）。因为内容是钉死的，下载源可以换成公司内部的镜像（由机器的主人用环境变量或安装命令的选项指定，主持会话调用工具时不能传）。连接的时限设得很短，没有网络的机器几秒内就得到“不可用”
机器上已有的同名命令优先用它，不管版本，只在报告里写一句一律不用。它可能是别的版本（不同版本建出的索引可能不同：只跑过 1.6.4，这是从它的更新记录推断的），还可能配了后台服务、钩子和遥测
什么时候装第一次要用的时候，由主持会话调用一个工具来装不变：第一次要用的时候装，装好留着，同一账号的各次运行共用。客户端等不及一次工具调用时“再调用一次”的约定也不变：安装在服务端继续，下一次调用等它
装不上怎么办返回“不可用”和原因，运行继续，只用 nanolize 自己的静态证据不变：返回“不可用”和原因，运行继续，但不带图，并且在页面和交付报告里明说（见第 10 节要你定的事）。另外允许指定一个事先下载好的压缩包，校验值同样要对上，给不能上网的集群用
确认装好了装好后写一份回执；之后每次使用，启动一次那个环境的解释器去问版本解开后写一份回执（版本、平台、校验值）；每次使用前核对回执和启动脚本在不在。不为了“问版本”而启动它
占多少空间文档里写的是约 250 MB约 310 MB 一个版本（Linux arm64 的包在磁盘上实际占 317 MB）；没人用的旧版本按现有规则过期删除
这一步比现在更保守。现在装 Graphify 是让 pip 当场解析并安装一串没有钉版本的依赖（只装预编译的包，不运行构建脚本）；换成 codegraph 之后只是“下载一个内容钉死的文件、核对、解压”。它自己有一条安装命令，会去改 agent 的配置（加查询服务、权限和提示钩子），nanolize 永远不调用那条命令，文档里也要写明不要手工去跑。

4.3 怎么运行

现在是入口文档给出一条 Graphify 命令，由主持会话在自己的终端里执行：nanolize 的代码从不启动 Graphify，这一步没有 nanolize 的沙箱，也没有时限。codegraph 有几条硬性条件，交给主持会话照着文档做容易出错，所以改成 nanolize 的一个工具把整件事做完，主持会话只调用一次。命令行和环境变量只在一个模块里拼，有测试守着。

步骤做什么为什么
1. 准备一个副本把仓库在当前提交上克隆一份到本地盘的临时目录（带 Git 信息的克隆，不是导出的文件夹），用代码里现成的做法：共享对象库、不检出，再按提交逐字写出文件，不运行账号里的任何过滤器和钩子。是不是本地盘，用代码里现成的“这是哪种文件系统”的判断；判断不出来的系统（比如 macOS）按可用算；确实找不到本地盘就报“不可用”，并提示把临时目录指到本地盘索引库只能建在被索引的目录里面（读它的代码所见），而原仓库要保持原样。在网络家目录上建索引每次都失败（数据库被锁，6 次里 6 次，和隔离方式无关）；本地盘、内存盘正常，另一种网络文件系统上一个三文件的小目录也正常。不带 Git 的导出文件夹会少索引文件：tqdm 少 12 个，包括五个属于清单的 Python 文件
2. 建索引在副本上运行“建索引”这一个子命令（带上“索引目录不进 Git”的选项），走 nanolize 跑检查用的同一个执行通道。环境是固定的：关遥测、不许自己下载、不起后台服务、主目录指向一个空的临时目录，除语言设置外不继承调用方的环境变量，只把 nanolize 自己在用的那个 Git 所在的目录放进路径（它找不到 Git 就会按“没有 Git”的方式建索引，少文件，把关那一步会报一个看不懂的错）；机器支持沙箱时自动放进不带网络、整机只读的沙箱里遥测默认是开的（读代码所见）；这样运行时它照常工作，主目录和副本里都没有留下别的东西。实测时进程完全没有网络；在 nanolize 用的那种沙箱里也试过，建出的内容相同。没有沙箱的机器（比如 macOS）上只有环境变量这一层保护，回执里要写明是哪一种
3. 把关四个条件都满足才算数：命令成功；索引状态是“完成”；索引记下的提交号等于当前提交、未提交文件清单为空；索引记下的工具版本等于钉住的版本这些字段它都自己记在库里。干净的克隆上这份清单应当为空；不为空说明副本被动过
4. 取回先在本地盘上把库整理成单独一个完整的文件，再连同一份回执（版本、校验值、各类数目、它没有索引而清单里有的文件）拷进运行的状态目录。删掉副本和临时主目录；删之前确认临时主目录是空的，不空就报告从网络盘上读这个库没有问题。库的大小：tqdm 3 MB，detectron2 25 MB。“临时主目录不空”是给将来版本的一道绊线：哪天它开始往主目录写东西，这里会第一时间发现
存放的位置放在运行的状态目录下一个新的子目录里，并把它加进“作业里的 agent 读不到”的名单（现在只有作业、评审、运行三个子目录在名单里，别的位置读得到）库里有整个原版的名字、函数签名和文档字符串，包括测试。作者不能看到测试，这是现有的规矩；现在 Graphify 的图放在笔记目录里，只靠 agent 的设置挡着
5. 之后后面的绑定、把关、页面都只读这个库，不再启动 codegraph。读的时候按“不可变文件”打开它的后台服务、查询服务、监视、Git 钩子一概不用。普通的只读打开会改写库旁边的一个附属文件（实测遇到过），按不可变打开就不会
  • 过期怎么办。现在导入图的那一刻要求图建在仓库当前的提交上（导入之后，带图信息的计划是按内容判断的）；而转换清单时会提交一批恢复出来的测试文件，提交号就变了，所以在转换之后再导入就得先重跑一遍工具。绑定一律按内容判断：索引给每个文件记的内容摘要，和 nanolize 自己算的是同一种（实测 detectron2 的 438 个、tqdm 的 47 个清单文件逐个相同），所以只要非测试文件的摘要都对得上，索引就算是当前的；对不上就重建，几秒钟的事，不再让用户看到“图过期”这类错误。
  • 可复现。同一提交、同一版本，三次构建的内容相同；关掉原生内核用备用引擎，内容也相同。这两条写进对着真程序的核对脚本。不同机器架构之间是否相同，没有量过。
  • 时间上限和并发。两个实测项目是 2–3 秒和约 7 秒；给一个宽松的固定上限（比如 10 分钟），超时按“不可用”处理。建索引和安装一样要加锁：两个调用同时来，只建一次，后来的等结果。

4.4 支持哪些平台

  • nanolize 的自动测试只在 Linux x86-64 上跑；代码里有 macOS 的分支，但那里没有沙箱；从代码看 Windows 上现在跑不了作业（没有试过）。
  • codegraph 这四个平台的包里，实际运行过的只有 Linux arm64 那一个。Linux x86-64 的要在实现时第一次跑；两个 macOS 的包没有条件试。
  • 建议：四个校验值都写进去，但文档里标明哪些试过；接入时留一个对着真程序的核对脚本（接替现在 Graphify 的那个），每个平台第一次用之前跑一遍。它对系统库的最低要求没有查清，旧系统上如果启动不了，报“不可用”并说明原因。

4.5 以后怎么升级

  • 它今年 1 月出第一个版本，到现在包登记处有过 85 个版本，最近三个月 5 个；实测的 1.6.4 发布才两天。所以不跟着它升级，只在有具体理由时升。
  • 升级是一次普通的代码修改：改版本号和四个校验值，重跑接入时留下的核对脚本（定义和行号对不对、顶层导入的覆盖、两次构建是否相同、和上一版索引的差异），看过差异再合并。索引不是钉住的版本建的，一律拒收。
  • 这次实测留下的脚本要先改成不依赖具体目录才能当回归用；其中“调用边准不准”那一项是人工读的，不是脚本，升级时只对有差异的边抽查。

5.2 改一个名字就行、但必须一起改的

  • 评审页面的开关。assets/viewer.js 里用“提供方是不是 graphify”这一个判断来决定显不显示关系图、摘要和“映射还没审”的提示。只在 Python 一侧改了提供方的名字，页面上这些东西会无声地消失，而且没有哪个 CI 里的测试会失败（能发现的浏览器测试不在 CI 里）。要和 Python 一侧、public_view.py 的白名单同一个提交改，并补一个不依赖浏览器的测试。
  • 运行页面的步骤名。“Graphify import”在四个地方各写了一遍，必须一起改。而且这个名字在提交进仓库的演示页面里也录了一份，测试会比对，所以演示页面要用离线作业重新录制，不是刷新一下就行。建议这次改成不带工具名的名字，以后再换工具不用再录。这一步旁边那句规则说明（中英文各一处，“只认建在当前提交上的图；社区只是预览”）换了之后不成立，也要改。“绑定”如果作为新的一步显示在页面上，步骤清单本身就变了，同样要重新录制。

6.2 “绑定”这一步做什么

输入是主持会话写好的清单（或事先给定的清单）和索引库，输出是同一份清单加上图信息。功能的标识、原样带过去的文件、对外接口、检查，一概不动。位置在“转换清单并提交”之后、“规划”之前：转换还会改清单（加上原样带过去的文件、对外接口的说明），在它之前绑定，后面一改就对不上了。

  • 核对索引是不是当前的：清单里每个被索引的文件，索引记的内容摘要要和仓库现在的一致；索引必须是钉住的那个版本建的。不比提交号（提交号照旧记在块里，后面几处要用）。
  • 把边归到功能上：每条跨文件的边，按两头的文件各属于哪个功能，记到“功能 A → 功能 B”上。事实边记进清单；提示边单独记在旁边的文件里。同一个文件里的边不算。
  • 写进清单的：每个功能的文件数、被索引的文件数、符号数；每一对功能之间的事实关系，带各类边的处数、其中有多少是从包的 __init__.py 发出的、有多少是整体导入。
  • 不写进清单、放在旁边的：每条关系的具体例子（哪个文件第几行引用了什么）、提示边、索引没有覆盖的文件名单、清单声明了却没有任何边的依赖、有引用却没声明依赖的功能对、只有提示边的功能对。这些在回执里给主持会话看，也留一份文件给第二期和第四期用。
  • 一处已知的坑：转换过的清单里带着“知识”部分，一旦再挂上图信息就会被现有的校验拒掉（读代码所见，没有实际跑过）。绑定时要把它去掉，由后面重新生成。
  • 绑定被拒时怎么办：带上图信息之后，每次规划都会多做一道“源文件是否干净”的检查，它比“Git 状态干净”严：仓库里有子模块、有经过过滤器或换行规则改写的文件、有没被忽略的未跟踪文件，都会被拒。这样的仓库今天能跑，是因为一行入口的清单从来不带图信息。所以绑定被拒时和“装不上 codegraph”同样处理：照旧不带图信息往下走，并且明说原因。

6.3 为什么例子和提示边不进清单

两个原因。一是大小和稳定：清单里的图信息会原样进计划（出现两次），清单的摘要也随它变，而计划必须和重新计算的结果逐字相同；每一处例子加起来有几百 KB。二是提示边里有连错的，而清单里的关系会被抄给作者。所以清单里只放事实关系的类型和处数。至于公开不公开，是另一层的事：公开页面拿到的是按白名单重新拼的视图，例子不加进白名单就不会出现在公开页面上（文件路径和对外接口里的符号名本来就在公开视图里）。

6.4 要守住的几条

  • 计划必须和重新计算的结果逐字相同。所以计划的计算只用绑定时写进清单的内容；规划、录基线不读索引库（把关和本机页面另读）；没有图信息的计划不能因为这次改动多出任何字段。
  • 绑定会改变清单的摘要。所以绑定必须在启动评审之前；评审开着的时候重新绑定，会让那次评审作废。同一个提交、同一份清单，两次绑定的结果要逐字相同，重建索引之后也一样。
  • 绑定之后又改了文件归属，要能发现。块里记一个“当时文件归属”的摘要，对不上就要求重新绑定。
  • 没被索引的文件要说清楚。shell 脚本、样式表属于某个功能但索引里没有它们（detectron2 清单里 12 个，tqdm 1 个），YAML 只有文件名。页面上按功能显示“几个文件里几个有索引”（这两个数在清单里，要加进公开视图的白名单；具体是哪些文件在旁边那份文件里），不能显示成“和谁都没关系”。
  • 两个来源，两个数。页面上的关系来自索引，第二期的把关以导入表为主，同一对功能两边的数会不一样（detectron2 上是 537 对和 437 对）。每个数旁边都写明来源。
  • 解析方式这个字段只是它这一个版本的内部约定。没见过的取值一律归为提示；工具版本不在允许名单里就拒收。
  • 带图信息的清单，还没有在现在的作业流程里真跑过。上一次带图信息的真实运行在 11 月上半月；那之后才有转换清单时恢复测试、两个作业、并行、性能验收、借原版源码这些功能。带上图信息后，作业里每一次规划都会在作业自己的工作树（或草稿作业的克隆）上做那道“源文件是否干净”的检查。现有的测试只有一个单作业的样例。所以第一期的验证必须包含一次两个作业加并行的真实运行。
  • 被跟踪的符号链接：nanolize 给它算的摘要和索引算的不是一回事，这样的文件会一直被判成“过期”。绑定时把符号链接排除在比对之外。

6.5 草稿没有了，主持会话拿什么写清单

保留的功能之间有引用，但清单没声明依赖导入表加事实边改正后的清单上仍有 14 处导入、涉及 7 个保留的功能（按导入表算；加上事实边后的数要实现时重算）
这个功能里有哪些符号被别的功能用到，却不在它声明的对外接口里索引里的事实边（到符号一级，这是导入表没有的）之前用 Graphify 的图量过：跨功能使用的符号里 81% 已在声明的接口里。换成索引后要重量
仅供参考的一栏：提示边指向被去掉功能的地方索引里的提示边，带它标的把握值被取消的那次：只靠提示边的越界引用有 1 对，是连错的（配置对象的 update）；可视化那一对上另有 4 处提示边，是对的。对错混在一起，所以这一栏永远不拦截
配套，不靠索引：把提交时已经在跑的作业就绪审计的结果报出来，主作业和草稿作业各一份现有的审计，原样可用第一次取消的原因在提交那一刻就能看到
配套，不靠索引：交付时对照计划，列出候选里有哪些文件原本只属于被去掉的功能（范围有没有在修复里变大）计划里的文件归属 + 候选的文件列表如果 11 月 21 日那次加进来的文件确实属于被去掉的功能（推断），会列出其中和原版同路径的那些：38 个 .py 配置、几个数据集文件、6 个模型模块。换了名字写的文件按路径对不出来
配套，不靠索引：没有任何途径进入候选的配置文件，以及其中被保留的代码或测试按名字提到的。补救是在提交之前把它们加进清单的“原样带过去”名单计划 + 现有的借出规则 + 文本搜索列出 157 个；49 个出事的 YAML 里按不带后缀的名字能标出 45 个（严格按全名只有 8 个）。误报率没有量过

怎么接。

  • 核对结果不能放进计划本身：保存的计划必须和重新计算的结果完全相同。做法是在规划工具的回答里、和现有的提示并排返回，另存一份文件。
  • 拦截放在提交那一步，因为越界引用取决于最后选了什么。只拦第一类（普通文件里的越界引用，而且必须是导入表或事实边给出的）。处理办法有三种，但不是对等的：加依赖、把文件挪到别的功能，都要改清单，改了清单这次评审就作废，要重新绑定、重新规划、重新开评审；只有“写明理由后放行”能在开着的评审上做。所以最好在开评审之前就把核对结果看完。
  • 强制绑定也在这一期开：能绑定而没有绑定的清单不让提交，在提交那一步查。装不上索引或绑定被拒的运行照旧放行并明说；从命令行或测试里直接启动评审的调用方不查。
  • 没有索引时照样能跑：装不上 codegraph 的机器上，这些核对退回到只用导入表，少掉的不少：调用点的行号、顺着转出的名字找到定义文件才看得出的那 104 对依赖、“import 时执行了什么”、跨功能使用的符号，以及所有非 Python 的代码。回执和页面上要写明这次用的是哪一种。
  • 如实说一个弱点：无人值守时“写明理由后放行”是主持会话自己写的一句话，所以这道拦截对它来说更像一次强提醒。真正兜底的是第三期。
  • 从命令行或测试里直接启动评审的调用方默认不拦，只有走入口文档的运行才拦，免得一次改动波及测试里上百处直接启动评审和录基线的地方。

改哪里。新增一个做核对的模块（读计划、导入表和索引库）；mcp_server.py（规划工具的回答、启动评审的回执）；capability_verification.py 和 knowledge.py 里“计划旁边允许带什么”的两份名单（不加进去，下一次录基线会说计划被改过）；execution.py、execution_server.py 和评审页面自己的脚本 assets/execution.js（提交时的拦截；本机启动评审时也跑就绪审计并报出结果）；运行页面第二阶段显示结果；入口文档。新增工具会改变一个记录工具说明的摘要，和以往每次改工具说明一样。

验证：拿 detectron2 三次提交的计划和 tqdm 的计划，加上这次实测留下的两个索引库离线回放，不花钱。

第三期（不靠索引）：范围基线——在“只留下保留部分的原版”上实跑一遍

为什么要它。索引和导入表都是静态的，看不到配置文件、注册表和字符串路径（3.6 节）。detectron2 第二次取消的 9 条失败里有 7 条属于这几类；第三次提交里最后剩下的那 1 条也是。这些失败有一个共同点：原版如果只留下保留的那部分，它自己就过不了这些检查。这件事跑一遍就知道，不用等作者把代码写完再比较。换不换工具，这一期都一样要做。

做什么。

  • 冻结阶段多一步，从原版造一棵树：拿掉只属于被去掉功能的文件，包括那些“没有任何途径进入候选”的配置文件；再把保留的包 __init__.py 里“只是把被去掉的模块带进来”的导入语句去掉。然后像对候选那样准备环境，把保留的检查跑一遍；设计出来的测试出来之后再跑一遍。
  • 在这棵树上过不了的检查，是范围划分造成的。当场报出来：哪条检查、缺的是什么文件或名字、它属于哪个被去掉的功能。
  • 设计出来的测试如果在这棵树上过不了，退回给设计者并附上原因。实跑比一句说明可靠。
  • 后面比较候选时，失败的归因就准了：在这棵树上本来就不过的，不派作者去修。
这一步还没有做过原型，有一处硬骨头。不能只是把文件拿掉：detectron2 保留的 6 个包 __init__.py 在顶层导入了被去掉的模块（近 20 处），直接拿掉文件，这棵树一导入就报错，93 条检查里至少 52 条会在导入时失败，看不出哪 9 条才是真问题。所以必须自动去掉那些导入语句。这件事有风险：星号导入、__all__ 列表、带副作用的导入都要处理对。内置数据集那一条正是靠导入来完成注册的，去掉它之后依赖注册的检查会像在候选上一样失败，这是要看到的结果，不是误报。索引在这里能帮上一点：哪一条导入语句把哪个被去掉的模块带进来、在第几行到第几行，索引里现成有（一条导入语句是一个节点，带起止行和原文）；一条语句同时导入几个名字时，去掉其中哪一个仍然要自己解析。建议先用 detectron2 被取消的那份范围做一次原型：造出这棵树，跑那 93 条检查，看失败的是不是正好那 9 条。原型不成立，这一期就不做。

能提前多少，要如实说。在两个作业的模式下，草稿作业的作者和主作业的冻结是同时进行的。被取消的那一对里：9 条失败里有 5 条是原版自带的检查，它们在第一次基线时就能显形，那是提交后约 10 分钟，并行的作者才刚开始写；另外 4 条是设计出来的测试，要到测试设计结束才存在，那时已经花了约 $73 的作者和约 $66 的设计与评审。所以这一步省下的是“写完、比较完才发现”的那一段和后面的修复轮次，不是全部花费。

配置文件不在这一期。那 49 个 YAML 出事，是因为借给作者哪些资源文件是按“最近的上层目录里谁有源码”定的，它们所在的目录里恰好只有被去掉功能的 .py 配置，于是没有作者拿到。真正的补救是把这类文件放进清单的“原样带过去”名单，而那是第一阶段、提交之前定的，属于第二期最后一项核对。原样带过去的文件不计入体积，所以体积的基准会变（那次是从 654,599 降到 641,370）。

改哪里。job_tools/freeze.py 和 execution.py（冻结阶段的新一步和它的记录）；造这棵树的新代码（含改写 __init__.py 的那部分）；leaf_test_design.py（设计的测试在这棵树上试跑、退回）；repair_policy.py 和失败摘要（归因）；verification.py（在这棵树上跑检查）。

代价和要定的事。多一次不带敲除的基线（detectron2 那次带敲除的两次基线是 9 和 19 分钟）。还要定作业遇到范围问题怎么办（第 10 节）。

第四期：页面和作业进一步用索引

页面。

  • 功能之间的关系点开看例子：哪个文件第几行调用了哪个文件里的什么。例子第一期存在清单旁边的文件里，不进公开视图，所以这一条只在本机打开的页面上有：由本机的页面服务读那份文件或直接查索引库。公开分享的页面上只有类型和处数。
  • 勾掉一个功能时当场看到后果：从保留部分指向它的引用亮起来，按第二期的分类标出；有人值守时你可以在页面上逐条确认。两边的选择逻辑要一起改、一起对拍。
  • 往下钻到符号放在最后：评审页面现在一律只拿“公开视图”，公开链接的网关也只开放几个固定地址。要显示符号就得有第二种只给本机的视图。有了索引库这件事比原来容易（符号、起止行、谁调用它都是现成的查询），但页面和网关那一侧的工作量不变，可以先不做。

作业。

  • 给作者的说明里列出“这段代码引用了、但没借给你的文件”，带上行号。被取消的那次里，没有任何作者被借到可视化模块。多借文件会抬高和原版的重复度，所以先只说明、不多借。
  • 报告“同一层的两个 scope 互相引用”。这是 PR #56 留下的已知限制之一。
  • 给每个作者列出“你这个 scope 里被别的功能用到的符号”，用索引里的事实边。
  • 不把 codegraph 交给作业里的 agent。它自带一个给 agent 用的查询服务，但那会在沙箱里多起一个进程、多一套它自己写的提示，而且多个作者同时用会争同一个库。需要的答案由 nanolize 自己从库里查好，写进说明。

改哪里。清单里图信息的字段和校验、public_view.py、knowledge.py、assets/understanding-graph.js、viewer.js、planner.js 和它在 Python 里的那一份；source_reference.py（说明里的那几句）；scopes.py（只加报告）。

第五期：给主持会话一份结构摘要（先做实验，再决定做不做）

现状。Graphify 的导入会产出一份“草稿”：每个社区是一个候选功能。实测里这份草稿和人工功能树对不上，主持会话也没有用它；换成 codegraph 之后社区没有了，这份草稿随之取消（第一期）。剩下的问题是：主持会话动手写功能树之前，要不要给它一份由索引算出来的材料。

  • 之前量过三种自动切法（按 Graphify 的社区、按目录、用边重新聚类），和人工功能树的吻合度都很低，其中按目录最好。codegraph 自己的立场也是“模块就是目录”。
  • 所以可以试的只有一种：按目录分组，附上组与组之间的事实边数量、每组里 import 时执行注册的文件、被最多功能用到的符号。它是参考材料，不是候选功能。
  • 主持会话现在靠 nanolize 的静态证据和自己读仓库写清单，这台机器上那次 detectron2 运行的清单就是这样来的。多一份材料是让它更快更准，还是多一份要读的东西，没有数据。

建议。先花半天做一个不花钱的离线实验：对 detectron2 和 tqdm 生成这份摘要，对照现有的功能树看它能不能指出树里划错的地方（比如那次被划成可选的内置数据集）。有用再立项；没用就保持“主持会话写清单、然后绑定”的做法。

离线这一半已经做了（2026-11-22，不调用模型）。只用索引给 detectron2 和 tqdm 各生成了一份摘要（106 KB 和 5.6 KB），生成时不看功能树，再拿 detectron2 被取消的那次范围来打分。三处划错里，摘要只带着一处的信号：内置数据集在 import 时注册，它是“整体导入一个模块，而那个模块在 import 时做注册”的 55 条里的一条，摘要说不出哪一条要紧。核心引用可视化模块那一条看不出来：那个文件在“被引用最多的文件”里排第 69（共 339 个）。配置文件那一条索引里没有。tqdm 的摘要没有给出主持会话自己看不到的东西。同样的信息，在有了一份草稿范围之后清楚得多：第二期的核对在那次范围上只报 2 条和 1 对，正好包含前两处。所以这一半不支持把结构摘要单独做成一期；更划算的是让第二期的核对在主持会话写出第一版清单之后马上跑，让它据此改。可以顺手带上的只有“哪些模块在 import 时做注册”的名单（detectron2 是 51 个文件）。另一半没有测：主持会话拿到摘要之后是不是真的写得更好，要起真的主持会话、各跑几次才看得出来。

9. 潜在风险和对策

风险会怎样对策
codegraph 很新、变得快实测的版本发布才两天；今年已有过 85 个版本。新版本可能改变解析结果，也可能出问题钉死一个版本和校验值，不跟着升；升级是一次带对比的代码修改（4.5 节）
有连错的边detectron2 的跨文件调用边估计约 1.4% 连错（点估计）；tqdm 因为一个测试夹具高达 27%。用错了会凭空多出依赖，或者错拦一次提交全方案一条规则：只有“按导入解析”的边算事实；其余不进清单。拦截和推依赖只用事实边和导入表
有它看不到的依赖经项目自己的导入钩子导入的代码几乎没有边；函数内导入只有一半有迹可循；配置文件、注册表、C++ 扩展看不到。Graphify 靠按名字推断多连上了几对真的依赖导入表继续做主；第三期的实跑兜底；页面和文档明说“索引全绿不等于范围没问题”
只在两个 Python 项目上量过别的语言没有数据；不同机器架构之间结果是否相同没有量过第一期的核对脚本用的小项目里带一个 C++ 文件；核对脚本在 Linux x86-64 上也跑一遍
建索引的环境条件要在本地盘的 Git 克隆上建；在一台机器的网络家目录上试了 6 次都失败由 nanolize 的工具统一做，不让主持会话照文档手工跑；临时目录不可用时报“不可用”并说明原因
下载和供应链要从包登记处下载一个约 66 MB 的压缩包（Linux arm64 的那一个，解开约 310 MB；其他平台的没有量）；登记处或网络不可用时装不上校验值钉在代码里，对不上不解压；装不上时运行照常继续、不带图；支持事先下载好的压缩包
它的遥测和安装命令遥测默认开；它的安装命令会改 agent 配置只用“建索引”这一个子命令，固定带关遥测的环境变量、空的临时主目录；有沙箱时不给网络。安装命令永不调用
把静态核对当成充分条件索引和导入表都看不到注册表、import 副作用以外的动态行为、字符串路径。核对全绿，范围仍可能是错的页面和文档明说“必要而非充分”；第三期的实跑兜底
误报挡住提交越界引用里绝大多数是 __init__.py 转出名字分类，只拦普通文件里的那一类；可以写明理由放行；命令行和测试的调用方默认不拦
拦截在无人值守时形同提醒主持会话可以自己写一句理由放行接受这一点；靠第三期在冻结阶段实跑
绑定带来的副作用清单带上图信息后，作者读到的材料里会多出“相关功能”的提示，计划里多一句话第一期明确逐项接受或关掉（第 10 节第 7 件）

带图信息的清单没有在现在的作业流程里真跑过上一次是 11 月上半月。带上图信息后每次规划多一道“源文件是否干净”的检查，会在作业的工作树和草稿作业的克隆上执行；带子模块、过滤器改写文件或未跟踪文件的仓库会在绑定时被拒绑定被拒时照旧不带图信息往下走并明说；第一期的验证包含一次两个作业加并行的真实运行
索引库里有测试的内容库里有整个原版的名字、签名和文档字符串，包括测试；状态目录现在并不是整个都对作业保密把索引库、回执和例子文件的位置加进“作业读不到”的名单，并有测试守着（第一期）

10. 要你定的事

“用 codegraph 替换 Graphify”已经定了，下面是替换时还要你拿主意的事。每一条我都给了建议；你不回的，我按建议做。

问题我的建议
1第一期作为一个大的合并请求来做，可以吗只能这样（第 7 节第一期开头）：拆成两步的话，中间状态过不了自动测试。里面分组提交，多个会话并行，评审按组看
2用户看得见的名字：入口选项 graphify=on|off 改叫什么改成 index=on|off|require（默认 on），步骤名相应叫“结构索引”；数据里记工具名 codegraph 和版本。不建议叫 graph=：同一份说明里“graph”已经指图契约，graph=off 会被读成“不做契约转换”。也可以直接叫 codegraph=，代价是以后再换工具要再改一次名。旧的选项名不保留：入口遇到不认识的选项会停下并说明，README 里的例子同时改

11. 工作量和验证

以这个仓库以往的大改动为参照：多会话并行、带评审和 CI 的一个合并请求，实际用时 4.5–9 小时。下面的“一个单位”指这样一个合并请求。都是估计。

12. 背景：这件事是怎么来的

  • 设计的初衷是让代码图既用在选功能的页面上，也帮到后面的作业。实际上在 Claude Code 主持的一行入口运行里（11 月 16 日以来的那些），图生成并导入之后就被搁在一边：提交的功能清单不带任何图信息，页面上现成的“关系图”视图没有出现过。
  • 历史上它起过作用：11 月上半月不走一行入口的那些运行，提交的清单都带着审过的图映射。没有哪次修改删掉了这条路；是后来写的运行步骤和一行入口没有把“导入图”和“写清单”连起来。
  • 三次 detectron2 只保留核心的运行都遇到了范围划分的问题，处理方式各不相同（带缺口交付、修复时把文件加回来、取消重来），没有一次是在提交前解决的。
  • 这三点的证据（哪次提交、哪份记录、逐项对比）在此前那版方案的第 4、5 节，这里不重复。那一页里关于 Graphify 的做法由本页取代。
