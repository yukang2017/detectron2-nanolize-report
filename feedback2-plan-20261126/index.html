二 · 保留清单（白名单）。 选项是 carry=。不写：什么都不按清单或规则保留。carry=<路径>：你点名的文件或文件夹，比如 carry=awq/kernels/csrc。carry=auto：按规则保留给显卡写的内核代码。两种可以写在一起。保留的文件原样带进交付、不算进压缩比例。不写的时候，规则会保留什么照样在提交前和结果里列出来，带着可以直接抄的写法。用 carry=auto 的代价是整个仓库能压掉的变少：llm-awq 估计从减少 29.7% 变成 17%–23%，DeepInfer 从 42.8% 变成 30%–36%（估计）。细节在第 4 节。

三 · 本机没法验证的代码。 选项是 untested=keep|rewrite|drop，默认 drop。drop：这一版不包含。keep：按原版保留，不算进比例。rewrite：让作者在没有测试的情况下重写。因为测试环境的原因没法验证的，按原版保留，并提示修好环境再跑（只有写了 untested=rewrite 才重写）。drop 不会去掉保留的代码还要用的东西，也不碰 carry= 下面的路径。默认 drop 有一个后果要先说清楚，在第 5 节的方框里。细节在第 5 节。

这一页用到的几个词（展开）
  • 配对：一次提交变成两个作业，主作业冻结并验收，草稿作业同时写第一版。
  • 清单：主持会话写的一份文件，列着有哪些功能、各用哪些文件、用哪些检查。主持会话是替使用者启动并照看这次运行的那个 agent 会话；skill 是工具给主持会话的那份说明。
  • 候选：作者交上来、等着验收的一版代码（记录里的候选 4、候选 21 就是）。待选是另一回事：只列出、不保留、等你点名的代码（不写 carry=auto 时，规则会保留的那些也在里面）。
  • 冻结：作业的第一个阶段，录原版的基线、验证测试、设计测试，最后封存。合同是冻结下来的那套检查和原版的基线。
  • 有效测试：把这项功能的代码弄坏以后会失败的测试。敲除是工具故意把一项功能弄坏、看测试会不会失败的那一步。
  • 门槛：工具判定一条检查算不算数的几道关：在原版上通过、够轻、重复跑结果一样、把功能弄坏后它会失败。
  • 准备步骤：主持会话写的构建命令。它要声明自己依赖哪些文件（inputs），这一页叫“声明的输入”。
  • 设备内核代码：给显卡这类加速器写的内核代码。内核 DSL：专门用来写 GPU 内核的 Python 库（比如 TileLang、Triton）；用它写的文件，对工具来说是普通的 Python 文件。
  • 提示：规则认不出、但看起来像内核的文件，工具把它点出来给主持会话看。
  • 适配器：工具用来驱动 Claude 或 Codex 会话的那一层。
  • 接缝：按原版保留的代码和重写的代码相接的地方。
  • 夹具：一个专门写的小测试项目。
  • 等轮次：原型里两个作业的检查用一把锁轮流跑；等轮次就是排队等这把锁。
  • 隔离模式、提示模式：本机配对时管进程的两种办法。机器给得了独立进程空间，会话就关在自己的进程空间里；给不了，就在提示词里告诉会话不看、不停别的进程。

一 · 没有调度器也能配对pair=on 没有可用的计算节点就被拒绝，无人值守时改成一个作业。文件隔离（你说的沙箱办法）其实已经有了；还靠节点解决的是两件事：会话能看到、能打断对方正在跑的检查进程，以及负载。写了 pair=on：有可用的调度器和今天一样；没有调度器，一定在本机起两个作业。进程分两种模式：机器给得了独立进程空间就隔离，给不了就在提示词里约束，加三道保险。草稿作业低优先级运行、不跑 GPU 检查；因为机器太忙而没算数的检查，在结果里逐条列出。不写 pair 就是一个作业，集群上也是。原型在我们的机器上把一次本机配对跑到了交付。运行 A：已交付，带缺口（唯一的原因是清单里原样保留的 fuzzing 功能没有有效测试）；检查 19/19；25.0 分钟；花费（美元）28.64（两个作业自己的记录，不含主持会话）。同一份清单做成一个作业，运行 B：带失败交付：行为比较 19/19 通过，安装检查 3 步过了 2 步；没过的那一步是这次运行的主持会话自己写错的命令，任何候选都过不了；检查 19/19；80.3 分钟；花费（美元）45.85（同样只算作业自己的记录）。各只有一次。“提示”模式：三个试验合起来看到的是：没有人提醒时，以往的会话里确实有少数会按名字停进程（332 个里 8 个，每次都是自己的命令卡在后台时）；提醒之后的两次本机配对（21 个干活的会话、185 条命令）和一个 Codex 小试验里，没有一条命令去看或去停别的进程，其中有两回正是以前会触发 pkill 的情形。样本很小，这是“说了会照做”的迹象，不是一个比例提示不是墙：一个不照做的会话仍然看得到、有的机器上还停得掉别的进程；三道保险针对的是：会话不必按名字停进程、检查被误杀不算失败、事后看得见；三道都还没有做，也没有试过。收益不大：llm-awq 那次运行按记录算，最多能省约 19.5% 的时间。使用者那种机器（不是容器、单卡、Codex）我们没有，没法实测。不写 pair 时，集群上原来会自动配对的大选择现在是一个作业。1.1、1.2、1.3
二 · 保留清单（白名单）白名单机制已经有（清单里的 carry：原样保留、不算进比例），但入口没有选项，无人值守时没有规则，页面不显示。入口加 carry=。不写：什么都不按清单或规则保留。carry=<路径>：你点名的文件或文件夹。carry=auto：按规则只保留设备内核代码（含 CUDA 源码的编译扩展、用内核 DSL 写的设备内核文件）。其余编译代码只列出、不保留。不写的时候，待选的代码照样在提交前和结果里列出来，带着可以直接抄的写法。只读实测（16 个公开仓库加我们自己的两个项目）：llm-awq 保留 42.2%、DeepInfer 23.9%、detectron2 5.8%（正好是上一轮那次运行里手写的 17 个文件）；五个不该保留任何东西的项目（librosa、timm、nanoGPT、requests、click）一个文件都不保留，也没有待选。用 carry=auto 时整个仓库能压掉的变少：llm-awq 估计从减少 29.7% 变成 17%–23%，DeepInfer 从 42.8% 变成 30%–36%（估计）。规则不认识的内核库，要靠主持会话读提示；保留的内核和重写的调用方之间只查名字和构建，不查行为。不写 carry 时，没有有效测试的内核按 untested= 办：默认是这一版不包含。2.1、2.2、2.4
三 · 本机没法验证的代码没有哪一步决定“测不了就删”；实际是没有检查盯着的代码由作者盲写（可能写少、写错）。上一轮的 untested=carry 只管提交前能判断的；冻结结束才发现的仍然重写。untested=keep|rewrite|drop，默认 drop：这一版不包含。提交前就知道的，在提交前去掉；冻结结束才发现的，作业自己去掉（多录一次基线）。因为测试环境的原因没法验证的，按原版保留，并提示修好环境再跑（只有写了 untested=rewrite 才重写）。保留的代码还要用的不去掉；carry= 下面的路径不碰。每次交付都报告“相对原版少了什么”；体积数字分成“重写变小的、这一版不包含的、原样保留的”三部分。我们自己的五次交付里没有发现硬件分支被删（作者是 Claude）。要分两种情况。一整项功能测不了（比如整个后端）：保留得住。有测试的函数里面给另一种硬件写的分支：按文件保留留不住，只能事后报告。在试验的三个小项目里（其中两个有这类代码），没被执行的硬件相关代码全是后一种。默认 drop 有一个后果，写在第 5 节的方框里。DeepInfer 那次去掉的到底是整块后端还是文件里的分支，记录里没有；要使用者给一个文件清单才能确定（请求）。3.1、3.2，和共用的 2.3

提示词里的那句话。意思是：这台机器上还有别的作业的进程；不要列出或查看不是你启动的进程（不用 ps、top、pgrep，不看 /proc 下面别的进程号）；不要按名字或模式停进程（不用 pkill、killall）；只停你自己启动的，按它自己的进程号；可能跑很久的命令放在 timeout 下面跑。最后这半句是看了试验 T1 之后加的；T2 和运行 C 用的是没有它的写法。停掉自己后台命令的那个工具做出来之后，这句话里还要点出它（保险一）。

Other jobs' processes run on this machine beside yours. Do not list or inspect processes you did not start (no ps, top, pgrep, nothing under /proc for other process ids), and never stop processes by name or pattern (no pkill, no killall): stop only what you started, by its own process id; run what may take long under timeout.
  • 保险一：让会话停得掉自己的后台命令。 给每个会话一个停掉自己后台命令的工具（agent 自己就有这样的工具，今天适配器没有把它交给会话），并在那句话里说清楚不用 pkill 时该怎么做：可能跑很久的命令放在 timeout 下面跑；自己的后台命令用这个工具停，或者按启动时记下的进程号停。这一道直接来自试验 T1：没有人提醒的会话伸手去用 pkill -f，只有一种情形，就是它自己的一条命令超过了命令工具的时限、被挪到后台，而它没有工具能停它。
  • 保险二。 主作业的检查如果是被信号结束的，先重跑一次，再算结果：被杀掉的检查不等于失败的检查。
  • 保险三。 两个作业结束时，把它们的会话跑过的命令读一遍，找列出、查看进程或给进程发信号的命令；结果里写明有多少条、是哪些、在哪个会话里（一栏“会话有没有看过或动过别的进程”）。这就是试验 T1 用的那个脚本，做成交付的一步。

为什么是“四分之一”

为什么是“四分之一”。 调查里的应用项目，设备源码占它所在扩展的 39% 到 100%（llm-awq 66%，detectron2 59%）。有一个项目相反：一个编译器项目有 250 万 tokens 的 C++，里面只有一个 2,789 tokens 的设备模板文件；如果规则是“扩展里有一个设备文件就整个保留”，这 250 万 tokens 会被整个保留。所以方案定为：设备源码占到扩展的四分之一才整个保留，不到就只保留设备文件本身。〔试验〕

提示会不会乱点

提示会不会乱点。 提示是“一个表里没有的库的装饰器盖住了半个文件”。脚本里另有一张“永远不算提示”的名单（36 个常见的库，比如 pytest、click、torch）。在四个普通的库上（click、requests、timm、librosa），带着名单一个提示都没有；去掉名单，timm 的 322 个文件里有 5 个被提示。没有量过的是：大量用任务队列、路由、重试这类装饰器的应用项目。〔试验〕

K1　入口选项 carry=：不写就不保留

使用者看到的

规则
只能写 auto 和路径（文件或文件夹，用逗号隔开），两种可以写在一起。没有 off 这个值：不写就是不保留。不能写功能的编号。一个路径如果什么都匹配不到，评审开始之前就被拒绝，这样打错字不会悄悄地什么都没保留。carry= 下面的路径永远不会被去掉，也不会被重写，不管 untested= 写的是什么。
不写的时候
什么都不按清单或规则保留。待选的代码（carry=auto 会保留的那些，和别的编译代码）照样在提交前和结果里列出来，带着可以直接抄的写法；其中按现在的设置这一版不会包含的，逐项标出来。
原因
问题二和问题三是一个机制，共用一张原因表（第 6 节）。这一项新增两种说法：owner_choice（使用者指定的：你写了路径；照样给它设计测试）和 kept_by_rule（规则认出是设备内核代码，依据写进清单的备注；检查够得着的地方照样设计测试）。分析原来给新原因起的名字是 performance_critical；评审指出规则只知道这是设备代码，不知道它调优过，名字不该这么说。

K2　规则（写了 carry=auto 时）：只保留设备内核代码

保留什么
  • 编译扩展（准备步骤声明为输入的路径下面，编译器会读的所有非 Python 文件）：设备源码占它四分之一以上，就整个保留。设备源码按后缀认：.cu、.cuh、.metal、.cl、.ocl，这张表随工具发布，是数据。不到四分之一，只保留设备文件本身，其余只列出、不保留。
  • Python 文件：一半以上是设备内核代码的保留。按一张随工具发布的内核库的表来认；表里没有的库，主持会话读过一个被提示的文件、确认是内核之后保留，并把库名写进清单的备注。
  • 一个目录里别的文件都保留了，它的空 __init__.py 也保留（这样这个目录能整个算一项保留的功能）。nanolize 归为测试的文件永远不保留。
只列出、不保留（待选）
其余编译的东西：不含设备源码的 C、C++、Rust 扩展，给处理器用的 numba 和 Cython。它们在提交前和结果里都列出来，带着体积；你把路径写进 carry= 才保留。理由：这类代码在哪台机器上都能跑、能测，性能验收管得住；我们自己的运行重写过一个 C 扩展，没有修复，性能 4 条标准全过。〔上轮运行〕 这是你的回答（2.2）。

K4　接缝：保留的代码和重写的代码相接的地方（第一批就做）

借给作者读
保留的文件以只读的方式借给导入它们、或者构建它们的那些功能的作者。今天作者对它们只知道一个路径，要对着看不见的代码写调用和构建文件。
编译选项
告诉作者：对保留的源码，保持原版的编译选项。一个构建文件如果本身是声明的输入、又不是包的顶层入口，也一起保留（比如 llm-awq 的 awq/kernels/setup.py，前提是准备步骤声明了它）。
构建失败时
错误全部出在保留的文件里的构建失败，交给构建入口所在范围的作者，并点出保留的文件名。今天这种情况不会叫任何作者：上一轮做的构建修复只把“作者自己文件里的出错位置”告诉作者。
结果里的一行
原版和交付的构建定义里，编译选项不一样时，结果里有一行。这是文本比较，只是一个提示：源文件列表、宏定义的变化它看不出来，页面上照实这样说。
作业内部
文件全部被保留的范围不再叫作者；敲除不动保留的文件；一个目录里有内容的文件都保留了，就算整个保留。

K5　一条“停下来”的规则，代替“把原版放回去”

什么时候触发

(a) 默认开（上一版方案的建议）不写 carry= 时就按规则保留设备内核，要另写一个值才关掉。无人值守是常见的情况，那里没有人读“建议你保留”这种话。决定提到了评审之前：配对时，草稿作业不会白写后来要丢掉的文件，测试设计者也不为它们开会话。内核就是项目主体的仓库，剩下能重写的很少（pytorch_scatter 70%、diff-gaussian-rasterization 96% 被保留）；页面在提交前说出占比。

写了 carry=auto 的代价，是上面“代价的估计”那张表里的数。不写 carry 时，使用者跑的这两个项目里没有有效测试的内核不再是“反正会保留”：默认的 untested=drop 下它们这一版不包含，写了 untested=keep 才保留。carry=auto 比 untested=keep 多保留的，是那些有有效测试的设备内核；现有的证据里，没有一次运行显示这样的内核被重写之后变慢或者坏掉。

结论：工具里没有“测不了就删”这一步。实际发生的是：没有任何检查盯着的代码，交给作者在看不到测试的情况下重写，它可能被写少，也可能被写错，而且没有任何信号。定下来的做法：选项是 untested=keep|rewrite|drop，默认 drop，本机没法验证的功能这一版不包含；提交前就知道的在提交前去掉，冻结结束才发现的由作业自己去掉。因为测试环境的原因没法验证的，按原版保留，并提示修好环境再跑（只有写了 untested=rewrite 才重写）。每次交付都报告“相对原版少了什么”。

默认值的一个后果。 默认是 drop。它不去掉保留的代码还要用的东西，而“要用”是按计划里的导入表判断的。靠运行时拼出来的名字才加载的代码（比如一个按字符串挑后端的分发器；DeepInfer 给每种加速器的内核就是这样挑的）不算“要用”。所以什么都不写的时候，一个在这台机器上没有有效测试、又只通过这种方式用到的后端，这一版不会包含，哪怕它正是给使用者手上的硬件写的；也没有检查会发现（它正是因为这样才没有有效测试）。

页面和结果怎么显示：总结的第一行和页面点出哪些没有包含；提交前的待选列表把“按现在的设置这一版不会包含”的每一项标出来。要留下它：carry=auto（设备内核）、carry=<路径>，或者 untested=keep。

DeepInfer 那次去掉的到底是哪一种情况，记录里没有：可能是一整块后端（那是一项没有有效测试的功能，这个方案管得到），也可能是有测试的文件里面、给另一种设备的分支（这个方案只能事后报告它）。请使用者给一份“交付相对原版少了哪些文件”的清单就能定下来（第 7 节的请求）。

可选：想知道自己的机器是哪一种模式

这一条不再是请求：作业开始时自己会探测，机器给不给得了独立的进程空间，不用事先问使用者。想提前知道自己的机器是哪一种，可以跑下面的脚本：存成 session-probe.sh，运行 sh session-probe.sh。它起一个只会睡 30 秒的进程，然后分别在不带沙箱、bubblewrap 做出的独立进程空间、Codex 自己的沙箱里看三件事：看得到多少个进程，读不读得到那个进程的命令行，能不能给它发信号。不调用模型，不写文件，不联网，几秒钟结束；需要 python3。

怎么读：看 bubblewrap 那一段。它跑得起来（命令行 not readable、can signal it: no）：会话会有自己的进程空间，是隔离模式。写着 could not start 或 not installed：是提示模式。

脚本全文（18 行）
#!/bin/sh
# What can a sandboxed session see of, and do to, another process of this account?
# Calls no model, changes nothing, takes a few seconds. Needs python3; uses bwrap and codex where they are installed.
python3 -c "import time; time.sleep(30)  # probe-marker" &
M=$!
sleep 1
T='n=$(ls /proc | grep -c "^[0-9]"); echo "  processes visible: $n"; c=$(tr "\0" " " < /proc/'$M'/cmdline 2>/dev/null | cut -c1-50); echo "  command line of the other process: ${c:-not readable}"; if kill -0 '$M' 2>/dev/null; then echo "  can signal it: yes"; else echo "  can signal it: no"; fi'
echo "system: $(uname -sr)"
echo "without a sandbox:"; sh -c "$T"
if command -v bwrap >/dev/null 2>&1; then
  echo "bubblewrap with a process space of its own:"
  bwrap --ro-bind / / --dev /dev --unshare-pid --proc /proc sh -c "$T" 2>&1 || echo "  could not start"
else echo "bubblewrap: not installed"; fi
if command -v codex >/dev/null 2>&1; then
  echo "codex sandbox ($(codex --version 2>/dev/null)):"
  codex sandbox -- sh -c "$T" 2>&1 || echo "  could not start"
else echo "codex: not installed"; fi
kill "$M" 2>/dev/null
