只有方案，代码一行没改。开工要等你说“开始”。你说开始时没有提到的编号，按建议做。

一 · 没有调度器也能配对：能做。 没装调度器的机器上，pair=on 改成在本机起两个作业，不再被拒绝。两边的文件今天已经隔开（就是你说的沙箱办法）；还没隔开的是进程：一边的会话可能看到、甚至杀掉另一边正在跑的测试。所以开始前先探测一次，隔不开的机器仍然只起一个作业，并写明原因。使用者的机器属于哪一种，要他们跑一个一分钟的脚本才知道（请求 R1）。收益不大：llm-awq 那次运行按记录算，最多能省约 19.5% 的时间。细节在第 3 节，要你定 1.1–1.3。

二 · 白名单：工具里已经有一半，缺的是入口。 保留的文件今天就原样带进交付、不算进压缩比例。加选项 carry=<路径>（你要的白名单）；另外建议默认自动保留给显卡写的内核代码。代价是整个仓库能压掉的变少：llm-awq 估计从减少 29.7% 变成 17%–23%，DeepInfer 从 42.8% 变成 30%–36%（估计）。细节在第 4 节，要你定 2.1–2.4。

三 · 测不了的代码：加你要的选项。 untested=carry（保留，默认，不算进比例）、rewrite（让作者在没有测试的情况下重写）、drop（这一版不要）。工具里没有“删除”这一步，现在发生的是没有测试盯着的重写。DeepInfer 那次少的 49 个文件是什么，记录里没有，要使用者给一份文件清单（请求 R2）。细节在第 5 节，要你定 3.1–3.2。

这一页用到的几个词（展开）
  • 配对：一次提交变成两个作业，主作业冻结并验收，草稿作业同时写第一版。
  • 清单：主持会话写的一份文件，列着有哪些功能、各用哪些文件、用哪些检查。主持会话是替使用者启动并照看这次运行的那个 agent 会话；skill 是工具给主持会话的那份说明。
  • 候选：作者交上来、等着验收的一版代码（记录里的候选 4、候选 21 就是）。待选是另一回事：自动规则只列出、不保留、等你点名的代码。
  • 冻结：作业的第一个阶段，录原版的基线、验证测试、设计测试，最后封存。合同是冻结下来的那套检查和原版的基线。
  • 有效测试：把这项功能的代码弄坏以后会失败的测试。敲除是工具故意把一项功能弄坏、看测试会不会失败的那一步。
  • 门槛：工具判定一条检查算不算数的几道关：在原版上通过、够轻、重复跑结果一样、把功能弄坏后它会失败。
  • 准备步骤：主持会话写的构建命令。它要声明自己依赖哪些文件（inputs），这一页叫“声明的输入”。
  • 设备内核代码：给显卡这类加速器写的内核代码。内核 DSL：专门用来写 GPU 内核的 Python 库（比如 TileLang、Triton）；用它写的文件，对工具来说是普通的 Python 文件。
  • 提示：规则认不出、但看起来像内核的文件，工具把它点出来给主持会话看。
  • 适配器：工具用来驱动 Claude 或 Codex 会话的那一层。
  • 接缝：按原版保留的代码和重写的代码相接的地方。
  • 夹具：一个专门写的小测试项目。
  • 等轮次：原型里两个作业的检查用一把锁轮流跑；等轮次就是排队等这把锁。

1. 结论的细表

问题现在代码里实际是怎样建议怎么改试验里看到的代价和风险要你定的
一 · 没有调度器也能配对pair=on 没有可用的计算节点就被拒绝，无人值守时改成一个作业。文件隔离（你说的沙箱办法）其实已经有了；还靠节点解决的是两件事：会话能看到、能打断对方正在跑的检查进程，以及负载。没装调度器的机器上，pair=on 就在本机起两个作业。每个会话关进自己的进程空间（看不到、也碰不到别的进程）；开始前探测一次，做不到的机器就不配对；草稿作业低优先级运行、不跑 GPU 检查；因为机器太忙而没算数的检查，在结果里逐条列出。原型在我们的机器上把一次本机配对跑到了交付。运行 A：已交付，带缺口（唯一的原因是清单里原样保留的 fuzzing 功能没有有效测试）；检查 19/19；25.0 分钟；花费（美元）28.64（两个作业自己的记录，不含主持会话）。同一份清单做成一个作业，运行 B：带失败交付：行为比较 19/19 通过，安装检查 3 步过了 2 步；没过的那一步是这次运行的主持会话自己写错的命令，任何候选都过不了；检查 19/19；80.3 分钟；花费（美元）45.85（同样只算作业自己的记录）。各只有一次。按方案自己的规则，我们这台机器在正式实现之后并不会配对（第 3 节开头的表）。收益不大：llm-awq 那次运行按记录算，最多能省约 19.5% 的时间。使用者那种机器（不是容器、单卡、Codex）我们没有，没法实测。1.1–1.3
二 · 保护核心代码（白名单）白名单机制已经有（清单里的 carry：原样保留、不算进比例），但入口没有选项，无人值守时没有规则，页面不显示。入口加 carry=：你列的路径，加一条自动规则（只保留设备内核代码：含 CUDA 源码的编译扩展、用内核 DSL 写的设备内核文件），其余编译代码只列出、不保留（待你点名）；提交前就显示保留了多少。只读实测（16 个公开仓库加我们自己的两个项目）：llm-awq 保留 42.2%、DeepInfer 23.9%、detectron2 5.8%（正好是上一轮那次运行里手写的 17 个文件）；五个不该保留任何东西的项目（librosa、timm、nanoGPT、requests、click）一个文件都不保留，也没有待选。整个仓库能压掉的变少：llm-awq 估计从减少 29.7% 变成 17%–23%，DeepInfer 从 42.8% 变成 30%–36%（估计）。自动规则不认识的内核库，要靠主持会话读提示；保留的内核和重写的调用方之间只查名字和构建，不查行为。2.1–2.4
三 · 测不了的代码没有哪一步决定“测不了就删”；实际是没有检查盯着的代码由作者盲写（可能写少、写错）。上一轮的 untested=carry 只管提交前能判断的；冻结结束才发现的仍然重写。选项改成三个取值：carry 保留、rewrite 盲写、新增 drop 这一版不要；提交前多认两种情况（用例全被跳过、要的 GPU 数超过机器）；冻结结束时作业自己保留；每次交付都报告“相对原版少了什么”。我们自己的五次交付里没有发现硬件分支被删（作者是 Claude）。要分两种情况。一整项功能测不了（比如整个后端）：保留得住。有测试的函数里面给另一种硬件写的分支：按文件保留留不住，只能事后报告。在试验的三个小项目里（其中两个有这类代码），没被执行的硬件相关代码全是后一种。DeepInfer 那次去掉的到底是整块后端还是文件里的分支，记录里没有；要使用者给一个文件清单才能确定（R2）。3.1–3.2，和共用的 2.3

问题二和问题三是同一个机制：一些文件按原版保留，不算进压缩比例，每个都带一个原因，和一个“什么时候决定的”。所以它们共用一份保留清单、一张原因表、一套体积数字，还有两件共同要你定的事（0.1：保留的代码不算交付的缺口；2.3：要保留的超过一半时继续还是停下）。问题一和它们互不相干，可以分开做。

代码里记下的原因和你的描述有出入的地方，这一页两边都写。问题一：你说的沙箱办法，就是今天两个作业之间隔开文件的办法，已经在用；还依赖节点的是另外两件事（进程和负载）。问题二：llm-awq 那次运行的记录里确实有变慢，三项慢了 17.5% 到 19.6%，都在 20% 的容差之内，记录没有说是哪个文件造成的；另外，白名单内的部分今天就不算进作业的比例，缺的是入口、规则和显示。问题三：工具里没有“删除”这个动作；记录里写的是 13 项功能未验证、生产源码文件少了 49 个，没有写哪些文件没了。

到现在什么都没有实现。三个试验用的原型（本机配对、冻结结束时由作业保留、保护规则的脚本）只在本地，从没有推送过。

L3　负载：没有节点，就减轻它，并且如实报告

降低草稿作业的优先级
草稿作业的工作进程、会话、会话自己跑的命令、它的检查和构建步骤，都用较低的处理器优先级运行。改动只有一行；没有特权的进程不能把优先级再调回去。它便宜，而且管得到作者自己跑的命令；别的办法见下面的比较。在容器的处理器配额下它不起作用（我们的机器就是这样），所以在我们这里验证不了；在工作站上，它把核让给主作业的门槛。
下限和上限
机器至少 8 核、32 GB 才做本机配对；不够就是一个作业，写明原因。本机配对里同时进行的设计者会话数按核数封顶（今天最多 32 个，每项功能一个）。这几个数是方案提的，没有量过（列在第 7 节的默认设定里，不用回答，有意见再说）。
显卡
草稿作业不跑声明了 GPU 的检查。集群配对的草稿作业在没有显卡的登录机上今天就是这样；我们上一轮的 detectron2 运行里，这在导入之后多花了一次修复。〔上轮运行〕 草稿作业的 Claude 作者会话拿不到设备（沙箱不给）。Codex 作者只能通过环境变量请它不用，而它可以自己再设回去；结果里会写明这一点。
报告
草稿作业在工作的时候，门槛因为超时或不稳定而拒掉的每一条检查、每一个设计出的测试文件、每一个测速，都在结果里逐条列出，标为“在草稿作业旁边判定的”。读结果的人靠这份清单分辨：这个缺口是负载造成的，还是真的。

两个作业的检查批次轮流（一把锁）。原型里有。真实运行 A 里两边等轮次都是 0 秒（主作业 0.0，草稿作业 0.0）：这次运行里两个作业的检查批次没有撞上过，所以它说明不了这把锁的代价。评审指出：它不针对记录在案的原因（那个负载是作者的会话，锁管不到）；等待会吃掉等待的那一步自己的时限（等过轮次的设计试跑或测量，会丢掉它正在等的那条标准）；主作业是更长的那条链，却要排在草稿作业的构建后面。留作量过的备选：实际使用里如果两套测试同时跑成了内存问题，再启用。

为什么是“四分之一”

为什么是“四分之一”。 调查里的应用项目，设备源码占它所在扩展的 39% 到 100%（llm-awq 66%，detectron2 59%）。有一个项目相反：一个编译器项目有 250 万 tokens 的 C++，里面只有一个 2,789 tokens 的设备模板文件；如果规则是“扩展里有一个设备文件就整个保留”，这 250 万 tokens 会被整个保留。所以方案定为：设备源码占到扩展的四分之一才整个保留，不到就只保留设备文件本身。〔试验〕

什么时候触发

选法是什么好处代价
(a) 默认开（建议）不写 carry= 时按规则保留设备内核；你写 carry=off 才不保留。无人值守是常见的情况，那里没有人读“建议你保留”这种话。决定提到了评审之前：配对时，草稿作业不会白写后来要丢掉的文件，测试设计者也不为它们开会话。内核就是项目主体的仓库，剩下能重写的很少（pytorch_scatter 70%、diff-gaussian-rasterization 96% 被保留）；页面在提交前说出占比。
(b) 默认关只保留你列的；待选的代码照样列出来。压缩得最多。没有有效测试的内核仍然靠问题三的改动保留；有有效测试、后来才发现变慢或构建不过的，要等到 K5 的“停下来”规则触发时才发现。
(c) 只在 performance=on 时开使用者自己说了速度要紧，才保留。和你说的原因（变慢）对得上。不开性能验收的运行里，变慢从来量不到；正是这些运行没有了保护。

关于 (a) 还有两点要说在前面。第一，在使用者跑的这两个项目上，内核这些功能本来就没有有效测试，问题三的改动无论如何都会保留它们；所以在那里 (a) 不再多损失压缩比例，上面“代价的估计”那张表里的数两种改动都一样。第二，(a) 比问题三多做的，是保留那些有有效测试的设备内核；现有的证据里，没有一次运行显示这样的内核被重写之后变慢或者坏掉，所以这一部分靠的是你自己对这类代码的判断。

做法能得到什么为什么不选，或为什么放后面
只加入口选项，由使用者自己列，不要规则你要的白名单，改动最小两份记录都是无人值守，没有人会去列。DeepInfer 那次已经沿用了 40 个保留路径，五个内核不在里面。〔推断〕 方案里它是 K1，规则 K2 加在它上面。
第一版规则：项目自己的构建会编译的源码全部保留规则简单评审：它保留的是“被编译的”，不是设备代码。DeepInfer 的 33 个 C++ 文件里没有任何 CUDA 源码；tinyinfer 的 C 扩展我们重写过，没有出问题。收窄成了 K2。
扩展里只要有一个设备文件就整个保留规则更简单调查里一个编译器项目的 250 万 tokens 的 C++ 会因为一个 2,789 tokens 的模板文件被整个保留。改成了“四分之一”。
给处理器用的编译代码也默认保留更保险这类代码哪里都能跑、能测，性能验收管得住；umap 里它是 55,039 tokens。方案里是待选；要你定（2.2）。
结束时才给“下次建议保留哪些”最省事评审：钱已经花完了才说（llm-awq 是候选 13 到 21 和九次 GPU 比较；DeepInfer 是五次整模型启动）。挪到开始白花的那一刻，就是 K5。
保留的代码一律记成缺口如实：没有东西验证过重写的调用方把保留的内核用对了评审：这样所有 GPU 项目永远都是“带缺口”，这个状态就不值钱了；而今天“没有接口条目就豁免”又等于什么都没说。K3：不算缺口，单独一行，写明有没有检查依赖它；接缝另外查（K4）。
写了清单就替换掉规则写法上更短评审：使用者加一个路径，就不声不响地把规则关了。改成：清单加在规则上，只有 off 关规则。
选项叫 protect=，原因叫 performance_critical，和问题三的 untested=carry 并列名字贴近你的说法评审：同一个动作有了两个名字、三类结果。K1：一份清单。名字要你定（2.4）。

不建议做的

结论：工具里没有“测不了就删”这一步。实际发生的是：没有任何检查盯着的代码，交给作者在看不到测试的情况下重写，它可能被写少，也可能被写错，而且没有任何信号。上一轮加的 untested=carry 只管主持会话在提交前就能判断的那几种；冻结结束才发现没有有效测试的，仍然重写。方案是：把选项改成三个取值（保留、盲写、这一版不要），提交前多认两种情况，冻结结束时由作业自己保留，并且每次交付都报告“相对原版少了什么”。

DeepInfer 那次去掉的到底是哪一种情况，记录里没有：可能是一整块后端（那是一项没有有效测试的功能，这个方案管得到），也可能是有测试的文件里面、给另一种设备的分支（这个方案只能事后报告它）。请使用者给一份“交付相对原版少了哪些文件”的清单就能定下来（请求 R2）。

U4　“保留”要尽量等于“在重写的代码旁边还能用”（和 K4 共用）

借给作者读

每个候选上的静态检查

查不到的

怎么算

为什么要定

R1　探针脚本

请没有调度器、在自己机器上跑 nanolize 的使用者，在平时跑的那台机器、那个账号下，把下面的脚本存成 session-probe.sh，运行 sh session-probe.sh，把输出整段发回来（十行左右）。它起一个只会睡 30 秒的进程，然后分别在不带沙箱、bubblewrap 做出的独立进程空间（方案里两种作者的会话都要放进去）、Codex 自己的沙箱里看三件事：看得到多少个进程，读不读得到那个进程的命令行，能不能给它发信号。不调用模型，不写文件，不联网，几秒钟结束；需要 python3。

怎么读：先看 bubblewrap 那一段。写着命令行 not readable、can signal it: no：这台机器可以本机配对，两种作者都可以（改动之后 Codex 的会话也放进同样的进程空间）。写着 could not start 或 not installed（容器里常见）：这台机器给不了会话独立的进程空间，这时再看 codex sandbox 那一段：can signal it: yes，不配对；发不了信号但读得到命令行，按 1.2 的答案办。Claude 作者在这种机器上不配对。哪一段是什么就照原样发回来。输出的第一行是系统内核的版本，不想给可以删掉。

脚本全文（18 行）
#!/bin/sh
# What can a sandboxed session see of, and do to, another process of this account?
# Calls no model, changes nothing, takes a few seconds. Needs python3; uses bwrap and codex where they are installed.
python3 -c "import time; time.sleep(30)  # probe-marker" &
M=$!
sleep 1
T='n=$(ls /proc | grep -c "^[0-9]"); echo "  processes visible: $n"; c=$(tr "\0" " " < /proc/'$M'/cmdline 2>/dev/null | cut -c1-50); echo "  command line of the other process: ${c:-not readable}"; if kill -0 '$M' 2>/dev/null; then echo "  can signal it: yes"; else echo "  can signal it: no"; fi'
echo "system: $(uname -sr)"
echo "without a sandbox:"; sh -c "$T"
if command -v bwrap >/dev/null 2>&1; then
  echo "bubblewrap with a process space of its own:"
  bwrap --ro-bind / / --dev /dev --unshare-pid --proc /proc sh -c "$T" 2>&1 || echo "  could not start"
else echo "bubblewrap: not installed"; fi
if command -v codex >/dev/null 2>&1; then
  echo "codex sandbox ($(codex --version 2>/dev/null)):"
  codex sandbox -- sh -c "$T" 2>&1 || echo "  could not start"
else echo "codex: not installed"; fi
kill "$M" 2>/dev/null

  command line of the other process: python3 -c import time; time.sleep(30)  # probe-ma
  can signal it: yes
bubblewrap with a process space of its own:

  could not start
codex sandbox (codex-cli 0.166.0):
  processes visible: 96
  command line of the other process: python3 -c import time; time.sleep(30)  # probe-ma
  can signal it: no

也就是：这台机器上做不出独立的进程空间；Codex 的沙箱读得到另一个进程的命令行，但不能给它发信号。〔试验〕
