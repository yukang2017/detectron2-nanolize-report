1. GPU 环境（反馈 1，加 issue #63 第 1 条）

G1　GPU 测试没配环境，全被跳过部分属实 缺口是真的；那一次到底为什么被跳过，代码判断不了

反馈
一位使用者：主持会话只自动配好了 CPU 测试需要的环境，GPU 测试没有可用的环境，全被跳过了。
代码里
nanolize 只有一个测试环境，建一次，从来不问“GPU 测试能不能在里面跑”。具体有四处。skill 的步骤 0 让主持会话去掉“重的可选框架”。准备环境的工具不接受作为参数传进来的 pip 选项（test_environment.py，有测试钉住）；包索引只能通过启动服务时的环境变量给，或者写一个直接的 wheel 地址，而 skill 没有告诉主持会话这两条路。环境的回执里没有任何加速器信息。被跳过的用例：每条检查的结果里有跳过的个数，报告站点的检查卡片上也有，但没有合计、没有事件，也不读跳过的原因；一个检查里只有部分用例被跳过时照样算通过。如果一条检查的用例全被跳过，现有代码其实会报：它不算有效测试，交付时列为缺口。所以“全被跳过却没人说”只在 GPU 用例和别的用例混在同一条检查里时才会发生。那次运行为什么被跳过，四种原因都可能：装的是 CPU 版；检查没声明 gpus，批次没申请 GPU；检查其实在登录机器上跑；准备步骤在没有 CUDA 的机器上编的扩展。要看那次的环境锁文件、清单和基线记录才能定。
我这边的旁证
11 月 24 日连跑的八个主作业里，原版上被跳过的用例一共 27 个，分布在五个项目，记录里没有跳过的原因，也没有任何合计或提示。另外，这台机器以前在没有 GPU 的节点上建 torch 环境时，会不报错地装成 CPU 版，所有包都能导入。
小改动
skill 步骤 0：读跳过的原因并按原因报数（无人值守时记进问题清单）；说清三条出路（用户自己给解释器；用直接的 wheel 地址，或者在启动服务之前设好包索引的环境变量——运行中的主持会话改不了它；带着“这些测试没验证”继续）；给需要设备的检查写 gpus，并补一段说明这个字段；再加一句让主持会话去读下面这个事件。代码：录基线之后发一个汇总事件（多少条检查、多少个用例在原版上被跳过、什么都没验证）。这个提示不能进基线自己的问题列表，否则这次运行的交付永远到不了“成功”，只能是“带缺口交付”。
更完整的做法
记下每个被跳过用例的原因，按原因汇总到报告和运行页；准备环境的工具直接接受经校验的包索引参数（只限 https，记进回执）；回执里记加速器信息；有检查声明 gpus 时，在跑检查的节点上先探一次设备。
预期收益
主持会话在步骤 0 看到的是它自己那台机器上的跳过情况，在集群上那是登录机器，不是跑检查的节点；节点上的情况要到提交之后第一次基线录完、汇总事件出来才知道（连跑里第一次基线用了 3 到 30 分钟）。这仍然比几小时后才发现要早得多。
风险
连跑的八个项目里有五个会跳过一些用例，所以这个事件大多数运行都会出现，只能做提示、不能算缺口。跳过原因是项目自己的输出，要限长、当数据处理。声明 gpus 会让整个作业的批次都排到 GPU 节点上，所以这一条必须和 G4 的 skill 文字一起上。

2. GPU 资源（反馈 2）

G4　评测要很多张卡，申请不到部分属实 卡住的不是“写测试”这一步；可能是申请被直接拒绝，也可能是节点在忙或被配额卡住

反馈
一位使用者：他的评测要用很多张 GPU（十几张，官方配置是几十张），设计测试的阶段卡住了，因为申请不到这么多卡。
代码里
检查可以声明 gpus（0 到 64）。每个批次固定申请一个节点，GPU 数取这一批里声明最多的那个检查（check_executor.py）；作业所有者也可以给所有批次统一指定。基线是一个装着所有检查的批次，敲除矩阵和每次完整比较也是，所以清单里只要有一个检查写了 12 张卡，这些批次全都要一个 12 卡的节点；64 是字段上限，而且不能跨节点。提交之前，代码不检查这样的节点有没有，但 skill 让主持会话先看分区、再用 sbatch --test-only 带上最大的卡数问一次；只有在无人值守、而且拒绝是“别的原因”时，才把值原样提交。如果没有任何节点满足得了，调度器在提交时就会拒绝，不用排队：成对模式的主作业直接暂停；单作业在自动模式下退回本机并在事件里写明，本机没有 GPU 设备时随即因为“这些检查在这里跑不了”而暂停，本机有 GPU 设备时就在本机跑。真正要等几小时的是另一种情况：这样的节点有，但在忙，或者被配额限制卡住。那时探测之后的批次最多等 10 倍 queue_timeout（按 skill 给的 1800 秒就是 5 小时），单作业在冻结里失败，成对模式的主作业暂停，而 skill 对“排队等待”的恢复循环没有次数上限。和描述不同的地方：设计出的测试的试跑不申请 GPU，也申请不了；如果评测是作为性能声明给的，作业只用 1 张卡量，不管文档写几张。到底是哪个批次在等，要看那次作业的事件记录。调度器这部分是读代码得出的，我没有去实际提交。
小改动
skill 三句（第一批，和 G1 一起）：检查声明“这条命令能跑起来的最少卡数”，不抄项目的官方配置；一个节点装不下、或者站点上长期排不到的评测，不作为这次运行的检查（告诉用户、记进问题清单，或者开性能验收、当作声明用 1 张卡量）；调度器已经拒绝的申请不再提交。代码（第二批）：申请被拒绝或等待超时而暂停时，说明里用检查的编号点出是哪一条要了多少张卡（公开记录里有意不放检查的名字；排队的事件里现在已经有卡数）。不去解析分区的 GPU 配置：各站点写法不同，而且它本来也看不出“在忙”和“配额”。
更完整的做法
按需要分批：不要 GPU 的检查一批（不申请 GPU），要 GPU 的检查单独成批（性能测量已经是这样分的）。GPU 批次等不到卡时，这些检查记为“没跑”并写明原因，作业继续。这才是能解决“在忙、排不上”的改法。
不采纳
跨节点的检查（几十张卡分在多个节点上）不建议做：批次脚本、节点身份、工作进程都假定单节点，改动面很大。
预期收益
小改动只是让主持会话少写出排不上的申请、让暂停的原因看得懂。分批之后，CPU 检查和测试设计不再被 GPU 队列拖住。
风险
分批会改变“一次观察在同一处完成”的含义，依赖前一个检查留下的文件的检查会受影响。用少于官方的卡数跑，验证的是另一种配置，结果里要写明。

3. 没有测试的仓库（反馈 3）

T1　仓库没有测试时，要人先说一声部分属实 设计测试是自动的；卡在别的三处

反馈
一位使用者：仓库本身没有测试时，nanolize 不会自己做主补上，还是要人先说一声。
代码里
设计测试默认开着，是冻结阶段的固定步骤，对每个“没有有效测试的外部叶子”自动设计，没有任何代码在等人。没有测试的仓库会卡在三处。一、提交被拒。清单里没有 pytest 检查时，作业不知道怎么跑一个设计出的测试文件，要主持会话给出 check_validation.test_template；这个拒绝只在点提交时才出现，页面上显示的是“Invalid selection”，而提交前的回执写的是“不会拒绝提交”；也没有任何一步把 pytest 加进测试环境。二、可能没有设计目标。转换这一步通过三条路把一个能力认作“外部”：__all__；包外的文件（测试、示例、脚本）用到它；清单里手写的 python -c 检查。有测试的仓库通常走第二条，没有测试的仓库这条路基本就没了（探针里放的示例脚本还被算成了产品源码）。主持会话可以手工补，但 skill 没有要求。内部叶子不要求有测试。用一个没有 __all__ 的小包做探针：给了模板之后，就绪审计是 ready，提交检查也通过。按代码，这样的作业录完基线后会报“基线不可用”，最多带缺口交付；这是读代码得出的，没有实际提交过。三、skill 的文字。有三句话让有人值守的主持会话停下来问（原版测试命令失败就停下来问；要往仓库加检查先问用户），却没有一句讲“没有测试怎么办”。主持会话实际会怎么做，要各跑一次有人值守和无人值守才知道。
我这边的旁证
11 月 24 日的 detectron2 全功能运行里，第一次基线之后有 41 个叶子没有能用的原版测试，作业自己设计了测试（连同迁移一共处理了 47 个叶子），没有人介入。所以“不会自己补”不是普遍情况，问题集中在“完全没有测试”的仓库。
小改动
skill 加一段“没有测试的仓库”：没有测试命令不算失败；把 pytest 加进测试环境；不往仓库里写文件；给用户用得到的能力写上公开入口并设为外部；提交时给出模板（要重新开评审才生效，这一句要写明）；总结里写明所有行为检查都是作业设计的。代码两处：评审一开始就把“缺模板、提交会被拒”写进回执；选择里既没有任何检查、也没有任何外部叶子时，直接拒绝提交并说明原因（叶子都有检查的选择不受影响）。只把就绪审计改成“受阻”是不够的：对默认的作业，这个审计只是建议，受阻也能提交。回执说的是默认的选择，用户改了选择之后结论可能不同。
更完整的做法
没有 __all__ 时，自动提议公开模块的公开名字（单独标成“没有证据的提议”）；仓库没有声明测试依赖时，提议环境的工具自动加上 pytest。
预期收益
没有测试的仓库在无人值守时能一路走到提交；有人值守时第一次点提交就成功；一个没有任何检查可用的作业在提交时就被挡住，而不是几分钟后才报基线不可用。
风险
这种交付的每一条行为检查都是模型写的，对原版行为的证据有限，交付时必须写明。设计的花费和叶子数成正比（连跑的 tqdm：18 个叶子、23 个设计会话，设计者 59.63 美元、评审 32.94 美元；detectron2 全功能：47 个叶子，设计者和评审一共 80 个会话，273 美元）。自动提议公开名字会把辅助函数也纳入合同，重写会更贴近原版结构、体积更差。

P2　分段：45k 的上限和按字母序切（补丁 0003）属实 两部分都属实；补丁管的是上限，管不了排序

代码里

6. detectron2 全功能运行那一页里“需要改 nanolize 的”

来自 11 月 24 日 detectron2 全功能运行的记录页：B1、B2 要改代码，B3 是 skill 的说明和工具的实际行为对不上的 6 处。那次运行的记录不在这台机器上，所以它的数字取自那一页；机制是读代码和用小的合成探针确认的。

R1　B1：比较记录超过读取上限，运行页读不了作业属实

反馈
全功能运行的比较记录超过 32 MiB 的读取上限，运行页的数据接口返回 503，状态工具报错，轨迹页少了两次比较，还把第一次比较的数字显示成最后一次的。
代码里
比较记录写的时候不检查大小，读的时候有 32 MiB 的上限（records.py）。运行页读记录时只接住“文件不存在”，超限就让整个接口失败；轨迹记录读不了的那次比较直接当没有，于是把读得到的最后一次当成最后一次。那次运行里占地方的是每条检查的模块清单，它在比较之后没有任何代码再读，验证包本来也不带它。现有的“记录太大就放弃一部分用例证据”的机制只在单个检查报告超过两万个用例、或用例标识超过 2 MiB 时才启动。另外两点那一页没写：不用控制器的固定流程作业，自己读比较记录时也带这个上限，那种作业会直接停；每条检查每一侧、每个输出流最多 256 KiB 的捕获，也是占地方的一项。
我这边的旁证
连跑里 packaging 的比较记录是 22.3 MB、click 是 16.3 MB（上限约 33.6 MB），但它们大的原因不一样：packaging 有 82% 是用例标识，click 有 66% 是范围证据，模块清单只占 5.6% 和 10.3%。所以只处理模块清单不够。
小改动
