一、性能验收

由用户打开的一个开关。打开后，测试设计者在冻结阶段为每个节点写性能测试；每个候选在行为通过之后和原版在同一台机器上交替计时；慢得超过容差就进入性能修复，最多 2 次；仍不达标就带缺口交付。不打开时，作业的提示词、记录和报告里不出现任何与性能有关的东西。

已定的规则内容
开关由用户打开；不开就什么都不做，报告里也不提性能
优先级行为 > 性能 > 体积
谁写性能测试测试设计者；包括计时基准和数次数的测试
基准的有效性作业要验证它真能测出变慢，才算验收标准
测量原版和候选在同一节点上交替跑；内置“原版对原版”的噪声测量
容差默认允许比原版慢 20%，用户可改；噪声超过容差时自动放宽并在报告里写明
性能修复最多 2 次；告诉作者是哪个基准、慢了多少、在测什么；可以读该能力的原版文件；写出来的仍过防默写
修不好带缺口交付，不算失败
不做给作者的“性能设计事实”
在哪跑机器上有 Slurm 就用（现有的默认行为）

  • 对所有人都会变的只有：工具说明、文档、命令行帮助，以及工具契约的摘要。

2. 性能测试由谁写、写成什么样

  • 由测试设计者在冻结阶段的 design_leaf_tests 里写（leaf_test_design.py:232 起，execution.py:3560 起）。
  • 哪些节点：每个被选中的叶子节点，除了用户豁免的、graph-contract 里的内部节点、以及没有自己独占的 Python 源码的节点（后者没法注入变慢，写了也成不了验收标准，在记录里注明原因）。
  • 会话：本来就要进测试设计的节点，在同一个会话里一并要求；已有有效测试的节点，多一个只写性能文件的会话。多出来的会话数会在提交前的估算里显示。
  • 设计者可以回答“这个节点没有值得测的工作量”（比如只有常量、薄封装），写一句理由，记入记录。
  • 两种文件，都放在节点的设计测试目录下：
  • 计时基准 bench_名字.py：里面是不带参数（或只带一个 data 参数）的 bench_名字 函数，只通过公开接口跑一段工作量，不做断言。可以有配套的 setup_名字，在计时之外准备输入。由一个新的运行程序 benchmark_runner.py 计时，做法仿照现有的场景文件。
  • 计数测试 count_名字.py：普通的 pytest 文件，断言的是“做了多少工作”而不是返回值——调用了多少次传入的函数、往流里写了多少次、起了多少线程、输入翻倍时这些数怎么增长。只断言上界或增长规律，不断言偶然的精确次数、下界或耗时。
  • 每个基准函数和计数测试都要有一句话的说明：测的是什么工作、输入多大，不提测试、文件和代码。作者性能不达标时看到的就是这句话加测出来的差距，看不到文件。性能文件不写事实。
  • 设计者被要求选用户会在意的工作量：节点的主要操作，输入大到一次调用在原版上要 0.001 到 5 秒，时间花在这个节点自己的函数里，每次运行都一样（固定大小和种子，不联网、不睡眠、不依赖时钟）。
  • 回答格式只在打开时多两个字段（性能文件列表、“没有值得测的”理由）；每个节点每轮最多 3 个性能文件，每个基准文件最多 8 个函数。
  • 静态检查（运行之前）：路径和命名规则；和测试文件相同的导入、调用、名字规则；基准文件不能有测试函数、装饰器、yield、多余的参数；说明要过和场景说明同样的检查。计数文件如果会被项目自己的 pytest 配置收集进行为检查（比如配置了 python_files = *.py），拒绝。
  • 评审：性能文件通过试运行之后才送评审。评审的新规则：不因为没有事实或没有断言而否决；但说明不清楚、不走公开接口、计时部分自己造输入或睡眠、工作量不是用户会跑的（专门挑大小让差距出现或消失）、计数断言了偶然的精确次数或只有原版内部结构才能满足的上界，都否决。

3. 一个基准怎样才算验收标准

  • 现有的敲除机制在 leaf_test_validity.py：导出冻结的提交、用 _Knockout（:792 起）改写节点自己的文件、跑检查。性能这边复用它的导出部分，新增一个 _Slowdown 改写器。
  • 注入变慢：把节点独占文件里每个普通函数的函数体包起来，函数返回前空转，使“在这个节点的函数里花的时间”（含它调用的东西）变成两倍。嵌套和互相调用的节点函数只算最外层那一次，不会被重复放慢。倍数是代码里的常量，不是用户选项。异步函数和生成器不包。
  • 规则：一个计时基准，只有在它的节点被放慢到两倍时会因此不达标，才算这个节点的验收标准。这同时证明了三件事：工作量确实跑在这个节点里；跑的是树里的代码而不是别处装的副本；测量管线在这台机器的噪声之上能看见这么大的变慢。
  • 计数测试按现有设计测试的办法验证：在原版上通过、重复运行结果一致、节点被敲除时因行为失败。
  • 一轮性能文件的试运行：计数文件和这一轮的测试一起走现有的试运行。基准文件一轮发一个批次，三个分支：A 是原版，B 是原版再跑一遍（测噪声），X 是把这个节点放慢后的原版。先在 A 上校准每个函数要重复调用多少次，这个次数随后冻结，以后每次测量各分支都用同样的次数。
  • 一个基准函数的结局：在原版上就失败、单次调用太慢（超过 5 秒）、导出失败、噪声超过上限（100%）、放慢后没有超过允许差距（“没测出变慢”）、节点没有可放慢的函数——都不算验收标准，并记下原因；其余的算，并记下噪声、允许差距、放慢后的变化、调用次数和原版用时。
  • 噪声超过用户容差时不直接丢弃：把这个基准的允许差距放宽到噪声之上，并标记“已放宽”，它必须在放宽后的差距下仍能测出注入的变慢；报告里会写明。
  • 还有下一轮时，含有“不算标准”的函数的基准文件整份退回，把每个函数的原因告诉设计者（例如“这个节点放慢到两倍时这段工作量只慢了 4%，请测时间花在这个节点里的工作量”）。最后一轮里，只要有一个函数算标准就保留文件，其余函数照测照报，但永不作为标准。
  • 冻结的记录：作业目录里的 performance-contract.json，在封存契约时和设计测试的记录一起冻结。内容：设置、原版提交、测量地点、每个文件及其每个基准（编号 perf-N、说明、调用次数、原版用时、噪声、允许差距、放慢后的变化、是否算标准及原因）、每个节点有几个标准、汇总。名字、路径和说明只留在这个私有文件里，公开记录只有编号和计数。

4. 怎么测、怎么比

  • 不把性能测试做成一种新的“检查”。清单里的检查在十几处被当作行为验收标准来读（基线、比较、修复分类、义务账本、叶子有效性、验证包、报告等）；加一种 compare: time 就得在每一处排除它。改成单独的冻结记录加一种新的证据记录（种类 performance），现有读检查的地方一处都不用动。
  • 每次测量是一个批次、三个分支、各自独立导出：A 原版、B 原版再来一遍、X 候选。轮次交替进行（A B X，B X A，X A B……）。三个分支在同一个节点、同一段时间里跑，运行是串行的，不受并行度设置影响。
  • 统计方法（提议）：每轮每个函数取多次计时调用的中位数；噪声 = 各轮里 B 相对 A 的最大偏差；慢了多少 = 各轮 X/A 的中位数；允许差距 = 用户容差，噪声超过容差时放宽到噪声的 1.25 倍并标记，超过 100% 则这次测量对它“无结论”，既不算过也不算不过。
  • 不达标要确认一次：超出允许差距时，同一批次里再测一遍，两次都超才判为“变慢”。这和现在敲除要单独重跑确认一次是同一个道理。
  • 省时间：3 轮之后每个函数的比值都在允许差距一半以内的文件提前结束。
  • 候选上抛异常记为错误，超时（原版用时的三倍加十秒）记为超时，两者都算不达标。计数测试在 A 和 X 上各跑一次，按退出码和用例比较；用户的容差不适用于计数，界限就是测试自己写的。
  • 批次怎么上节点：批次协议本身不用改（一个请求本来就是“一个节点、一段时间”），只是给节点侧的函数白名单（check_worker.py:31）加一个新函数，它一次拿到原版和候选两棵树，自己跑完三个分支。时间太长时按文件拆成多个请求，每个请求各有自己的三个分支，绝不把分支拆到不同请求里。节点上没有 git 时，退回到作业进程所在的机器上测，并在记录里写明。
  • 三个分支用的都是原版里那份性能文件（像原版回放那样把它们放进每个导出），所以不管候选的树里那些路径上是什么，跑的都是同一份基准代码。每次运行都经过现有的检查运行函数，沙箱、限制、环境和运行时审计照常生效。
  • 不存储、不跨时间比较任何用时。冻结的只有基准文件、记录和每个函数的调用次数，所以不需要类似基线保护的机制。
  • 每次比较的私有记录里有：状态、容差、轮数、测量地点，每个基准的比值、慢了多少、噪声、允许差距、是否放宽、是否确认、各分支的用时和样本。controller 和日志看到的只有编号、所属能力、计数和百分比，没有文件名、函数名和说明。

5. 在作业流程里的位置

  • 每个候选的顺序：行为检查 → 行为比对 → 安装检查 → 性能比较 → 任务成本评估。
  • 新增一个证据工具 compare_performance（放在 job_tools/verify.py，安装检查之后）。它只测行为已通过的候选，条件和现有的任务成本评估完全相同；否则只记下“行为验收未完成”，不发任何批次。
  • “每次体积优化后重测”不需要新规则：证据是绑定到候选的，优化产生的新候选没有性能记录，建议里自然会把它列为缺失。
  • 三个计数器分开：行为修复（现有）、性能修复（新增的进度键，上限默认 2）、体积优化（现有，默认上限改成 2）。性能修复不占行为修复的次数。
  • 性能修复是作者的一种新模式 performance_repair，通过现有的“修复”角色进入（authoring.py:293）：候选行为已通过、而它的性能记录是不达标时，修复调用就是性能修复。不新增角色，controller 每轮读的工具参数格式不变。
  • 优先级落在决策函数里（execution.py:2900-2982 的 _repair_decision，固定流程和 controller 的建议都用它）：行为修复 → 交付修复 → 性能修复 → 体积优化。性能不达标期间不会选体积优化。
  • 回退：体积优化之后原本达标的基准不达标了，恢复到记住的那个已接受候选；性能修复把行为弄坏了，同样恢复，这次修复仍然计数。
  • “记住哪个候选”的规则在打开性能时先看性能再看体积：性能达标的候选优先于不达标的，同一类里才比体积。
  • 性能修复次数用完仍不达标时不算停止：行为是通过的，建议就是交付，交付时带上缺口。
  • 任务成本评估不会在一个即将被性能修复替换的候选上开始。
  • 固定流程的验证步骤序列在打开时多一步；controller 的建议在缺性能记录时指向这个工具；controller 的指南在打开时追加一段专门的说明。
  • 对没开的作业隐藏这个工具（提议）：给工具加一个“是否可用”的判断，没开的作业的 controller 既看不到也不能调用它。这是“关着就没有任何提示词变化”的要求。

6. 性能不达标时告诉作者什么

  • 反馈里新增一段 performance，只在打开且有测量结果时出现。每条发现包含：基准编号（perf-N）、类型、所属能力、设计者写的那一句话（测的是什么工作）、慢了百分之多少、允许百分之多少；计数测试给“超出上界”；跑不起来的给异常类型。另有剩余修复次数。
  • 绝不包含：文件路径、函数名、工作量的代码、输入、计数断言里的具体数字、原版的用时。那句话可以给作者，是因为它在文件被接受时已经过了和事实同样的检查。最多列 20 条，最慢的在前。
  • 不是修复的调用拿不到这些发现：体积优化的调用只看到状态，以及回退之后是哪些基准被弄慢了。
  • 可以读原版文件：性能修复时，按现有的“失败后可参考源码”规则，把不达标基准所属能力的原版生产文件放到参考目录里，只读，不能导入、执行或照抄。下游的发放、收回、计数都不用改。
  • 防默写照常生效，不需要改：每次保存作者的草稿都会过那一关，和调用的模式无关。
  • 新增的作者提示词条目：性能修复的阶段说明（行为已通过，把列出的工作量做到和原版一样快，可以为此增加代码，不要针对没给你看的工作量做特殊处理，不要为了速度放弃校验和其他行为）、怎么读这些发现、范围说明、参考源码的用法。
  • 另有一句（提议）加在打开了性能的作业的作者提示词里：“验证方还会拿你的实现和原版在每个能力的工作量上计时，并统计它做了多少工作；比用户允许的更慢会带着测量结果退回。你看不到这些工作量。”

7. 交付和显示

  • 缺口名字：performance_not_preserved，放在交付的缺口表里（job_tools/acceptance.py:76 起）。它永远不标为失败，所以作业状态是“完成但有缺口”，不会是失败。
  • 一个名字对应四种情况，在明细里区分：不达标（测到了变慢的基准）、无结论（噪声太大）、没有标准（设计没产出能用的基准）、没测量。摘要里的文字相应不同，例如“性能未保持：7 个基准里 2 个比允许的慢，已做 2 次性能修复（最慢的慢 43%，允许 20%）”。
  • 公开的作业结果里（只在打开时）有一段 performance：状态、容差、轮数、基准总数、算标准的个数、通过/变慢/无结论各多少、不算标准的原因分布、放宽了几个、最大慢了多少、测了几个节点、修复用了几次、回退了几次优化、在哪测的。只有数字和枚举值。
  • 报告页和进度页各加一项，只在有数据时显示；进度页多两个阶段名（性能比较、性能修复）和一个计数器。
  • 用户私有的文件：performance-contract.json 和每个候选的 performance.json（编号对应的文件、函数、说明和全部样本）。
  • 性能不进可移植验证包：在别的机器上重放用时没有意义。

内部的实施步骤

步骤内容怎么单独验证
1. 开关，以及“关着什么都不变”的证明选项经 MCP、服务端、命令行进入作业配置；两条拒绝规则。选项测试；关着时提示词摘要和基准记录不变。这一步没有任何行为变化。
2. 测量内核，不带作业基准运行程序；三个分支的测量、统计和判定；注入变慢和导出部分的重构；节点侧白名单的新函数。运行程序和测量内核的测试，用假的调度器测批次。在往下做之前，先在真实仓库和真实节点上试这一步，把统计里的常数定下来；这不花模型费用。
3. 设计和冻结设计者和评审的新提示词、回答格式和载荷；静态检查；一轮的试运行；哪些节点、多少会话；冻结的记录；封存；耗时估算。设计测试；关着时现有的设计测试不变。
4. 证据、验收、交付compare_performance 和工具的可用性判断；证据记录；缺口；结果；公开视图、报告和进度页。不带修复逻辑就能手工验证：一个作业测量后带着或不带缺口交付。
5. 修复循环决策函数、记住候选的规则、回退；修复模式和计数器；作者的反馈和参考源码；固定流程的顺序；controller 的建议、指南和上下文。作业测试和固定流程测试；建议和策略的表格测试。
6. 文档、技能、生成的文件，和一次真实运行手写的文档和两个技能；各个同步脚本；中文文案。在 tqdm 上开着性能模式真跑一次（付费，等你点头）。

风险

  • 最难的是第 2 步。统计方法既不能在共享节点上把相同的代码判为不达标，又不能放过真实的 30% 退步；注入变慢的“测得出”对只有一部分时间花在节点里的工作量也要有意义。方案里的常数（噪声放宽系数 1.25、上限 100%、提前结束的 3 轮、每个样本 0.2 秒）都是估计值，要靠真实项目上的测量来定。
  • 成本。每个已有有效测试的节点多一个设计会话；冻结时每个基准文件大约跑 4×轮数 次，每个候选的每次比较约 3×轮数 次（不达标的文件再翻倍）。20 个节点、每个两份几秒钟的基准文件，每个候选就是几十分钟。提交前的估算会显示。
  • GPU 上的工作量不在第一版的计时范围内。对异步的 GPU 调用，墙钟时间量到的只是发起调用的时间。第一版的计时针对 CPU 工作量；像 accelerate 这类项目，第一版能靠得住的是数次数的测试（搬了几次设备、精度类型对不对）。GPU 计时需要另外设计同步点，建议作为后续。
  • 注入变慢覆盖不到的节点：没有独占 Python 源码的（C 扩展、共享文件）、只有生成器或异步函数的、工作在导入时完成的。这些节点最后没有验收标准，交付时会说明有多少个。graph-contract 里的内部节点第一版也不单独写基准。
  • 计数测试的形式。按讨论做成普通的 pytest 文件，上界由设计者写。这样不达标的计数测试没有“慢了多少”，用户的容差对它不适用，上界是模型写的。
  • 固定流程里的原版分支是从作业唯一的工作树里导出的原版提交，借用了那个工作树里编译好的原生文件。如果候选的集成替换过这类文件，两个分支拿到的都是候选的。读代码没看到这种路径，实现时要专门测。
  • 一个可能已经存在的问题（没有通过运行验证）：交付后的原版回放先把两棵树复制到作业进程的临时目录，再把批次发出去；检查在计算节点上跑时，节点可能看不到那个目录。现在本机也要默认用 Slurm 了，实现时先验证这一条，属实就一并修。
  • controller 作业里的优先级是建议而不是硬性拦截，和现在“行为优先于体积”的做法一致：没有工具会拒绝一次违背建议的体积优化调用，验收和交付会如实说明没达到什么。
  • 体积优化默认值要先落地。它会改变基准记录；先单独做完并处理好基准记录，性能验收才能证明“关着时基准记录一个字节都不变”。

规模：2 个新模块（performance.py 约 650 行，benchmark_runner.py 约 170 行），改动约 30 个源文件和 4 个前端资源，手写文档和技能约 12 个文件，新增 7 个测试模块、扩展约 30 个。量级是 2,500–3,000 行源码和提示词，测试差不多同样多。

二、graphify 自动准备

新增一个工具 prepare_graphify（命令行 nanolize graphify-prepare）：把固定版本的 graphify 装进 nanolize 自己的目录，返回可执行文件路径。技能文档从“没装就跳过”改成“没装就调用它”。

工具和命令

  • MCP 工具：prepare_graphify(allow_execution=False, version=None, python=None, timeout=600)。不带仓库参数，它不读也不写目标仓库。
  • 命令行：nanolize graphify-prepare [--graphify-version V] [--python P] [--timeout S] --allow-execution [--json]。
  • 代码放在新模块 src/nanolize/graphify_tool.py，复用“准备测试环境”那套建环境、跑 pip、记录结果的函数，以及现有的文件锁。

固定版本

  • 版本号是模块里的一个常量，作为唯一来源。提议钉 0.9.111（本机实测能装、能跑、nanolize 能导入它的产物）；文档里现在写的是 0.9.100，一并改掉。
  • 交给 pip 的要求固定是 graphifyy==版本：包名是常量，版本只允许数字和点，所以带不进别的包、附加项、地址或 pip 选项。
  • 它自己的依赖（31 个包）不钉版本，由 pip 解析；装了什么记在锁文件和回执里，和“准备测试环境”一致。

装在哪

  • ~/.cache/nanolize/tools/graphify-版本/（遵循 XDG_CACHE_HOME），每个版本一个独立环境，账号下所有运行共用。和 nanolize 现有的两个用户级缓存目录是同一套规则。
  • 不放在工作目录下：那样每次运行都要联网重装，每个工作目录多 160 MB 和几千个文件。
  • 升级版本后旧目录会留下。做法：每次使用时更新目录时间，顺带清掉 30 天没用过、带 nanolize 回执的旧版本目录。

流程

  • 没有 allow_execution=True 直接拒绝。
  • 在文件锁里：已有可用的安装（回执齐全、可执行文件在、探测到的版本一致）就直接返回；否则删掉残留、建环境、pip install --only-binary :all: --retries 2 --timeout 15 graphifyy==版本、探测版本、写锁文件，最后写回执。
  • --only-binary :all: 保证 pip 不执行任何构建脚本；没有现成安装包的平台得到“不可用”而不是源码构建。
  • 短的重试和超时让离线时几秒内就失败，而不是等几分钟。

返回什么

  • 成功：状态 ready、可执行文件路径、版本、这次是否新装、目录、锁文件及其摘要、日志路径，以及运行 graphify 时必须带的两个环境变量。
  • 失败：状态 unavailable 加原因（建环境失败或超时、安装失败或超时、版本不符、可执行文件缺失、Python 版本不支持、拿不到锁、目录不可写）和日志路径。安装失败不抛异常，不会让运行停下。
  • 仍然会抛异常的只有：没授权、参数格式不对。

绝不做的事

  • 不运行 graphify 的任何命令，连 --version 都不跑；版本通过读安装信息得到。原因：子代理读了 0.9.111 的代码，除少数几个命令外，graphify 一启动就会去改写已装在各个 agent 里的 graphify 技能，除非带环境变量 GRAPHIFY_NO_AUTO_REFRESH=1。
  • 不写仓库、不写用户的 PATH 目录、不写任何 agent 的目录；不接受调用方给的包名、地址、输出目录或命令。
  • 目录落在某个 Git 仓库里时拒绝（比如 HOME 指进了仓库）。

  • 反馈（需要你定，会放宽给作者的信息通道）：对“文件不存在”这类错误，在反馈里加上相对路径，只限原版里既不是测试也不是 Python 源码的文件；同时允许事实里写测试读取的数据或配置文件的相对路径。
