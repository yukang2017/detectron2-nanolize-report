  • 配对：一次提交变成两个作业，主作业冻结并验收，草稿作业同时写第一版。本机配对：两个作业都在提交的这台机器上。
  • 主持会话：替使用者启动并照看这次运行的那个 agent 会话；skill 是工具给主持会话的那份说明。清单：主持会话写的一份文件，列着有哪些功能、各用哪些文件、用哪些检查。

  • 冻结：作业的第一个阶段，录原版的基线、验证测试、设计测试，最后封存。候选：作者交上来、等着验收的一版代码。待选是另一回事：只列出、不保留、等你点名的代码。
  • 有效测试：把这项功能的代码弄坏以后会失败的测试。敲除是工具故意把一项功能弄坏、看测试会不会失败的那一步。
  • 准备步骤：主持会话写的构建命令，它要声明自己依赖哪些文件（“声明的输入”）。
  • 设备内核代码：给显卡这类加速器写的内核代码。
  • 缺口：交付里没有被检查证明的部分。作业的三种结局：succeeded（没有缺口，推送）、completed_with_gaps（带缺口交付，不推送）、delivered_with_failures（带失败交付）。
  • 控制器流程、固定流程：作业的两种跑法。真实运行默认是控制器流程（一个 agent 决定下一步）；固定流程按写死的步骤走。范围：一次作者调用负责的一组功能。
  • 适配器：工具用来驱动 Claude 或 Codex 会话的那一层。接缝：按原版保留的代码和重写的代码相接的地方。夹具：一个专门写的小测试项目。
  • 隔离模式、提示模式：本机配对时管进程的两种办法（结果里写作 isolated、by_instruction）。
  • 独立进程空间：操作系统让一组进程只看得见自己这一组的那种隔离（看不到、也停不了别的进程）。
  • 门槛：主作业在冻结阶段拿原版做的几道检验（基线、敲除、设计测试的试跑、测速）。失去的判定：其中因为超时或结果不稳定而没能成为验收标准的。
  • 主线：控制器流程里由工具自己按固定顺序做的步骤（相对 agent 决定的那些）。台账：每项功能验证到了哪一步的那张表。就绪检查：提交之前工具对计划做的检查。

pair | carry | untested | 对照表 | 会看到什么

入口多了两个选项（carry=、untested=），pair= 的默认值变了。三个都可以不写。下面先是总表，再是每个选项的取值和例子，然后是一张“哪种代码在哪种写法下怎么处理”的表，最后是使用者会看到什么。

选项取值不写时含义
pair=on / offoff：一个作业on：两个作业。有可用的调度器：和以前一样（主作业的检查在计算节点上）。机器上没有装调度器：一定在本机配对（仍被拒绝的四种情况见下面）。
carry=auto / 路径（文件或文件夹，逗号分隔；可以和 auto 写在一起）不按清单或规则保留任何代码原样保留、不算进比例的文件。auto 是规则（只保留设备内核代码）；路径是你点名的。

和改之前的主分支比，变了三处。不写 pair 不再是“由作业决定”（以前选中的代码达到 20,000 tokens、又有计算节点能用时会自动成为两个作业），而是一个作业，集群上也是。untested=carry 改叫 untested=keep，旧写法取消（磁盘上已有的记录里的 carry 仍读作 keep）。untested 的默认从保留改成不包含。

环境的原因修过之后模块仍然导入不了；一条检查在原版上就失败，或者两次结果不一样；一条检查在原版上没有跑到任何用例；用例因为缺一个包被跳过；用例被跳过而原因读不出来；要 GPU 的批次只是没排上；本机配对里一条检查两次启动都被别的进程停掉。总是按原版保留，并提示“修好环境再跑一次”。只有写了 untested=rewrite 才重写。

没有有效测试敲除够不着的编译代码；有测试，但功能被弄坏它发现不了；设计不出测试。按 untested= 办。“敲除够不着的编译代码”由主持会话在提交前写进清单才算数；作业自己遇到做不了敲除的功能时，把它算作有效（tinyinfer 那次就是这样，第 7 节）。

问题
两个作业在同一台机器上时，一个作业的会话能看到、也能按名字停掉另一个作业正在跑的检查。
现在的代码
  • 两种办法，提交时探测一次。 isolated（隔离）：只有当这次作业用到的每一种运行器都确知能放进独立进程空间时才算。Claude Code 适配器的会话本来就在沙箱程序的进程空间里（设置里关掉沙箱的除外）；Codex 的命令要先在包装里把 Codex 自己的沙箱命令试跑成功一次（不调用模型，不花钱）。有一种说不准，整个配对就是 by_instruction（提示）。
  • 那句话两种办法下都给，给每个会话：作者、修复的作者、控制器的 agent、测试设计者、测试评审者。内容：这台机器上还有别的作业的进程；不要列出或查看不是你启动的进程（不用 ps、top、pgrep，不看别的进程号在 /proc 下面的东西）；不要按名字或模式停进程（不用 pkill、killall），只按进程号停你自己启动的；可能跑很久的命令放在 timeout 下面；你自己的命令如果转到了后台，用你自己的那个工具停掉它，或者按你启动时记下的进程号停。
  • 保险一：给会话一个停掉自己后台命令的办法。 Claude Code 的会话只要有 shell 工具，工具列表里就多一个停后台任务的工具（按已安装的命令行里实际的名字去找，找不到就和以前一样启动）。每个作业的每个会话都给，不只是本机配对。Codex 没有可以加的东西。
  • 保险二：被信号结束的运行重跑一次再算。 本机配对的作业里，一条检查、一个基准测试文件的运行、一条声明的性能命令，如果像被 TERM 或 KILL 停掉那样结束，就再启动一次，第二次的结果才算。验收方自己掐掉的（超时、输出超限、中断）不重跑；第二次只得到剩下的时间。原版和候选都这样，但每一次都留记录：那一行结果上的标记、作业目录里的 check-reruns.json、结果里的 result.pair.second_runs（按作业、按原版还是候选计数；复审查到候选的测速重跑被记到了原版一侧，已修）。

不检查“同一条标准”在修复之前也失败过。所有者允许 0 次修复的作业，第一次比较失败就会给建议。几个范围共用输入时点哪个范围的名、对没选中的功能怎么措辞，留着没改。
怎么验证的
单元测试，包括“修好之后又被后面的调用弄坏”“从没被告知过就不停”“构建后来通过了就收回”。〔单元测试、评审〕 真实运行里没有专门去触发它。

问题三 · 本机没法验证的代码

U1　三个取值，默认 drop 已做

现在的代码
清单字段 untested_capabilities 取 keep、rewrite、drop，没有写就是 drop。已有记录里的旧值 carry 读作 keep，清单本身不改写（保存下来的计划要和重新算出来的一模一样，改写会让这两天里录下的基线都读不回来）。
使用者怎么看到
总结和运行页最前面：“这一版不包含：…（本机没法验证）。要留下，写 untested=keep 或把路径写进 carry=。”
限制
untested= 只管没有有效测试的功能。自己的测试在本机跑不了、但有另一条有效检查碰到它的功能不在其内：它照常被重写，交付里记成“只验证了一部分”并写明原因，摘要里不单独点它的名字。这是最后一次真实运行查出的；主分支上也是这样，没有改（第 9 节）。把测试策略设成严格的作业，以前会因为一个没有有效测试的功能停下；现在默认会被去掉的功能不再让它停下，要从事件和结果里读。别的版本提交的作业，新代码不接着做：在它动手之前就拒绝，并说把这次选择重新提交一遍。这是复审之后改的（第 5 节）：原先，一个在封存之前停下的旧作业会被新代码按新的默认一路做到交付才被拒绝。旧的作业目录仍然可以用来读它的计划、导出验证包、单独做验证。
怎么验证的
单元测试。〔单元测试〕 真实运行：twoback-drop，已交付，没有缺口（succeeded）；默认的 drop 什么都没去掉

U2　三组原因，处处分开；提交之前多认几种情况 已做，范围比方案宽

现在的代码
  • 一张表管所有原因：每个原因属于哪一组、这样保留的功能还设计不设计测试。各个包都从这张表读。分组见第 2 节。
  • 比方案宽的地方，都往“保留”那边偏。 用例因为缺一个包被跳过、被跳过却读不出原因、要 GPU 的批次只是没排上：都算环境的原因，保留并提示。声明了 GPU、也拿到了 GPU、却还是因为设备跳过了每个用例：算“原因读不出”（环境用不了这块设备，比如装的是 CPU 版的框架），也保留。只有一项功能的每条检查都指向硬件，才算硬件的原因。理由：默认 drop 会去掉代码，所以每一处拿不准都判给保留。
  • 提交之前。 试跑的总结多了四张清单：用例在这里全部被跳过的功能、要的 GPU 比哪里都多的功能、因为环境被跳过的功能、试跑只抽了一部分检查所以说不准的功能。只有试跑把一项功能的每条检查都试过、每条都这么说，才点它的名。
  • 代码不替主持会话在提交之前套用 untested=：那是 skill 里给主持会话的规则（drop：不选它，并在清单的 dropped_capabilities 里写明原因；keep：写进保留；rewrite：照选）。评审页打开时这些功能没有勾选；服务端的两个预设也把它们留在外面；清单说不包含、这次选择却选了的，在回执和作业的第一批事件里点出来。
限制
提交之前这一步靠主持会话照 skill 做。第一次本机配对的运行查出一个和这一步有关的缺陷：试跑把“用例因为缺包被整个跳过”的功能放进了硬件的那张清单，照那张清单默认会把它去掉；那次的主持会话按 skill 的定义改判成环境的原因并保留了它。〔真实运行〕 修了没有：已修，07:30 合并：用例被跳过的原因里提到包、模块、库、SDK 或驱动的，算环境的原因，即使它同时点了加速器的名。在这之前启动的三次运行（twoback-drop-static、twoback-keep、twoback-carry-auto）的记录里仍是旧的归类（硬件）。 一条通过了、但两次输出不一样的检查，原因还是记成“原版上失败”（标签不对，方向是保留）。设计者从没试过的功能，会被记成“设计不出测试”。
怎么验证的
单元测试：21 种情形各自落在哪个原因、哪一组。〔单元测试〕 评审提的三条重要意见（两种环境的原因被当成硬件而去掉；试跑从一条抽样的检查就说“每条都这样”；清单说不包含、却仍被选中时没有任何提示）都已修。〔评审〕 主持会话在真实运行里提交前做了什么，见 twoback-drop 的经过。

U3　冻结结束时，作业自己按 untested= 处理 已做

现在的代码
  • 封存之前做一次（作业工具 settle_untested）。对象：选中的、有文件的、不是整项保留的、按基线没有有效测试或根本没有检查的功能。
  • 环境的原因：保留并提示（除非 rewrite）。keep：全部保留。drop：离开这次选择，除非留下的东西还要用它（U4）。rewrite：什么都不变。
  • 然后重新计划，强制再录一次基线，封存。作业把决定记在自己的记录里（列入封存的文件），评审过的清单不改。
  • 配对时，草稿作业为被保留或被去掉的功能写的文件不导入。性能合同里属于被去掉功能的基准和声明也拿掉。
  • 什么都不剩（没有一项选中的功能还有文件留给作者）：作业停下，给三条出路（修环境、选别的功能、用 untested=rewrite）。超过一半：继续，第一条事件先说“超过选中源码的一半（N%）”。
  • 只做一次：第二次基线之后仍然没有有效测试的，照旧重写并标出来。一项功能如果只是因为基线的时间用完、敲除没跑到，不动它：时间限制不算“本机没法验证”。
使用者怎么看到
事件：untested_capabilities_dropped、untested_capabilities_carried_in_freeze、untested_environment_advice，各自按原因的组列出功能；配对时还有 draft_files_left_out。结果里每项不包含的功能写着是提交前去掉的还是冻结结束时去掉的。
限制
多录一次基线，和作业上一次录的一样长。第二次基线可能和第一次不一样（要 GPU 的批次这次没排上、一条不稳定的检查），那时有的功能会从“有有效测试”变成“重写并标出”。“什么都不剩”是一个失败的作业，不是暂停。保留的文件一共不能超过 2,000 个，超出的功能仍由作者写。
怎么验证的
单元测试，包括两种流程下的整个作业走完冻结、导入和交付。〔单元测试〕 评审找到的阻断问题（去掉一个和留下的功能共用检查的功能，会让作业停下）和“中途被打断的作业再也恢复不了”都已修。〔评审〕 真实运行：twoback-drop，已交付，没有缺口（succeeded）；默认的 drop 什么都没去掉

U4　drop 不去掉留下的东西还要用的；接缝的检查和 K4 共用 已做，比方案多一层

现在的代码
  • 一项功能只有在留下的东西都不需要它时才去掉。“需要”有三样：留下的功能声明依赖它，或是它的子功能；留下的文件导入它的文件（包括包的每一级 __init__.py，和被当作模块导入的编译源文件）；留下的检查点了它的名、在录基线时加载过它的模块、或者检查的测试文件导入它。最后一样是评审之后加的，方案里没有。
  • 判断不了的，保留；结果里把它列在“说不准”下面，不冒充“要用”。去掉它会让计划通不过就绪检查的，不保存这个计划，改成全部保留。录完基线发现留下的检查因为少了它而失败的，把它拿回来保留，再录一次。
  • 这样留下的功能按原版保留、不重写，原因记作“留下的代码还要用”，同时记着它本来的起因。必选的功能、有文件在 carry= 下面的功能，永远不去掉。

限制
所有者的安装检查、交付检查和准备步骤需要什么，没有读（它们是命令，基线里没有它们加载了什么的记录）。靠运行时拼出来的名字加载的代码不算“要用”：这就是第 2 节方框里的那个后果。
怎么验证的

2名字检查：重写后的模块里只要任何地方出现八个字样之一（注释里提到 importlib、一个类里用了 __dict__ 都算），这个模块的名字就全算“说不准”；真的缺了也不报，检查的状态还写“通过”。接缝的修复把“说不准”放得太宽改成读语法结构：只有会在导入时给这个模块造出名字的写法才算；注释、文档字符串、类里的 __dict__、对别的对象的 setattr 都不算。有名字没判定出来时，状态是“说不准”，页面不再把它显示成通过。缺口的规则没变：只为确定缺的名字。〔报告〕
3本机配对里，原版的一条检查两次启动都被信号停掉时，冻结结束时的处理把它读成“原版上就失败”：这项功能整个作业都按原版保留，提示“修好环境”。方向是保留，但原因说错了。本机配对的重跑，碰上“没法验证的代码”的处理原因表里多了一个原因“检查被停掉”（环境的原因，保留），提示也换了：一个进程两次停掉了这条检查，这对原版什么都说明不了，再跑一次。被停两次的运行在范围基线里不算结论：不会因为它去保留、暂停或放过什么。
4候选的基准运行和性能命令的重跑，被记到原版那一侧：结果里候选一侧永远是 0，而 skill 要主持会话逐条告诉使用者的正是候选一侧。本机配对的修复重跑记在它所在的那棵树的一侧。第一版修法是给测速的函数加一个参数；最后的做法是把这一侧记在检查自己身上，函数的参数恢复原样。〔报告〕
5作业自己保留的、和重写的代码共用文件的功能：它的文件的原因被记成“单独列出的文件”，报告说“没有因为缺测试而保留的”。保留规则的“每个文件的原因”，碰上“没法验证的代码”的处理作业在冻结结束时保留文件，会把自己的原因逐个文件写进它做计划用的清单；这样的文件在报告和页面上按作业的原因分组，不再算成“你点名的”。〔报告〕
