一、校验方自己的 Git 命令

问题。检查在沙箱里运行，沙箱只让被测代码写它所在的那棵树。检查结束后，校验方自己（在沙箱外）会在这棵树上运行 Git：读取状态、提交候选、回退被拒绝的修改。Git 靠树里的 .git 找到仓库，并且先读这个仓库的设置；设置里可以写要启动的程序（过滤器、签名程序、远端的传输命令），也可以把工作目录指到别处。被测代码能改写 .git，所以它能让校验方的下一条 Git 命令在沙箱外替它运行程序。我用一个探针确认了这一点：把工作树的 .git 换成自带设置的仓库后，原来的 git add 会执行其中的过滤器。

做法 1从仓库那一侧找 Git 目录

作业的工作树、封存的原版树、修复用的树，都是主人检出的那个仓库的附属工作树。仓库自己记着每个附属工作树的位置，这份记录被测代码写不到。现在所有 Git 调用都经过同一个入口：先从仓库的记录里找到这棵树对应的 Git 目录，再把它和工作目录明确传给 Git。树里的 .git 写了什么，不再读取。

找仓库不靠调用方登记：作业目录里有作业自己的记录（写明作业目录和主人的检出），入口按位置读它。这样从哪个入口进来（工作进程、作业工具、重置、调试、修复、报告）都一样，不会因为漏登记而留下缺口。

做法 2设计测试用的树：仓库放在树的旁边

原来这棵树自带仓库。现在仓库放在它旁边（<树>.git），树是它的附属工作树，于是适用做法 1。沙箱里的检查仍然能读到这个仓库（里面只有这棵树本来就有的内容）。

做法 3三处必须把仓库留在树里的地方，改为不再运行 Git

  • 安装检查的构建副本（用户报告里点名的 git rev-parse）：构建工具要读版本信息，仓库只能在副本里。步骤运行前后各把 HEAD 当普通文件读一次来比较。
  • 敲除测试用的导出树：提交时记下它跟踪了哪些文件，之后需要这份清单时查记录。
  • 作者的工作区：检查“作者有没有自己提交、加远端、链接别的仓库”原来用四条 Git 命令，现在直接读仓库目录里的文件。

比原来更严的两点（有意为之）。构建步骤把副本切到同一提交上的另一个分支，现在算“改动了副本”（原来只有换提交才算）。作者把对象打包（git gc）会被当作“提交过”一样拒绝本次尝试并重建仓库，因为打包后不读包就分不清里面有没有提交。正常的构建和作者都不会做这两件事。

没有改的。主人自己的检出照旧让 Git 自己找仓库：那里只运行原版代码。被改写的 .git 不做修复（Git 从不把它列入文件，提交和状态不受影响）。

二、七项一致性改进

来源是行为一致性评审页面。第七项实现后已经回退，原因见表后的说明；下表保留它当时的做法作为记录。它的判断是：转换清单时，只要一个测试文件里有一个测试用了内部名字，整条检查就被剔除，文件里其余只用公开接口的测试跟着离开验收，于是交付的代码在这些行为上没有人检查。七项改进分三层：先让缺口看得见（1、2），再把公开测试找回并交接剩余部分（3、4），最后控制修复成本并覆盖原测试没覆盖的行为（5、6、7）。

#改进现在的行为已知限制
1被剔除的检查要留下记录转换把每条离开验收的检查写进清单，带着它的测试函数和原因；记录随清单进入计划。审核页在提交前显示数量。作业里还有测试没被验证时，以“完成但有缺口”结束，并写明数量；全部落实后回到“成功”。交付报告按能力分列。数量是静态数出来的测试函数个数，不是运行时的用例数。
2交付后回放被剔除的测试交付决定之后，把仍然离开验收的原版测试文件在原版和交付代码上各跑一遍：每个文件一个进程、各自限时。只报告，不改变状态，也不交给任何 agent。可以关掉。文件顶部把占位对象当基类或遍历时，这个文件收集不了，记为未运行。非 pytest 的命令整条回放，没有逐个测试的结果。
3按测试函数取舍，找回公开测试转换把被剔除的检查按测试函数拆开，只用公开接口的测试写进原测试文件旁边的新文件，作为契约检查继续参与验收。新文件要先提交到仓库；无人值守时由启动的 agent 用报告给出的那一条命令提交。测试共用的辅助模块里只要有一处私有导入，导入它的测试全部留给第 4 项（bidict 有 55 个这样的测试）。
4找不回的测试交给测试设计留下的测试成为设计者的迁移任务（位置、原因、涉及的名字）。每个测试最后是四种状态之一：仍在验收、已迁移、已排除（附理由）、未验证。未验证的让第 1 项的缺口保持打开。一个叶子一次最多交 40 个；手动运行设计命令不做迁移。
5事实绑定到测试，失败反馈给出比较内容每条事实写明它陈述的是哪些测试；检查失败时指向对应的事实。主人允许修复读原版时，修复还会拿到失败断言比较的那一行（最多五个用例，有长度上限，路径和地址被遮住），并能借到能力目录下的资源文件。每次给出都有记录。没有逐用例报告的检查拿不到断言内容。候选代码能通过返回值往下一次反馈里放几百个字符。
6差分场景设计者除了写断言式测试，还可以写场景文件：只给输入。校验方在原版上录下返回值、输出、警告和异常，在候选上逐个用例比较。场景也要通过“敲掉对应功能后会变”的检验。默认只在本来就要运行的设计会话里提供；设成 all 时为每个叶子都设计。上限：每个叶子每轮最多 8 个文件（测试和场景合计），一个场景文件最多 100 个场景函数（一个叶子一轮最多 800 个用例），每 8 个被接受的文件一个复核会话。项目只能通过 pytest 自己的路径设置导入时，场景运行不了。便携验证包把一个场景当一条输出比较。

过程中自己做的决定

用户要求需要决策时自己决定并记录。完整记录在工作目录里（负责人 30 多条，四位协作者各一份）。影响行为的几条：

  • 找回的测试文件由转换写进主人的仓库，并提交到当前分支。作业只从提交运行，计划和就绪检查都要求文件已经存在。这是调用授权之外唯一一处写主人仓库的地方：有人值守时先说明、提交前询问；无人值守时直接做，并在总结里写明提交。没有分支被检出时不找回。
  • 场景文件默认只在本来就要运行的设计会话里提供。评审页面说这是没试过的方向，现有作业不应默认为它多花模型调用。
  • 结果分支不改成中性名字。只有作者是 Claude Code 时换前缀，Codex 用户看到的名字不变。
  • 导入图的绑定按内容判断。这改变了一条已有规则（原来任何新提交都让图过期，空提交也算）。
  • 主人不允许修复读原版时，doctest 示例缺失算缺口，不算失败。否则每个候选都会失败，并安排注定修不好的付费修复。
  • 没给 CI 加沙箱程序（上一轮用户的决定，继续有效）。
  • 任务评估在默认设置下超时，没有改默认值。推理强度的默认值和 900 秒的时限都是主人之前定的；我只在脚手架的设置里为两次运行调低了推理强度，并在页面上写明。
  • 场景文件的函数上限定为 100。最初合入的是 40，随后结束的真实作业里有 51 和 60 个函数的文件，所以改了。
  • 第七项改进整项回退（主人的决定，依据见第二节的说明）。体积标记只出现在报告里、不影响作者，本可以单独保留；主人选择一起回退。
  • 最后加跑一次 python-dotenv。前两个作业都不在当时的最新提交上，也都不是默认配置；这一次在 cdfb5cd 上用默认配置和旧代码那次的推理强度运行，用来直接对比。

删除的东西。没有删除仓库里原有的功能。没带进来的只有前端分支的开发笔记。工作过程中删除的是自己建的临时目录：两次流程对照用的检出、评审者各自的检出。

运行中发现的问题

发现原因处理
tomli 第一次运行：测试设计中途停止，场景文件全部丢失设计阶段试运行新文件时只规划这些文件的检查，但清单里“被剔除检查”的记录还在，记录里找回的测试指向一条试运行清单里没有的检查，规划被拒绝。只有“转换找回了测试”加“随后设计测试”才会出现，单元测试没有覆盖这个组合。已修复并加了测试；第二次运行在同一位置通过（13 个场景文件、283 个用例）。同类问题在控制者选用较少检查的契约时也会出现，一并修了。设计停止的原因现在会写进作业的私有记录（原来事件里只有错误类型）。
任务评估者在两个项目上四次超时（上限 900 秒；11 月 14 日旧代码上同一会话是 143 和 186 秒）有两个原因。第一个是这次改动带来的：评估者的工作区是原版的副本，里面也有设计阶段写出的文件；场景文件有几十个时，它去读这些文件、给它们写运行器并运行。第二个在这次改动之前就有：适配器默认的推理强度是最高一档，而任务评估的每个会话限时 900 秒；11 月 14 日的两次运行是在这个默认值出现之前做的。第一个原因：在评估者的说明里写明这些文件是校验方自己的检查、不属于项目、不要读也不要运行。tomli 最后一次运行里，评估者列目录时就排除了这个目录，只读了项目自己的源码和测试，说明这句话起了作用。但它仍然超时：它给任务写了验收脚本，并拿原版、两个正确补丁和几个错误补丁逐一试过，写任务说明时时间到了。第二个原因没有改代码（两个数字都是主人之前定的，改哪一个应由主人决定）。为了看到这个作业的后半段，我在脚手架的适配器设置里把任务评估这一类会话的推理强度改回命令行自己的默认值再恢复作业：评估者 177 秒完成（1.35 美元），随后三组求解和评分各约一分钟。作者和控制者保持最高一档。
设计阶段的事件写着“接受 0 个设计的测试……12 份提案被拒”，而实际接受了 38 个场景文件被拒的场景文件和被拒的测试算在同一个数字里，读起来像是测试全被拒了。两类分开计数、各说一句。同一次提交给场景文件加了函数数量的上限，起初定为 40：我合并前只对照了当时已有的两个作业（最大的文件 36 个函数）。随后结束的 tomli 作业里有两个被接受的文件分别是 51 和 60 个函数，按 40 会整个文件被拒、而且这个叶子不会再被询问。上限改为 100，并加了一条“60 个函数的文件不因数量被拒”的测试。
转换报告里的提交命令在没有 Git 身份的账号上失败新克隆的仓库和这台机器的账号都没有配置身份，提交时 Git 报错，文件已经被暂存。转换先问 Git 能不能给出身份；不能时命令里带上 nanolize 自己的身份，报告写明这次提交算谁的。
适配器设置必须同时暴露 nanolize 自己的运行环境作者的提示里用到那个解释器来数 token，而它在被隐藏的目录下。是我这边脚手架的设置问题，nanolize 的试运行给出了明确的错误信息。
tomli 的维护脚本（基准、模糊测试、性能分析）没有映射到任何能力，提交时被拒绝清单只映射了包本身的源码。拒绝发生在提交时，而不是规划或启动审核时。在清单里加了一个可选能力并在提交时排除。拒绝的时机是原有行为，没有改。

没做的、没验证的、留给主人决定的

  • 第七项回退之后没有用真实模型运行。三个跑完的作业都在回退之前的提交上；回退后的验证只有测试和拉取请求的检查。回退把作者策略恢复成旧代码的文字，其余六项改进和问题修复没有动。
  • 适配器默认的推理强度只在较早的提交上跑过。用默认强度的两个作业在 f832e3f 和 dbc4df1 上；cdfb5cd 上的那次用的是命令行默认值。
  • 迁移任务没有用真实模型运行。python-dotenv 和 tomli 都没有需要迁移的测试；有迁移任务的项目运行一次要几个小时。它由带脚本化设计者的作业测试覆盖。
  • 公开文档字符串在重写后大多丢失，这个问题回到了原样。第七项原本想解决它（旧代码交付的 32 个公开名字里只有 7 个有文档字符串），回退后又没有任何规则要求保留。如果以后要重新做，这次的经验是：只针对公开名字、要求和原版一致而不是“用自己的话写”（否则 click 这类把文档字符串当帮助文本的项目会被改掉输出），并且不要和“清晰优先于体积”捆在一起。
  • 花费。在命令行默认的推理强度和默认配置下，python-dotenv 整个作业 29 美元（旧代码 28 美元），其中事实阶段 11.5 美元（旧代码 10 美元）。在适配器默认的最高推理强度下，同一项目的事实阶段约 57 美元；场景设成 all 另加约 55 美元。tomli 上（最高推理强度）事实阶段约 7 美元、场景约 20 美元。端到端验证一共花了约 255 美元（适配器报告的数字，超时的会话没有计价）：python-dotenv 两次约 133 和 29 美元，tomli 四次合计约 92 美元。
  • 仓库里的固定流程基准文件没有重新录制（见验证一节）。
  • 沙箱相关的测试在 CI 上被跳过（CI 没有沙箱程序；上一轮用户决定不加）。它们在这台机器上运行并通过。
  • 各项改进的已知限制：被剔除检查的记录在约 7,600 个测试函数时会超过大小上限（实验里最大的项目约 1,100 个）；共用辅助模块里的一处私有导入会拦住所有导入它的测试；没有分支被检出、又有文件要写时一个测试也不找回；回放按整条命令去重，两条检查用不同选项运行同一文件时会跑两次；审核页的数字按转换时的决定统计，不随作业的最终状态变化；主人不允许读原版时，对“某个文件为它建了 doctest 套件”的判断是按整棵树而不是按检查做的；文档字符串所在文件属于被排除的能力时，修复借不到它，这类用例仍然算失败；项目只能靠 pytest 自己的路径设置导入时不能用场景；便携验证包把一个场景当一条输出比较。
  • 任务评估在默认设置下会超时。适配器默认的推理强度（最高一档）和任务评估每个会话 900 秒的上限放在一起，评估者在 python-dotenv 和 tomli 上都做不完；第一次超时让整个作业失败（恢复后第二次超时才记为“未验证”继续），而作业对外的状态只写“执行流程没能完成”，原因要到作业的私有记录里找。同样的上限也让 tomli 的一个事实撰写会话超时（走到这一步的三次运行里每次都有 1 个，结果是 2 个测试没有事实覆盖）。这两个数字都不是这次改的，我没有动；现在可用的办法是在适配器设置里给这类会话单独设推理强度，或者在任务评估设置里调高时限。
  • 只由文档示例组成的 unittest 检查，在 Python 3.12 及以上的行为不同。主人不允许修复读原版时，这样的检查在没有那些文档字符串的候选上一个测试也不运行；从 Python 3.12 起 unittest 对这种运行返回 5，于是检查被记为退步，并安排一次作者做不到的修复；在 Python 3.11 上它是一个交付缺口。检查里只要有一个自己的测试就不受影响。这是拉取请求的检查在 Python 3.13 上暴露的；测试已经改成在两个版本上都成立，产品这一侧没有改（要在比较的第一道判断里为一种运行器的退出码开例外，另外两个模块也各自读这个状态）。
  • 评审里决定不处理的：作者命令通过 conda run 等启动时认不出是 Claude Code 适配器，分支仍叫 codex/…；两个不在默认流程上的工具的回答里仍带整份清单；在这次改动之前导入过 Graphify 图、且项目有被收集的 notebook 的清单需要重新导入。
  • 上一轮安全修复留下的事项没有变化：容器主机上的一项加固按用户的决定搁置；报告伪造在同一进程内仍然可能；持有页面链接的人等同于主人。
