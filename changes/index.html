决定 1：错误类型、候选自己的位置、缺失的模块名都可以给作者。异常消息的原文仍然不给。

1.1合入运行时失败摘要，两种策略都开启

第一批已有原型动契约
改什么
对“原版通过、现在不通过”的用例，每条错误给作者三样：type（内置异常名，其余一律记为 Exception）、origin（谁抛的：候选、候选调用的库、验证方、其他）、where（候选自己文件里最内层的一帧，格式是“路径:行 in 函数”）。每个检查最多 5 条，其余只计数。原型现在只对 controller 作业生效，把这个限制去掉，固定策略也给。
改哪里
新增 failure_digest.py；接入点是 leaf_test_validity.parse_junit、verification._run_check、repair_policy.classify_verification_failures、rewrite.safe_feedback、job_tools/authoring.py、controller_memory.py
完成标准
原型自带的 13 个测试通过；固定策略的反馈里出现 errors 字段并有测试；候选抛出的异常消息、测试文件里的任何文字都不出现在作者反馈里（已有测试，保留）。
说明

1.2运行时摘要里给出缺失的模块名和名字

第一批新增动契约
改什么
错误类型是 ImportError 或 ModuleNotFoundError 时，多给一个 missing 字段：缺的模块名，或“模块.名字”。只接受点分标识符，最长 200 字符，并且必须出现在这个检查的静态 import 清单里；不满足就不给这个字段。
改哪里
failure_digest.describe；静态 import 清单来自 check_scope._imports（check_scope.py:150）
完成标准
测试：测试文件 from pkg.x import Y 而候选没有 pkg.x 时，作者拿到 "missing": "pkg.x"；候选自己抛一个带任意文字的 ImportError 时，拿不到 missing。
说明
限定在静态 import 清单里，是因为候选的代码就运行在检查进程里。这样这个字段只能说出测试本来就要 import 的名字，带不出别的内容。

1.3集成时静态检查缺失的模块和名字

第一批新增动契约
改什么
候选集成之后、执行任何检查之前，把每个保留检查静态 import 的项目内模块和名字，与候选树实际提供的做比对。缺的作为候选缺陷 missing_import 反馈给作者，列出模块名、名字、涉及的检查别名和功能。controller 据此可以直接安排修复，不用先跑一轮全量对比。
改哪里
check_scope.inspect_check_scope（已有每个检查的静态 import 证据）；缺陷通道沿用 import_shadowing：repair_policy.py:28 的 CANDIDATE_DEFECT_ISSUES、capability_verification.py:665,705；集成入口 rewrite.integrate
完成标准
测试：缺一个模块的候选，在一次检查都没执行的情况下得到 missing_import 反馈。只报两种确定的情况：模块文件不存在；模块存在、顶层没有这个名字、且模块里没有 import * 和 __getattr__。条件 import 和动态 import 不报。
说明
三次 detectron2 运行里，近三分之二的错误是这一类。

4 · 检查在计算节点上跑

决定 4：先看这台服务器有没有计算节点（例如 Slurm），有就用；没有再在本地跑。

4.1把“在哪里执行检查”抽成一层，默认自动选择

第二批新增
改什么
新增一个检查执行器，两种实现：本地、Slurm。配置项 check_executor 默认 auto，owner 可以显式指定种类和资源（分区、账户、CPU、内存、GPU、时长）。采基线、重复基线、敲除、全量对比、owner 的交付检查都走这一层。作业的主进程不动：controller 和作者调用留在提交作业的那台机器上。
改哪里
新模块（例如 check_executor.py）；调用方是 verification._run_checks（verification.py:853）和 leaf_test_validity.py 里执行检查的地方
完成标准
配置为本地时，结果和现在逐项相同。
说明
现有的 execution_backend 选项是把整个作业提交成一个 Slurm 作业，保留不动。不采用它来解决这个问题，原因有两个：作者调用要访问模型服务，计算节点常常没有外网；节点会在作者会话期间空占。

4.2自动探测的规则

第二批新增
改什么

  1. sbatch、srun、squeue、scancel、sinfo 都能找到。
  2. sinfo 能列出当前用户可用、状态正常的分区。
  3. 作业的状态目录和两个工作树在计算节点上可见。用一个探针作业验证：在节点上读一个刚写下的文件。
  4. 探针作业在排队时限内（默认 120 秒）跑起来。
改哪里
复用 execution_backends.SlurmBackend.probe（execution_backends.py:327，已经检查命令是否存在），加上分区和共享目录的探测
完成标准

4.4节点内并行：各用一份副本，并且只认通过

第二批新增
改什么
  1. 采基线时，每个检查多做一次“在副本里的对照运行”。结果和工作树里一致的才标为可并行，标记进基线记录。
  2. 执行时，可并行的检查在各自的私有副本里并发跑，通过的直接记为通过。
  3. 没通过的，一律回到封存的工作树上单独重跑一次，以这次的结果为准。
  4. 副本建在节点的本地盘上。用写时复制的克隆，文件系统不支持就普通拷贝；不用硬链接。
  5. 结束进程按会话或进程组，然后再删副本。
改哪里
执行器内部；可并行标记写进基线记录（job_tools/freeze.py、baseline_guard.py）；路径检查用当前分支新加的 records.redirected
完成标准
测试：两个会互相干扰的检查并发执行时，不产生任何失败记录；一个在副本里结果不同的检查不会被标为可并行。
说明
实测过：8 个并发共用一棵树，160 个检查里 100 个失败；各用一份副本则 159 个与串行一致。并行失败不能直接记账，是因为同一份代码一次通过一次失败会成为清不掉的验收缺口。本地执行器也用同一套规则。
