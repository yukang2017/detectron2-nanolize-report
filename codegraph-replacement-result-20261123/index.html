1. 先说结论

  • 四期都实现了，在分支 claude/codegraph-structure-index、合并请求 #57 里。我没有合并，合并由你定。最终的头（3fab8e05）在 CI 上 13 项全部通过。
  • Graphify 换成了钉死版本的 codegraph 1.6.4。安装、建索引都由 nanolize 自己做（下载一个包、核对校验值、解压；在本地盘的副本上、在沙箱里建索引），主持会话不再敲命令。入口选项是 index=on|off|require，默认 on。
  • 图现在真的被用上了。清单写好之后和索引“绑定”，功能之间的事实关系进清单；规划、选择页面、作业都读它。
  • 范围的问题现在在提交之前暴露。主持会话写出第一版清单后马上做范围核对，据此改清单；有“保留的文件用到只属于被去掉功能的文件”这类问题时，提交会被拦住（开关已打开）。
  • 真到了作业里才暴露的范围问题，不再让作者白修。作业冻结时在“去掉被去掉功能的原版”上跑一遍保留的检查，在那里就失败的记为范围的缺口；一批里新发现超过 5 条就停下等你。

2. 要解决的问题

这次改动针对的是修改方案里整理出来的四个问题。前两个是 Graphify 本身带来的，后两个是 detectron2 那次实验暴露的（两回提交之后被取消、第三回带着失败交付；第二回取消和第三回的失败都出在“功能范围怎么划”上，第一回是清单里检查和功能的对应没写对）。

问题当时的表现现在怎么解决哪一期
图建出来了，但没有被用上一行入口的运行里，主持会话让 Graphify 建图并导入，然后另写一份功能清单，清单不带任何图信息。关系图视图和依赖把关都没有发生主持会话写完清单后多一步“绑定”：nanolize 把清单和结构索引对上，把功能之间的事实关系（类型和处数）写进清单。之后的规划、页面、作业都读这份带关系的清单第一期
安装和运行不在 nanolize 手里建图那条命令由主持会话照文档在自己的终端里敲，没有沙箱也没有时限；机器上已有同名命令时直接用，不管版本换成钉死版本的 codegraph 1.6.4。下载一个压缩包、核对校验值、解压，不运行任何安装程序；建索引是 nanolize 自己的一个工具，在本地盘的副本上、在沙箱里做，主持会话不再敲任何命令第一期
范围划错了，要到作业跑起来才知道detectron2 只保留核心功能时：保留的代码用到了被去掉的可视化模块；被去掉的数据集模块在被导入时做了注册；49 个配置文件没有任何途径进入新代码。这些都是提交之后、花了作者的钱才暴露的提交之前做一次“范围核对”：保留的部分还向被去掉的部分要什么，逐条列出来。主持会话写出第一版清单之后马上核对一次，据此改清单；正式规划后再核对一次；有“保留的文件用到只属于被去掉功能的文件”这类问题时，不改清单也不写理由就不让提交第二期
范围造成的失败被当成作者的错，反复返修一个检查如果离开被去掉的功能就一定过不了，作者怎么改都没用；旧流程会一轮轮地让作者修，直到把被去掉的功能写回来或者把预算花完作业冻结时多做一份“范围基线”：把原版里被去掉的部分拿掉再跑一遍保留的检查。在那里就失败的检查记为范围的缺口，不再派给作者（前提是那棵树里保留的文件都还能导入）；一批里新发现超过 5 条，这个作业在调用自己的作者之前停下第三期

第四期不针对某个单独的问题，而是把索引里的事实进一步用起来：选择页面上能看到“按现在的选择会断掉什么”，作者被告知“你的代码引用了哪些没借给你的原版文件”和“别的保留功能在用你的哪些名字”。

3. 改了什么、怎么改的

下面按一次运行经过的顺序说。每一条是“现在发生什么”，括号里是它所在的模块。

第一期：换掉工具，并让清单和索引绑定

  • 安装：四个平台各钉一个包的校验值（sha512）。第一次用时下载一个压缩包（约 66 MB），核对无误才解压；不运行安装程序，也永远不调用 codegraph 自己那条会改 agent 配置的安装命令；机器上已有的同名命令不用（codegraph_tool.py）。
  • 建索引：一次工具调用（build_code_index）。nanolize 把当前提交拷到本地盘的临时目录，在检查用的沙箱里运行工具（没有网络），遥测固定关掉，核对建出来的索引确实是这个提交的，再把索引库放进运行的状态目录里。作者会话读不到这个目录。机器不支持沙箱时只有清理过的环境变量这一层保护，回执里写明是哪一种（这次用到的机器都有沙箱）。
  • 绑定：清单转换并提交之后、正式规划之前，bind_understanding 把清单里每一对功能之间的事实关系（导入、调用、实例化、引用、继承、装饰，各多少处）写进清单。只收索引经由导入语句或文件路径解析出来的事实边；靠名字猜出来的提示边不进清单，放在旁边一份只有你能看的绑定报告里。
  • 是否过期按文件内容判断，不比提交号：索引里每个源文件的哈希要和现在的文件对得上。
  • 入口选项：index=on|off|require（默认 on）取代原来的 graphify=on|off。装不上、建不出、绑定不了时运行照常继续，但会说出来：第一阶段的回执、选择页面、交付结果和报告页面各有一句；用 index=require 时遇到这种情况就停下。有两种情况不继续：工作区里有未跟踪、未被忽略的非测试文件——带着它作业本来也起不来，所以要先处理掉（无人值守时运行在第一阶段结束并说出文件名）；你自己给的清单带着旧版本的图信息、而这次又没法重新绑定时，运行也在第一阶段结束并说明。
  • 去掉的：graphify_tool.py、两个工具（prepare_graphify、import_understanding）、两条命令、“导入图 → 审草稿 → 写映射”这条旧通路、docs/graphify.md 和三份技能说明里的相关内容。main 上提到 Graphify 的 540 行现在剩 116 行：源码里 20 行（跳过名单里的目录名、读到旧版本数据时的提示、清理旧环境的代码），其余在测试和指南里讲旧版本记录的一节。

第二期：提交之前的范围核对

  • 核对什么：对一份选择，从计划、nanolize 自己的导入表和结构索引三处取证，分十类列出来。最要紧的几类：保留的文件用到只属于被去掉功能的文件；保留的包的 __init__.py 导入了被去掉的模块；被去掉的模块在被导入时会执行什么（注册之类）；保留的功能之间有引用却没有声明依赖；没有任何途径进入新代码的配置文件，以及其中被保留的代码或测试点名的那些（scope_check.py）。
  • 什么时候核对：四次。主持会话写出第一版清单后马上一次（试规划草稿）；正式规划一次；评审启动时一次；每次按下 Submit 时对实际提交的选择再做一次，结果留在作业里。
  • 什么会拦住提交：两类。一是“保留的文件用到只属于被去掉功能的文件”（一个文件里对那个目标的每一处导入都写在 try/except ImportError 或 if TYPE_CHECKING: 下面时，单独标出、不拦）；二是“清单本来可以绑定却没有绑定”。第一类被拦住时有三条出路：在同一个页面上把那个功能选回来；改清单重新评审；写一句理由后照原样提交（理由留在作业里）。第二类是先绑定再提交，或者写理由。这个开关现在是打开（一个常量；依据见 5.4）。
  • 没有索引时核对照做，只用导入表；有三类查不了、四类查得少，回执里写明是哪几类。
  • 交付时再数一遍：交付的代码里如果又出现了只属于被去掉功能的文件（修复时把它写回来了），结果里写有几个、属于哪些功能，报告页面写两个数（几个文件、几个功能）。

第三期：范围基线

  • 做什么：controller 作业（默认的那种）在冻结阶段、封存之前，建一棵“原版去掉被去掉功能”的树：只属于被去掉功能的文件拿掉，保留文件里只为了引入它们的 import 语句剥掉；用你给的准备配方把这棵树准备好，在里面跑一遍保留的检查（scope_baseline.py）。
  • 怎么判定：一个检查在这棵树里失败两次、在没动过的原版上通过，才算“范围造成的”。候选代码如果只是以同样的方式失败，这个检查不再派给作者，交付时记为范围的缺口（这样的交付最多是“带缺口完成”）。候选自己多出来的失败仍然是作者的。前提是那棵树里保留的文件都还能导入；如果有保留的文件在被导入时就用到了被去掉的代码，这一步不做归因，失败的检查照旧归作者，但计入下面的上限。
  • 超过 5 条就停：一次范围基线（一批）里新发现超过 5 条，这个作业在调用自己的作者之前暂停，等你发话：照原样继续（归到范围上的检查作为缺口交付，归不了的仍归作者），或者取消、改选择再提交。无人值守的主持会话不替你继续，记录后让作业停着。配对运行里两个作业各做各的范围基线。主作业暂停时会要求草稿作业在当前这一步之后停下（正在跑的作者调用先跑完）；草稿作业暂停时只在主作业的记录里留一句话，主作业照常继续（见 7.2）。
  • 测试设计也用它：新设计的测试如果在原版上过、在这棵树里不过（并且在作业自己的原版副本上确实过），退回设计者一次，告诉它这个测试依赖了被去掉的功能。
  • 不做的情况：固定作业不做；选择没有去掉任何源文件时不做。这一步自己的问题（树建不出来、准备配方跑不过、计算节点不可用）不会让冻结失败，只记录并说明。两个例外：刚抓的基线本身有问题时这一步直接跳过、不留记录；这一步的记录文件写不下去时冻结会失败。

第四期：页面和作业多用一点索引

  • 选择页面：每个功能列出和它有关系的功能（多少处、哪种引用），另有一节说明“按现在的选择会断掉什么”。在你自己机器上打开的页面还能展开到具体的文件和行；公开页面只有类别和数目。（以前带 Graphify 图信息的清单也画关系图；一行入口的运行里清单不带图信息，所以实际上看不到。）
  • 作者：借给作者的原版文件清单里多两段：它借到的代码引用了哪些没借给它的原版文件；别的保留功能在用它这部分代码的哪些名字（要保留）。借出的文件本身没有变多（job_structure.py）。
  • controller：同一层里一个范围的原版代码引用另一个范围时会被告知。这只是报告，不改变范围的划分和先后；用处是合并之后出现失败时，判断是不是两份各写各的草稿没对上。
  • 运行页面：第一阶段的步骤改名为“结构索引”并多一步“绑定”；第二阶段多一项“范围核对”；冻结阶段多一项“范围基线”；交付阶段在有文件被写回来时多一项。中英文都有。

4.3 评审查出的几件要紧的事

这些都不是测试或 CI 查出来的——出问题的代码自己的测试当时都是过的。列在这里是因为它们说明了哪些地方风险大：

  • 范围基线会动到你自己的仓库。它每次运行都执行一次 git worktree prune，会把你那些“目录暂时不在”的 worktree 的登记删掉（比如放在没挂载的盘上的），删了不能恢复。改成只移除作业自己那棵树；顺带堵上了另一条在特定 Git 设置下会有同样后果的路（那一步的提交可能触发 Git 自己的自动维护）。
  • 交付结果把文件路径和行号带到了公开的地方。范围基线的摘要进了作业的公开记录，公开评审的访客能读到。改成结果里只有计数和功能编号。（这一条是做页面的那个包在自己的报告里指出的，不是互审查出的。）
  • 规划旁边的核对报告，作业的 Codex 作者会话和候选代码的检查读得到。那份文件带着每一条引用的文件、行号和名字，原来放在工作目录的 notes/ 里，不在“不许读”的名单里（Claude 作者会话原来就被设置文件挡着）。改成放进状态目录并列入名单。
  • 我把你定的一件事写反了。你定的是“范围基线一批里超过 5 条就停下，不再花作者的钱”；我给页面包的任务说明里写成了“无人值守时记录后继续”，等于把停下取消了。互审和方案核对都指了出来，已改回你的决定。
  • 只要有一个大文件或非 UTF-8 文件，仓库就永远绑定不了。工具对超过 1 MiB 的文件和不是 UTF-8 的文件写的哈希不是文件内容的哈希。我用真实工具实测确认了它的两种写法，绑定现在都认。
  • 作者被告知要保留一个其实不存在的名字。在 detectron2 的真实数据上：作者被告知要在 __init__.py 里保留 _C，而它是编译出来的扩展模块，照做就会把扩展挡住。已改。
  • 按名字导入的模块，它在被导入时做的注册没列出来。在 detectron2 的真实规划上有 6 处（panoptic_fpn、retinanet、semantic_seg）。已改。
  • 照提示加依赖会把可选功能并进核心。核对报告“保留的功能之间有未声明的依赖”时，原来的提示是“加上依赖”；照做会让被依赖的功能再也去不掉。现在把“只是 __init__.py 里转出名字”和“双向引用”的情况标出来，提示里写明什么时候不该加。

7.1 做法和方案不同

方案里说的实际做的为什么
提交按期分组提交按工作包分组（169 个提交），第 4.1 节给了“包 → 期”的对照；中间有些提交 CI 是红的，最终的头全绿多会话并行时每个包独立交付、独立评审；事后按期重排要拆开互相交织的改动，容易引入错误。合并时可以用 squash 压成一个提交
仓库带子模块、被过滤器改写的文件时：索引照建，只是不绑定带子模块、带被过滤器改写的文件的仓库建不了索引，运行不带索引继续并写明原因。工作区里有未跟踪、未被忽略的非测试文件时不一样：有人值守时等你处理掉那个文件，无人值守时运行在第一阶段结束并说出文件名（带着它作业本来也起不来）建索引要先把提交逐字拷到本地盘，这一步和绑定用的是同一道“来源是否干净”的检查
索引过期时自动重建绑定回答“未绑定：索引不是当前的”，并告诉主持会话再调一次建索引多一次工具调用，少一条自动改状态的路
范围基线是冻结里新增的一步放在“抓基线”那一步里面、封存之前；只有 controller 作业做，固定作业不做；配对的两个作业各做一份不增加新的工具和记录行，录制的基准不用重录
范围基线的成本约等于多跑一遍基线更贵：每个规划一次（测试设计前后各一次）；准备配方在那棵树里再跑一遍；失败的检查在树里再跑一次、在原版上对照一次互审发现“只跑一次就下结论”会把偶然失败记成范围造成的
页面上对每条发现逐条确认被拦住时写一句理由，管整个选择逐条确认要改两个页面的交互，留到以后
范围基线的树把“谁也拿不到”的配置文件也去掉只去掉规则上只借给被去掉功能的那些；顶层的配置文件（setup.py 之类）留在树里去掉它们会让准备配方在那棵树里跑不起来
升级工具时用的核对脚本包含“和 Python 解析器对定义和行号”“顶层导入覆盖率”两项比较脚本有 16 项检查，这两项没做它们是升级时才用的；现在的 16 项已经覆盖“索引和记录逐行相同”

7.2 还留着的限制（挑要紧的）

  • codegraph 看不到的东西照旧看不到：用 importlib.import_module 这类调用导入的模块、从注册表里按字符串取的名字、运行时拼出来的路径、Python 和 C++ 之间的关系。范围核对通过只说明“从 import 和引用上看没问题”，页面上写了“必要、不充分”。
  • macOS 没跑过：两个平台只钉了校验值。
  • “超过 5 条就停”是绝对数、按批计：300 个检查里 6 个会停，6 个里 5 个不停；第一次基线发现 5 条、设计之后又发现 4 条也不停。这个数法是实现对你那句话的读法，要不要改见第 8 节。
  • 配对里只有草稿作业暂停时：主作业自己的范围基线一般随后也会发现同样的问题而暂停（这次 detectron2 运行里两者的第一次范围基线相差约 8 分钟）；但如果主作业自己那次范围基线没出结果（节点不可用、那棵树没准备好），它会继续并自己付作者的钱。
  • 范围核对不看保留的测试文件导入了什么：这次 detectron2 运行里有一个保留的测试文件在模块级导入了被去掉的项目，核对没有列出它，是主持会话自己试跑查出来的。作业里的范围基线能查出这种情况（那个检查会被记成范围的缺口），但那时已经提交了。
  • 定时的性能基准测试如果碰到了被去掉的功能，范围基线不解释它：会花最多两次性能修复，然后记为“性能未保持”。
  • “带保护的导入”只看 import 怎么写，不看后面用到这个名字的地方是不是也有保护。
  • 核对让每次规划多一次整树快照（没有单独量过；两次快照在 detectron2 上合计约 8 秒）；每次提交多出来的两次已经去掉。
  • 索引存放目录不清理：每棵源码树一个条目（只加测试的提交不新增；tqdm 约 3 MB，detectron2 约 27 MB）。
  • 几种大小上限：一个提交的文件超过 2 GiB、索引文件超过 1 GiB 时没有索引；功能之间的关系超过 15,000 对时有索引但清单绑定不了。Windows 没有支持。范围基线的剥离器只处理 Python。
  • 还有三种暂停在技能说明里没有写明无人值守时怎么办（时间预算用完、token 预算用完、原版在运行中被改动）。它们不是这次引入的。
  • 没有被第二个人读过的改动：几个包在自己那轮评审之后又做的修正；最后两个小包（流程复查的文字修正、草稿作业不被带起）是在整体通读之后并入的，只有它们各自的评审。
  • 每次范围基线在你仓库的对象库里留下一个没有引用的提交，等 Git 自己回收。
  • 命令行起的评审（nanolize review）不做范围核对，也就不会被拦。
  • 原有代码里的两处，没有动：作业在你仓库的 worktree 里提交时，可能触发 Git 自己的自动维护（默认设置下只会清理三个月以上的陈旧登记）；nanolize reset（你明确要求重置时才运行）仍然会执行一次 git worktree prune。它们都不是这次改动引入的，按“先报告、不擅自修”处理。
  • 合并之后，旧版本留下的记录会被拒绝并给出提示：带 Graphify 图信息的规划和清单、以前导出的知识包、合并前开着的评审和没跑完的作业。升级前把在跑的作业跑完，旧的规划重新做一遍。
