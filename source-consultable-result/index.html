一、要解决的问题

这次修改的出发点是 2026-11-18 的流程评审和随后定稿的修改方案（第二版）。方案里的问题可以归成六条，下面每条写的是修改之前的情况，数字都来自以前运行的记录。

问题修改之前的情况以前的记录里它的代价
1　写事实这一步冻结阶段里专门有一步，让模型把每个测试钉住的行为写成文字，再让另一个模型评审，写不全还要补写第二遍。存在的唯一理由是作者看不到源码。python-dotenv 一次 39.3 分钟的运行里占 17.8 分钟；tqdm 三次运行每次 49–52 美元
2　作者看不到源码作者只能靠功能图、行为描述、事实和失败反馈来猜行为。借源码要等检查失败之后，而且有限额（每次最多加 5 个功能，每个作业 15 个）。修复时指路的信息少，容易多轮。修复轮数和每轮的花费；另外是一整套只为这种模式存在的设置、提示词和文档说法
3　保存时因为重合度被拒绝担心作者默写原版：保存时量一次和原版的重合度，超过限制的文件被拒绝，作者要重写，随后还要一轮 controller。tqdm 三次运行每次 11–22 美元的重写
4　第一次对比之前的 controller 回合作业从第一步起每一步都先问一次 controller，而在第一次完整对比有结果之前没有需要它决定的事。并且它在封存之前出场，就有可能通过它的选择影响测试。tqdm 每次 2–4 美元，以及每个回合的等待
5　校验方和作者排着队建工作区、录基线、设计测试、再录基线、封存，全部做完才开始写第一版，尽管写第一版并不需要这些产物（去掉事实之后）。tqdm 上按记录推算，两条线并起来能从 97–111 分钟降到 64–71 分钟
6　长步骤是一个整体设计测试和它之后的再录基线绑在一步里，中间没有进度，节点中途不可用时不能只重做后半段；设计者同时开工的数量是固定值，不是目标数。detectron2 的冻结记录里这一步以小时计

六条问题有同一个根：流程是按“作者看不到原版源码”设计的。作者看不到源码，所以要有人把测试钉住的行为写成文字（事实）；因为有这些文字，要评审它们、要给它们设门槛、要在提交之前估算它们；因为担心作者默写原版，要在保存时拒绝重合度高的文件；因为有拒绝和重写，对比之前就需要 controller 来决定怎么办。负责人的决定是把这个前提换掉：作者从第一次调用起可以读源码，事实整个去掉，旧模式不留。

三、做法

你让我带着帮手做，遇到要决策的自己定并做好记录。实际的做法是这样的：

  • 六个会话，各管一块。我加五个同样配置的帮手。方案的五个工作包按代码的归属重新切成五块（冻结和检查执行器；借源码和作者侧；不带事实的测试设计；知识包、报告、进度页和文档；两个作业），我自己负责固定流程、controller 的准入和说明书，以及合并。每个帮手在自己的工作副本和分支上提交，不推送主分支。
  • 先写接口，再动手。开工前把各块之间的接口写成文件（谁提供哪个函数、哪个字段），之后改接口要先说。每个人的决定记在各自的文件里，一共 180 条左右。
  • 每一块的代码都让只挑错的子代理审过。一共 12 轮，发现的问题见第五节。评审者只读代码和方案，不改东西。多数是在提交被合并进集成分支之前审的；有几处是之后补的或者没有审：删掉事实撰写者的那部分是后来补审的，我自己的代码在集成分支上放了几个小时才审，知识和报告那一块只审了前 11 个提交，最后几个小提交没有审。
  • 我逐个提交挑进集成分支。不整枝合并，有冲突就让提交者在新的基础上重做。集成分支开了一个草稿拉取请求，把它的 CI 当测试机用：13 个作业（Python 3.11 和 3.13 各 6 片测试，加一个打包检查），一次约 25 分钟。本机所有会话合起来只有 4 个 CPU 核，所以本机只跑各自改到的测试模块。
  • 付费的运行只有我做。帮手们的验收都用假的模型（演练）。四次真实运行里两次在实现途中，两次在最后，见第四节。

借源码作者留在工作区里的一个文件能决定之后的调用借到什么scope.json 被当成了会话的范围声明。现在只认调用方声明的会话。
借源码清理提交误删了一个函数每次作者调用在借文件时都会失败。在任何提交被合并之前由 CI 和本地运行发现并改正。
测试设计场景用例的名字可以绕过门槛用赋值或在代码块里绑定的场景函数，名字取的是函数自己的 __name__，没有任何门槛读过它，却会显示在负责人的页面上。现在这样的文件整个被拒绝。
测试设计补审一个节点可能一直跑到设计结束之后其他节点已经通过的测试会因为没有时间而被丢掉。现在补审最多用剩余时间的一半。
测试设计场景用例可以用原版测试的名字来命名设计者读过原版的测试；它把场景函数起名为某个原版测试的名字时，这个名字会在用例失败时告诉修复的作者。对“删掉事实撰写者”这部分的补充评审发现；现在这样的函数会被从文件里拿掉。
知识和报告这个版本自己的计划被当成旧版本的而拒绝某个检查点到的知识记录的编号以 fact. 开头时，计划、录基线、验证都通过，然后在封存时的导出和报告里报错。现在只按记录的字段判断。
知识和报告报告把草稿作业和主作业借出的文件数相加两个作业借的是同一份原版，相加是错的；“打开了 X 个，共借出 Y 个”把按调用的计数和不同文件的计数放在了一起。
固定流程（我自己的代码）导入之后工作进程被杀掉，恢复时这次导入不被承认被杀掉的操作在日志里只有一个占位的结果，代码把它当成了导入的结果。恢复后的主作业认为还没有作者调用，会在导入的候选上面再按层写一遍第一版：草稿的钱白花，还多用作者调用。
固定流程（我自己的代码）等草稿时被暂停、恢复后再导入，导入被算成两次作者调用每一条没有结果的导入记录都被算成了那一次封存的导入。有作者调用上限时，作业会在还允许一次修复的时候直接交付一个没过检查的候选。
固定流程（我自己的代码）第一次基线不安全时，设计测试再也不会做设计这一步读到不安全的基线后什么都没设计，却被记成“设计做过了”；之后强制重录的基线正常了，作业直接封存。缺有效测试的节点全部带着缺口封存，而且没有任何提示。现在不安全的基线在设计之前处理。
固定流程（我自己的代码）作者调用失败的草稿作业仍然报“草稿完成”作者会话异常退出但已经写了文件时，只有一个 scope、或者失败发生在最后一层，草稿作业照样报完成；失败在前面的层则报失败。方案说的是有一个 scope 的调用失败就算失败。现在三种情况一致。
固定流程（我自己的代码）由一个作者写完整个选择的草稿作业，写完却报失败负责人的作者调用上限比层数少、或者某一层的并行组什么都没存下时，固定流程让一个作者一次写完全部。这次调用花了钱、也保存了，草稿作业随后却报“没有 scope-1、scope-2 的文件”而失败，主作业再自己写一遍。第二轮评审发现；现在这样的调用算全部 scope 都写了。
冻结停止信号在写进度的时候被吞掉作业被取消或到期时，如果信号正好落在写进度字段的地方，这一步会照常跑下去。
冻结设计之后的再录基线，中途停下就丢不掉设计了它先结算设计、再写基线的记录；在两者之间被停下的调用之后无法再放弃这次设计，候选的工作树里还留着被放弃的文件。
冻结评审之后的一个修复让敲除矩阵在节点上报错一个变量在某条路径上没有赋值。同一轮里由提交者自己的测试发现并修掉。
冻结集成时把受保护的文件放回去的规则太宽第一版会把“准备步骤在原版和候选里都重新生成的文件”也换回提交里的版本，这本身就是改了冻结的输入。现在只在放回去能得到基线观察到的那个文件时才放。

我写固定流程的规则时，和集成之后发现的

缺陷怎么发现的
不能用的基线会让大多数作业在第一次对比之前停下。原来这个停止由 controller 决定是否越过；对比之前没有 controller 之后，没有人能越过。改成：不能用的基线在第一次对比之前不停，封存把它的问题记成缺口；不安全的基线强制重录一次，仍不安全就暂停等负责人。我在写准入规则时对着已有的测试发现。
并行模式关着时，把并行工具从 controller 面前藏起来会改变它的回答格式，依赖这个格式的测试会跟着变。改成工具照旧可见，只在“每个请求只点一个 scope 的实现拆分”这一种情况下放行。我第一版这么写了，跑测试时发现，在合并之前改掉。
没有被问的回合如果也写一条决策记录，会让回合编号错位。改成这样的步骤不留决策记录、不占编号。我写准入规则时对着已有的测试发现。
导入的草稿被两次中断之后，会被算到之后某次保存的头上（要求导入和之后的一次保存都在封存之后、写日志之前被杀掉）。两个作业那一块的评审者读出来的序列；我写了测试，修改前失败、修改后通过。
草稿完成这个新的终态，页面的状态表里没有。集成后的页面脚本测试。
别的块的测试里代替作者调用的替身不认识新增的两个参数，报类型错误。CI。
controller 的说明书里还有一句说交付需要“docstring 示例已验证”，而对应的缺口已经不存在；并行模式的提示词还说它会放宽设计者的并发数。CI 和我自己通读。
冻结预留这个设置已经不起任何作用，但上下文和进度页上还在倒计时，并且说“之后再设计测试会被拒绝”。我自己通读时发现，连同设置一起删掉。
对拍记录的测试不能重复通过：借阅记录里有随机的编号和纳秒时间没有归一化；录下来的文件里还会带上本机账号的路径。重录固定流程的对拍记录时发现；测试里补了归一化，路径换成占位符。
导入了草稿的主作业，进度页上“按层写第一版”一直显示每一层都在等待。对我的代码的第二轮评审发现；现在显示为由导入写入。
一个测试用等号比较由两次时钟读数相减得到的秒数。时钟的起点随机器而变，同一个数在一台机器上算出来是 900.0，在另一台上是 899.9999999999999。最后一次只改文字的提交的 CI 里，它在 Python 3.13 的那台机器上失败了，之前的几次都通过。改成按四舍五入后的数比较；被测的代码没有问题。

事我定的理由，和放弃了什么
第一次对比之前的步骤怎么记不留决策记录，不占回合编号；作业的事件里说一次“没有问 controller”和原因否则回合编号会错位。进度页上这些步骤显示为固定流程的步骤。
基线有问题时没有 controller 可问不能用的基线在第一次对比之前不让作业停下；不安全的基线强制重录一次，仍不安全就暂停，等你恢复原来这是 controller 的决定。放弃了：在这之前由模型判断要不要继续。
按层写第一版怎么接进现有的工具并行工具对 controller 照旧可见；模式关着时只放行“每个请求只点一个 scope 的实现拆分”藏起工具会改变 controller 的回答格式。一层最多 4 个作者同时写，和方案一致。
冻结预留（freeze_reserve）整个删掉；旧的策略文件里还写着它时接受并忽略它已经不限制任何事。直接报错会让以前的启动脚本因为一个不起作用的设置而失败。
旧的借源码设置（source_reference）传了旧的取值就拒绝并说明原因，不是悄悄忽略否则以为“作者看不到源码”的负责人会在不知情的情况下借出源码。
旧版本留下的计划、基线、对比、报告不转换，遇到时用一句话拒绝，说明要用写它的那个版本方案说旧作业不兼容。作业要在它开始的那个版本上跑完。
导入草稿的方式把草稿的文件复制进主作业自己的工作区，按作者的草稿来保存，记一次作者调用一次保存就是一个检查点，而且保存这一步本来就会量重合度。放弃了：单独开一个实现工作区。
共享的临时目录所有作业的所有 Codex 会话都读不到，不只是配对的作业单个作业里设计者和作者也共用它。Claude 的适配器本来就各有各的临时目录。
需要 GPU 的安装检查或准备步骤，而本机没有 GPU这样的选择不配对，只跑一个作业；强制配对会被拒绝这种作业一开始要问你“没有 GPU 要不要继续”，这个回答决定基线和测试在什么环境里做，不能在草稿作业的作者已经在写的时候给。
“打开数”的含义是会话的命令点到了哪些借来的文件，不是对读取的测量；只列目录、只看大小的命令不算计数来自会话的事件，没有任何东西观察文件系统。会偏高或偏低的情况见第七节。
设计者同时开工的数量不设置时等于目标数，最多 32；并行模式不再把它改成 16方案要求等于目标数。16 会卡住目标更多的设计。
场景用例的名字就是函数名，限制为不超过 80 个字符的标识符；运行时出现了门槛没见过的用例，整个文件拒绝这是设计者传出来的文字里唯一没有人评审的。放弃了：用工厂函数生成场景函数。
“负责人指定了优化次数”怎么判断只看数字是不是默认的 2；恰好写 2 的负责人被当成没有指定配置里只存了数字。要区分得在四个入口都加标记，而且有测试钉着现在的格式。
演示页面按新流程重新录制了全部七个场景（录制时的代码比最终的早几个提交，之后只用最终的页面资源重新生成）旧的录像里还有写事实这一步和从第一步开始的 controller 回合。
替身调度器做成测试用的工具，装进一个目录后放到 PATH 最前面这样检查执行器一直跑到它启动的进程，而不碰真实的调度器。

你会注意到的变化说明
冻结快了没有写事实这一步。小项目的冻结从二十分钟降到两分钟以内；有要设计的测试时，时间主要是设计者的会话和两次录基线。
进度页冻结阶段没有“测试事实”这一项；设计之后的再录基线是单独一步；长步骤显示进行到哪；第一次对比之前的步骤显示为固定流程的步骤；有草稿作业时多一行，带链接。
报告有一句总的说明：作者读过被检查功能的源码，所以检查通过说明行为保住了。还有一张表，列出每次作者调用借了多少文件、命令点到了多少、调用之后的重合度；以及交付代码和原版的重合度。
新的开关--pair on|off（命令行）和 pair（工具参数）：强制或禁止两个作业。不写就按三个条件自动决定。
不再接受的--source-reference 和它的两种取值（拒绝并说明原因）；命令 write-facts 和工具 write_test_facts；测试策略里的 facts 开关；controller 给修复多借几个功能的参数。
旧版本留下的东西还没跑完的作业本来就只能在它开始的那个版本上继续（运行环境的标识不同会被拒绝），这一点没有变。修改之前的版本留下的计划、导出包和报告，在新版本上读取时会用同一句话拒绝并说明原因。
查重默认只告知、只量、不拒绝。想恢复拒绝，把 original_overlap 的 max_rewrites 设成 1。
本机已装的插件没有动，仍然是 main 上以前的版本。合并之后要重装才会用到新流程。

问题留着的理由
一个在冻结阶段被暂停的作业，恢复的时候如果正好撞上它的工作进程在退出，作业会直接失败，不能再恢复。在配对里，这时草稿作业还会接着写，而主作业已经结束。比这次修改更早，main 上是同样的代码；在恢复逻辑的核心里，时间内来不及给它写出可靠的测试。
配对里草稿作业没建起来时，主作业仍然按“配对的主作业”来跑：检查仍然绑在节点上，封存之前的手动调用仍然被拒绝。要在主作业已经启动之后草稿作业的创建才失败，才会遇到；这时手动导入不再被挡，记录里会写明发生了什么。
主作业自己启动失败时，如果草稿作业已经被恢复，草稿作业会继续跑。对一个正在跑的主作业反复点恢复，每次多一条事件。恢复草稿作业的那段时间里主作业的控制锁一直被占着。都是恢复路径上的次要问题，不影响结果。
强制配对、而安装检查声明了本机没有的 GPU 时，拒绝发生在每次提交的时候（页面上显示“选择无效”），而不是评审开始的时候。提示得晚，不影响结果。
草稿作业的作者被告知要保留哪些 docstring 示例，依据的是草稿作业自己那份不带敲除的基线；那里被排除的检查钉住的示例不会被告知，导入之后要多一次修复。只多花一次修复，主作业的验证不受影响。
负责人对一个正在跑的主作业手动发导入，会被当成工作进程自己的一步，而不是手动调用。比这次修改更早。
手动对草稿作业调用“草稿完成”，会接受一个作者调用失败的草稿作业，主作业随后会导入它。手动调用是负责人自己的决定，主作业对导入的东西会自己完整验证。
负责人授权新增检查之后，如果这些检查冻结的文件正好被当前的候选改过或删过，固定流程不会自己重新保存这个候选：它的第一次对比会停下，要靠恢复候选来解决。这时作业已经有 controller 和负责人在场；见冻结那一块的决定记录。
敲除矩阵在节点上重发时，它的时间从自己开始时算，所以在队列里等过的那一次会比截止时间晚结束。第一次发送本来就是这样；改它要在节点上的函数里引入墙上时钟的截止时间。
一个测试偶尔失败：读作业记录的时机正好落在“状态已经写成结束”和“最后一步的记录写进日志”之间。是测试的读取时机问题，main 上同一个模块的测试也是这样读的；CI 会自动重跑一次。只在一次 CI 里出现过。
有一个测试在这台开发机上失败、在 CI 上通过（一个适配器进程的退出码不同）。比这次修改更早，没有查。
场景用例的名字只限制了形式和“不能以原版测试命名”；设计者仍然可以在 80 个字符里放别的提示。设计者回答里的一个标签只有计划的校验在读。前一条要更严就得评审名字，方案明确说不评审；后一条是改设计者回答的格式，不适合放在收尾时做。

一次到达真实调度器的只读查询

我们的规则是任何调度器命令都不碰。为了测试“检查在计算节点上跑”，帮手写了一个替身调度器：四个同名的小程序，把本机当作唯一的节点，放在一个目录里并排在 PATH 最前面。有一个测试在替身的目录已经从 PATH 上撤掉之后，又问了一次“这个作业在调度器那里还剩什么”。这台开发机的 PATH 后面有真实的调度器，于是这个问题到了它那里：一共 4 次，每次本地跑这个测试时 1 次，都是只读的 squeue 查询，查的是替身发的作业号（1 或 2），真实的调度器回答“无效的作业号”。没有提交任何作业，没有取消任何作业。发现的途径是 CI：CI 上没有调度器，这个测试在那里失败了。修复是让这个问题在替身还在 PATH 上的时候问。之后我做真实的两个作业运行时更进一步：把真实调度器的目录从 PATH 里去掉，而不只是把替身排在前面，启动前逐个核对四个命令解析到的是替身，并且确认其余的调度器命令一个都找不到。
