分两个阶段。第一阶段各包在自己的工作树里解决自己的冲突文件。这时别的包的文件还带着冲突标记，测试跑不了，只能保证每个文件能编译、没有未定义的名字；包 a 还对每个文件做了三方合并的行数核对（每一行在解决后的文件里出现的次数等于 main 加分支减分叉点，例外逐条列出）。主持会话把交来的文件拼起来，重新生成生成文件，提交合并（eabc96e）。 第二阶段各包在合并提交上跑自己那些模块的测试（两边的都跑），修合并弄坏的，再处理分给自己的问题：每个问题先用一个失败的测试或不调用模型的小重现证明它在哪棵树上存在，再改，再加回归测试，把结论写进问题清单。各包只在自己的分支上做小提交，不推送，由主持会话挑进集成分支。整套测试只在 PR 的 CI 上跑，本机只跑用得到的模块（这台机器给所有会话一共 4 个核）。

两边改了同一处时的规则

  • 两边都留下。main 自分叉点以来加的东西和分支加的东西，合并后都必须能用。
  • 两边因为不同的原因改了同一段代码：写出同时做到两件事的代码。
  • 两者确实不能同时成立：保留分支的 controller 流程结构，把 main 的行为放进去，并把这个选择连同理由和放弃了什么写进决定记录。
  • 不为了让冲突消失而删掉任何一边的测试。规则被合并替换了的测试，改写成陈述合并后的规则，一个都没有删。
  • 冲突不只是带标记的那几处：没有标记的合并部分也要读，找一边改了、另一边还按旧方式用的调用、参数和名字。

改变行为的决定

下面是决定记录里会改变行为的 12 条。每条都写了是什么、为什么、放弃了什么；完整的记录在工作目录里（见最后一节）。

  1. controller 又能看到 reviewer 角色。分支把它藏了起来，理由是它的报告到不了任何工具的结果里；main（3797f0f）已经把报告放进调用结果的 review 字段，这个理由不成立了。run_parallel_agents 仍然不接受 reviewer。分支上“拒绝 reviewer 调用”的三个测试改成了说明这个角色可用。
  2. 性能测量是“代码的证据”，和其他证据一样。在 controller 作业里，文件相同、重新保存的候选（恢复出来的、选中的、保存没变的草稿）沿用原来的性能测量；固定流程的作业照旧对恢复出来的候选重新测量；所有者设 evidence_reuse: false 就回到旧行为。放弃的是 main 的那句“每个新候选都要重新测量，恢复出来的也一样”。不这样做，建议和工具会对同一个候选说相反的话，没完没了。进度页上，候选的性能一栏只显示在这个候选自己身上做的比较。
  3. controller 看到的工具 = 这个作业有的工具（main）减去隐藏的工具（分支）。visible_tools(settings=None, config=None)，answer_schema、parse、_judged 都带这两个参数。作业没有的工具报“unknown tool”，隐藏的工具会告诉 controller 同样的事现在去哪里做。
  4. 性能验收在灵活流程里的位置。委托（follow）在性能比较的结果是 passed 或 no_criteria 时继续，其他结果停下来问 controller；在性能修复之前也停下，和别的修复一样。提示词的顺序是 controller.guide、controller.guide.performance、controller.parallel。
  5. 并行模式里的性能修复是一次 run_agent，不按 scope 拆开（没过的基准不是某个 scope 的问题）。controller 自己发起的修复组按它的模式记账：在性能比较没过的候选上，一个修复组算一次性能修复，记在所有者给性能修复的上限里。放弃的是“并行的性能修复”，记录里写明以后可以单独加。复查之后改了一点：从别的候选出发的组，按那个候选的证据来判断（见交叉复查的 M-3）。
  6. 缺口 performance_not_preserved 什么时候算关不掉。比较失败且所有者不再允许性能修复；或者封存之后契约里没有判据、或什么都测不了。没有这条规则，这个缺口会永远算“还能关”，deliver(require="best_reachable") 就一直被挡住。
  7. 性能文件在作业的第一次设计调用里为所有叶子设计，不受 leaves 影响；以后的设计调用不再设计性能文件，契约也不动。性能是所有者的要求，不是 controller 可以挑的目标。放弃的是按 leaves 收窄性能文件，以及在以后的调用里重试。
  8. 带设计测试的基线保不住时，性能文件跟着测试一起丢掉。这次设计接受的性能文件不再列在记录里，性能契约按回退后的提交重写，事件里单独说丢了多少性能文件。考虑过但没做：丢掉之后删掉契约、让下一次设计调用重新设计性能文件。
  9. 回放把副本放在哪里，用 main 的规则。两边修的是同一个 bug，做法不能同时成立：main 只在测试文件要送到计算节点时才把副本放进作业目录，在本机跑时放在临时目录；分支总放在作业目录。保留 main 的做法，去掉分支的 within 参数；分支那条测试改成钉住 main 的规则。
  10. 同一件事两边各写了一遍的，只留一个。读 pytest 配置的 repository.pytest_settings 合成一个函数（用分支的函数体，没有 [pytest] 小节的 pytest.ini 也算 pytest 的配置），两边的调用方都用它。“试跑按作业的选择来规划”用分支的写法（_trial(tree, plan, ...)），main 的 removed 参数没有了。
  11. 一个测试文件什么时候“原样保留”。main 的条件（整个文件需要的不超过它每个测试声明的）和分支的规则（没人引用的 import 跟着每个测试写出）都留下，比较时按测试自己用到的东西算。放弃的是：只通过这种 import 才需要某个功能的文件，现在写出一份而不是原样保留。
  12. 默认值和说法，取改过的一边。有三处是一边还带着分叉点的旧文字、另一边已经改了：优化次数默认 2（main）；stop 对别的运行的作业是取消，只有到过第一个检查点的才能恢复（分支）；任务成本评估沿用任何一次测量过的、文件相同的尝试的结论（分支）。另外，controller 作业里不带名字的 run_checks 只跑所有者的交付检查（分支）。

有没有丢东西

合并提交之后，主持会话用一个脚本做了一次“丢失的新增行”核对：对两边自分叉点以来都改过的每个文件（66 个，不含生成文件），列出某一边新增、而合并后的文件里没有的行（去掉首尾空白后不少于 12 个字符的才算）。34 个文件有这样的行。命中只是线索，不是证明，因为一行可能被改写成同时承载两边的内容。 各包把自己文件里列出的每一行都对着合并后的文件读了一遍，结论都是不需要恢复任何东西：这些行要么是为了同时承载两边而重写的签名、调用和文档字符串，要么是按上面的决定有意去掉的（例如分支的 within 参数、main 的 removed 写法、分支隐藏 reviewer 的那几行）。

文档、技能和提示词目录由一个独立的辅助会话复查：10 个文件、列出的 95 行，其中 80 行的内容在合并后的文字里（有的换了说法），15 行是按两条决定有意替换的（reviewer 角色又可见；性能记录是代码的证据），丢失的是 0 行，没有改任何文件。 它另外做的三项核对也没有发现问题：没有哪一边新增的短行缺失；没有哪一行是分叉点和两边都有、合并后却没有的；prompts.json 逐条核对，某一边写了而合并后没有的句子只有上面两条决定涉及的那几句。
