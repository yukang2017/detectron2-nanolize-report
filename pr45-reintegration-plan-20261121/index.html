4.2 自动合并了、但结果不对的地方

必须改：多 worker 时，设计试跑的“换哈希种子重复”失效。
分支上的 E-1 是这样接进去的：一个表示“这批要换种子”的参数 vary 一路传到树里那个重复检查的地方。#45 加的副本路径在它前面：检查先在副本里跑、重复、定论，定论了的就不再进树里那个循环。而副本路径调用重复时没有带 vary。两边改的是不同的行，所以 Git 没有报冲突。
在试合并的代码上跑了一个小探针（两条结果取决于字符串集合迭代顺序的检查）：1 个 worker 时它们被判为不稳定，记录里有两个种子；3 个 worker 时它们在副本里被判为稳定，没有换种子。调用处我自己读过：进副本路径的那一行和副本里重复的那一行都没有这个参数，只有树里那一行有。

影响面：只影响检查 worker 多于 1 个的作业，也就是并行模式开 widen，或负责人自己设了 worker 数，或在计算节点上设了 CPU 数。第 4 次 tqdm 运行（pair 加并行，4 个检查 worker）的记录里，三次设计试跑共 144 项结果，其中 120 项是在副本里定论的：75 个设计出来的测试和 45 个次数文件全部在内，只有 24 个场景文件在树里跑。换句话说，照现在的自动合并结果，那样一次运行里 E-1 只管得到场景文件。默认设置（1 个检查 worker）不受影响。

第 7 件：重新说一遍

现象没变：#45 之后，多 worker 的作业里，在副本里定论的检查没在原版的树里跑过；副本“有没有被改动”只看源码、测试、依赖这几类文件。检查留下别的文件时，基线不再发现它。

前一版的做法为什么不够：我写的是“改成看所有文件，缓存目录除外”。评审指出两点。一，原版的树里那道保护是按 Git 判断的，被 Git 忽略的文件不算改动；而副本里用不了 Git（分支自己的评审实测过），直接数文件就会把覆盖率数据、构建产物这类被忽略的文件也算进去。二，一条检查只要在副本里没定论，就整场作业都拿不到“可并排”的标记，之后每次比较都只能一条条跑；而不带 #45 时，它在树里跑完会被再探一次并拿到标记。评审的探针：六条各留下一个被忽略的覆盖率文件的检查、3 个 worker，不带 #45 是 7.0 秒且都有标记；带 #45 是 2.2 秒；带 #45 再照我前一版的写法改，是 8.4 秒且都没有标记。也就是比不带 #45 还慢。tqdm 的测试不留这类文件，所以在 tqdm 上跑看不出来。

选项做什么代价
A. 这次不做（我现在的建议）作业基线照 #45 原样，把这个缺口写进文档的已知边界。设计试跑那一层第 2 步已经解决，分支依赖的那道闸在试跑里是完整的多 worker 的作业里，检查留下非监控类型的文件，基线发现不了；不带 #45 时能发现。另开一个改动把它做对
B. 这次做对规则按原版的树里那道保护来：副本里新增、消失或变了的文件算改动，缓存和私有目录除外，再到树里问 Git 这些名字是不是被忽略的；并且让“只因为副本被改动而没定论”的检查在树里跑完后再探一次，仍可拿到标记要设计加测试，估计多 2 小时左右；规则本身还要再过一遍评审

第 8 件：更正后的说法

先分两种情况，这部分前一版没错：

  • 主作业慢，草稿作业先做完：草稿作业自己结束，主作业封存后直接导入，不用等。唯一一次 pair 加并行的真实运行就是这样，草稿作业比主作业封存早 51 分钟结束，导入只等了 5.8 秒。今天三次验证里草稿第一版约 37–43 分钟、冻结约 78–84 分钟，这个规模的项目上这是通常的情况。
  • 主作业快，封存时草稿作业还在干活：还在写第一版的各层就写完；正在比较就比较完结束。

错的是“正在修复”这一种。前一版说修复的结果会被丢下、交出去的是上一个候选。实际是：这一步跑完后，那次修复先被存成一个新候选，然后草稿作业结束，交给主作业的就是这个新候选，而草稿作业自己没有比较过它。并行的修复组也一样，它自己会合并并存成新候选。评审用探针确认了：主作业导入的是修复之后的那个候选。所以没有东西被丢；要定的其实是“交一个草稿作业没比较过的候选”行不行。主作业导入之后总会用完整的契约重新比较。

另有一个例外前一版没提：主作业等草稿作业有上限（它导入开始时剩余运行时间的一半）。等到上限草稿作业还没结束，它会被取消，这时它写的东西全部作废，包括只是在写第一版的情形；这种结局下等了多久现在也没有记录。

选项做什么代价
A. 保持现状，什么都不加（我现在的建议）交接修复后的新候选，照 #45 原样交出去的候选草稿作业没比较过，可能比它比较过的那个差；但主作业反正会完整比较，而且这是把已经花钱做的修复用上
B. 保持现状，加记录在草稿作业的结束记录里写：主作业封存时它在跑哪个工具、从封存到结束多少秒、交出去的候选它自己比较过没有；并在“等到上限”的结局里记下等了多久要读主作业的封存时间，这是草稿作业现在不读的东西；新字段只在主作业先封存时才加，否则默认作业的记录也会变。比前一版以为的“只加两个数”要多
C. 改做法封存后交出草稿作业最后一个比较过的候选，刚做完的修复不用等了那一步又不用它的结果，正是前一版以为的“现状”

7. 没验证的，和已知的风险

  • 三块功能的细读是读代码加 Git 比较得出的；跑过的只有 E-1 那个探针，以及第 4.3 节的测试。
  • 并行模式的真实运行只有一次（第 4 次 tqdm：扣掉等节点 178.2 分钟、$161.07），当时的结论是并行直接省下约 4 分钟，不能说更快。那次的代码没有修复上限，也没有随行为比较跑的次数检查。
  • PR #47 没有写回退 #45 的原因。带 #45 的三次运行（第 3、4、5 次）比之前两次慢，当时的数据分不开是不是代码造成的；同设置重复一次就差了 138.5 分钟。把 #45 带回来，这个问题也跟着回来，只有再跑才知道。
  • 分支自己的评审曾经否掉“在副本里观察一条检查”这个做法：副本里 Git 用不了或者会作用到原版的 Git 目录，副本带着指向原树的字节码缓存，副本里的运行看不到前一次运行留在树里的东西。按这份方案，作业自己的两次基线仍然在这样的副本里给检查定论。对基线来说，在副本里失败的检查会退回树里跑，所以后果是速度和少一个标记，不是记录出错。
  • 检查在副本里并排跑时量到的用时，是和别的检查挤在一起的用时。有没有检查因此越过“轻量检查”的界线，要真实运行才知道。
  • CI 机器的 CPU 配额如果是 1，并行模式的整作业测试就走不到副本路径，新补的多 worker 测试要自己把 worker 数设死。
  • 演示页的并行场景重录能不能按脚本走到预期的结束状态，取决于冲突解得对不对；录制本身就是这一步的测试。

8. 工作量和花费（估计）
