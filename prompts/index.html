提示词整合建议

你的问题是：各个步骤的提示词太多、分布太乱，想整合到一起，比如放进一个 JSON 文件。这份报告先清点现在所有会被模型读到的文字放在哪里，再回答“放进一个 JSON”行不行、建议怎么做、分几步、代价是什么。这是建议，主线代码没有改。为了确认可行，我另外做了一个只走第一步的原型。

结论

  • 可以整合进一个 JSON 文件，建议这样做。在这套代码上它的代价比一般情况小：现有提示词几乎不含需要转义的字符，本来就是一段一行，仓库里也已经有“一个 JSON 做唯一来源、CI 检查是否同步”的做法。
  • 让人觉得乱的，不只是目录里那 24 个文件。还有约 5.3 万字符会被模型读到的文字直接写在 Python 代码里，其中作者读到的约 63 处分散在 9 个模块。只把现有文件合成一个，要看全“某个角色到底收到了什么”仍然得翻代码。
  • 建议的终点：各步骤的提示词文字都在一个 prompts.json 里，每条写明谁读、有哪些槽位；代码里只剩条目的 id；另有一个命令和一份生成的总览，按角色显示最终收到的全文。工具说明、拒绝消息和 skills 留在原处，但在总览里看得到。
  • 建议的走法：先做三步（步骤 0、1、2），每一步模型收到的每个字节都不变，可以放心合并。去重会改变模型读到的内容，单独放在最后，需要用真实模型比较后再决定。
  • 它解决的是“分布乱”，不直接解决“多”。文件从 24 个变成 1 个，但条目不会变少：把代码里的句子收进来之后条目反而更多，只是都在一个地方、按角色排好。要让文字本身变少，靠的是最后那步去重。
  • 原型结果：第 1 步已在本地分支上做出来：23 个文本经新的加载方式读出来逐字节相同，固定流程回放 57 条全部一致。全量测试正在跑，结果出来后补在“原型”一节。

放进一个 JSON 文件，行不行

行。通常反对把长文本放进 JSON 的几条理由，在这套代码上都量过：

通常的担心在这里量到的
到处都要转义现有 23 个提示词文本约 6.8 万字符，其中双引号 42 个、反斜杠 0 个。放进 JSON 只有这 42 个引号要写成 \"
改一个词，整段在 diff 里都变了现在的文件已经是一段一行：有 40 行超过 500 个字符，mcp/server.md 整个文件就是一行 9,358 个字符。所以今天改一个词，diff 里也是一整段。建议把每个文本存成“每行一个字符串”的数组，粒度和现在一样
没法预览 Markdown23 个文本里只有 2 个用到 Markdown 语法（标题和几行列表），其余都是纯段落。这些文件叫 .md，但基本不是 Markdown
仓库里没有这种做法已经有：assets/workflow.json 是流程表的唯一来源，脚本用它生成两份 README 和 skill 里的表格，CI 检查有没有过期。rewrite/policy.json 本来就是 JSON。不过那两个文件里都是短字符串，长文本放进 JSON 在这个仓库是第一次
读取变慢原型每次调用都重新解析整个文件：取一条小提示词从约 0.04 毫秒变成约 0.26 毫秒，生成一次作者提示词从 0.18 毫秒变成 0.89 毫秒。和一次模型调用相比可以忽略；正式实现按文件修改时间缓存，就回到原来的量级

确实存在的代价：

  • 一处语法错，所有命令都起不来。现在坏一个提示词文件只影响一个角色。合成一个 JSON 后，少一个逗号就会让所有命令在启动时失败，因为规则是在模块导入时读的。应对办法有三条：规则改成用到时才读；加载失败时报出文件、行和列；加一个 nanolize prompts check 并放进 CI。这样后果和“某个 Python 文件有语法错”差不多：任何一次测试都会立刻发现，但在一个正在跑作业的可编辑安装上改坏文件，下一次调用仍然会失败。
  • 改起来并不比现在容易，只是好找。长段落仍然是一行很长的字符串，改一个词的 diff 和现在一样大。读任何一条都要打开一个约 1.6 万 tokens 的文件；现在最小的文件只有 16 tokens。对人来说用编辑器搜 id 即可，对改代码的 agent 来说要按 id 搜到行再读那一段。
  • JSON 不能写注释。对某条提示词的说明要放进字段里。
  • 逐行的修改历史在搬家那一次断开，没合并的分支会遇到冲突。细节见“约束和风险”。

建议的结构

一个文件 src/nanolize/prompts/prompts.json。每段提示词文字是一个条目，id 以读它的角色开头。

{
  "schema_version": 1,
  "prompts": {
    "author.prompt": {
      "roles": ["author"],
      "title": "The author's prompt for every call",
      "slots": {
        "worktree": "path of the authoring workspace",
        "plan_path": "path of the frozen contract",
        "policy_instructions": "the policy's requirements, one per line",
        "feedback": "the feedback line when a feedback file exists, else empty"
      },
      "text": [
        "Independently rewrite the selected capability graph in this new authoring repository.",
        "Start in a fresh context without the original analysis conversation. …",
        "Authoring workspace: ${worktree}"
      ]
    },
    "author.feedback.repair": {
      "roles": ["author"],
      "title": "Instruction inside repair feedback",
      "text": [
        "Repair one root cause or related capability group at a time, … the frozen target and checks stay unchanged."
      ]
    },
    "shared.isolation": {
      "roles": ["examiner", "solver", "judge", "test_designer", "controller", "review_chat"],
      "title": "Isolation notice appended at launch",
      "text": ["…"]
    }
  },
  "policy": { "schema_version": 1, "requirements": ["…"] }
}
  • text 是行的数组。用换行把它们接起来，就是现在加载函数返回的内容，一个字节不差。空行就是一个空字符串。
  • slots 写明每个槽位是什么。现在槽位只出现在文本里的 ${name}，含义要去调用处找。
  • roles 是固定的几个名字组成的列表，可以按它筛选。多个角色共用的条目放在 shared.* 下，列出所有读它的角色。
  • id 按角色分组：author.*、controller.*、examiner.*、solver.*、judge.*、test_designer.*、review_chat.*、host.*。打开文件按前缀搜，就能看到一个角色的全部文字。
  • 结构化的规则（现在的 policy.json）是同一个文件里的一个对象。
  • 加载接口很小：prompts.text(id) 取文本，prompts.render(id, 槽位…) 填槽位。代码里的 id 一律写成字面量，这样才能检查“用到的 id 都存在”。过渡期间旧的 load_prompt("rewrite/runner.md") 继续可用。

配套的三样东西

  • 一个命令。nanolize prompts list 列出所有条目和读它的角色；nanolize prompts show author 显示这个角色最终收到的全文；nanolize prompts check 做下面的检查。
  • 一份生成的总览文档。按角色排好的全文，包括留在代码里的工具说明。它不是从目录文件拼出来的，而是直接调用真实的拼装代码、用占位值渲染出来的，所以和模型实际收到的一致。CI 检查它有没有过期，做法和现在的流程表一样。想一眼看全时看它，想改时改 JSON。
  • 几条自动检查。文件能解析，没有重复的键（解析时就要查，普通的解析会悄悄保留后一个）；格式是规范的；代码里用到的 id 都存在，每个条目都有人用；文本里的槽位和声明的一致；安装包里带着这个文件，而且不再带别的提示词文件；重复句子的清单只能变短。

JSON 还是 TOML

结构不依赖格式。下面是同一个条目在两种格式里的样子。

JSON

"author.feedback.repair": {
  "roles": ["author"],
  "title": "Instruction inside repair feedback",
  "text": [
    "Repair one root cause or related capability group at a time, including necessary shared dependencies. Do not treat an unmet token target as a reason to stop repair. Gaps are not failures; the frozen target and checks stay unchanged."
  ]
},

TOML

# why this sentence exists can be written here; a comment is never sent to the model
["author.feedback.repair"]
roles = ["author"]
title = "Instruction inside repair feedback"
text = '''
Repair one root cause or related capability group at a time, including necessary shared dependencies. Do not treat an unmet token target as a reason to stop repair. Gaps are not failures; the frozen target and checks stay unchanged.'''

TOML 的好处是长文本不用加引号和逗号，可以写注释，少一类容易犯的语法错；评审核对过，23 个文本用它也能逐字节读回来。JSON 的好处是和你的想法、仓库现有的两个 JSON 一致，标准库既能读也能写（格式检查因此很容易做），原型已经验证过。我建议用 JSON；如果你更在意手工改起来顺手，TOML 是合理的替代，以后要换也只是一次机械转换。

分步做法

每一步单独合并。“不变”指模型收到的每个提示词、每个工作区文件都和这一步之前逐字节相同，因此不需要重新评估模型行为。

步骤做什么模型读到的内容怎么确认
0　先留底，再让它看得见不搬任何文字。新增命令 nanolize prompts list 和 nanolize prompts show <角色>，再生成一份总览文档：直接调用现有的拼装代码，用占位值把每个角色最终收到的全文渲染出来。同时把每一段渲染结果的摘要值存成一份快照放进测试，覆盖作者提示词的 16 种组合、契约文件和反馈文件里的指令、知识包说明、controller 的工具定义、MCP 工具列表。不变这一步本身就是后面几步的对照基准：之后每搬一次，快照必须一个字节都不变。
1　24 个资源合进一个文件建立 prompts.json，加载函数改成从它读；旧的文件名继续可用，调用处以后再逐个改成 id。删掉 24 个文件，改打包配置、发布检查脚本、目录索引和 AGENTS.md 里的那条规矩。不变快照不变。原型已做到：23 个文本逐字节相同，固定流程回放 57 条全部一致。
2　作者读到的代码内文字搬进来先给约 63 处句子列出逐条清单（现在只有估数）。能原样搬的搬进目录文件；把“不许看源码”配置下那两句的字符串替换，改成在目录文件里声明两种写法。和代码绑死的留在原处，并在总览里标出来（见下一节）。不变快照不变。抽查过 6 处：3 处可以原样搬，3 处不适合搬。
3　减少重复（改内容，单独决定）对 14 组重复逐组决定：同一个读者读到两遍的，留一处；不同读者各自需要的，保留。会变契约和知识包的摘要值都会变，以前导出的知识包要重新导出；断言措辞的测试要跟着改；作者提示词变了，候选质量可能变，需要用真实模型跑一次对比。

顺序的理由：步骤 0 不搬任何东西，却同时给出“看得全”和“之后每一步的对照基准”，所以放最前。步骤 1 最便宜，原型已经证明可行。步骤 2 解决“作者读到的东西到处都是”，是最能缓解你说的问题的一步。步骤 3 才碰内容。

哪些放进去，哪些不放

划线的原则：独立成段的指令放进目录文件；对某个接口或某个条件的说明，留在那个接口或条件旁边。前者是你说的“各种步骤的提示词”，后者离开它描述的代码就看不懂，分开放更容易改一处忘一处。

什么建议理由
24 个提示词资源放进去（步骤 1）它们就是各步骤的提示词
作者读到的代码内句子（约 63 处）能原样搬的放进去（步骤 2）它们会被拼进提示词或写进作者工作区的文件，和提示词是同一类东西。三类留在代码里：拒绝原因表（它的键是代码要用的分类，值是半句话）、自检脚本（一整段 Python 源码）、会话备注（拼了别的常量）
controller 工具的 7 条参数说明、40 个作业工具摘要留在工具定义旁边，总览里显示它们是接口的一部分，随函数的参数一起改；分开放更容易改一处忘一处
44 个 MCP 工具说明留在 mcp_server.py，总览里显示已经集中在一个文件里，不属于“分布乱”。里面有 100 个双引号，多数是 JSON 例子，放进 JSON 要逐个转义。搬出去还会改变工具契约的摘要值（见下一节）
拒绝消息和“为什么现在不能调用”（约 110 条）不放每一句属于触发它的那个条件，离开条件看不懂
skills/ 的 9 个文件、两个插件清单不放插件格式要求它们是各自目录下的文件
命令行帮助（约 185 条）不放给人和宿主 agent 查用法，不是提示词
assets/workflow.json不动已经是流程表的唯一来源

口径要说清楚：步骤 2 做完后，各个步骤的角色（作者、controller、出题、解题、评判、测试设计、评审对话）收到的指令文字基本都在目录文件里。但按上面图里最宽的口径（七块合计约 21 万字符），目录文件里大约是 39%；留在外面的是接口说明、回复句子和 skills。它们不搬，但会出现在生成的总览里。

约束和风险

这些是搬提示词时一定会碰到的机制，都对着代码核实过。

机制它是什么对整合的影响
运行环境标识对安装包里的每个文件算摘要；作业记下启动时的值，值变了就不能续跑每合并一步，之前启动、还没结束的作业都不能续跑。这和任何代码改动一样，但分几步就有几次，合并前先让在跑的作业结束
MCP 工具契约摘要对 44 个 MCP 工具的名字、参数和说明算摘要；计划和提交都带着它，不一致会被拒绝步骤 0 到 2 不影响它（核对过）。只有搬 MCP 工具说明才会改变它。顺带发现一个现有的不一致：这个值在 Python 3.13 和 3.11 上本来就不同，因为 3.13 在编译时去掉了说明文字的缩进（44 条说明总长 23,490 对 24,610 个字符）。我在两个版本上各算了一次，确认不同。它和提示词整合无关，可以另外单独处理
契约和知识包的摘要作者契约、知识包各有一个摘要值，内容包含规则和几段说明文字步骤 0 到 2 不变。步骤 3 改措辞就会变，以前导出的知识包通不过“重新渲染后一致”的检查，需要重新导出
固定流程回放基准仓库里记录了固定流程下每个作者提示词的摘要，用来发现意外变化它只覆盖固定策略，而默认是 controller 策略；仓库里的那份基准只在一个特定的 Python 上运行，别的环境直接跳过。所以不能只靠它证明字节没变，需要步骤 0 的快照
导入时加载规则文件在模块导入时读取，而命令行入口会导入这个模块目录文件只要有一处语法错，所有命令都起不来，包括 --version、MCP 服务和页面服务。评审时实际试过。今天只有规则文件一个文件能造成这种后果

原型：只做了步骤 1

为了确认第 1 步真的可行，我在一个本地分支上把它做了出来。没有推送，主线代码没有动。

  • 做了什么：一个一次性的转换脚本，把 23 个文本文件和规则文件收进 prompts.json（79,287 字节，457 行）；加载函数改成读这个文件，旧文件名照常可用；删掉原来的 24 个文件；改了打包配置和一处测试。27 个已有文件有改动，新增 2 个文件。
  • 文字有没有变：23 个文本经新的加载函数读出来，和原文件逐字节相同；规则文件解析出来的内容相同。评审另外独立核对了一遍：MCP 工具契约摘要、MCP 说明、规则的两种写法、隔离说明、四种作者提示词、知识包说明，改动前后都一致。
  • 固定流程回放：57 条记录全部一致，和改动之前录的基准没有差别。
  • 全量测试：正在跑，结果出来后更新这一行。

原型没有做、正式实现要补上的：

  • 几处说明文字还指向已删除的文件：AGENTS.md 里“提示词按阶段分目录放”的规矩、提示词目录自己的索引、docs/job-tools.md 的两处、一处代码注释。不改的话，照 AGENTS.md 做事的 agent 会新建一个既不会被打包也不会被加载的文件。
  • 转换脚本是一次性的，原文件删掉后它的检查模式就不能用了。正式实现里要换成对目录文件本身的检查。
  • 每次读取都重新解析整个文件，没有缓存。
  • 槽位只有名字没有说明；角色是随手写的文字，还不能用来按角色筛选。
  • 没有 prompts 命令，没有总览文档，没有快照（它们属于步骤 0）。

这份建议被挑出的毛病

按之前的做法，这份建议在给你之前请一个只负责挑错的评审对着代码和原型审了一轮，只做了这一轮。它提了 15 条，下面是改变了建议内容的几条。

  • 我原来打算把 44 个 MCP 工具说明也搬进 JSON，并写了“工具契约摘要不会变”。这不成立：这个摘要在两种 Python 版本上本来就不同，搬过去必然在其中一种上改变。现在的建议是不搬。
  • 我原来写“一个文件是所有指令文字的唯一来源”。实际做不到：按最宽的口径，步骤 2 做完后目录文件里大约是四成。现在写明了口径和边界。
  • 我原来想在目录文件里声明“每个角色由哪些片段按什么顺序组成”。这表达不了真实的拼装：作者提示词有四个独立的条件、16 种组合，同一份规则有三种渲染方式。现在改成总览直接调用现有的拼装代码。
  • 我原来靠固定流程回放来证明字节不变。它不够：只覆盖固定策略。所以加了步骤 0 的快照。
  • 我没写的几项代价：一处语法错所有命令都起不来；修改历史断开；没合并的分支会冲突。都已写进上面两节。
  • 我有一句话说错了：草稿里写“提示词里那两句改一个字，每次作者调用都报错”。实际只在“不许看源码”的配置下才报错，默认配置不检查。上文已改。

没有复核的数字：14 组重复、作者约 63 处、controller 约 140 处，是清点代码得到的估数，评审没有逐条核对。步骤 2 的第一件事就是把清单列出来。其余数字（资源数、tokens、字符数、工具数、打包配置等）评审逐项核对过。
