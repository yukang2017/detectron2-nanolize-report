tqdm 三次压缩运行的轨迹对比

这一页把三次用 nanolize 压缩 tqdm 的运行放在一起比。三次用的模型和 effort 相同（claude-fable-5-2，high），都是无人值守、保留全部功能。 A 是分支 flexible-tools-parallel 开发的起点（main @ 4a1f832）；B 和 C 是这个分支的终点（2d4682f），B 关着并行模式，C 开着。 A 对 B 看的是分支里 controller 的灵活回答（下面叫 flexible）有没有用；B 对 C 看的是并行模式有没有用。

结论
  1. flexible（A 对 B）没有带来可测的变化。两次走的步骤完全一样，结果相当。B 快 39 分钟，但这 39 分钟全部落在两边都做的同样七步模型会话里，而这些会话的提示词分支基本没改；除去这七步，两次都是 9 分钟。flexible 实际改变的是：controller 用 4 轮而不是 7 轮走完了同一条路。
  2. 并行（B 对 C）没有让 tqdm 更快。C 慢 51 分钟。并行模式在三处起了作用：写事实时同时起的会话从 8 个加到 16 个，但这一步没有变快；修复和体积优化各有一个 4 人并行组，合计 32 分钟。作者一侧其余的时间和并行关一样，每次只有一个会话在跑。慢在修复（多 45 分钟）和多出的一轮体积优化（25 分钟）。C 的冻结阶段少 25 分钟，是只给一个节点设计测试换来的，留下 23 个没验证的原版测试。
  3. 三次的交付质量接近。体积是原版的 48.2%、47.7%、49.4%；最终候选的检查全部通过；都因为同样两类缺口以“有缺口”交付。
  4. 每种设置只有一次运行，B 和 C 还不在同一台机器上。十几分钟以内的差别可能只是两次运行之间的波动，这一页不把它们当作结论。

先说几个词

controller
每一轮决定“接下来调用哪些工具”的模型会话。它不写代码，只安排：让作者写哪一部分、什么时候保存、比对、修复、交付。
作者
真正写代码的模型会话。它看不到原版源码，只看契约和知识记录。
冻结
重写开始前的准备阶段：写测试事实（把保留下来的测试钉住的行为写成文字）、在原版上录基线、给没有有效测试的节点设计测试、封存契约。封存之后检查清单不再变。
scope
交给一个作者会话写的一组功能。默认每个 scope 不超过 45,000 个原版源码 token。
防默写
保存候选时把作者写的代码和原版逐行比较。整体超过 40% 相同，或某个 8 行以上的函数超过 60% 相同，就拒绝保存，让作者重写。
探针
一段运行代码并记录输出的小脚本。候选代码的输出必须和原版的一样。
缺口
交付时仍然没能证明的部分。有缺口的交付状态是 completed_with_gaps，不算失败。

controller 每一轮做了什么

每一行是 controller 的一次决策：它什么时候开始想、想了多久、排了哪些调用、这些调用的结果。一轮里排的调用按顺序执行；前一步没有按预期结束，后面的就不执行，回到 controller 重新决定。

flexible 有没有用（A 对 B）

flexible 指分支给 controller 的几样新能力：一个回答里可以给调用加条件（前一步是某个结果才执行后一步）；可以把后面的若干步交给主线自己走，不用每步都回来问；冻结阶段的各步可以单独、重复地调用。并行模式是分支的另一部分，B 里是关着的。

两次走的是同一条路

A 和 B 做的事一步都不差：写事实 → 录基线 → 设计测试 → 封存 → 作者写 scope-1 → 作者写 scope-2 → 保存被防默写拒绝 → 作者重写 → 保存成功，命令行的检查没过 → 作者修复命令行 → 全部通过 → 交付。 两次都是 4 次真正的作者调用、1 轮修复、不需要体积优化，最后是同样两类缺口。

这些差别能不能算在分支头上

我比较了两个版本的全部提示词。分支新增了并行模式用的两段，改了 controller 的指南（约 3.4 万字符涨到 5.7 万）和它的试跑提示，测试设计者的提示多了一百多个字符。 事实编写、事实评审、设计评审和作者的提示词没有改。所以写事实和作者这两块（合计少 28 分钟）在两次运行里用的是同样的提示，差别更可能是两次运行之间的波动。 作为参照：同一份代码在另一个小项目（python-dotenv）上跑的几次里，同一步作者调用的用时在 534 到 831 秒之间。

flexible 实际改变了什么

  • 开头少一轮。A 先用一轮建工作区，再用一轮排冻结的四步；B 第一轮就把整个冻结交给主线。
  • 结尾少两轮。B 在最后一个回答里排了七步：修复、保存、先只比对命令行的检查、完整比对、安装检查、选定、交付，每一步都以前一步的结果为条件。A 做同样的事用了三轮。从最后一次作者调用结束到作业结束，A 用了 3.3 分钟，B 用了 2.3 分钟。
  • 每一轮变重了。B 的最后一轮读了 33 万 token、想了 105 秒；A 的对应一轮读了 21 万 token、想了 60 秒。所以轮数从 7 降到 4，决策总用时却没变（4.1 对 4.2 分钟），controller 的花费从 $4.80 降到 $4.04。
小结。在这种一路按主线走完的运行里，flexible 的净效果接近零：少 3 轮、省不到 1 美元，没有让结果变好或变差。 它给的是 controller 偏离主线的余地，而 A 和 B 都没有偏离。C 用到了这种余地，效果有好有坏，见下一节。

并行有没有用（B 对 C）

并行模式做三件事：首次实现时，互不依赖的 scope 可以交给几个作者同时写；controller 可以把一次修复或优化拆成几个请求同时跑，各自在自己的工作区里写，写完合并；冻结阶段的会话、检查可以开得更宽。

首次实现为什么没有并行

tqdm 的原版源码是 45,979 个 token。按每个 scope 最多 45,000 的规则，它被切成 scope-1（43,250 token，整个 tqdm 包）和依赖它的 scope-2（2,729 token，维护脚本和 benchmarks）。两个 scope 一前一后，各占一层，没有可以同时写的。 所以两次运行里最大的一块作者时间（写初稿加防默写后的重写，B 是 61.9 分钟，C 是 66.6 分钟）在 C 里也是一个作者接一个作者地跑。

C 慢在哪

  • 修复多 45 分钟。C 的首个候选有 6 项探针没过，B 只有 1 项。并行修复组修好了 4 项，剩下 gui 和“旧别名”两项。第 7 轮重跑了没存上的那个请求，gui 修好了；“旧别名”又单独修了两次（第 8、9 轮）。第 7 到第 9 轮从 15:35 到 16:22 共 47 分钟，全部是单个作者会话顺序跑。 controller 在理由里写明：知识记录没有说这个探针打印什么，它只能把猜测一条条写给作者；第 9 轮把猜测写具体之后才修对，那一次作者用了 21.3 分钟。
  • 多一轮体积优化，25 分钟。几轮修复把体积从 48.3% 推到 52.7%，超过了 50% 的目标，于是做了一轮优化。B 的首个候选是 47.5%，修复后 47.7%，不需要优化。
  • controller 决策多 15 分钟。11 轮共 19.7 分钟，B 是 4 轮共 4.2 分钟。
  • 冻结少 25 分钟，但这是少做了事。C 的 controller 在第 2 轮只点了 keras 一个节点设计测试（38.2 分钟）；B 给 10 个节点设计（68.7 分钟）。C 因此有 23 个原版测试没有交给任何设计者，封存之后再也补不上，这是它“没验证的原版测试”远多于 A、B 的原因。 这是 flexible 给的余地被用坏的一例：能单独调用设计这一步，controller 就可能只调用一部分。合并后的 main 已经改了：建议里会列出还没设计的目标，并在封存前提示再设计一轮。
小结。在 tqdm 上，并行开没有带来更短的时间。两个并行组只占全程的七分之一；最大的一块作者时间（首次实现）因为 tqdm 只切出一前一后两个 scope 而并行不了。 C 比 B 慢的 51 分钟，主要来自首个候选没过的检查更多、其中一项前后经过四次作者调用才通过，以及由此引出的一轮体积优化。这些和并行开关没有直接关系，也可能和两次运行的检查清单不同有关，这一对运行分不清。

  • 每种设置只有一次运行。模型会话的用时在两次运行之间本来就有波动，十几分钟以内的差别不足以下结论。这一页能确定的是“路径是否相同”“哪一步多做了或少做了”，不是“哪个版本快百分之几”。
  • B 和 C 不是受控对照。不同的机器，各自做的发现阶段，检查清单不同（57 项对 36 项），原版 token 数不同。

  • 数字从哪来。三次运行各有一份轨迹文件，由作业自己的记录生成（controller 每一轮的决策、每次工具调用的参数和结果、每次模型调用的用时和花费）。这一页里 A、B、C 的数字都从这三份文件里来；差值和合计是这里算的。不在这三份文件里的有：分支的提交数、提示词的比较、合并后 main 改了什么，来自代码仓库；scope 分层那张表，是用 main 的代码在 B 保存的计划上试算的；A 和 B 用的是同一份功能图，是比较两次作业保存的计划确认的（35 个节点的编号和依赖关系完全相同）；python-dotenv 的用时来自另外几次运行的记录；补充一节的 D 来自那次运行自己的作业记录。
