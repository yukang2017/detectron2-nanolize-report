3. 每一项现在怎么做

A-1：程序自己读的文档文字，点名、原样保留

录基线时对原版的产品源码做一次静态扫描（不导入、不运行）：找 名字.__doc__、getattr(名字, "__doc__")、模块里裸写的 __doc__，以及和这种读取写在同一个表达式里拼接的模块级字符串常量。结果存进基线。每次作者调用时，借给它的原版文件索引 reference.json 里多一个键，按文件列出这些对象和常量，以及是哪个文件读的。作者读到的所有“不要照抄文档字符串”的地方都改成了两个例外：一是检查会当作 doctest 运行的示例（原来就有），二是程序自己打印或解析的文档字符串和拼在一起的常量，这些逐字照抄。规则里同时写明：这份名单是读源码找到的，不一定全；程序以名单看不到的方式展示给用户的文档字符串（比如某个库把它当帮助文字打印）同样是行为。

方案里没有写死、实现时定下来的：

  • 只是“告诉”，不强制：校验方不核对候选的这些文字。强制的话，以前五次交付的候选没有一个能过，等于给每次运行加几轮修复。
  • 重复度：被点名的常量在候选里如果是顶层的一个纯字符串赋值，而且内容和原版的那个常量相同，就不计入“和原版相同的行”。否则作者照要求抄了，又会被当作照抄退回。
  • 名单只列“这次保留下来的代码会读”的文字。只有文档生成脚本之类没被保留的文件在读的文档字符串，不要求作者保留（负责人此前否定过“给所有公开对象保留文档字符串”）。
  • 只是把文档字符串交给另一个文档字符串（new.__doc__ = old.__doc__、装饰器的参数）不算“程序在读”。
  • 扫描读不了某个文件时只跳过那个文件，不会丢基线，结果里记下没读成的文件数和错误类型。

已知的边界：扫描认不出：运行时才知道名字的 getattr(obj, name).__doc__、inspect.getdoc、help()、self.__doc__、继承来的成员、赋值给 __doc__ 的文字、库替程序读文档字符串。tqdm 上 README 生成脚本逐个读类成员文档字符串的那一处就属于认不出的。

A-2：只读文档字符串的断言不进验收

只改提示词，一共八条（设计者的主提示词、场景文件、迁移原测试、返修；评审者的主提示词、场景文件、迁移、排除）。设计者：不要断言一个文档字符串存在或写了什么，也不要拿它做计算（__doc__、inspect.getdoc、help 都算），除非被测的这个功能自己的代码会打印或解析它，而那种情况通过它打印出来的内容去测。场景文件不返回、不打印文档字符串。评审者有对应的否决理由。这里说的是项目源码里给某个名字写的文档字符串。

方案里没有写死、实现时定下来的：

  • 原版自己的测试如果断言了某个公开名字的文档字符串：这条测试不迁移，记成“无法验证”，它别的断言照常另写成测试。设计者和评审者对这一点的说法是一致的。
  • 返修时“不要为了让评审通过而削弱或删掉断言”这条规则加了一个例外：评审理由点名的文档字符串断言要删掉。
  • 测试自己定义的对象（比如验证一个装饰器会不会把 __doc__ 带过去）不在此列，那是行为。

已知的边界：没有机械门禁，靠提示词里的判断。原版测试因此记成“无法验证”时，交付最多是“带缺口完成”，这是方案里写明的代价。

B-1：测试自己的代码里出错时，作者多读到一个封闭字段

只读解释器自己生成的、句式固定的消息（Python 3.11 到 3.14 相同的句式；整句匹配，单行），读出三个字段：operation（在做什么）、value（手里的值是哪种内置类型）、other_value（另一个值的类型，比如另一个操作数）。操作词表是：len、subscript、iterate、call、attribute、operand、compare、unpack、contains、context、await、hash、format、integer、number、string、path；类型只认 27 种内置类型名，别的类名一律不读。第 5 次那个例子现在作者读到的是 operation: len、value: NoneType。作者读到的说明里同时解释了 origin 的四个取值（以前只有 controller 读得到）：verifier 是检查的测试文件里出的错，通常是你的代码给了它一个形状不对的值；candidate 是你的代码里；library 是你的代码调用的库里；other 是分不清，或者是检查自己的程序、检查直接调用的库。

方案里没有写死、实现时定下来的：

  • 一条检查的不同错误超过 5 条时，排序和取舍仍按没有这些字段时的规则，字段只在合并到同一条的错误都相同时保留。
  • 候选和测试在同一个进程里，候选可以伪造这种消息，所以字段只取封闭词表里的词，能传出去的只有几个比特；消息的文字本身仍然不给作者。

已知的边界：项目里和内置类型同名的类会被说成那个内置类型。没有固定句式的错误（比如函数签名不匹配）不读，报告里列了没读的句式。

C-1：计数测试出错单独报告

计数标准的结果里，失败用例抛的不是断言失败（或者是测试的准备阶段出错）时，记成 error 加 error_type，作者读到的是“这条基准在你的实现上跑不起来，抛的是什么”，不再是“做了更多被计数的工作”。只有断言没过才是 bound_exceeded。

方案里没有写死、实现时定下来的：

  • 测试结束之后才失败的断言（夹具收尾时断言计数）仍算“超过界限”：测试已经给出了结论。
  • 同一个函数的多个用例里只要有一个是抛异常的，就记成出错。

已知的边界：计数测试如果在子进程里运行脚本、再对退出码做断言，失败的类型还是断言失败，仍记成“超过界限”。

C-2：缺文件时，告诉作者缺的是哪个文件

每次比较的报告里多一项 changes.absent：原版有、候选没有、而且可能被一个错误点名的文件（不含 Python 源码、测试、Git 自己的文件，以及隐藏目录里别的工具会执行或遵从的文件）。一个“找不到文件”的错误，如果消息里的路径对得上其中一个文件，作者读到的 missing_file 就是这个文件在原版里的相对路径，比如 .meta/.readme.rst。测试在临时目录里复制了一份项目再运行的情况也能认：记录里只保存路径末尾几段的摘要，拿它去对“原版有、候选没有”的文件。计数标准的发现里同样带这个字段。

方案里没有写死、实现时定下来的：

  • 证据规则：普通路径沿用原来的规则（这次比较里和原版不同的文件）；隐藏目录里的路径必须是“原版有、候选没有”；临时目录里的路径必须恰好对上一个这样的文件，对上两个就谁也不说。
  • 永远不说的：.git、nanolize 自己的状态目录、虚拟环境、构建产物、测试、Python 文件，以及别的工具会执行或遵从的文件（代理、CI 服务、编辑器的，比如 .github 下的工作流）。
  • 消息里的路径本身不保存名字，只保存摘要：以前保存的话，用户自己的目录名会留在每一份比较记录里。

已知的边界：计时基准出错时不带这个字段（方案没有要求）。

D：计数文件带标记进清单，随行为对比一起跑

设计出的文件提交时（封存之前），通过验收的计数文件的检查也写进清单，带 count: true。随后重新录基线时它在原版上跑，之后每次完整的行为对比都在候选上跑（针对性对比跑点到的那些）。它的结果不进行为检查的列表，单独放在比较报告的 count_checks 里：计数检查没过，行为对比照样可以通过。行为还有没过的检查时，那次行为修复的作者同时读到计数发现（每条量的是什么、怎么没过，不给断言里的数字、不给文件名和函数名）。行为通过之后，compare_performance 不再跑计数文件，直接取同一份代码的行为对比里的结果；到交付还没过的计数标准仍然是“性能没有保持”这条缺口，不是失败。

方案里没有写死、实现时定下来的：

  • 没有采用“到处加一个过滤条件”的做法：计数检查在计划里有自己的一栏、在报告里有自己的列表。这样漏改的读取方只会看不见计数检查（和改动之前一样），不会把它错当成行为检查。
  • 性能修复仍然等计时测量之后才安排：五次运行的第一次测量都有计时类没过，先修计数会在计时结果出来之前用掉两次里的一次。
  • 一次修复只读到它的请求点名的那些功能上的计数发现（没有点名功能时是全部）；没被任何请求点名的，留给之后的性能修复。controller 的比较结果里因此多了一项，列出没过的计数检查属于哪些功能，它想让某条随行为一起修，就点名那个功能。
  • 针对性对比如果没跑某条计数检查，结论是“未验证”，作者的反馈里写明有几条计数标准这次没跑。
  • 原版自己跑不过或者不稳定的计数检查不算基线问题，它的标准记成“无法判断”。
  • controller 的说明里加了一段，讲比较结果里 count_checks 那一栏是什么、该怎么用（controller 读不到工具说明，原来没人告诉它）。
  • 改动之前冻结的作业恢复时照旧：它的计数文件不在清单里，仍由性能对比来跑。

已知的边界：计数检查和行为检查在同一趟里跑，它如果在项目里留下文件或改了输入，会像任何检查一样让那次对比“未验证”。运行页上不单独显示计数检查。

E-1：设计出来的测试，重复运行时换哈希种子

只在设计阶段的试跑里：第一遍用默认种子 0，重复的几遍各换一个种子（默认三遍时是 1 和 2），前提是检查自己和它的环境都没有固定种子。输出或结果变了的文件按原有的“重复不一致”退回设计者，多附一句说明换了什么、该怎么改；如果这个文件是替原测试迁移的，说明改成“把那条原测试列为无法验证，不要放松断言”。之后的基线和所有对比仍然用种子 0。不增加运行次数。

方案里没有写死、实现时定下来的：

  • 只换种子，不换位置。中间做过一版“重复的几遍放到另一个路径的副本里跑”，评审后撤回了，经过见第 4 节。

已知的边界：换种子挡得住的是“结果跟着字符串集合的迭代顺序走”的测试；挡不住“结果跟着对象的内存地址走”的测试，而后者正是这一项的起因。默认只换两个种子，所以只有两个元素的集合约有四分之一的概率三次顺序都一样（四个元素以上基本不会）。

E-2：无人值守时怎么对待时过时不过的检查

controller 的说明里加了一段：没有负责人在场的作业里，一条在同一份代码上既通过过又没通过的检查，如果最新的完整对比里它没过，最多再安排一次修复，并在给作者的话里说明它是时过时不过；之后不再为它修，恢复最好的候选，用默认要求交付。验收报告里，没人值守时“同一份代码上结果不一致”这条缺口标成关不掉，不再挡住“能达到的最好状态”的交付。

方案里没有写死、实现时定下来的：

  • “最多再修一次”只写在说明里，代码里不计数：要计数得记住跨候选的历史，作业现在不保存。真正在代码里止损的是 E-3 的上限。
  • 说明里点明了工具允许的那一步（恢复、然后用默认要求交付）：评审发现原来写的那一步会被工具拒绝。

已知的边界：最后一次完整对比如果恰好是没过的那次，交付状态是“带失败交付”，这条检查列在没过的检查里。

E-3：给行为修复一个次数上限

新设置 max_behavior_repairs，默认 6，可以是 0 到 20，也可以关掉。计数用的是已有的 repair_attempts，数什么没有变（一次修复调用算 1，一组并行作者算 1，工作区里从头另写一版不算，性能修复另算）。到上限时新的行为修复请求被整个拒绝，拒绝里写“需要几次、还剩几次、已用几次”。固定流程的作业停下来（原因 repair_limit_reached），恢复最好的候选；它仍有没过的检查时以“带失败交付”结束，没过的检查列在交付记录里。controller 的上下文里有上限和剩余次数；到了上限、而且没有更好的候选可以恢复时，“对比没过”这条缺口标成关不掉，委托出去的交付才走得通。

方案里没有写死、实现时定下来的：

  • 用了新的停止原因，没有复用“作者调用次数到上限”那个：后者的所有文字说的都是另一个上限。
  • 写法：Python 里 None 是不设上限；MCP 工具里空值是默认 6，"off" 才是不设上限（宿主会把没填的参数补成空值，不能因此把上限关掉）；命令行是 --max-behavior-repairs N|off。
  • 到上限时只把“对比没过”和跟着它的几条缺口算作关不掉；负责人自己的交付检查、安装检查没过不在此列（再跑一次可能就过了，那不是修复）。
  • 只有在没有别的出路时才算关不掉：没有已经做完但还没成为候选的作者产出（含没有返回的一批调用）、没有失败更少的已保存候选、给出的建议也不是先恢复某个候选。
  • 默认值不写进作业配置，所以默认作业的配置文件和改动之前逐字节相同，以前的作业恢复时按默认值算。
  • 改动之前就在修复中途被打断的固定流程作业，升级后恢复时把那次已经开始的修复做完再停。

已知的边界：工作区里“从头另写一版”的请求到上限后仍然可以发。运行页不显示上限和剩余次数。一行入口没有这个选项。

F-1：性能修复怎么计数：说清楚，拒绝时带数字

计数规则没有动（负责人确认过：两个工具计数不同是本意）。改的是三处：controller 的说明里写明 run_workspace_agents 的每个修复请求算一次性能修复（两个工作区各修一次就是两次），交给 run_parallel_agents 的一组算一次；上下文里加 repairs_left；拒绝时写“这个请求需要 2 次，还剩 1 次（已用 1 次，共 2 次）”。

4. 和方案不一样的地方

十项的做法都是方案里的。有一项（E-1）方案估计的效果不成立；另有几处是方案没有写死、读了代码或者经过评审之后定下来的。都记在这里，原因也写上。

E-1：方案说“换哈希种子能挡住约 46%–71%”，这个数不成立

方案里那组数字是我用一个独立脚本、在关掉地址随机化的条件下量的。写完换种子的代码、提交之前，我用第 5 次运行留下的原版和 nanolize 自己的场景运行器重放了一遍，结果不一样：

条件（都是原版 tqdm、第 5 次那个场景文件）跑了给出另一个输出
源码树放在路径甲，种子都是 052 次0 次
源码树放在路径甲，换种子 1–3060 次0 次
源码树放在比甲长一个字符的路径，种子都是 060 次26 次

也就是说，让那条检查变来变去的不是哈希种子，而是源码树放在哪个路径（路径的长度决定模块路径字符串的长度，进而影响后面对象落在内存的哪里）。第 5 次里它在原版上 9 遍都一样、在候选上 7 次有 4 次没过，原因是候选总在另一个目录里。

我先做了一版“重复的几遍既换种子、也放到另一个路径的副本里跑”，在 24 个位置上试：原来的重复运行能挡住 10 次，这一版能挡住 18 次；第 3、4、5 次已通过验收的 264 条检查重放，误伤 0 条。但只挑错的评审用实测否定了这一版：

  • 副本没有自己的 Git 仓库。在作业的沙箱里，凡是代码会调用 Git 的测试（比如按 Git 取版本号的项目）在副本里都会失败，被当成“重复不一致”退回；沙箱外，副本里的 Git 操作会落到原来那棵树的仓库上。
  • 副本带着原来那棵树的字节码缓存，一批里的第一个文件可能因此被无故退回。
  • 重复的几遍都在副本里之后，没有哪一遍看得到文件自己第一次运行留下的状态，试跑会放过基线随后判为不稳定的文件。
  • 每批试跑多复制两份源码树，没有时限，也没有算进这一批向节点申请的时间。

评审同时指出我漏看的一点：nanolize 每次试跑本来就有一次“换路径”的运行，就是敲除对照（把每个文件在一份干净的导出里跑一遍，要求结果相同），那套导出机制对 Git、编译产物、干净状态都处理好了。所以现状已经是每次试跑取一个换路径的样本，第 5 次那条检查是连着三次都碰巧一样。

决定：撤回副本，分支里的 E-1 只保留方案里批准的“换哈希种子”。它不增加运行，重放 264 条检查误伤 0 条；它挡得住依赖字符串集合顺序的测试，挡不住依赖内存地址的测试。后一类现在靠三样东西：设计者提示词里点明“不要让结果跟着按身份比较的对象的顺序或内存地址走”；进了验收之后，无人值守时最多再修一次（E-2）；行为修复有上限（E-3）。更彻底的做法是通过现有的导出机制多取几个换路径的样本（比如设计试跑里再做一次不同路径长度的对照运行），我把它作为后续建议列在第 8 节，没有放进这次的分支。

其他在实现时定下来的事

  • D 的结构：计数检查在计划和报告里各有自己的一栏，而不是带一个标记、让每个读清单的地方去过滤。理由在上一节。
  • E-3 的停止原因和写法：新的停止原因；MCP 工具里空值是默认值、"off" 才是不设上限。
  • E-3 到上限时哪些缺口算关不掉：只有“对比没过”和跟着它的几条，而且只在没有更好的候选、没有未保存的产出时。第一版只看计数器，评审用一个真实跑出来的例子指出它会在“还差一次恢复就有更好候选”的时候把失败的候选交付出去。
  • A-1 的重复度：方案留了两个选项，选了“把被点名的常量排除在重复度之外”，并且只排除内容和原版相同的那个常量，防止借这个名字藏照抄的代码。
  • C-2 的记录：路径在树外时只保存末尾几段的摘要，不保存任何目录名。
  • B-1 的第三个字段：两个值参与的句式里，另一个值的类型单独一个字段，否则 1 + None 会被说成 int。

7. 评审

每个包的作者先各自请一个只挑错的评审看自己的改动并改掉问题，然后才是下面的两轮。评审的规则是：只找缺陷，不夸、不复述；每条发现要有具体的情景，并标明是跑出来的、读出来的还是怀疑。两轮的范围和轮数是事先定好的。

第 2 轮：对着修复再评审一遍

第 1 轮的每一条发现，对照它的修复逐条核对：情景是不是处理了、修复是不是比发现窄、新加的测试没有这个修复会不会失败；同时找修复本身带来的新问题。四个包由一个独立评审做，文档文字包由第 1 轮评审它的人做。

范围结论新发现处理
失败信息、计数检查、上限、重复运行四个包的修复，加合并时补的文字没有阻断性的缺陷，没有泄露，没有会崩溃的路径，没有结束不了的作业。第 1 轮这四个包的 35 条发现里：25 条改对，6 条改得不完整，其余记为边界或没有改（运行页）15 条，其中 6 条会改变作业做的事或说的话各包再改一次；随后只对这批修复做一次复核：15 条里 13 条改对，1 条不完整（在另一份契约下做的对比仍可能挡住止损，记为边界），余下的小问题两个包各再改一次后冻结
文档文字包的修复没有阻断性的缺陷；tqdm 上的结果不变，全范围作业仍然告诉作者类文档字符串和那个常量10 条，其中 2 条是修复引入的回退（docopt(doc=__doc__) 这类最常见的写法被漏掉；条件分支里的定义压过了实际生效的 import）再改一次，再复核一次，又发现 6 条（1 条回退、几条边角）。之后按评审给出的改法做最后一次修改，评审用原有的探针重跑一遍，然后冻结，剩下的记为已知边界

文档文字的扫描是这次改动里最难收敛的一块：每一轮修复都带出新的边角情况。让它停在这里的理由是：这个功能只是“告诉作者”，不强制；扫描漏掉一个名字，结果和改动之前一样；多报一个名字，作者多保留几十个 token。而 tqdm 上的结果在所有这些轮次里始终没有变过。

两轮加起来一共约 93 条发现（第 1 轮 56 条，第 2 轮和复核 37 条）。没有一条是“测试的内容或错误消息的文字泄露给作者或公开页面”。
