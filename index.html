压缩流程

nanolize 的做法是让一个看不到原版代码的模型,根据一份行为说明把仓库重新写一遍,再用原版的检查来验证新代码的行为和原版一致。流程里有四个角色。

四个角色

角色是什么能看到看不到
控制器一个无界面的模型会话。每一轮读取作业状态,输出一串工具调用,由 harness 依次执行。契约、知识包、每项检查的通过或失败、体积测量、作者的会话总结原版源码、测试代码、检查的具体输出
作者另一个模型会话,在沙箱里写代码和修复。每次会话上限 110 分钟,只有 Bash、读、改、写四种工具。自己的工作区、契约、知识包、上一轮的失败反馈(哪项功能、哪类失败)、owner 批准的诊断原版源码和测试、Git 历史、其他运行的产物、缓存里的任何原版副本
Harnessnanolize 的确定性程序,不是模型。执行检查、保存证据、判定验收。原版和候选两棵树、全部检查不适用
Owner发起并监督运行的一方,本次由一个 Claude 会话代行。回答控制器的提问,把失败细节转述成不含原版源码的诊断。全部,包括原版和检查细节不适用,但交给作者的内容不得包含原版源码

步骤

  1. 冻结输入。固定原版提交;从原版分析出 106 项功能和一份知识包(9,177 条行为契约,其中 1,340 条是 owner 复核后补充的),知识包描述公开接口、类型、校验、报错和数值行为,不包含实现代码。同时冻结 160 项 CPU 行为检查、GPU 上的 66 个上游测试文件、4 项安装检查,以及体积基线 862,476 tokens。
  2. 订立契约。控制器保存契约:保留全部 106 项功能,实现要简洁可读,没有强制压缩率,功能和安装通过后不再做纯体积优化,如实报告实际体积。契约还规定不得删功能、不得写占位实现、不得把代码压成一行或编码成数据。
  3. 作者实现。控制器调用 run_agent,把指令交给作者。作者在沙箱里按知识包写代码,自己构建、导入、跑冒烟测试,并维护一份进度笔记。
  4. 保存候选。save_candidate 把工作区保存为结果分支上的一次提交。
  5. 构建环境并采集基线。prepare_environment 编译候选的原生扩展;capture_baseline 在原版上跑全部 160 项检查,记录输出作为基线。
  6. 行为比对。compare_behavior 在候选上跑同样的检查,逐项和基线对比。160 项里有 71 项是上游自带的测试,38 项是运行时入口检查,28 项是按功能分组的 CPU 行为套件,23 项是各子项目的特征检查。
  7. 追加检查。run_checks 确认加载的原生扩展出自候选自己的构建,并在 GPU 节点上重新编译候选、跑 66 个上游测试文件(366 个测试),和原版逐项对比;check_installation 做 4 项全新安装检查(构建依赖、只安装候选、已安装的接口和打包资源、已安装的 Faster R-CNN CPU 推理);audit_coverage 审计功能覆盖;measure_code 测体积。
  8. 修复循环。有失败就回到第 3 步:控制器把失败证据写进指令,开一次修复会话。作者拿到的反馈只说哪项功能、哪类失败,不给测试代码和期望输出;控制器信息不够时可以向 owner 提问。
  9. 验收和交付。evaluate_acceptance 要求同时满足:完整的行为比对通过、覆盖审计通过、安装通过、GPU 和原生扩展检查通过、候选已被选定。之后 select_candidate、deliver,结果写入分支。

作者的沙箱用 bubblewrap 搭建:临时目录是全新的,只有工作区可写,依赖只读挂载,owner 的目录和可能含有原版副本的缓存目录都被遮住。事后审计了全部 18 次会话的工具调用,没有发现读取工作区和依赖目录以外路径的调用,也没有执行联网命令。

检查之外发现的一个缺陷

候选 6 通过了全部 160 项 CPU 检查和 GPU 对比,但作者在笔记里两次提到旋转框 IoU 的实现可疑。Owner 用原版和候选的同一套构建,对相同的随机旋转框做了对拍:

输入原版候选 6候选 7(修复后)
7,100 对普通框(相交、不相交、轴对齐、细长)—与原版逐位一致与原版逐位一致
600 个框与自身求 IoU(批量)正常进程崩溃(stack smashing)正常,输出与原版相同
含重复框的旋转 NMS正常进程崩溃正常,结果与原版相同
20,000 个自重叠中与原版不同的值—336 个0 个

原因是作者凭记忆写出的是上游较早的版本:CPU 分支用 std::sort 配一个带容差的比较器给凸包顶点排序,这个比较器不满足严格弱序,属于未定义行为。会不会崩溃取决于编译器和编译选项,在 CPU 检查用的那套构建上只是算错,不崩溃,所以没有被发现。修复方法是让 CPU 分支改用 CUDA 分支已有的逐对交换排序。

这件事说明检查全部通过不等于行为与原版等价。其他模块里可能还有同类但没被发现的差异。

已知缺口

  • 报告页没有生成。交付成功,但 harness 自带的报告站点生成失败,报错是映射文件必须指向候选仓库里的源码文件。推测是作者的功能映射里包含了 187 个配置文件,而报告生成器只接受源码文件;这个推测没有验证。
  • 没有真实执行过的代码路径。Caffe2 导出的 7 个模块只在桩模块上运行过,环境里没有 caffe2;DensePose 的视频读取没有运行,环境里没有 PyAV。
  • 覆盖盲区。原版在 GPU 节点上失败的 1 个测试和跳过的 5 个测试,对候选同样没有验证力。
  • 作者自报的偏离。PyAV 改成了可选导入;修正了原版的几处缺陷(例如 CSE 评估里写死的设备名),没有照原样复现。这些改动通过了检查,但严格来说与原版行为不同。
  • 交付树里带着作者的进度笔记。PROGRESS.md(8,022 tokens)按文档计,不计入体积。控制器的交付说明里写的 671,146 tokens(77.8%)把它算了进去。

如果需要真正重写、压缩率更高的结果,要么另开一轮并接受几十次会话的成本,要么换一个对上游代码没有记忆的作者模型。

测量口径

  • tokens。tiktoken 0.12.0 的 cl100k_base 编码,每个文件单独计数后求和。统计源码和配置两类文件;没有改动的原版测试(81 个文件)、文档和二进制资源不计入。压缩前后使用 harness 的同一个测量函数。
  • 注释和文档字符串的拆分。Python 用标准库的分词器识别注释和独立的字符串语句;C++ 和 CUDA 用正则匹配注释;YAML 统计整行注释。这是按文件类型做的估算。
  • 与原版的相似度。对同路径文件做逐行最长公共子序列匹配,统计相同行的比例,不含测试目录。
  • 耗时。来自作业记录里每个操作的起止时间。作者会话的 384 分钟包含启动和重试的开销,模型实际运行 376 分钟。
  • 费用和模型 tokens。每次会话结束时由 Claude Code 报告,18 次会话求和。输入 tokens 包含缓存命中的部分。
