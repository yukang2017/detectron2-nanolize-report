几个词

  • 主持会话：发起并看管一次运行的那个模型会话。它划功能图、写检查清单、提交作业，最后写总结。
  • 两个作业：一次运行拆成主作业和草稿作业。主作业抓基线、设计测试、冻结检查，再验证；草稿作业同时写第一版代码。并行模式允许一个作业同时用几个作者。
  • 基线：在没改过的原版上把每个检查跑一遍，记下结果，之后拿它和重写出来的代码比。冻结：基线和检查定下来之后不再改。
  • 能力、叶子：功能图把仓库的功能分成一个个能力，最末一级叫叶子。已验证是指这个能力有检查并且通过；部分验证是指它的某个叶子没有有效测试。
  • 测试设计：叶子没有有效测试时，由设计会话对着原版写测试文件和场景文件（场景文件只给输入，原版上的输出就是标准），再由评审会话审。
  • 作者：写代码的模型会话。并行分组：控制器一次同时派出的几个作者调用。控制器：作业里决定下一步做什么的会话。试调：正式开始前对模型调用做的短试验。
  • 检查清单：主持会话写的、这次运行要用哪些检查的清单；留在清单里的叫保留的检查。对外接口：仓库对使用者公开的那部分名字，测试只许通过它们来测。行为契约：一个叶子的有效测试。
  • 缺口：交付时说明的、没有被检查覆盖到或没验证到的部分；带缺口交付就是检查都过了、但有这样的部分。
  • 与原版相同的行：交付代码里和原版逐行相同的比例。技能文档：告诉主持会话每一步怎么做的那份说明。

4. requests：一次“交付了但什么都没验证”，和它的修复

requests 在 25634d02 上的第一次运行交付了，但 17 个能力里 0 个通过验证。检查清单里的 15 个检查在没改过的原版上全部被判违规；交付时 16 个检查里唯一通过的，是测试设计被接受的那 1 个场景文件。测试设计的会话花了 $100.27。这次运行（作业 $123.54，主持会话 $12.58）不计入上面的表和合计。

原因

  • 主持会话照技能文档给每个检查加了“导入审计”，只允许 requests 的模块来自仓库的 src 目录。
  • requests 自己会把 urllib3、idna 和字符检测库登记成 requests.packages.* 的别名，这些模块来自测试环境。于是检查清单里的每个检查在没改过的原版上都被判违规，哪怕退出码是 0、用例全过。
  • 基线因此不可用。测试设计一共有 186 次被拒：177 次被判“在原版上不通过”（主持会话的判断是它们继承了同一个审计），8 次超出对外接口，1 次被评审否决。

为什么昨晚没事

  • 昨晚的主持会话第一次提交时写的是同一个审计，基线同样不可用。它在提交两分钟后自己取消了作业，把测试环境的包目录加进允许范围，重新提交；之后基线可用，作业正常跑完（91 / 91 个检查，带缺口交付）。
  • 25634d02 的技能文档在“基线不可用”这个事件上新加了一段：把情况告诉用户，给出两条路（让作业继续，或取消、改检查清单、重交），没有用户的话两条都不选。
  • 这次的主持会话在自己的问题清单里引了两条理由：技能文档这句话，和这一轮说明里的“只提交一次”。昨晚的说明里也有“只提交一次”，昨晚的主持会话仍然取消了。
  • 判定违规的那段代码在两个版本之间没有变；上游提交相同，测试环境里和这件事有关的包（urllib3、idna、字符检测库）版本也相同。两晚找回的测试文件不完全相同。

修复和验证

  • 只改了技能文档：在那一段后面写明，无人值守时不会有用户来回话；“无人值守”一节加一条规则——基线不可用、原因在检查清单里并且能从基线记录里指出来时，取消、改检查清单、重交一次；第二次仍不可用或指不出原因，就让作业带缺口继续。
  • 重跑时还把说明里的“只提交一次”换成了和新规则不冲突的说法，所以技能文档单独起多大作用没有分离出来。
  • 重跑的经过：第一次提交又写成只允许 src，约两分半后草稿作业报基线不可用，主持会话在事件出来约两分钟后取消，改好检查清单重交，新的基线里检查清单的 17 个检查全过。绕这一圈多花约 8 分钟。
  • 这次重跑就是表里的 requests：29 / 29 个检查通过（检查清单里的 17 个，加测试设计加进来的 12 个），19 / 21 个能力已验证，作业花费 $34.04（含被取消那次提交的一次控制器调用；它的两个作者会话被中途取消，没有花费记录）。
第一次运行里还看到两处这次没有改的：技能文档在提交之前没有任何一步要求带着审计实际跑一次检查（两晚重交之前，主持会话都是自己手工抓了一次基线）；所有保留的检查在原版上都不通过时，作业仍然进入测试设计。
一个和新规则容易混的旧事件（修复之前就有）：草稿作业会报“基线不可用（没有行为契约）”，哪怕它的检查全过——草稿作业不做测试设计，留给测试设计的叶子在它那里算没有契约。tomli、tqdm、packaging 三次都出现了，主持会话都判断这不是检查清单的错，没有取消。

5. 体积：为什么要统一口径

作业自己报的体积比例，分母是“原版里计入的文件”。主持会话可以把某些文件设为“原样携带”（原样带进交付、两边都不计）。同一个仓库两晚选的携带文件不一样，报出来的比例就不可比。

最明显的是 bidict：这次主持会话没有携带锁文件 uv.lock（86,997 token），它被算进了原版，而交付的代码里没有这个文件，作业报的比例就成了 17.69%；昨晚携带了它，报的是 41.28%。去掉这个文件按同一口径算，是 44.69% 对 41.28%。

统一口径的做法：对每个仓库，把两晚任意一次携带过的文件在三边（原版、这次交付、昨晚交付）都去掉，再重新量交付目录里源码加配置的 token（按路径归类，测试和文档不算）。tqdm 只有这一次，用的是它自己作业的口径。重新量的结果和作业自己报的交付 token 数还会差一点（这次 tomli 差 15、click 差 12）：作业的算法把交付里新加或改过的文档也计入，这两次的作者各写了一个很短的 README，按路径归类时文档不计。

9. 做法和限制

  • 八个仓库用的是之前几轮同一份仓库名单上的提交，其中七个和昨晚相同；tqdm 用的是第 3 节表里 11 月 21 日那次运行的提交。一个跑完再起下一个。
  • 每次运行由一个全新的主持会话从一行指令开始：全部功能、两个作业、并行模式开、不测性能、无人值守。主作业的检查发到计算节点上跑（草稿作业的检查和安装检查不在计算节点上）。
  • 给主持会话的说明和昨晚相同，只多了几处这台机器上要隐藏的路径。说明里原有一句“只提交一次，除非工具拒绝、别无他法才取消重交”；修复之后改成“除非技能文档让无人值守的主持会话这么做，或工具拒绝、别无他法”。
  • 用时取自作业自己的记录和调度器的记账。扣掉的是这次运行每一批节点申请的排队时间之和（两晚算法相同）；排队时作业是否在做别的事没有区分。合计是各次运行自己的用时相加，不含两次运行之间的间隔。
  • 花费取自每次模型调用自己的记录，主持会话的花费取自它退出时记下的数。
  • 合计和差值都按未取整的数算，和用表里的数相加减可能差 0.1 分钟或 1 美分。
  • 体积、相同行、函数体重合都是 nanolize 自己的度量。通过的检查是有界的证据，不等于功能完全等价。
  • 每个仓库每个版本只有一次运行，表里的差别里混着运行之间的随机波动。
  • 各次运行的主持会话都记了自己的问题清单；除了第 4 节写到的几条，其余没有逐条核对，这里不列。
