1. 结论

  • 新代码上整套流程照常跑完，全程没有人工干预。提交按 pair=on 拆成主作业和草稿作业，检查和性能测量都在计算节点上跑；没有暂停、没有失败的会话，调度器上的申请没有人动过。结束状态和两个缺口的种类都和上次相同。
  • 总用时和上次差不多：103.0 对 105.3 分钟（−2.3）。冻结阶段快了 11.6 分钟（65.1 对 76.7），封存之后慢了 9.3 分钟（37.9 对 28.6）。封存之后变慢，是因为这次草稿导入后有 3 条行为检查失败，多做了一轮行为修复；上次这一步一次通过。拆解见第 3 节。
  • 花费少了 $5.34（$127.01 对 $132.36）。设计者少 $6.96、评审少 $5.49，作者多 $6.40（多出的一次行为修复，以及第一版的第一次调用更长）。
  • 体积小了 3 个百分点：54.91% 对 57.96%。少掉的 1,954 token 几乎全在文档字符串、注释和非 Python 文件上，代码本身一样多（27,835 对 27,823 token）。这次写第一版的作者第一次拿到了“这个范围自己该写多少”的数（PR #43 的改动）。体积目标 50% 仍然没达到，之后仍然没有任何动作。见第 5 节。
  • 节点申请这一块，PR #43 的修改在这次运行里看得到，但只管到一半。检查批次现在按预计用时申请（41 分钟、201 分钟，上次每个都是 4 小时），设计出来的测试的试跑不再被拒收。申请从 9 个降到 7 个，同时占着的分配最多从 4 个降到 2 个，占用从 11.0 降到 7.0 核·小时；这几个数里也有这次返修和评审更少的成分，不全是这项修改带来的。性能测量的请求没有被这项修改覆盖：3 次被等待中的分配拒收，每次重新申请一个 4 小时的分配。见第 9 节。
  • 和原版的重复没有变好，还略高了一点，仍然要你定。重复度 72%（上次 68%），42 个函数有 60% 以上和原版相同（上次 36 个），逐行相同 63.0%（上次 57.1%）。PR #43 没有动这一块。
  • 没能验证的原测试函数从 4 个变成 10 个。要迁移的 24 条原测试里，这次设计者迁移成了 14 条，上次 20 条。见第 8 节。

作者这次拿到的体积目标

PR #43 改了写第一版的作者拿到的体积数字（那一页的 A1、A2 两项）。那一页在别的仓库上核对过这些数字对得上，写明没有核对的是真实的作者读到之后怎么做。这次草稿作业的两次作者调用里看得到：

  • 整个工作区的目标是 30,153 token：总目标 31,981 减去校验方自己放进候选的 1,828。这样作者自己数出来的数和拿到的目标是同一个口径。
  • 每次调用另有这个范围自己的份额，按范围在原版里占的比例分：范围 1（整个包）28,363，范围 2（维护脚本和基准）1,789。上次的调用里没有这个数。

体积降了 3 个百分点，但不能直接算成这项改动的效果。能确定的事实是这几条：这次第一版就是 54.05%（上次第一版 57.91%）；少掉的几乎全是文档字符串（4,208 对 5,158 token）、注释和非 Python 文件，Python 代码一样多；第一版失败的 3 条行为检查都是文档字符串或由它生成的文字（第 6 节），修复后体积回升了 536 token。作者是不是因为看到了份额才少写文档字符串，没有读它的会话记录确认；只有一次运行，也排除不了模型这次恰好写得短。

体积目标是原版的 50%（31,981 token），交付的是 35,120。作业在行为和性能都通过后直接选定、交付，没有做体积优化轮（最多 2 次，用了 0 次）。PR #43 的决策记录里写明这一点有意不改：目标是建议性的，不加只为压体积的作者调用。

重复度方面，作业的设置和上次一样：上限 40%、只量不退回。每次作者调用结束时的重复度是 73%、71%（第一版的两次调用）、72%（行为修复）、72%（性能修复）。这一块 PR #43 没有改；那一页把同类的条目列在“有意不做”里。

13. 口径和没有做的事

  • 时间取自作业自己的事件和操作记录；花费和 token 取自各次调用的记录（Claude Code 报的美元数），缓存读取单列。
  • 等节点的时间取自调度器的记账（只读查询），是各申请从提交到开始的秒数之和。本页的用时除了标着“实际”的，都已经扣掉它：每一段等待从它所在的那一步、所属的阶段和作业总用时里扣掉。会话的时间、草稿作业的时间和花费没有扣。
  • 拒收的记录是运行期间每 20 秒抓一次各个分配的服务日志得到的；分配结束时作业会删掉它的目录，所以事后查不到。
  • 两次各只跑了一遍。差别里混着代码的改动和模型每次写得不一样；只有节点申请（第 9 节）和作者拿到的体积数字（第 5 节）这两处能直接对上 PR #43 的改动，其余都按“这次对上次”写，没有归因。
  • 交付的代码没有另外做人工检查或第三方对拍；“行为保持”指 71 条冻结的检查和 265 条性能标准，加上回放的原测试。
  • 性能是在一台计算节点上、同一批次里对比的相对值，不是对某个硬件的绝对承诺。
  • 没有读作者的会话记录；第 5、6 节里关于文档字符串的话只基于失败的断言和体积的分类统计。
  • 没有改 nanolize 的代码，没有动调度器上的任何申请，交付的分支没有推送。
